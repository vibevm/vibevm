# Guarded one-file migration application and recovery (Unreleased)

M13D1 is accepted at its neutral one-file application/recovery boundary. It adds `vibe refactor migration-operation` and configured MCP `manifest_migration_operation` over the accepted neutral C1/C2 planner. Source/feature/Redbook converters and editor coordination remain separate capabilities.

Three new strict epoch1 formats are registered: `migration-operation-request`, `migration-operation-report` and `migration-application-journal`. The first two are transient protocol values. The journal is retained recovery state (`recoverable = false`), including exact approved request/identities and before-state references; deleting it is not cache cleanup. Required-nullable fields distinguish an explicit unavailable value from a missing field. Unknown fields, schema/revision and invalid state combinations refuse.

CLI authority is supplied separately from the operation JSON:

```sh
vibe refactor migration-operation \
  --project-root /absolute/owned-project \
  --target-relative vibe.toml \
  --recovery-store /absolute/recovery-store < operation.json
```

This shows the invocation shape, not a ready-made approval. `operation.json` must name the same authority and carry the exact caller-approved planning request and before/after/diff identities for apply, or the retained intent for recovery. Missing or mismatched flags produce typed preflight refusal. A saved/forwarded JSON request alone grants no file or store authority. Explicit grants remain the caller's ownership assertion, not a filesystem classifier of fixtures/upstream data.

MCP operations require an explicit `--migration-recovery-store` server grant and a finite file set. Omitting `--migration-file` grants only root `vibe.toml`; an explicit list replaces that default. Generic server store configuration alone does not enable migration. Project/store changes and protected machine-cache overlap refuse. Existing non-migration tools retain their authority rules.

The engine serializes participating clients sharing the same physical project and designated physical recovery store. It replays the approved plan, checks exact target state, retains and synchronizes a before image, checkpoints intent, then publishes. It supports apply/repeat, read-only inspect and explicit complete/restore recovery. Missing stores/locks/journals are not created by inspection/recovery. Initial valid apply can create store/barrier state before a stale-source refusal or no-op; reports retain those effects rather than claim zero state.

Unknown/third states and unproven foreign stages are preserved. Errors can follow completed or uncertain effects and never imply successful rollback. A live receipt follows the actual staged object through final observation; a same-byte replacement is not treated as that object. On a later journal load, recovery recognizes exact bytes and Unix mode rather than proving persistent per-object history. The closed `target_object_history_unproven` warning and unconfirmed historical durability make that distinction visible. Recovery does not negate an earlier receipt mismatch.

Concurrency guarantees exclude unrelated writers, different recovery stores and ancestor/descendant project scopes. Tests use process exits at named domain boundaries, not power cuts or every underlying filesystem syscall. Linux is the measured runtime. macOS/Windows implementation paths and reduced durability reporting are retained; native execution proof remains unperformed. Unix mode preservation is separate from Windows byte-only metadata scope; no ACL/owner/xattr or hostile-CAS guarantee is implied.

MCP operation preflight has a closed typed report channel. An executed operation whose report fails validation retains explicitly unvalidated diagnostics as text, without publishing an invalid normal structured report. `ToolOutput` now represents absence separately from present JSON null; protocol rendering uses the lossless option. Legacy Rust accessors, Deref and tuple conversion map absence to null and are documented as lossy; callers needing presence use the new methods. New enum variants require exhaustive Rust consumers to adapt.

No authored `vibe.toml`, `vibe.lock` or `vibe install -g` grammar changes here. The arbitrary prototype default8MiB ceiling is not adopted as a format law: observations use explicit bounds and checked/fallible allocation. This is not a promise of immunity to host-wide memory exhaustion.
