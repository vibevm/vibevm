# Break 003 — `repomd.json`: `files.*.size` rides the wire as a decimal string

**Date:** 2026-08-20 · **Format:** `index-repomd` · **Epoch:** 1 (unchanged)

> The third note, and the first one that executes a standing rule rather than
> a local decision: the owner ruled on 2026-08-20 (BACKLOG `B-091`, «вариант
> (б)») that **integers wider than 32 bits are encoded on the wire as decimal
> strings — as a general rule.** This file is that rule's first landing; the
> wording enters PROP-044 separately, by the owner's hand.

## What changed on the wire

Every `file` entry of `repomd.json::files` now carries its size as a canonical
decimal **string**. Before:

```json
"primary.jsonl": { "kind": "file", "size": 3951, "sha256": "sha256:…" }
```

After:

```json
"primary.jsonl": { "kind": "file", "size": "3951", "sha256": "sha256:…" }
```

Canonical means: ASCII digits only, no sign, no leading zeros except the bare
`0`, value within the unsigned 64-bit range — one number, one spelling.
Directory entries are byte-identical to before; only the `size` field of
`file` entries changes, and only in its JSON type.

## Why it is a break rather than an addition

A reader of the old form meeting a new file gets a **type** refusal, not a
value refusal: the field was a JSON number and is now a string, and both the
hand-written reader and the generated one reject `"size": 3951` (number) and
`"size": "007"` (non-canonical string) loudly, never coercing
([PROP-044 §2, law 1](../../spec/common/PROP-044-change-native-formats.md#laws)
— a wrong answer must never look like a right one). The reverse meeting is
symmetric. That refusal is the point: it announces itself.

## Why a string at all

JTD (RFC 8927) has **no 64-bit integer** — `uint64` and `int64` are both
rejected by the pinned generator as `InvalidType` (measured 2026-08-15,
BACKLOG `B-091`). Until this change the schema said `uint32`: a TRUE claim
below 2^32 and a FALSE one at or above it — our own writer's `u64` could emit
a document our own schema called invalid. That divergence was recorded, not
resolved; this change resolves it by making the schema describe the writer
truthfully. The alternatives stay measured and stay worse: an empty schema
generates `Option<Value>`, losing the type AND the requiredness; `float64`
breaks value equality past 2^53.

## Why no epoch

Same reasoning as Breaks 001 and 002. An epoch mints a parallel world and
costs a support window; this change needs neither. The system is
pre-publication (`public = false`, migrations do not run), and the golden
corpus — the one committed catalog — was reprojected in the same change that
moved the writer, so there is no old world on disk to support
(`crates/vibe-index/tests/golden_corpus.rs` proves the journal still maps to
the committed bytes, and now maps to the string form).

## Who fixes it

Nobody downstream. The index operator regenerates; the writer and the
projection moved together, so any full rebuild produces the new shape. A
catalog not rebuilt keeps working with its matching binary — mixing an old
binary with a new catalog (or vice versa) is the announced type refusal
above, not a silent misread.

## Sunset

None. The numeric form is not published in parallel and is not supported
after this change. A reader that must understand both worlds does not exist
and is not planned.

## User recipe

```sh
vibe-index reindex --full --data-dir <path>
```

Any full rebuild rewrites `repomd.json` in the new shape.

## The red proof

The break is proved, not asserted: the generated reader refuses a document of
the OLD form — `"size": 123` as a JSON number — with a type error
(`wire_parity_repomd.rs::the_generated_reader_refuses_the_old_numeric_size_form`),
and the hand-written reader refuses it symmetrically
(`types/repomd.rs::size_wire_refuses_a_json_number`). A reader that quietly
accepted both spellings would make one number wear two forms — exactly the
ambiguity this break exists to retire.
