**Decisions already made.**
- One cancellation path: the stop file feeds `Signals` (the existing application interrupt owner) through `Context::stop_file`. The project CancellationToken path and `bind_legacy` stay unchanged.
- The stop semantics are those of an unanswered SIGINT: no question is asked. On Unix the running child's process group receives SIGINT through the existing `signal_child`. On Windows the running child is ended with the existing `HostProcesses` `force_end` (TerminateProcess), because a child started without a console receives no console control event. Each child is stopped at most once (`stopped_child`).
- Existence rule for the stop file: any path that `symlink_metadata` does not report as NotFound counts as a request, identical to cancellation.rs. vibe never deletes the file.
- The outcome is the existing `interrupted` code with exit status 1, the step recorded `interrupted` in steps.json, and the work directory kept. The JSON envelope gains `"stopped_by": "stop-file"` or `"stopped_by": "signal"`, and the first cause recorded wins (OnceLock).
- Test fixture: package org.example/stoppable@1.0.0 in an AppRegistry, recipe step id `build`, a slow file that gates `sleep 30`, and the stop file at <root>/stop. The test is Linux-only, like cli_app_interrupt.rs.
- The Windows cross-check is advisory evidence, not the gate; the gate is the Linux check.

**Not in this entry.** Widening the `--stop-file` gate to update -g, uninstall -g, app modify and app import (that is ADV-CONTROL-STOP-3, including its spec wording), killing the whole Windows process tree (taskkill /T), fixing pre-existing Windows build failures, adding a Windows CI workflow, or adding `resume` to the envelope.
