# Ordinary secret inputs: decide at the operation, not at the package kind

Scope: the outstanding SECRET-BOUNDARY decision in NST-COMMON-CHOICES-DESIGN. This does not authorize an additional implementation lane during corporate kit work. Acceptance is by real operation, not a matrix of parameter types.

PROP-069 `SECRET-BOUNDARY` limits transient answers to the authorized operation that needs them. Its `APP-CONFIGURATION-JOURNEY` distinguishes package acquisition from application execution. The actual shared authored-input normalizer in `crates/vibe-core/src/manifest/configuration/intent.rs` rejects a secret answer; `submitted.rs` excludes it from persistable submissions. The reconciliation-04 N2 negative controls are evidence for that refusal. They are not a positive secret transport test. App execution has a separately retained positive ephemeral-resupply case (A4); it is not ordinary acquisition.

**Decision:** no secret field in ordinary answers files, lock records, public preview, JSON/MCP diagnostics or maintenance receipts. No generic package hook environment, keyring lookup or provider session to turn a pure acquisition into an authorized consumer. A declaration alone is not a request to collect a value. If an execution operation actually needs a secret, ownership belongs to that operation; a missing value must not silently authorize execution.

**Bounded closure check at the existing DESIGN gate:** identify a selected ordinary execution operation, its caller and its already authorized sink. For pure acquisition/inspection, record why no sink exists and cite the existing refusal proof; do not build a channel just to pass a test. For the existing application operation, cite its positive case and preserve its scope. If another selected operation has a genuine consumer, name the exact caller and trust boundary before implementation, then test with a synthetic marker scoped to that operation, checking absence of the value and digest from public outputs and durable state. If a required user journey lacks an authorized consumer, report it as unresolved, not supported. No real provider, private input, platform runner, or new task node is required to decide this boundary.
