## Project tree inside the conversation — design study after consolidation

See `PROP-076#HERMES-TUI-PROJECT-TREE`. Compare the pinned native TUI in an actual terminal before choosing a renderer. Keep its nonblocking composer, streaming, native approvals and session picker. Compare a native widget/overlay with a full-screen project view; do not build a competing chat frontend just to draw a tree. Source starting points: Hermes `ui-tui/src/sdk/types.ts` (ambient versus modal widgets) and `website/docs/user-guide/tui.md`; Vibe `crates/vibe-cli/src/cli/command.rs` (package/spec tree) and `cli/aiui.rs` (headless state and symbolic rendering). Check integration APIs and versions at execution time; a widget type is not evidence of a shipped integration.

First UX prototype: a discreet run status in chat; open the task tree on demand or from the event, focus the exact failed check, inspect its evidence, and return to the unsent draft. On wide terminals compare a collapsible side panel; on narrow terminals use a full-screen overlay. Use branch glyphs, indentation and short text states, not color alone; support keyboard-only navigation, resize and plain output. Source updates preserve focus by stable task ID. A DAG may have many prerequisites: show them as links, not invented parentage. Verify the reported result against the same plan revision as the dashboard and a separate operation receipt. Include a stale snapshot and an unlinked event control, and confirm viewing does not submit, rerun, or mutate anything. This is a planned design/qualification slice, not current SYS or CORP implementation.
