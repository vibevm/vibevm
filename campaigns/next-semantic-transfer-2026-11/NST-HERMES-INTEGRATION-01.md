## Closing the IDE must not stop active Hermes work

Owner requirement relayed by builder: «наша интеграция с агентом hermes в рамках задачи про IDE должна работать так, чтобы IDE можно было закрывать и открывать, а Hermes продолжал бы работать. Это должно работать от любого непривилегированного пользователя на Mac/Linux/Windows».

Closing the last IDE window detaches the viewer, not the running user's Hermes work. Reopening must reattach to the same conversation and operation and show progress or its actual recorded outcome without resubmission. Stored chat history alone is insufficient. Define explicit ordinary-user start, stop and ownership behavior; neither closing a window nor opening another silently terminates, replaces or duplicates the owner. Do not require elevation, a system service or a different account. Logout, reboot and crash recovery are separate claims.

For each of macOS, Linux and Windows, drive a bounded operation as an ordinary user, hold it at a witnessed progress point, close all IDE windows, then let it advance with no viewer. Reopen and check the same identity, progress/outcome and exactly one execution. Also verify that an explicitly stopped owner is not mistaken for running work. Report unrun platforms separately. This future requirement does not expand the accepted initial Linux READY transport slice.

## Entry and delivery of the later node

Start only after review of the domain consolidation: identify the actual owners for launcher/capabilities, selected project, prepared instructions, operation identity/outcome, receipts and interaction. Do not invent a second session store, composer, permission system, or task runner. Reuse Hermes lifecycle, history, tools and authorization, and the existing accepted adapter evidence. The upstream frontends are compatibility references, not the implementation base for the new TUI.

The core acceptance journey is the native local conversation from project launch through continuation, two viewers and reconnect, declared instruction scope and actual delivery, then the same supported outcome in the new integrated TUI, compared with native Hermes. Use the existing local-interactive journey brief for the checks. Classify cold startup, selected worktree, supported platforms and remaining native limits against the actual runtime. At entry re-evaluate the released Hermes API and both prompt debts; absence of an upstream merge does not prevent starting this node or authorize silently claiming strict delivery.

Integration candidates, **not four automatic mandates**: reconnect a conversation to an actual Vibe operation and report its verified outcome without re-execution; promote a learned procedure to a reviewed versioned skill; explain a discrepancy using the governing specification and observed project state; notify a conversation of an operation outcome without model polling or implicit consent to retry. Prioritize the first concrete journey that benefits from the consolidated owners. Retain only selected, tested additions; document a disposition for the others. At IDE acceptance, hand over the accepted behavior, remaining debt and reproducible provider-free evidence.
