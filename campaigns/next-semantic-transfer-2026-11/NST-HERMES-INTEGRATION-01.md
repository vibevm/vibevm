## Original terminal client: research, feature matrix, implementation

Owner direction, superseding the earlier overlay-first proposal: design a new Vibe/Hermes terminal frontend, not a fork or skin of `ui-tui`. Preserve the backend authorities; do not preselect a toolkit, panel layout, key binding or base client. This work lives entirely in `NST-HERMES-INTEGRATION` after consolidation. Canon: `PROP-076#HERMES-TUI-ORIGINAL-DESIGN` and `#HERMES-TUI-PROJECT-TREE`.

1. **Build the comparison set at execution time.** Download the then-current official Hermes TUI sources into a fresh isolated research directory. Record upstream origin, tag/commit, release, license and inspected entry points. Identify leading comparable agent terminals and useful specialist tools for tree navigation, diffs and long-running jobs. Explain inclusion by the user journey they do particularly well, not popularity alone. For closed-source products, use permitted black-box trials and official documentation; distinguish observed, documented, absent and untested behavior. Do not vendor their code or assets.
2. **Run the same journeys.** Start and resume a conversation; switch projects and sessions; type while streaming; interrupt; handle approval; inspect a tool call and diff; trace a failed check from notification to task to evidence; return to an unfinished draft. Compare keyboard-only use, mouse support, discoverability, narrow/wide terminals, resize, accessibility/plain fallback, reconnect, long transcripts and large trees. Record both wins and failure modes, with versioned evidence. Count actions and lost context; do not score screenshots as proof of usability.
3. **Publish the feature matrix before choosing the design.** Each row names a user outcome, reference implementations, evidence, strengths/trade-offs, current Hermes/Vibe gap, intended behavior in the new client, domain owner and acceptance test. Include capabilities unique to the combination: an authoritative campaign tree distinct from the package/spec tree and agent activity; operation receipts and spec references linked from the conversation. Resolve conflicting treatments as explicit design decisions, retaining the underlying user needs. The result is a versioned target matrix, not a list from which only the easiest features are implemented.
4. **Design and implement from the matrix.** Prototype materially different interaction models and compare them on the same journeys. Choose layout, navigation, pseudographics, focus and rendering only after this comparison. Deliver every target row in testable slices against the consolidated owners. Track each row through implementation and verification; removing or deferring a target is a visible scope decision, not a silent PASS. Preserve history, drafts and pending approvals across navigation. Opening the tree must not run a job, query a model or change task status.
5. **Exit criterion.** Provide the matrix with evidence for every target row and real terminal demonstrations of the joined-up journeys. Establish where the new client improves on the references and where trade-offs remain. Do not call a widget prototype a completed TUI or infer cross-platform support from a headless rendering test.
