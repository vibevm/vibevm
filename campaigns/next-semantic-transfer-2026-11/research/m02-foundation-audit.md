## Findings that affect transfer scope

1. A.1/A.2 are characterization fixtures using existing requirements/facts seams, not a production change-binding parser. Both alpha/beta `change.toml` say this literally; they deserialize as `toml::Value`. Their shape is different from B.1's durable manifest. Do not migrate them as alleged epoch-zero authored customer state.
2. Most A semantics already have main owners: requirements query separates authoring/adoption, carries explicit artifact requirements and emits no terminal verdict. A's extra useful result is the concrete two-project/personal-plan counterexample suite, not another query or registry. Exact descriptor-first origin observation is a prototype call to `vibe_facts::observe_declared_document`; its main owner was outside this packet, so this audit does not declare that seam already present.
3. B.1/B.2 contain real pure production library logic and saved/captured-byte adapters. They are not just flags or tests. Main `manifest/mod.rs` and requirements `lib.rs` expose no equivalent change owner. The missing reusable functionality in this audited surface is stable authored change identity/roles and independent intent/work/contribution identities. This bounded absence is not a whole-repository absence claim.
4. Duplicate change IDs have a pure `validate_change_catalog` helper and unit assertion, but no production caller was found in the entire pinned Rust allowlist. Saved lookup reads one ID and does not call it. Therefore “duplicate IDs refuse before mutation” is established for the helper, not for a complete catalog/write entry point.
5. A.2's named “preserves_identity” test compares shared raw byte snapshots and metadata reports, not B.2 `IntentIdentity`. Its personal-plan file is outside the queried project root. This valid narrow independence demonstration is weaker than a complete durable intent-hash perturbation proof. Inventory repeats the identical test name twice; that is one evidence item, not two.
6. B.1 migration is an explicit pure schema-token proposal. Neither `plan_change_migration` nor `plan_saved_change_migration` publishes bytes. The latter reads role inputs and returns `(plan, retained manifest snapshot)`. No whole M-13 applying machinery or M-16 editor/barrier engine is necessary to parse or plan this behavior. Application, if requested later, belongs to those existing owners.
7. B.2 intent hashes exact normative bytes, not normalized prose. Slug/title/metadata edits are ignored; whitespace in normative documents changes identity. Work ordering is canonicalized structurally. Work needs are bounded nonblank literal targets, not proof that artifacts exist.
8. There are later pinned additions in the same modules: bound-origin recipe, release-impact evidence-only registrations and full-pass selection. Do not indiscriminately copy all `change/` for the four tasks. Preserve their semantic boundary when making a transfer decision; this report does not commission those later features.

## Main owner reconciliation and minimal integration order

Observed main overlap: `vibe-requirements::{query, rows, sources}` owns read-only metadata/adoption assembly, `tests_requirements` already asserts no terminal/fulfilled/verified/verdict text, and `tests_query::authoring_and_adoption_map_through_all_their_states` covers separate adoption states. `digest` owns source/scope/report recipes; its scope intentionally includes registry witnesses, so it is NOT an adoption-independent intent hash. `vibe-core::manifest::declarant_path` owns portable paths. `configuration::intent` normalizes package feature/profile/parameter choices; `configuration::basis` compares retained automatic reliance. Their “intent”/“basis” vocabulary does not make them change-document or work-DAG owners. `manifest::render_toml` decorates a structural reserialization and can drop mismatched keys; it is not exact token replay and cannot substitute for B.1's migration promise.

Recommended sequence (root decision, not status promotion):

1. Keep/reconcile the A.1/A.2 fixture contracts and their current requirements/facts APIs. Validate two-consumer leaf equality, distinct local addresses and adoption/evidence/personal-plan separation through existing owners. Resolve descriptor-observation availability explicitly. No new scheduler, cursor, registry or terminal evaluator.
2. Add the B.1 pure declaration owner under the incumbent core manifest boundary, retaining shared portability and actual ID/role/origin validation. Treat configured root as trusted input. Reuse the actual M-13 pure token-replay seam for B.1 migration; the amended packet establishes this concrete dependency (details below). Review target native-format registration before landing. Do not replace opaque metadata/comment preservation with struct serialization. Keep catalog duplicate-check reachability an explicit acceptance question.
3. Add B.2 structural graph and domain-specific framed identities against that validated declaration. Keep exact bytes, ordering, input-set refusal, contribution closure and recipe boundaries explicit. Reuse vocabulary owners where semantically identical without converting Work needs into terminal evidence.
4. Compose saved/captured adapters with existing held-read machinery. This source shows read-only operation can stand on its own; editor participation, migration publication, scaffold, origin rebase, closure or full-pass lifecycle must remain separate integrations with their own actual consumers. They do not belong in a parser/hash prerequisite bundle.

No broad framework is needed. The four tasks are two characterization atoms followed by one authored-data owner and its pure identity/DAG consumer.

## Amended corpus and M-13 dependency reconciliation

`formats/REGISTRY.toml` explicitly registers change-manifest epoch 1, schema="none", recoverable=false, foreign_parsers="ours", unknown_fields="deny", corpus=`formats/corpora/change-manifest/e1`, sunset="none". Thus the prototype has a registered native authored format; hand-written domain parsing here is not evidence of an unregistered JSON wire. Target format registration still needs its own review; main registry was not authorized.

The representative corpus has exactly the strings used by core and requirements tests. Negative corpus differences are precise: schema 9; ../intent.md; closure normative/input true; root unknown_control; invalid selected_content_hash. The first four are consumed by the B.1 registered-corpus test; invalid-content-binding and valid/bound-origin belong to the later origin-binding capability. No test execution is inferred from corpus existence.

Pinned `manifest/mod.rs::replay_authored_tokens` is a thin crate-private wrapper over `manifest/migration.rs::replay_edits` (line 552). `MigrationTokenEdit` holds original byte range/token and replacement token. Replay walks source coordinates with a cursor, refuses overlap/backward/invalid ranges, empty no-op insertions and duplicate insertion point, uses `str::get` to reject invalid UTF8 boundaries/out-of-range coordinates, compares exact original token, and copies untouched slices verbatim. Change migration validates the source independently, proposes one schema-token replacement, replays it and validates the target. This is a real source dependency on the M-13 **pure token replay** capability, not on all historical M-13 tasks and not on applying/recovering filesystem edits. Main manifest export/module inventory in this packet has no migration module or replay export. Therefore B.1's full migration subpart needs that narrowly scoped owner reconciled before landing; its standalone parser and B.2 pure identities do not require migration publication.

A.1/A.2 satisfy a useful fixture-characterization purpose in source. Their tests should be judged against those exact clauses. The bounds above prevent overclaiming production parsing, authentication or terminal acceptance; they do not invalidate characterization merely because it intentionally uses fixtures. A.2's raw-byte identity interpretation is explicit in the pinned permanent contract.
