# Common app runtime: two concrete seams

Read-only source review begun at `e27d3cabd`, with main advancing to `8f84aefb9` during root work. Relevant files below were inspected directly. Read alongside `common-app-vertical-decisions.md`; those root decisions supersede the earlier report's suggestion of mandatory first-use default review. No repo edits, builds or new agents. This report resolves data/projection/path details, not another inventory.

## 1. Reuse the existing algebra faithfully in one generated vocabulary

Use `ConfigurationDecl` as the retained description source, `ConfigurationIntentDecl` plus app disabled_features as the original input, `ConfigurationDecl::normalize_input` as normalization, and `ChoiceModel::evaluate` as the only feature/group evaluator. Generated types are wire projections/admissions, not a second semantic model or evaluator.

| Current source/type | Faithful reusable data | Missing or misleading if used alone |
|---|---|---|
| `manifest/configuration.rs::ConfigurationDecl` | Ordered feature/group/parameter/profile descriptions; exact closed effect variants and typed config-value map | Compiled FeatureModel/ChoiceModel have private indexed state and lose presentation. Do not serialize their Debug/internal graph. |
| `configuration/choices/types.rs::{Selection,MergeIntent,ChoicePolicy,ChoiceGuard}` | Omitted vs explicit—including []; independent exact/additive; two positive guard namespaces | Unknown fields/closed enum handling must not silently erase intent. Generated collection omission rules must preserve explicit empty. |
| `manifest/configuration/intent.rs::ConfigurationIntentDecl` | Original policy/profile/features/default_features/selections/public parameters | No hard disables, ephemeral secrets, expected_definition or maintenance disposition; those are app submission/context data, not new source authority fields. |
| `NormalizedConfigurationInput` | Existing FeatureInput, ConsumerChoices, public typed supplied parameter map | Profile and explicit parameter values have already been merged; origin is lost. It is not original intent or an executable result. |
| `ChoiceEvaluation` | controls, questions, conflicts, invalid answers, provisional DefaultUse, resolved-only feature output | Its `original` echoes the **normalized ConsumerChoices passed to it**. After profile lowering that is not the original submitted ConfigurationIntentDecl. No parameters, config-value projection or stale-basis decision is present. |
| `GroupControl` / `MemberControl` | activity, eligibility, requested contributors, blocked_by guards, active/dormant projections, selection | A control.selection may be Some([]) despite mandatory underflow. It is diagnostic state, not proof of overall resolution. |
| `FeatureResolution` / `ImplicationReason` | selected IDs and first representative reason per implied feature, ordered by declaration | Not an exhaustive cause graph/proof. GroupDefault is closure fallback; it must not be mislabeled as a user-approved choice default. |
| `ChoiceConflict`, `AnswerError`, `EvaluationError` | Closed structured variants and their named fields | Map variants explicitly to machine data; never parse Display/Debug text for a code or group/member field. |

Minimal app result joins those existing values with parameter outcomes and basis status. Keep the core ChoiceEvaluation unchanged inside the domain result. Expose original app input separately. A feature-only Resolved outcome does **not** make the whole app configuration resolved if a parameter, secret resupply, stale definition or review is outstanding. Only the outer fully resolved variant can carry an executable app plan/effect projection. Provisional controls/default-use facts remain available for UI when unresolved.

For a selected installer, config-value effects are simpler than the earlier generic acceptance wording suggested: `ConfigurationEffect::ConfigValue { name }` references the one `ConfigurationDecl.config_values` map. Same-name references always select the same value. Iterate resolved selected features, deduplicate referenced names and retain the contributing feature IDs; there is no representable single-definition differing-value conflict to invent. Generic merges of genuinely different sources remain their separate obligation. This is inspectable/persisted data, not a runtime writer.

### Default reliance cannot be reconstructed from DefaultUse alone

`ChoiceEvaluation.defaults` records actual defaults supplied for active groups; it omits an inactive group and an omitted group with no current default. Root requires both to remain potential automatic reliance. Derive that reliance directly from the normalized policy/answer state for every declared choice group: UseDeclaredDefaults plus omitted/absent selection remains reliance even when the default is None or the group is dormant. Explicit [] does not. Use the existing FeatureResolution GroupDefault reasons to identify actual closure fallback, without another closure walk. Preserve profile, feature-default and parameter-default/absence reliance separately as root specified. No provisional DefaultUse becomes a durable accepted receipt until the complete app operation admits that result.

A fresh explicit submission may bind the actual current definition directly, with expected_definition checked when supplied. Stored reuse cannot silently replace its stale basis. This follows the root ruling; the earlier mandatory describe-before-first-default suggestion is withdrawn.

### One vocabulary, exact generator boundary

Canonical fragments live in `formats/vocabularies.json`; consuming schemas declare `metadata.x-vocabularies`. `xtask/src/codegen/shared_module.rs` emits one `generated::shared` type and reexports it after byte comparison. It currently rejects ordinary references shared between strict `foreign_parsers="none"` records and permissive `ours/many` public formats. Merely sharing fragment names is not enough.

Existing `xtask/src/codegen/reader_projection.rs` solves the public-output side: a consumer-site object-member ref may carry `x-reader-projection="permissive"`. The canonical shared fragment stays strict; the generated public adapter strips unknown object members, then uses that same type. Markers are prohibited at document roots, array elements and map values; use a meaningful object field enclosing the shared description/evaluation/input snapshot, not a duplicate fragment or invented identity wrapper. This is the existing mechanism used by native compile payload and scrape report health.

The submitted common **input** must retain honest closed admission: do not use permissive stripping to accept and discard unknown intent fields. The exact current mismatch is narrower than my first reading: `format_id::load_format_registry` already parses/validates effective `unknown_fields` (explicit allow|deny, otherwise none→deny and ours/many→allow), and `postproc::apply_registry_unknown_field_policy` already stamps schema-local structs for an explicit deny. But `Strictness::read/apply_strictness`, `shared_module::guard_shared_strictness/classify_fragment` and `reader_projection::validate_policies` still classify ordinary refs/strict owners by foreign_parsers. Thus many+deny works locally but cannot yet participate consistently in the shared join/rewiring.

Root's bounded correction: keep the single loader and its current defaults; have those three decisions consume the already computed effective unknown_fields policy. Reject contradictory policies for one schema; join unprojected shared refs by effective allow/deny; allow a permissive projection only in an effective-allow consumer with a real unprojected effective-deny canonical owner. The late postproc stamp should become redundant/consistent rather than a second interpretation. Keep foreign_parsers honest as the independent consumer-count fact. Clarify `PROP-044-change-native-formats.xml#M-FORMAT-REGISTRY` to name explicit reader policy as an independent registry axis, and `#M-SCHEMA-DESCRIBES-FORM` to require one effective policy across local/shared/projection generation. Existing unspecified formats retain exact role-derived behavior. No raw arbitrary payload or second serializer is needed.

Root correction after the first implementation milestone: the proposed ban on every effective-deny consumer was too broad. Existing scrape-report has foreign_parsers=many, unknown_fields=deny and an explicit permissive health field. Preserve that intentional strict-outer/permissive-field contract: public ours/many eligibility remains independent of the default; only strict canonical-owner lookup moves to effective unknown_fields. Private none consumers remain ineligible. New configuration input has no projections. The public-deny refusal oracle below is superseded by outer-deny/named-field-permissive and fully-strict-input cases; no registry flag is weakened to hide the counterexample.

The correction's focused oracles: existing none/ours/many defaults unchanged; many+deny input rejects unknown nested intent; many+deny and none+deny share one byte-identical type; many+allow output wrapper projection reads that type permissively; unprojected allow/deny mixture still refuses; a deny consumer cannot project permissively; conflicting owners of one schema refuse. These are proposed generator tests, not executed results.

Share the same Selection, typed scalar, description, control, diagnostic, parameter-result and original-input fragments across new public outputs and index4/pending2. Wire integer values use canonical decimal strings with explicit integer kind and checked i64 admission; reusing old describe's float64 annotation blindly risks a JavaScript roundtrip losing width. Use arrays where declaration/reason order matters. A missing answer, explicit empty answer and absent optional parameter each need a distinct representation. Do not rely on a generic omit-empty pass to preserve them accidentally.

Suggested names/spellings, submitted once for root approval:

- `vibe-configuration-description/1`, `vibe-configuration-input/1`, `vibe-configuration-evaluation/1`; rich app plan envelope `vibe-app-configuration-plan/1`, reusing the evaluation vocabulary and existing execution-plan semantics.
- `vibe app describe PACKAGE --configuration --json` selects the common description; without --configuration, the existing e1 behavior remains.
- `vibe app plan PACKAGE --configuration --json [--configuration-input FILE]` returns the common evaluation plus an execution plan only when resolved. No new standalone evaluate command is needed for the first app vertical; the library evaluation seam is reusable.
- `--configuration-input FILE` on `install -g`, root `update -g`, `app modify`, and `install -g --force` supplies a complete generated JSON input document. `-` can denote stdin if implemented consistently. Current CLI has root update; do not document a nonexistent `app update` alias merely because old prose says it.
- Input carries original AppConfigurationInput and optional `expectedDefinition`; actual selected option/installation supplies scope. The new description identifies package vs installer scopes and support. The client does not supply an authority-bearing consumer/instance label.

Proposed exact schema homes: `schemas/configuration/e1/description.jtd.json`, `input.jtd.json`, `evaluation.jtd.json`, and `app_plan.jtd.json`. They project the corresponding shared vocabulary fragments from `formats/vocabularies.json`; index remains the root-selected `schemas/application/e3/index.jtd.json`, pending work `schemas/application/e2/steps.jtd.json`. Public input is many+explicit deny; index/pending are strict. Public output schema-owned wrappers expose meaningful `definition`, `input`, `resolved` or `evaluation` object-member refs with explicit permissive projection **where that fragment actually has a strict input/durable owner**. Do not add unnecessary durable fields just to create a canonical owner. Keep public-only outer description/control wrappers schema-local where necessary, so their reused strict subobjects can be projected at legal consumer field sites; a marker cannot be buried inside the canonical vocabulary fragment. Share the actual repeated semantic values, not a fictitious universal wrapper. No projection marker is placed in the vocabulary home, on a root, array element or map value. Exact wrapper layout must follow the chosen generated type graph, not a freeform serde_json::Value escape.

Keep root's explicit index4/pending2 decisions. Shared fragments avoid parallel hand-written enums/records; existing e1 successful documents stay byte-shape compatible and refuse unrepresentable rich views.

## 2. Public path values: source versus realization

### Observed current behavior

`ParameterDecl::canonical` in `manifest/package/application/wizard.rs` returns path text unchanged after control/nonempty checks. It does **not** call filesystem canonicalize. `steps/params.rs::resolve_parameters` chooses last explicit raw assignment, then recorded value, then prompt/default; for Path it calls `HostFacts.resolve_path`, checks must_exist, and stores `path.to_string_lossy()` in ParamValue. CLI `commands/app/facts.rs::absolute_path` returns absolute inputs unchanged or joins relative inputs to the invocation CWD; it does not resolve symlinks, normalize `..`, expand `~`, or use the input-file directory. On current_dir failure it can return a relative path. `Installation.parameters` stores the resulting public string but no origin. Feeding that map back as a rich explicit-input map would freeze defaults and profiles into false user intent.

### Minimal additional domain data

Use one semantic origin enum for parameter results:

- Explicit — supplied by a complete input, CLI/GUI delta or an actual prompt answer;
- Profile { id } — the selected profile supplied the value and the user did not override it;
- Default — supplied by that parameter's declared default;
- Absent — optional parameter has no value; preserve this state and its automatic reliance;
- LegacyEffective — only for interpreting old v3 values; never pretend it was Explicit/Default.

Prompt Some(value) is Explicit; prompt None retains the actual fallback origin. Previous/Recorded is not an origin: persistence does not change whether a value came from an explicit answer, profile or default. Avoid reusing group ProjectionOrigin, which lacks profile/absence/legacy meaning and describes another stage.

A typed public parameter result needs id, declared type, optional canonical typed value, origin, and a source basis for retention. For paths, the canonical value is the realized **absolute path text**, not a promise of physical file identity. Keep the original input separately; a default/profile realization is never inserted into original.parameters. A secret outcome has only presence/resupply metadata, no value/source-answer bytes/hash. No schema draft is required to choose these domain facts.

Capture origin before normalization erases it: explicit input.parameters contains ID → Explicit; otherwise named profile.parameters contains ID → Profile; otherwise declared default → Default; otherwise Absent/required question. The existing normalization can expose a value+origin record for supplied parameters or the app assembler can retain this simple provenance while it calls normalization. Do not rerun type/choice rules to derive it.

### Exact maintenance strategy

1. Assemble original input using root's complete-submission versus stored-reuse/delta rules. Preserve which parameter setters were supplied **in this invocation**; equal text is not enough to detect an explicit rebind.
2. Determine source identity separately from current validation rules. A path source identity contains origin, profile ID when applicable, its typed lexical source value (or absence), and the fact that the current kind is still Path. It excludes labels/descriptions, invocation CWD and validation-only rules such as must_exist/bounds/allowed-values. Explicit inputs do not depend on unused defaults/profile presets; Profile uses its actual selected profile/preset; Default uses its declared lexical value. Keep this identity distinct from the conservative whole-configuration review basis. Changed validation rules do not authorize relocating a path.
3. First installation, a fresh complete submission, or an explicit setter for this parameter uses the current HostFacts resolver. A relative path is anchored to the invocation context, as today; do not silently change to package/input-file/app-root anchoring. Even `--set dir=data` repeated from a new CWD is a fresh explicit setter and intentionally rebinds. A GUI that edits only a group sends a delta without resubmitting unchanged path fields; complete replacement is explicitly fresh input.
4. On stored maintenance reuse with no setter or fresh complete replacement, if origin/profile ID/lexical source are unchanged and the type is still Path, reuse the previous absolute realization directly. Do not send the original relative text through the new CWD resolver, and do not pass the saved realization through an arbitrary host re-rooting callback again. The original Explicit/Profile/Default origin remains the same.
5. If source/origin changes, use current host resolution **only after the corresponding root review rule has accepted the changed/new automatic basis**. Preserve the old record until acceptance. A whole-definition review triggered by another semantic change or by new validation rules must not rebase an unchanged source: after acceptance, that path still uses its previous realization. Changing a profile's lexical path or switching profile identity is a source change; changing only must_exist is not.
6. Always revalidate canonical value/type and current must_exist against the host, including reused paths. A deleted required path refuses before effects. For new common records require the returned path to be absolute and losslessly representable in the declared text transport; a failing/relative/lossy HostFacts result must not become a silently reinterpretable durable value. Do not add symlink resolution or a no-ABA/filesystem-identity claim to this parameter operation.

The current request machinery already distinguishes presence of --set from absent input, and root's full-submission Option distinguishes replacement from reuse. Carry that ephemeral disposition into parameter resolution; do not persist a second operation history or infer it from a value comparison. A v3 legacy absolute path may remain a LegacyEffective suggestion/preserved value under the legacy route. Upgrading it to rich intent requires explicit confirmation of its new source meaning; equality with today's default proves nothing about its historical origin.

### Discriminating tests

- Install explicit `dir="data"` in CWD A, restart update in CWD B without a setter: retain A/data and Explicit origin. Resubmit `--set dir=data` in B: deliberately bind B/data. Verify original/review source and output are not confused.
- Install profile/default relative path in A; edit only a group in B: retain A/data, keep Profile/Default origin and absent original.parameters entry. Prompt None is the same fallback; prompt Some is Explicit.
- Change only display labels or an unused default under an explicit path: no rebase. Change a used profile/default path or origin: rediscovery before uninstall/dependencies/steps, then current-host realization on acceptance.
- Install default/profile `data` in A with must_exist=false; remove A/data, create B/data, restart in B and change must_exist=true. Even after accepting the whole-definition review, validate A/data and refuse. Never re-anchor to the existing B/data. Changing validation rules is not a new path source.
- Whole-definition review caused elsewhere, unchanged path source: after acceptance retain the old realization. A changed lexical source or explicitly resubmitted setter is what permits current-host rebinding.
- Absent optional parameter remains Absent; adding a default triggers the automatic-basis rule, not an unobserved new value. LegacyEffective never becomes Default by matching text.
- Roundtrip the generated vocabulary with omitted versus [], inactive controls, profile-derived normalized input vs submitted original, unresolved core result, i64 extremes and typed public path origins. Unknown input fields refuse; public projection strictness does not weaken durable records.
- Two selected features referencing one config-value name produce one value with both provenance IDs. No impossible differing-value test is invented for that source model.

No tests were executed in this read-only review. These deltas are sufficient to freeze the semantic/data seams for implementation without another generic runtime or research loop.
