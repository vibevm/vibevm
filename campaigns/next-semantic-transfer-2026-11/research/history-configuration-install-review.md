## C1 — Requested state is necessary; duplicating it as serialized evidence does not make it current authority

`cecd8552725a3fc17dd9139b1eabf0c5910db4ef` introduces a core `LockedConfiguration { epoch, requested, request_digest, resolved }` in `crates/vibe-core/src/manifest/lockfile.rs`; `vibe-wire/src/behaviour/lock_configuration.rs` owns canonical requested/resolved JSON and cross-links the digest. `vibe-install/src/record.rs` retains original roots and consumer/declaration origins, explicit/omitted/additive/exact/dormant answers, definitions, exact shown-default receipts, selected effects and provider provenance. `apply.rs` constructs/validates the record before effects and writes it into the resulting lock. `plan.rs` refuses configured replay without current normalized authority and compares old/current inputs and result; unknown configuration epochs do not take legacy lock regeneration.

The causal requirement is real: the same effective feature set can come from omitted defaults, explicit empty, exact answers or dormant answers; these diverge on update or multi-consumer merge. A selected feature set cannot reconstruct the original request. `record/m_05_d_1_cases.rs::production_apply_records_requested_and_resolved_separately` drives real plan/apply through a custom source and checks dormant `later`, derived `closure` absent from original request, and separately retained defaults. `exact_replay_rejects_changed_definition_or_lost_request` rejects changed capture, tampered derived closure, changed definition and missing current authority. These are meaningful semantics, but its `Fixture` constructs `CandidateConfiguration`, consumer/domain/instance identities and a solved route in Rust; it does not prove ordinary CLI bootstrap.

The storage has concrete duplication: TOML stores requested/resolved JSON strings; their schemas contain more JSON strings (`configuration`, normalized `definition`, `effects`, result/default request). `configuration_record` serializes definitions and reevaluates configuration; `validate_replay` parses/recompares full requests and source receipts. This is explainable evidence machinery, not a new independent user-state owner. Transfer should retain original intent separately from generated results in the incumbent authored/lock owners; core→wire dependency avoidance is a legitimate constraint, but it does not by itself require copying this nested representation or every environment wrapper.

**Final-state correction to a host-only reading:** later code at pin, `vibe-install/src/plan.rs:295–395`, calls `authored_configuration(workspace, ...)` before freshness; `authored_configuration.rs` reads every workspace node's original `consumer_configuration` and creates RequireSelection requests. `plan/transaction.rs::capture_authored` calls the existing normalized source seam; `vibe-package-source/src/source.rs::bind_request` captures the catalog and admits definitions from actual source metadata. Thus final ordinary explicit authored configured install has a real route; the initial cecd fixture boundary is not the final implementation ceiling. There is no implicit default consent: authored rows force RequireSelection. Final `record.rs::request_freshness` includes request/definition identity before Fresh. Full end-to-end authored CLI execution was not rerun here.

The exact statically reachable ordinary path is `CLI direct::run_with_scope → CliPackageSourceFactory::build → RegistryPackageSource → orchestrator execute_prepared → plan_prepared_mode → authored_configuration → PlanningSource::capture_authored → InstallResolver::bind_request → TransactionCatalog::admit_source_definitions → FrozenSource::solve_masked → cells::solve_catalog_request → ResolvoDepSolver::solve_configuration_routes → RouteResolution → plan/fetch::fetch_node → ordinary apply`. Fetch takes selected effects from `route_resolution` rather than choosing defaults again; apply validates them and records original/result data. Required preconditions include one original registry dependency matching each authored configuration row, a real consumer node, valid explicit selections, actual candidate metadata with checked definitions, the resolvo backend, and a supported registry-only configured graph. The final solver explicitly refuses native candidates, multiple differing instances of one package, conditional targets/obsoletes/non-registry declarations, and cross-package TargetFeature forwarding. Missing mandatory answers do not invoke E4 automatically: ordinary install has no call that constructs the choice host or starts its interactive follow-up. This is static call-path reachability, not a fresh CLI execution claim.

**Identity limit:** the original consumer is an actual workspace node path, but domain/instance/configuration/definition-owner/target-owner strings come from authored rows. They are not proof of multiple physical package installations. The existing solver/install graph remains package-coordinate based; carrying an instance label must not silently split a shared workspace package. ## C3 — Recovery is wired to real writes, but its retained-state completion path is library/test-only and expensive

`644bbd0de25e1335e21e513b3228c1a688256bf0` adds `preconditions.rs`, `removal.rs`, `vibe-workspace/src/configuration_transaction.rs`, updates actual install apply/boot/hook/prune paths, and rewrites ordinary uninstall to use complete graph planning. This is not merely a record or dormant framework. Apply now checks workspace manifest/lock bytes, current catalog and payload before writes; structural boot/subskill preflight runs before publishing transaction intent. Ready-path migration authoring moves from plan to apply. Checkpoints surround manifest, slot, boot, lock and post-install phases, and nonfatal post-install failure retains evidence instead of claiming complete rollback.

Useful invariants:

- `RemovalPlan` keeps deletion membership private; `plan_removal` validates the full locked graph and workspace roots, retains shared dependencies, explains reverse dependents, and refuses unproved capability/OR roots or configured removal without newly admitted intent.
- `plan_admitted_removal` takes a new normalized request and complete desired graph, then reuses ordinary apply; it does not infer new answers from old selected effects. Its positive test invokes this library route, whereas ordinary uninstall calls `plan_removal` and refuses configured locks.
- `validate_owned_slot_removal` verifies materializer footprint and refuses unrecorded files/directories, symlinks and unsupported native names. Pruning is limited to old-lock-owned slots; arbitrary orphan directories are not deletion authority.
- Recovery distinguishes absent, empty and populated paths, stores file bytes/permissions, rejects lossy path normalization, validates the admitted original target set on reopen, refuses a third state before any restoration, and preserves external-effect uncertainty. Changed boot needs compensation through the boot owner; local-prefix restoration does not claim total rollback.

Concrete costs and missing completion:

`ConfigurationTransaction::begin` recursively captures every workspace manifest/boot/redirect target and **all old plus new copy-slot paths** supplied by apply. It clones the complete before-image into checkpoint; every `checkpoint` rereads every target, and `persist` serializes both byte-image maps to JSON. The read code has no per-file/aggregate byte cap. Thus ordinary one-package changes can reread and serialize all retained slots repeatedly; this follows method bodies, not a type-count argument. No benchmark was run, so cost magnitude is unmeasured.

Any retained operation directory blocks another begin. There is deliberately no rollback-on-Drop. `reopen` needs the original admitted slot set; `restore_local_prefix` retains the journal after success and refuses changed boot until its owner compensates. Final source search finds reopen/restore calls in tests only. The production API can support an embedding, but no ordinary command completing this recovery was observed. `normal_execute_prepared_faults_at_actual_manifest_slot_boot_lock_writers` proves in source that manifest changes remain on injected failure, local restoration works at early checkpoints, and boot/lock checkpoints refuse local restoration with “boot compensation”. Tests manually supply the old workspace and slot set. Therefore durable evidence exists, but “recoverable install” is not proof of a complete operator recovery journey.

Another scope change needs reconciliation: prototype `plan_removal` removes every locked row outside surviving workspace-root closure, potentially collecting unrelated historical rows. Main's current uninstall deliberately limits removal to the selected root's old closure and retains unrelated historical rows. Prototype `apply_removal` also rejects any removed in-place clone even after frontend destructive approval, while main guards every planned in-place slot and supports its established staged-removal path. Do not overwrite either main behavior by importing the prototype wholesale.

**Main comparison:** `df040becb` already has whole-workspace graph removal and shared-transitive retention in `vibe-cli/.../uninstall/plan.rs`, per-slot destructive guards, reversible rename staging plus before/replacement checks in `uninstall/transaction.rs`, and install `apply/file_guard.rs` with slot rollback and lock/provenance guards. It lacks this durable configuration journal, but is not an unprotected starting point. Conversely main FileGuard's Drop restores bytes directly without a third-state check, so existing mechanisms are not automatically equivalent to the prototype's explicit recovery safety. The useful transfer question is adding original-configuration and crash-recovery invariants to actual incumbent transactions, not choosing one complete transaction framework by age.

## C4 — Shared choice UI has genuine effects behind a manually prepared host; its answer is not written back to authored source

`efc6da9a04034dc280b4d5a0eabe8f8b4c723f97` adds `ConfigurationChoiceHost`, CLI `install/choices.rs`, and registered MCP `configuration_choice`. Host construction requires `PreparedConfigurationDiscovery`, admitted definitions, full normalized request, source, install request and explicit application policy. It compares admitted definitions and refuses preexisting unshown default consent. Request skeleton comparison prevents answers replacing consumer/domain/instance/non-choice identity. `Evaluate` uses existing evaluator controls; `Prepare` binds defaults to exact shown identity, acquires the lease, begins normalized transaction and calls `plan_reconfiguration`. `Apply` consumes the one pending typed plan, starts the same request transaction, and calls real `vibe_install::apply_with_spec_format`.

These are real graph/effect/lock operations, not fake success DTOs. Tests inspect actual lock answers/default receipts and selected features. Radio/checkbox controls use cardinality and evaluator-projected guard eligibility. Missing/unknown/conflicting selections refuse; JSON/non-TTY never prompts; assume-yes only confirms apply after choices resolve. CLI checks requested root and effective offline posture before evaluation/application.

The limitation is concrete entrypoint ownership: `direct::run` takes the branch only with `--choice-host`; it connects a supplied Unix socket, and non-Unix returns unavailable. It does not start a host or prepare admitted source. `ServerContext::new/with_store_root` set configuration_choice=None; the tool returns unavailable until `with_configuration_choices` is called. At final pin, `ConfigurationChoiceHost::new`, the listener invoking `serve_cli`, and explicit MCP host attachment are only in the inspected fixture/test paths. The fixture creates a cache manifest copy, analysis capture, CandidateMetadata/ConfigurationAdmission and host, then runs the public transport. Calling the test “production_install_machine_and_tty” does not establish ordinary user bootstrap.

The host retains at most one pending plan in a Mutex. Its semantic ID names the reviewed request/graph/effects/record, but the typed plan is process-local; a restart loses it, and apply takes it before execution. This may be sensible for a bounded embedding; no durable apply/restart guarantee follows.

**Original-state ownership gap:** new answers live in host-normalized request and resulting lock configuration. The host does not edit `consumer_configuration` in `vibe.toml`. Generic apply merges required packages, not those answer rows. In the fixture the manifest has no authored configuration, so subsequent ordinary install has a configured lock but no current authored authority and refuses. If authored rows already exist and differ from host answers, final `authored_configuration` rejects the mismatch. This is source-derived behavior, not an executed new regression. Successful “applied intent” in a lock is therefore narrower than a complete editable/reloadable authoring flow.

**Transfer:** reuse active-control projection and exact shown-definition default binding, preserve semantic answering versus application confirmation, and put answer changes through the selected authored input owner. Socket, manual capture resource, environment wrappers and separate host lifecycle are not shown necessary for the ordinary local wizard that main already owns. They may remain legitimate embedding boundaries; they are not prerequisites to copy into every install.

## Bounded disposition

All five commits contain substantive product logic, not merely ceremony. Their strongest reusable parts are original-versus-derived input, candidate/default identity, source drift refusal, guarded deletion/recovery and complete-world comparison. Their principal integration debt is asymmetry: normal authored install and whole update exist at final pin, and explicit reconfiguration has an authored library fallback, while scoped update, configured exact reinstall and choice-host answer ownership retain narrower support; durable recovery evidence blocks retry without an observed ordinary recovery command. Main has already solved parts of graph removal and rollback differently and now has accepted shared kernel/intent admission with explicit unsupported effect guards. None of this batch is accepted as a complete feature or ready for literal transfer.

No historical acceptance bundle was used as runtime proof; their files are explicitly excluded in JSON. Large generated loader/version-stamp churn was excluded. Source and target observations are bound to their pins, not either dirty workspace. Missing-path probes were corrected by locating the actual `plan/transaction.rs` and source adapter paths; no absence claim rests on the mistaken probe.
