## Domain state machine and actual effect order

`Target::open` pins existing parent/name and parent identity. `Target::observe` reopens the logical parent through the project capability, compares identity and reads an ordinary regular single-link mutation snapshot. Source readers accepting hardlinks are correct for other tasks but are not interchangeable with this mutation contract.

Store acquisition happens **before** comparing target bytes and before a no-op return. Consequently an observed stale source or initial no-op can leave created store/barrier state even with no journal or target write. The current report tracks those effects. A1's stale case says no journal, not absolutely zero state; do not strengthen that claim without changing ordering and proving coordination. Malformed/grant/frozen preflight is earlier and its tests do assert no state.

New apply order: strict approval replay → existing target pin → disjoint store/bootstrap and barrier → source observation/equality → no-op or before image → Prepared journal → Publishing journal → image resync and source/name reobservation → target publication → verify actual bytes/current reader → Published journal. Recovery/restore retains the same before image and phases Restoring/Restored. Journal intent excludes mutable phase, while operation key binds physical project plus operation ID and intent binds physical store and complete approval.

Known supported observations:

- Prepared/Publishing + approved-before: complete can publish; restore can record Restored without a target write.
- Publishing + validated-after: complete writes Published checkpoint; restore can reverse under retained intent.
- Published + validated-after: exact apply/complete is NoOp; restore can publish before bytes.
- Restoring + either approved-before or validated-after: explicit restore can finish; unrelated complete is not silently substituted.
- Restored + approved-before: NoOp; same old apply does not reapply.
- Missing target, third bytes/mode, invalid journal/binding/image, Prepared+after and other unsupported combinations: refuse/preserve evidence.

Report `uncertain` is sticky across later writes; a later successful checkpoint cannot erase earlier unknown durability. Inspect/load mark durability unconfirmed rather than infer a flush from a surviving file. Restore failure may leave a valid Restoring journal and before image; that is reported, not claimed rolled back. Deterministic stage names identify candidates but do not authorize deleting unknown occupants.

## Concrete design corrections and limits

**Coordination scope:** the lock resides in the selected external store and is keyed by physical project. Same project with different recovery stores uses different barriers. The exact task says “under the declared participating-client barrier”; the permanent MIGRATION-APPLICATION-WIRE-LAW explicitly requires the same designated physical recovery store and excludes different stores and ancestor/descendant project scopes. Thus stating the guarantee as clients sharing the admitted project/store binding preserves the refined original contract rather than narrowing it. Neither all processes nor every invocation targeting that project is excluded. Test same-store contention; document different-store/uncooperating writers as outside that barrier. No new global lock registry is needed to disguise this limit. Main LifecycleLease::acquire is the separate outer lifecycle mutation barrier at canonical workspace .vibe/lifecycle.lock. Its scope is lifecycle state, and lifecycle already depends on workspace; importing it into this workspace domain would create a reverse dependency. D1’s refined source contract does not require that join. If later integration needs broader coordination, use an explicit outer adapter and preserve lock order rather than claiming today’s store-local barrier already provides it.

**Publication owner choice:** main `write_atomic_transactional_in_with_mode` uses deterministic stages but the shared helper classifies rename-error as BeforePublication for the non-owned path. The stronger `write_atomic_owned_in_with_mode` uses retained stage receipt and classifies rename-error PossiblyPublished; its wrapper currently passes no deterministic stage. This is a source-level stage-contract concern, not a reproduced failure. Prefer the stronger existing owned publication owner if its contract satisfies D1; evaluate deterministic restart/reuse before substituting it. If a combined capability or the non-owned entry is genuinely required, bind a precise fault-stage discriminator before production changes. Do not globally alter unrelated callers just because the prototype chose one API. Domain report truth must follow measured/guaranteed primitive evidence, not Err=>untouched.

**Bounds:** prototype defaults the one-file grant's journal/read ceiling to8MiB and offers a setter. The same cap also checks encoded journal size; escaping can exceed it even when raw before/after individually fit. It is an implementation policy, not an authored-format law. Root target direction is no arbitrary new global quota while retaining observed-length/allocation bounds. CLI exposes no cap override in the inspected owner. Decide this explicitly; do not copy the default silently.

**CLI authority (root decision):** prototype CLI directly creates the grant from payload authority strings and calls explicit invocation itself the human grant. For the new main command, root instead requires independent project/file/store grant flags outside operation JSON and exact equality with payload authority. This avoids treating a saved/forwarded request alone as ownership authorization. There is no existing main command compatibility to preserve here.

**MCP authority:** preserve the finite configured file/store builder, project/cache-root stability and protected machine-cache exclusion. An empty configured file set in prototype deliberately grants only root vibe.toml; no configured builder means no authority. The payload must match configured roots/file before opening them. Recheck protected-store policy before every creating/mutating store action. Server startup grant flags and actual context/dispatcher tests belong to full D1.

**Preflight transport:** prototype later ToolError widened to generic JSON. Root requires a closed typed operation-report preflight arm alongside C2's typed planning preflight, with real advertised/runtime/generated shape parity. Do not silently relabel operation preflight as executed output to carry data. Internal invalid reports must retain original observed evidence as explicitly unvalidated diagnostics, never a forged normal successful report.

**Stale documentation:** pinned journal schema metadata still says emitted required-nullable attributes/refusal remain to be confirmed, while actual wire/domain tests cover missing unix_mode refusal and explicit null acceptance. Verify through normal target generation/corpus, then write current facts rather than carry that stale pending sentence.
