It is a conservative unsupported boundary, not host readiness. The String control installs/project parameters/cold replays, with no config-effect data.

Refusals preserve semantic project state and publish no lock, slots or hook log. All worlds preserve original request, complete registry and independent cwd sentinel snapshot. ## Owners and smallest required design

`ConfigurationDecl::normalize_input` in core validates typed authored input through the existing parameter validator, whose Path canonicalization is lexical nonempty text only. `ConfigurationSnapshot` in resolver retains original consumer identities but no trusted filesystem root/capability: it cannot infer a host base from those keys or process cwd.

The ordinary planning host has legitimate selected root context: CLI install preview resolves --path, and the existing install resolver adapter passes project_root into the shared package-source construction. That establishes where root information exists, not an approved semantic base or grant to read arbitrary values. A future implementation needs an explicit host-owned base/containment/observation policy, shared install/update/cold behavior and capability boundary before admitting must_exist. Do not put ambient exists/canonicalize calls in the pure normalizer or turn Path into String to bypass the obligation. Whether a no-host-check lexical subset is useful also requires architecture, not this qualification.
