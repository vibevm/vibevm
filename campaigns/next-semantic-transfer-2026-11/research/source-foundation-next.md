## Decision summary

The next full source task cannot honestly be closed by adding descriptor structs plus the already-accepted pure token planner. Original A1 expressly includes an actual source-plan-to-existing-M13-application test and the first real `facts adopt` consumer. Its pinned test applies to a real `vibe.toml`, repeats idempotently and refuses a changed authored source without publishing a journal. Main currently has the token planner and filesystem primitives but lacks the migration domain transport/application/recovery owners used by that test.

Recommended sequence: **M13C2 strict neutral machine planning → bounded complete one-owned-file M13D1 apply/inspect/recover domain → A1 descriptor policy/reader/source recipe and actual Mixed exact-file facts adoption**, while establishing admission barriers so the newly accepted source declarations cannot silently flow into unsupported old suffix consumers. Complete downstream A2/A3/A4 readers as their classified capabilities arrive. Do not count the parser/pure-plan portion as full A1, and do not count A1's two apply tests as full D1 recovery/platform qualification.

This sequence follows actual dependency ownership, not the final prototype's large module boundaries. No completed M16 machine server/editor service is required: C2 explicitly excludes that dependency, D1 explicitly provides an adapter seam for later participating-buffer coordination, and the inspected apply path uses its own domain request/report/journal plus SafeFS project/store capabilities.

## The package policy should preserve explicit absence

I support root's proposed policy:

| Authored state | Recommended interpretation policy |
|---|---|
| Package: neither `sources` nor `source_exports` key present | Existing bounded legacy behavior |
| Package: `sources=[]` explicitly present | Explicit policy with no semantic sources; unmatched files stay raw/unclassified |
| Package: nonempty `sources` | One selector owns classification; no-match remains raw/unclassified; conflict remains path-specific NeedsInput |
| Package: source_exports only, including an explicit empty list | Explicit policy, never a route back into legacy semantic scanning; export declaration itself grants no interpretation |
| Project: sources absent or empty | Preserve the explicit existing SOURCE-HOST-OPT-IN legacy rule |
| Project: sources nonempty | Same row/precedence law under validated host coordinate, with explicit classification |

This deliberately preserves the actual prototype materializer/map key-presence boundary. It repairs the inconsistent facts/citation behavior rather than changing the stronger materializer interpretation. A package and a project may have different compatibility predicates because the permanent host rule expressly says absent/empty is legacy. That asymmetry must be named and owned, not accidentally arise from separate readers.

**Typed presence must survive round-trip.** Prototype PackageMetaWire has `Vec<SourceDescriptor>` and `Vec<SourceExport>` with `default` and `skip_serializing_if=Vec::is_empty`; therefore an explicit empty key can disappear after parse/serialize. Meanwhile `derived/selection.rs::read_descriptor_package` and descriptor_map inspect raw key presence, whereas facts `authored_for_selected` uses `meta.sources.is_empty()`. This is the concrete defect. A typed declaration/policy representation must retain absent versus explicit-empty and expose one authoritative mode to materializer, facts, citations and other admission owners. An Option-backed authored list or a private explicit-policy representation can do this; no second raw-TOML policy parser or redundant boolean that can disagree with its list is needed. Existing direct PackageMeta constructors/serializers must be adapted coherently.

`source_exports` is an ordinary-document binding feature of A2, not a prerequisite for A1's descriptor primitive. Do not add an empty export API simply to copy the final PackageMeta layout. Freeze the future policy now; when exports land, preserve presence, and resolve a named export only after the ordinary source has an actual CommonMark selection and captured heading resolution. An export-only declaration never infers CommonMark or Vibe semantics from its file suffix. Declaration syntax need not pretend it already proves file existence or unique headings.

## Admission closure before activating authored descriptors

The danger is not just a missing Rust type. Main's current package parser refuses source fields. Adding them makes previously rejected input admissible. Existing transformed materialization then still treats parseable `.md/.xml` under specs/README as Vibe; existing facts and several inspection routes still use the suffix scanner. A newly declared raw source must not cross those unchanged paths silently.

Recommended activation discipline:

1. Parse and retain source policy once with the selected manifest. Explicit mode is a semantic admission fact, not `sources.len()>0`.
2. Before any conversion, parser invocation or registry mutation, each source-accepting route either consumes the classification over the actual selected bytes or returns a precise unsupported-classified-operation result. No fallback after failed declared admission.
3. A first successful Mixed exact-file facts path can use unchanged installed bytes and record/lock consistency, with held ordinary source reads and no global byte cap or hardlink ban copied from mutation snapshots. Any desired install path used by its real CLI fixture must preserve the same policy and bytes. Unsupported transformed/directory/legacy entrypoints need pre-effect refusal, not semantic fall-through.
4. The materializer policy, selected resolver/point-pattern/embed/prompt reads, static/own/dynamic boot handling, facts/requirements/adoption/sync, documentation citation and semantic show/tree/check/progress readers form the later complete consumer inventory. Existing previous audit identifies concrete gaps; acceptance needs current targeted evidence for each promised path. A package install that immediately generates boot is not made safe merely by fixing the facts command afterwards.
5. Guarding a route as unsupported is an honest temporary rollout boundary, not completion of A3/A4 or permission to omit those useful prototype capabilities. Preserve legacy absent-package and project-empty behavior explicitly.

Keep declared media separate from physical extension. The prior source audit's Simple boot `project_spec_text(absolute, raw)` and lock citation reopen defects are A3/A4 integration issues; they are not reasons to widen the pure descriptor parser. New read adapters should pass declared media and the same captured buffer to existing parsers instead of rebuilding maps and reopening paths. Main's accepted selected-world/point-pattern/held-source owner is stronger than the prototype's old pattern lookup and must survive.

Generated boot outputs need the existing G3 ownership rule: INDEX/STATIC and direct publication artifacts are not authored sources. The prototype descriptor's three-name check predates main's direct `.vibe-boot-*` exclusion. Reconcile the reserved-path decision with the incumbent owner rather than introducing another divergent list. Directory defaults must not confer source semantics on reserved generated files.

## M13D1: exact capability consumed by source-plan application

The actual dependency is a **domain-owned one-file transaction**, not the whole machine-operation server:

- Independent caller grant selects one owned target file and a disjoint recovery store; payload path strings do not grant ownership.
- Strict operation/journal/report contracts retain approved planning request, before/after/diff identities and exact before image. Apply replays the original plan and validates its target reader before effects.
- A physical project/store binding and participating-client lock fence cooperating writers. Target parent/name and source bytes are observed again after durable preparation and immediately before publication; uncooperating-write races remain explicitly outside the guarantee.
- Durable before image and journal phases precede target publication. SafeFS deterministic stage publication carries actual stage/durability/possible-effect evidence. Idempotent repeat observes the retained operation; third states refuse without overwrite.
- Inspect/recover read existing state without inventing missing journals/locks; recovery completes/restores only known owned states and reports uncertain effects/residue truthfully.

Inspected final runtime/storage/recovery bodies use those domain capabilities. No M16 server import occurs in this dependency path. Main already exposes Project/Pinned, StableFileSnapshot, ExternalStore with project locking, deterministic `write_atomic_transactional_in_with_mode`, publish-stage and durability results. Main lacks the migration domain runtime/transport/journal and two exact read-only store helpers used by prototype inspect/recover (`open_existing_disjoint`, `lock_existing_project`) in the inspected ExternalStore method inventory. Extend that existing owner if required; do not build another store or lock system.

Main's accepted `vibe-install::apply::FileGuard` is useful evidence for safe publication/undo semantics, but it is private installation logic with in-memory before state, not a persistent process-exit migration journal. Reusing its name or Drop behavior cannot meet D1 recovery. The correct reuse is the underlying SafeFS capability/publication primitives and their established effect semantics. Avoid a workspace→install dependency cycle merely to call the private guard.

A1's two apply/repeat/stale cases do not establish full D1. D1 additionally requires interruption before/after every write, durable report/journal continuity across process exit, inspect/recover and third-state handling, ownership/foreign-upstream refusal, truthful weaker platform guarantees, and working Linux/macOS/Windows paths plus measured native proof explicitly separated. CLI/MCP effect grants and protected-store policy belong to its own surface boundary. Those are outstanding original obligations, not optional niceties to discard for speed. It is reasonable to build/accept the complete domain capability first and add A1's source recipe afterward, while tracking any unavailable native qualification honestly.
