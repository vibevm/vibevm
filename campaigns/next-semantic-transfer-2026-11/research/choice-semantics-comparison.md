# Existing app selection versus package configuration semantics

Main pin: `1448ed5cc33a4fadbce9d8331bf5f2d96052aec3`; prototype pin: `7fe6376ccef7f321302a8f18610fcb0c9cc2686f`. Inputs: `/tmp/nst-app-installation-study.md`, `/tmp/nst-choice-ux-causality.md`; the evaluator and discriminating tests below were also read directly from these Git objects. No builds/tests/network/DB or product writes. This comparison identifies semantics the common option system must express; root owns its architecture/specification.

**Main contributes the complete ordinary app user journey: describe → choose/profile/parameters → plan → execute → persisted installation → update/modify. Prototype contributes richer consumer-owned configuration semantics. Neither evaluator is a drop-in replacement for the other.** Reusing main's UI and lifecycle must preserve its existing app behavior, while making the option model express richer requests for all nine package kinds. Package kind must not silently select a weaker meaning for the same declared constraint.

## Exact semantic comparison

| Axis | Current main app behavior | Prototype behavior and evidence | Concrete distinction to preserve |
|---|---|---|---|
| Cardinality | `FeatureDecl` tree, required features and `exclusive_group`. Valid exclusive groups have exactly one default; `Tree::close` fills it whenever the group is active and empty. Free checkboxes are unrestricted subsets. | `feature_constraints::Cardinality` explicitly defines zero-or-more, one-or-more, zero-or-one, exactly-one. `Constraints::order` validates declared defaults against cardinality. | An active optional radio group allowing “none” cannot be encoded as a main exclusive group: main either inserts its default or refuses a no-default declaration. “Select at least one of any three plugins” is not the same as marking one particular plugin required. |
| Default policy | New install normally starts from feature defaults; group closure can insert `ExclusiveDefault`. This is established legacy behavior. | `DefaultPolicy::{RequireSelection,UseDeclaredDefaults}` and shown-definition receipts separate declared default from consent. Missing mandatory choice => NeedsSelection with no expansion. | Reusing main's implicit default rule for a new `RequireSelection` Redbook continuity request would silently choose MUP. Conversely, making existing app declarations require new explicit consent would break their unattended/default behavior. Compatibility must be explicit rather than accidental. |
| Omitted versus explicit empty | Empty `FeatureRequest` means use recorded/default choices. Prompt `Some([])` is distinguishable in the call, but required/group closure still applies, and installed state retains only the resulting set. | `Selection::{Omitted,Explicit(set)}`; explicit empty blocks default substitution even under use-defaults policy. Optional empty can resolve; mandatory empty stays NeedsSelection. | `{choice: omitted, use defaults}` can select `a`; `{choice: [], use defaults}` cannot. A resolved empty optional set alone cannot tell which original request occurred. Test `explicit_defaults_and_empty_policy`. |
| Additive versus exact | `--feature`/`--no-feature`, profile and prompt selections determine a base and local overrides; no per-consumer exact-set constraint. Modify has its own recorded-set merge. | `SelectionIntent::{Additive,Exact}`; additive requests union, exact requests must agree, and additive members must fit any exact set. | A asks exact `{a}` and B asks additive `{b}` for the same instance: conflict, not `{a,b}` and not last-writer-wins. A exact `{a,b}` plus B additive `{a}` is compatible. Tests `shared_additive_union_and_actual_evaluator`, `exact_conflicts_name_both_edges_and_additive_must_fit`. |
| Guards and closure | Parent selection/`requires`/required children imply features. Deselecting a parent removes descendants. Installer step `when`/`unless` can test feature/parameter/host facts after feature resolution. | Positive `Guard::Group`/`Guard::Member` on groups or members; acyclic dependency walk; inactive constraints do not demand choices. Ordinary feature closure is forbidden from implicitly selecting constrained members. | “WAL additions eligible only when WAL selected” is a choice guard, not a skipped installer step. Main's child→parent implication would actively select a parent; prototype's dormant guarded answer must not select its guard. Host command/env/file conditions are not package-choice implication rules. |
| Dormant intent | Installation stores selected features. A removed child/branch choice has no separate retained dormant-intent record. | Original edge selections remain in the echoed/stored request while guard-inactive choices contribute no effects. Reconfiguration can reactivate them. | Pick WAL+wal-specspaces; switch to MUP; later return to WAL. `wal-specspaces` must survive as dormant user intent without pulling WAL into the MUP world. Tests `dormant_intent_survives_until_positive_guard_is_active`, `update_retains_explicit_empty_and_dormant_intent`, F2 switch-back test. |
| Candidate/version definition | App evaluator receives an already selected `InstallerOptionDecl`; it does not participate in package candidate backtracking. Prior feature IDs absent from the new option are filtered. | `CandidateConfiguration` plus source/content/definition receipts bind effects to each candidate. Solver backtracks while retaining original incoming consumer requests; default consent changes can require rediscovery. | v2's branch enables incompatible dependency X, so solver selects v1: v2 effects/default receipt must not leak into v1. Tests `compatible_older_candidate_keeps_only_selected_effects`, `changed_semantic_default_requires_rediscovery`. |
| Consumer and instance ownership | One app installation record keyed by package installation, with local feature selection. App dependency resolution can reuse an installed matching package; it does not merge separately attributed consumer choice contracts. | Group requests by configuration domain/instance; package/configuration identity must agree. Conflicts retain consumer edge indices. Different explicit domains may keep different choices. | Two consumers of a shared instance asking different exact toolkit choices must produce a conflict naming both. The same requests in distinct environment domains can resolve independently. Tests `separate_environment_domains_keep_different_choices`, `owner_target_roles_and_configuration_are_identity`. |
| Dependency activation and forwarding | App features gate installer steps and their requirements; the app evaluator has no strong/weak forwarding algebra. **Main already has legacy dependency-feature/subskill expansion in `vibe-resolver/src/features.rs`; it is not absent from the product.** | Typed B1 `FeatureEffect` expansion supports optional dependency activation, strong/weak target features, subskills and config effects. Strong forwarding activates a dependency; weak forwarding records the request but only applies if another cause activates that dependency. | `backend?/trace` alone must not install backend. Adding `dep:backend` later activates trace regardless of merge order. Tests `weak_only_stays_dormant_and_strong_alone_activates`, `weak_forwarding_is_order_independent_and_survives_merge`, `required_and_already_active_dependencies_enable_weak_requests`. |
| Integrated effect coverage | Main's legacy expansion and app requirement planner are different existing owners; a shared form should not pretend their effect lifecycles are identical. | B1 pure algebra supports forwarding, **but C2's configured solver explicitly rejects cross-package `TargetFeature`**; native candidates, multiple package instances and non-registry dependency sources are also refused there. | A B1 unit test proving `backend/fast` does not prove a choice-bearing package can forward `fast` through the complete configured install route. `compatible_older_candidate_keeps_only_selected_effects` includes the explicit Unsupported assertion. Complete common options must close or explicitly account for these integration gaps; copying the prototype preserves them. |
| Config effects versus parameters | Typed app parameters support string/bool/integer/choice/path, required/default/bounds/allowed-values/path-existence, secret redaction. They feed templates/step conditions. | B1 config effects are declared typed bool/integer/string values attached to feature expansion; conflicting values refuse atomically. These are not an arbitrary user parameter form or a secret-value persistence policy. | Two selected features assign `mode` incompatible values: effect merge conflict. User enters `port=9090`: parameter validation. Encoding every parameter value as a feature would lose typed bounds, paths, secrets and value-origin semantics. Test `config_conflict_merge_refuses_atomically`; main `params::resolve_parameters`. |
| Profiles | A named profile supplies a base feature set; explicit flags overlay it, then normal closure. Attended profile default affects display order; unattended does not simply pick the first profile. | No equivalent profile-selection primitive in B2's request; it consumes explicit group/feature intent and policy. | “Minimal profile + enable GUI” closes to main's required roots and default toolkit. The profile must not become a new independent dependency/guard authority or erase explicit group intent. |
| Persistence/update | `Installation` records resolved features and non-secret parameters. Update reuses recorded choices; modify merges partial flags over recorded state, while profile replaces it. Profile ID is in plan/run, not installed record. | Requested configuration is retained separately from resolved choices and definition/default receipts. Removed options/new required groups yield reconfiguration; explicit choice is retained when a default changes. | Main may filter an undeclared old feature; next must diagnose removed original choice, including dormant ones. `update_keeps_explicit_choice_when_default_changes`, `removed_option_and_new_required_group_return_all_needs_without_writes`. Existing app state must not retroactively be claimed to carry exact/additive/default-consent provenance it never stored. |

## Discriminating examples with real source anchors

1. **Default closure is not the four-cardinality evaluator.** Main `crates/vibe-app/src/steps/features/tests.rs::the_rule_table` proves default `core+gui+gtk`, explicit `qt` replaces gtk and implies extras, and deselecting gui leaves core. `refusals_name_their_reason` proves disabling default gtk without a replacement conflicts. Core `manifest/package/application/wizard_validation.rs` requires one default per exclusive group. Prototype `crates/vibe-resolver/src/features/configuration/m_05_b_2_cases.rs::explicit_defaults_and_empty_policy` proves an explicit empty mandatory answer does not reuse the default.

2. **Do not flatten original intent into the installed feature set.** `{additions: omitted}`, `{additions: exact []}`, `{additions: additive []}` can presently produce the same effect set but impose different default/consumer-merge behavior later. `resolve_consumer_configuration` filters guarded members only for active constraints and retains the original edge values. Its `dormant_member_exact_intent_and_group_guards` test and `features/m_05_d_2_cases.rs::removed_dormant_option_reports_drift` cover retained inactive meaning. Main `Tree::remove_with_descendants` deliberately erases the effective children; its Installation has no original-edge layer.

3. **Local command override is not consumer merge.** Main `resolve_features` uses prompt → profile → previous only when request empty → defaults; the rule-table case explicitly says named flags replace previous with defaults. Main `operations/modify.rs::keep_recorded` deliberately overlays partial modify flags on the record instead. Both current behaviors must survive compatibility. Neither is the prototype's additive union/exact-bound merge across consumers.

4. **Selection conditions and execution conditions have different inputs.** Prototype `Constraints::order` checks unknown/private/multiply-owned members, dormant definitions, positive guard references and cycles before evaluating choices. Main `steps/plan.rs::holds` reads bounded host/parameter/feature predicates to select installer steps. Treating host-dependent `file_present` as an ordinary package guard would make the dependency/configuration result depend on local ambient state; treating all conditions as positive choice guards would remove supported app conditions.

5. **Candidate receipt and current defaults matter after a version change.** Prototype C2 `changed_semantic_default_requires_rediscovery` and E2 `update_keeps_explicit_choice_when_default_changes` distinguish an explicit selected option from permission to follow a particular previously shown default. Main's stored resolved set cannot reconstruct that distinction. A compatibility read of an old app record must state only what is known.

6. **Effects must retain incumbent domain semantics.** Prototype B1 `optional_activation_and_strong_forwarding_share_effect_set` exercises a dependency, target feature, subskill and typed config value in the same expansion. `config_conflict_merge_refuses_atomically` prevents partial merging of incompatible config. But the configured solver's refusal remains a real missing end-to-end seam. Main app installer step execution, package resolver edges and subskill activation cannot all be substituted with a generic shell action merely because they share the choice UI.

7. **Parameters already solve a different real problem.** Main `steps/params.rs::resolve_parameters` precedence is explicit `--set` → recorded → prompt/default; `ParameterDecl::canonical` validates both flags and prompt results. Secrets are withheld from plan/index values, not magically erased from arbitrary child output. Reuse this typed parameter behavior rather than downgrading the common system to booleans or manufacturing a promise that no child can persist a secret.

## Boundaries for root's shared-system decision

The shared definition/evaluator must express cardinality, positive choice guards, original answer state/policy, consumer/instance identity, typed parameters and deterministic effect results without losing main's feature tree/required/profile semantics. Existing main app declarations need their demonstrated default/override/modify behavior preserved. A new richer declaration must not inherit implicit defaults simply because it uses main's UI.

The existing local app callbacks/describe/plan/JSON/interactive controls are a working consumer of shared choice results. The application installer, workspace resolver/install/reconfiguration owner and their persistence adapters still own their respective effects and replay rules. The comparison does not require an external socket, grant daemon or manual capture-token step; those were limitations of the prototype's E4 embedding path, not option semantics.

All nine package kinds can use a common option contract without claiming every effect is meaningful or already wired for every kind. The specific incomplete edges identified above—especially configured dependency forwarding, native/multiple-instance resolution, interactive answer writeback, scoped/exact maintenance, and normal interactive choice bootstrap—must remain explicit implementation obligations. No source-only test has been promoted to runtime verification or old task acceptance here.
