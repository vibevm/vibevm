## R1 — Consumer identity solved one ambiguity but embeds another: request ranges are part of instance equality

`4271112df9f39937e9774fd9d1ca257492ec6ca6` creates the constrained consumer evaluator and its codec: `crates/vibe-core/src/manifest/package/features/constraints.rs`, `crates/vibe-resolver/src/features/configuration.rs`, and `crates/vibe-wire/src/behaviour/consumer_configuration.rs`.

Observed historical behavior is substantive: dormant definitions are validated without selecting their alternatives; positive group/member guard cycles refuse while ordinary feature cycles retain their own meaning; explicit empty differs from omitted; default policy only acts on omitted input; additive/exact conflicts retain both edge indices; unresolved/conflict returns `expansions=None`. The evaluator composes the existing feature-effect algebra and explicitly rejects closure that activates an unchosen constrained member. The three new test files exercise actual evaluator/codec calls, not just enum values. For example, `shared_additive_union_and_actual_evaluator` checks the resulting bool config effect; `dormant_member_exact_intent_and_group_guards` changes the guard from dormant to active and then expects exact conflict. These are source-level test definitions, not newly observed passes.

The same commit makes `ConfigurationInstance` contain `PackageIdentity::Vibe(PackageRef)` and defines its equality across domain, instance identity, configuration and that complete package reference. The wire admission rejects equal domain+instance labels when the full instances differ. The pure `separate_environment_domains_keep_different_choices` test permits separate supplied domains, but it does not instantiate separate stores or installations.

**New concrete transfer hazard, source-derived:** in the final source, `crates/vibe-install/src/authored_configuration.rs::authored_configuration` copies each consumer's actual `requires` PackageRef—including its requested version range—into `edge.package.reference`, then calls that admission function. `crates/vibe-core/src/package_ref.rs:378–391` derives equality including `version`. Consequently, two authored consumers naming the same domain/instance/configuration and same package, with compatible different requests `^1` and `=1.0.0`, are rejected as `instance identity disagrees on configuration/package` **before** candidate intersection. This follows directly from the compared values and caller; it was not executed as a new RED test. The final configured solver also rejects distinct full instances of one package. G1's authored multi-consumer fixture uses `^1` for both edges; its distinct-range fixture exercises legacy roots, not this configuration path.

This is a specific consequence of conflating stable shared-instance identity with incoming request constraints. Keep the domain/consumer distinction where it corresponds to a real installed instance, but do not import these wrappers unchanged into main's shared workspace package owner. Main already has `RootRequirements::collect/held` with real member origins and independent constraints; `ConfigurationDecl::normalize_input` accepts a diagnostic consumer key without inventing another installation. The main ChoiceModel can merge answers; candidate/instance binding must preserve the separate version requirements as inputs.

## R3 — Candidate freezing fixes changing metadata but chooses an eager, broad capture boundary

`f5a9dc9873e22989db4a54dde0e372dff85dcc64` adds source-bound `CandidateIdentity {source,content,definition}`, `TransactionCatalog` and `MetadataSnapshot`, plus the install/package-source forwarding path. Selected bodies were fully read; lower-level multi-registry walk and several backend implementations are excluded in JSON.

`TransactionCatalog::capture` enumerates **all versions** of every queued coordinate and recursively queues requires, recommends, technical OR alternatives and conditional dependency declarations from every candidate. Each candidate metadata result is required; an operational metadata error aborts capture even if that version may later be rejected. This is an actual broad-read design choice, not inferred from a struct name. The C1 test `solve_and_manifest_observation_share_catalog_identity` hard-pins app1 but expects metadata reads of both app1 and app2, once each; the corrupt fixture remains Provider failure. `MetadataSnapshot` makes capability prescan, SAT reads and recommendation trials reuse observed manifests, and recommendation code stops swallowing Provider failures.

The identity has real producers: local capture hashes the shippable tree before/after and rereads manifest bytes; Git lookup resolves a commit, reads by that commit, and clone fallback verifies the same commit before/after the file read. Git acquisition uses the captured commit rather than a fresh tag and verifies checkout before store insertion. Metadata clone/cache I/O is explicitly allowed; **catalog capture is not a universal zero-write operation**. In install planning, case-c authored-manifest seeding moves after successful planning so a failed catalog cannot leave that prior early product write. Each selected candidate is validated before acquisition, and fetch validates again against its bound source/content.

The final catalog.rs is byte-identical. Final candidate_metadata.rs additionally records a checked constrained definition and uses a separate digest domain for that grammar. `InstallResolver::bind_request` captures roots once, admits source definitions and owns the frozen request/resolution; plain `solve`, `manifest_of` and `solve_masked` each create a new transaction when called directly. Within the planner, the carried frozen source is what supplies coherence; the raw InstallResolver is not a permanent globally frozen cache.

**Causal tradeoff:** eliminating same-version metadata drift introduced an eager catalog whose failure/read scope includes unselected versions, recommendations and conditional branches. This is consistent with its strict corruption contract, but its latency/availability cost is not measured here and should not be accepted accidentally with the identity concept. Main's existing metadata seam returns Manifest, while fetched packages already have content/source facts; retain the actual observation at the metadata owner and validate it against acquired bytes. This report does not select eager versus demand capture or propose a universal replacement store.

## R4 — Candidate-conditioned dependencies are real; forwarding and multiple physical instances are not

`19ed29697dd84a66dc0af2634459879e1c450f6d` adds `resolvo_engine/configuration.rs`. Its algorithm first validates source definitions, evaluates all supplied consumers per candidate, rebuilds that candidate's dependencies, then lets the existing solver reject candidates. It does not accumulate effects in a mutable global feature union. Only the selected graph is traversed to return expansions, providers and eventual NeedsSelection/Rediscovery.

A default receipt binds **edge + full request + source/content/definition receipt + full normalized shown definition**. If any default-governed omitted request lacks the exact binding, evaluation replaces UseDeclaredDefaults with RequireSelection before even generating internal solver implications. A removed previously shown default still causes rediscovery. Thus stale consent cannot influence dependency search and later be excused as “no defaults used.” This is useful strictness, though binding every receipt to the entire request is conservative and may invalidate it on unrelated request edits; no UX/performance measurement was made.

For unresolved groups, the algorithm computes a **private known expansion** from already authorized ordinary features/selected eligible members. This allows ordinary dependencies to reject an otherwise prompt-requiring candidate before prompting. It never returns that partial expansion as successful configuration: selected unresolved rows cause an error at the end. The `unresolved_group_keeps_known_ordinary_implications` and `unreachable_mandatory_group_has_no_prompt` tests distinguish this from globally prompting on every discovered version.

`compatible_older_candidate_keeps_only_selected_effects` has explicit expected graph, full effects, provider list and request equality; a newer candidate's bad dependency/subskill/config value do not survive the expected older result. Other tests preserve the second consumer when it alone rejects the newest candidate, and compare changed/removed shown defaults.

This capability is narrower than B1's algebra. Both initial and final configured methods reject **any TargetFeature** (strong or weak), non-registry dependency declarations, native candidate selection and multiple full configuration instances for one package. Initial code also rejects technical OR; `5698d64d` later admits OR with selected witnesses. Conditional targets and obsoletes remain refused across the captured catalog. This is not a new complete forwarding solver.

Final source now independently derives package-owned definitions through `CandidateConfiguration::from_metadata`; `admit_source_definitions` and the solve path reject a supplied definition that differs from checked bytes. Initial C2 tests supplied normalized definitions manually, so their success alone did not establish ordinary authored-package delivery. Final missing-consumer definitions remain candidate-local NeedsSelection, surfaced only if selected, rather than inventing instance intent from the inventory.

**Main and transfer:** main ChoiceModel's `evaluate/finish` already retains original consumers and requires a fully resolved result, then checks both unchosen activation and lost chosen members through the shared FeatureModel. Add candidate-specific dependencies at main's existing resolver owner; preserve application `Manifest::resolution_requires()` in that provider. Cross-package forwarding is still required design/integration work; do not copy the old explicit Unsupported branch and call it completed common configuration. No new solver framework is recommended here.

## R5 — Visibility retries exposed lost intent, missing selected-edge evidence and an overstated fixpoint claim

`5698d64d9f822d0a19c368f0b67edf3cb836bc5e` is a broad repair, reviewed at named route/request/fetch/projection paths and selected test spans. Its lower-level naive/SAT and full witness-extraction diffs are **not** fully covered by this batch.

The concrete old failures visible in the diff are:

1. Workspace roots were coordinate-deduplicated; later member constraints could disappear. New `effective_root_constraints` retains origins and supersedes only the selected node's named declaration. Main already has the accepted equivalent boundary in `plan/roots.rs`; preserve that owner rather than reintroducing the prototype implementation.
2. Metadata and retry calls could reconstruct an unconfigured Manifest. New `NormalizedRequest` retains original roots/features/configuration, `all_roots` appends route constraints without deduplication, and `FrozenSource::manifest_of` reads the selected resolution's projected manifest. The planner carries that same frozen source across metadata, solve and masked routes.
3. Possible provider/OR declarations were insufficient to describe the actual selected graph. `RouteResolution::bind` checks every graph edge has a declaration/provider witness and maps configured dependency indices back to IDs. `visibility_projection::project_selected` builds effective edges from those witnesses, with authored access metadata, instead of unioning possible providers. A mask cannot silently create a new unsupported edge.
4. The old conditional loop skipped constraints whose target package name was already present, appended pinned roots and coordinate-deduplicated the union. New `ConditionalEdge` retains parent/declaration/dependency and passes every active constraint into the same request route. Invalid predicates no longer warn-and-skip. If the declaring candidate changes or the five-iteration bound does not stabilize, the route explicitly refuses.
5. `fetch_node`/in-place reuse now consume the selected `route_resolution.effects[coordinate@version]` instead of reevaluating defaults. `finish_route_projection` rejects added/inconsistent nodes/edges, removes absent-node effects/manifests and trims provenance. Successful retries replace the route result; errors clear it. Original request and commitments remain independently carried.

The spec delta matters: old `CONDITIONAL-FIXPOINT` was `impl/done` and said convergence was guaranteed with incremental libsolv; it becomes bounded semantics with changed-candidate/unstable combinations explicitly unsupported. This is a demonstrable narrowing of an overclaim, not merely more ceremony. Configured+conditional remains incomplete. Retaining incumbent OR/capability commitments prevents visibility retry from inventing different choices; it is not arbitrary full re-optimization after a mask.

Selected tests call actual standard source/planner routes and compare immutable request/provenance across a private-edge removal. The fake-source test additionally checks pointer identity of normalized intent. The conditional test adds an incompatible constraint to an already selected package and expects refusal with the original roots still present. These assertions are useful, but no fresh results are claimed.

**Current transfer limit:** main's feature/choice/intent primitives and RootRequirements are accepted, while `reject_configuration_inputs` and fetch's `ConfigurationUnsupported` explicitly prevent claiming configured package effects. The pinned main provider already calls `resolution_requires()` for ordinary package plus app installer dependencies. Extend that route while retaining original per-consumer version/choice input and selected candidate effects. Reuse of prototype evidence must include declaration support on masked forwarding, not only an equal final package set.

## R7 — Recovery tests found a real callback-report bug, but their guarantees are deliberately partial

`62a9fafd2fe4006f5872ecb16aeb9ca58d960c2f` adds three integration targets plus a shared fixture, and changes production apply/lifecycle behavior.

**Concrete repair:** post-install failure can be recorded in lifecycle callback reports rather than the legacy HookReport vector. Before this commit, apply tested only the latter before completing its configuration recovery journal. New `InstallSlotLifecycle::has_failed_post_install` reads flagged `slot:post-install` failures without draining reports; apply ORs that with the legacy status and enters `post-install-failed` instead of `recovery.complete()`. Final `apply.rs:635–674` retains that code. A nonfatal CLI exit may still be successful, while typed hook failure and an in-flight partial-effects journal remain. This is useful separation of user-facing soft-failure compatibility from recovery truth, not a cosmetic test commit.

The test definitions drive real `vibe_install::plan/apply`, orchestrator `execute_prepared` with the standard package-source factory, and an actual isolated `vibe` child for CLI cases. Redbook branch selection coexists with independent WAL/MUP roots; dormant selections survive MUP→WAL→MUP and exact requested/selected records are compared. Missing choice refuses even with assume-yes. Configured uninstall without a newly admitted request remains explicitly unsupported; the successful shared-root uninstall test clears configuration first. Thus “activation recovery matrix” is not complete configured maintenance delivery.

The new before-phase fault hook fires **after durable intent publication but before the writer**; the existing after-checkpoint hook remains distinct. Tests reopen the exact operation/target set and assert in-flight flags, retained before/checkpoint images, unchanged third-state bytes and external-effect uncertainty. They accept either local-byte restoration or explicit boot-compensation refusal; `complete_rollback` remains false and the journal is retained. Hooks write marker files, which must remain even if local prefix restoration succeeds. These are controlled in-process fault/observer injections, not arbitrary OS crashes or platform durability proof. CLI child tests explicitly avoid thread-local fault injection.

The exact-offline replay test uses ReplayOnly to panic on solve/metadata/fetch/materialize and then calls `PreparedReinstall::from_planned`, `validate`, `validate_slots`, and compares the returned resolution. This establishes a test for preparation/validation without those effects, **not a second executed apply of the replay**. Corruption variants check lock, payload, definition, source and an owned slot file; fixture cleanup is explicitly not product recovery.

**Transfer:** preserve the callback-report fix and discriminating partial-effects/third-state assertions wherever main's existing install owner needs them. Do not import a complete generic recovery store just because this test suite uses one, or claim complete rollback from local restoration. Root still chooses the recovery boundary for the selected real package journey.
