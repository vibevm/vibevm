## What users are supposed to gain

A local derivative is an independently owned modification or replacement of an exact upstream resource. It may be ordinary CommonMark, XML-data, Vibe-spec, an opaque binary/file or a nested tree containing code as inert data. Users must retain their own local source, inspect exact base/local/result changes, recreate disposable output, and explicitly rebase when upstream changes. A sealed upstream source or absence of prior demand evidence must not become a permission gate for creating that separately owned local result.

Whether a result fits an export target is a separate question. Whether it may execute or deploy is a third question requiring its own authority. A compatible result does not inherit base grants; a locally useful fork may exist even when one target rejects its interface. Those are concrete source/ownership semantics, not a request for another compiler, resolver, package manager or priority language.

## Incumbent mechanisms and their actual limits

**F17/F19 are real accepted compiler work.** Commit `2a9da5c8b2e9ba6b73d2192df1f6b6a541a7f373` preserves normal source once-coverage, distinct equal prose, uncovered regions and link meaning; F19 adds typed recursion-minted embed occurrences bound to the expanded body, checked emitted provenance and XML framing. `EmissionProvenance` retains artifact context, source lane digest, producer/backend, contribution witnesses, applied emitted transforms and output digest. Equal output bytes need not erase compiler context.

That is not a generic authored derivative chain. `EmbedOccurrence.source` names the effective pre-Embed input view, and directive_line is explicitly not an authored-file edit coordinate. Internal SourceResolutionSnapshot/EmbedResolutionSnapshot contain compiler observations, not a public resource-tree capture/binding service. Emitted transforms may rewrite opaque bytes under their separate contract; F19 explicitly does not promise universal semantic preservation or authenticated ownership history. Do not use compiler ranges for arbitrary source edits or call compiler artifact creation a completed local fork/rebase operation.

**Slot records are materialization accounting.** SlotRecord records source_hash, converter recipe, target spec format, derived_hash, overlay_hash and materializer-owned files with source mapping/copy-versus-convert disposition. Its verifier checks the fetched/locked source hash, current recipe/overlay and actual recorded payload hashes. This is valuable consistency/provenance evidence and a reusable owner for publication footprints. It is not an independent retained local authored source or a base→local→result binding with local owner/resource/recipe IDs. The inventory is the materializer-owned footprint; intentionally unrecorded build artifacts are outside it, so it is not automatically complete membership for an arbitrary derivative tree.

The word **overlay** is especially easy to overread: `PackageOverlay` stores consumer fact adoption statuses. `apply_overlay` replaces stage/state on recognized fact units. It is not arbitrary local text replacement, an editor overlay, a tree patch, or a derivative permission/ownership record. `derived_hash` proves no independent upstream authenticity merely by existing beside editable source_hash.

**Committed conversion is not five-family source interpretation.** At this accepted pin, transformed slot selection uses md/xml suffix plus specs-root/root-README placement, then the Vibe parser/pivot. Failed parses copy raw bytes; non-spec files and Mixed copy through. This preserves many opaque inputs, but it does not explicitly distinguish ordinary Markdown/XML-data from Vibe-spec when both can parse. Dirty A1 may address part of that boundary later and is not credited here. Generic byte replacement must preserve declared XML-data/opaque content; a successful Vibe parse is not permission to reinterpret it.

**Existing skill composition is useful but effectful preparation.** DeclaredSkill separates provider/source roots and can combine a local adapter with selected embedded resources into a cached tree. It rejects path collisions and checks the selected file set. Its composed key includes provider, skill name, paths and bytes. Authored local/embedded declarations survive cache deletion. However `prepare_declared_skill_projection` calls `hydrate_declared_skill`, which calls embedded source cache acquisition and can publish a composed cache under ambient settings. Offline does not mean no filesystem effects. The higher prepare function cannot be reused as a zero-network/install/cache passive derive/show API without separating already admitted input handling from hydration/publication. Reuse the file-selection/composition logic, not that misleading effect boundary.

**Ordinary source conversion is not rebase.** `refactor/convert_source` discovers candidates, refuses paired targets and installed slots, converts between representations, writes a sibling and removes the original with a local rollback attempt on remove failure. It does not retain old base/new base/local lineage, publish a new derivative binding or coordinate dirty editor epochs. M13 saved migration provides a stronger exact approved one-existing-file transaction and recovery, but its authority/grammar are still not M10's binding-plus-result or M16 participating editor operation. These are reuse candidates, not substitutes for C2.

**Existing deployment is not derivative activation.** The artifact owner rehashes recorded output before deployment and refuses stale/missing bytes; skill projection reconciles its owned files/receipts. This provides meaningful downstream machinery. No accepted derivative-specific descriptor, new grant, base/local drift admission or revocation cleanup joins those owners to an independently owned result. Matching output bytes cannot carry upstream trust into a new result by implication.

## Inspection credit and boundaries

The committed `decompile_static` reader takes supplied text and parses contributions/embeds without provider calls. F19's occurrence path distinguishes repeated inclusion from payload identity and checked source meaning; F17 avoids deduplicating unrelated equal text. This directly supports part of D1's occurrence-attribution requirement and explains the proposed partial status.

There is still no shared derivative resource identity navigable from source query and debugger; no base/local/result chain, same-snapshot derivative paging or all-family CLI/API/MCP parity. `compile_static_analyzed` calls the incumbent compiler with a supplied TransformPlan; it is not equivalent to merely opening committed output. Passive inspection should consume retained observations, or explicitly admit the pure builtin computation it requires, rather than silently invoking generic preparation. A stale typed tape check or compiler recipe rebuild is not a generic source-proven derivative freshness result.

B1 binding and C1 inert derive/show/diff follow coherently. A full replacement of an opaque file/tree need not wait for a structural parser to understand code: it remains data. Vibe-spec-specific projection uses the existing compiler; declared source interpretation and membership interfaces remain real prerequisites. Passive compatibility and D1 inspection can proceed without active deployment. C2 authored rebase/apply belongs in the upper shared editing/recovery adapter, with no workspace→orchestrator reverse dependency. B2's active admission half and D2 require actual new grants/target/artifact ownership; the original eight-task scope remains intact.

The original C2 contract records an earlier empty-patch attempt caused by a read-only writer perimeter and then supplies a corrected M16 adapter perimeter. That historical note is not evidence that the final pinned prototype C2 failed or succeeded; this audit does not rewrite prototype inventory from it. It does show why copying only a pure comparison function cannot count as C2's required guarded application/recovery.
