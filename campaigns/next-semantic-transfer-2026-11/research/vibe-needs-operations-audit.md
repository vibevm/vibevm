## Need 4 — durable per-agent enabled choice: missing consumer contract, substantial foundations

Observed: `cli/mcp.rs` exposes serve/install/status/upgrade/uninstall, no enable/disable. MCP package ownership receipt (`commands/mcp/package_registration.rs::OwnedEntry`) retains package, version, payload, pending_previous, not requested enabled state or actor. `register.rs::register_one` checks foreign edits and stores pending prior payload before config publication; reinstall recreates an absent owned entry. Client payload builders include `enabled: true` for supported formats. Simply editing generated config is drift and may refuse refresh; removing it is not durable disable.

Already reusable: per-package/server/agent/scope selection, ownership receipts and conservative foreign-edit rejection; global selected-agent uninstall preserves package while another registration remains. Package skills have a shared projection/binding owner and receipt reconciliation. Deploy has durable intent before external writes, inverse/ownership boundaries and staging recovery. ConfigurationIntentDecl already represents original requested profile/features/choice selections separately from normalized/effective state. This is package feature intent, NOT evidence of per-agent MCP/skill toggles.

First coherent fix: model desired activation and observed projection separately inside existing projection/receipt owners, with stable package+entry+agent+scope identity and explicit provenance. Implement one project-scoped MCP entry end-to-end, including repeat disable, reinstall/update preserving disabled, re-enable, JSON state and drift-safe recovery. Use native disabled representation only for a verified client capability; otherwise retract ONLY receipt-owned projection while retaining installed package and durable desired-off intent. Extend shared skills projection next; do not create another registry or confuse package feature selection with agent activation. Cross-agent/user/both breadth needs explicit scope precedence and separate commissioning.

Architecture dependencies: M-08-C.2 generic file/config operations -> M-08-C.3 receipt-preserving upgrades/inverses. M-05-D.1 requested/effective intent provides the separation pattern, not a substitute toggle implementation. M-08-A.2 exact client contracts qualifies native disabled forms. Their whole historical milestone groups are not prerequisites.

## Need 5 — cancel project operations with rollback: partial foundations, universal guarantee absent

Observed: app interrupt owner documents/signals Ctrl-C/SIGTERM/Windows controls, preserves interrupted work and resumable steps (PROP-065 cancellation/resume). These apply to application step operations, not every project command. `vibe-actions::CancellationToken` performs pre-body checks; this is not download cancellation or transaction rollback. Hosted cancellation tests reconcile removed declarations/parked rows; they are NOT user interrupt tests.

Current install apply already uses lifecycle lease, prepared publication and guarded rollback. An interrupted/parked slot reports a clean handoff only if rollback succeeded; rollback conflicts remain failures with retained tasks/run state. FileGuard refuses overwriting a third-party replacement during inverse. Deploy intent/checkpoints and app retained steps are existing recovery owners. Progress task drop emits Stopped, not a domain-level cancelled guarantee.

Missing: one supported cooperative cancellation request from project CLI/API through resolver/fetch/child processes, stopping boundaries and retained operation outcome, with explicit project mutation/effect state. No observed current-main proof that SIGINT during project install/update/apply/publish restores all manifest/lock/agent files. A process kill bypasses ordinary Rust guards; cannot market it as rollback.

First coherent fix: one ordinary project install download path, before project publication, with cooperative token, HTTP cancellation and supervised Git-child stop, owned staged-download cleanup/cache retention, explicit cancelled-before-publication outcome and matching progress terminal. Then cancellation checkpoints around prepared install/agent publication under existing lease/FileGuard, with rollback-conflict/recovery-required rather than fictitious success. Update/apply must share those owners after their own authored-manifest mutation boundaries are established.

Safe boundary: before publication, cancellation can stop safely with unchanged project and permitted cache writes. During a local owned transaction, finish guarded rollback or report retained partial/recovery-required effects. After local commit, cancellation is too late for that committed atom. External publish (remote repo/tag/release/upload or arbitrary lifecycle command) cannot promise old-world restoration: stop future effects, retain exact completed/unknown remote effects and reconcile; never silently delete externally completed effects. Download resume may reuse verified completed cache; journal resume links do not prove partial-byte reuse.

Architecture dependencies: M-16-C.2.1 retained lifecycle outcomes and M-16-C.3 cooperative controls (requested != stopped); M-16-C.1 scoped reservation is relevant for multi-client submission, not a reason to add another orchestrator. M-16-C.2.4 and M-07 publication fencing/recovery apply only to remote publish. M-17-C.2 is later long-job/replay/cancellation validation. Architecture map itself marks universal domain coverage unproven.

## Need 7 — cumulative disk-write events: partially present facts, live disk metric missing

Observed: existing transfer identity/batch, cumulative bytes, timestamps, sample cadence, journal/watch and progress events already support UI rate calculation. HTTP TransferReader settles prior read bytes on next read/finish; source says after writing, but reader itself cannot prove successful filesystem writes (can wrap another Read consumer). Git transfer bytes are explicitly reported network/process progress, not disk writes. `Transfer::written`/journal `written` is optional final size left on disk; Git uses final `.git/objects` size. That is neither a cumulative write counter nor a live rate and may include pre-existing objects. Transfer event schema has bytes/rate/peak, no independent live cumulative disk-written field.

First coherent fix: add an optional precisely defined logical successful-write byte counter to existing transfer samples/event/journal contracts, recorded at owned writer boundary after each successful write. State explicitly whether scope is transfer or operation; retain id/batch. No fabricated zeros for uninstrumented Git/external commands, no physical disk-I/O claim, no alias of received bytes, no double-counted parent/child aggregation. Start HTTP archive/cache writer instrumentation and schema/serialization parity; expand extraction/copy only if operation scope is requested. Reuse current sampler/watch rather than a second progress service.

Architecture: existing PROP-068 transfer owner is immediate dependency; M-16-B.1 strict generated events and M-16-C.3 transport are interface consumers, not prerequisites for the in-process metric. Full replay/operation journals are unnecessary for a first honest counter.
