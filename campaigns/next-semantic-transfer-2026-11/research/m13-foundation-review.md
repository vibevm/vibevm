## Actual architecture and dependencies

Pinned `manifest/migration.rs` owns selection, named profiles/edges, finite grammar checks, replay, final current-reader validation and framed SHA256 identities. It depends for its neutral part only on `Manifest`, `toml_edit::{Document,Item,TableLike,Value}` and sha2. Main already has both dependencies, and `Manifest::parse_str` validates in-memory bytes. No workspace, filesystem, SafeFS grant, lock, solver, native provider or GUI service is needed for this pure operation.

The final source file is mixed: selection carries `source_decisions: &[SourceDescriptor]`, result carries `checked_features: Option<CheckedFeatureManifest>`, and dispatcher knows source, features and Redbook. Those are concrete later recipe dependencies, not intrinsic requirements of exact token replay. Do not import unknown types as placeholders or add a second feature grammar merely to compile the final file.

Existing main `manifest/decor.rs` copies comments/whitespace into a freshly serialized document. It deliberately allows inline tables to become header tables, and matches some arrays by index. That is useful ordinary write behavior, but does not satisfy M13's stronger byte-identical untouched spans. Reuse its toml_edit dependency, not that rewrite algorithm as a purported exact migration engine.

Pinned `replay_edits` is already reused through crate-private `replay_authored_tokens` by `manifest/change/migration.rs`: validate change epoch, propose exact schema-token replacement, replay, validate output. That is the genuine dependency needed by M02B1's migration subpart. It needs neither full migration apply/recovery nor M16 editor barriers. Main has no equivalent exported planner/replay owner in inspected module inventory; whole-crates symbol search also found no named plan/diff/profile implementation. This is bounded structural evidence, not proof no unrelated edit helpers exist.

Public prototype plan consumers include workspace migration planning (C2 projection), core source/feature recipe tests, orchestrator Redbook proposal/apply facade and install Redbook fixtures. Workspace `core_outcome` is a strict adapter from source text/profile/decisions to the core call. The orchestrator proposes via core and validates exact proposal replay before handing saved apply to a different owner. These are downstream consumers, not prerequisites of C1.

## What is sound, what needs care

1. **Useful design:** explicit finite grammars, syntax-span edits, output checked by incumbent reader, no guessed epoch or intent, deterministic before/after/diff identity. This is substantially implemented library behavior, not empty abstraction.
2. **Finite scope is explicit:** neutral profiles admit only package+optional requires, six historical package kinds and limited dependency shapes. Unknown root tables/keys are refused, not dropped. A current manifest outside that finite grammar is not a current-profile no-op. Broad current-format support is not established by this recipe.
3. **Historical evidence overstatement:** canonical pinned MIGRATION-PLAN-LAW says rename is rehearsed on retained historical fixture bytes. Actual test `retained_historical_scalar_is_not_relabelled_as_package_manifest` retains `v = "snapshot"` but deliberately REFUSES it as not a package. All successful package fixtures are explicitly synthetic. Preserve the honest test explanation; canonical main text must not claim a positively migrated real historical corpus. Broad real-file rehearsal remains unperformed.
4. **No multihop framework:** registry is an explicit list of allowed edges. Do not describe it as a general automatic chain solver. The original requirement is satisfied for its bounded actual transform chain, with exact compatibility selection.
5. **Replay validation matters:** rejects overlapping/out-of-order spans, reversed ranges, non-UTF8 boundaries, wrong before-token, empty insertions and repeated insertion point. Source tests cover ordered end insertions, duplicate insertion and split UTF8; broader adversarial replay tests should bind these actual invariants before exporting reusable replay. It does not validate the destination grammar by itself; each owning recipe must do so.
6. **Diagnostic coupling:** `unprovable()` hardcodes field `package.materialization` even when replay is reused by source/features/Redbook. Do not carry that misleading ownership into a neutral exported replay helper. Choose actual edit field or a neutral replay location, retaining typed reason and sensitive-value discipline.
7. **Hash duplication:** neutral plan assembles diff hash inline while a second identical `diff_identity` helper serves Redbook. Use one owner for exact framing in the integrated core; retain independent golden vector. No new digest protocol needed.
8. **Pure plans are proposals:** public data structs can be constructed/modified; they are not authenticated authority or write grants. Downstream saved apply must revalidate as prototype already does. Do not make publication trust a struct merely because its type is named Plan.
9. **Future target-reader boundary:** pinned `read_migration_target` for nonfeature profiles checks recognized profile metadata then current Manifest parse, unlike planning's frozen target `check_shape`. That function's apply/recovery role is later scope; do not imply it alone enforces finite target profile syntax.

## Main feature compatibility — do not duplicate the prototype reader

Main already has substantial common feature semantics: `ConfigurationDecl`, typed effects Dependency/Forward/Subskill/ConfigValue, declared groups Choice/Closure, profiles, parameters, visibility, and `compile_choices` lowering to existing FeatureModel/ChoiceModel. Main package evaluator exists and currently explicitly refuses automatic/default/profile input, parameters and some owner requirement shapes. Lack of complete runtime does not mean there is no reader.

The prototype feature migration instead rewrites string entries under `[features]` into inline typed effect records, wraps exclusive arrays with cardinality, and validates using separate `feature_profile::read_typed`. Main's `FeaturesTable` still reads legacy string lists while the accepted target grammar is `[configuration]`. Copying that converter/reader would introduce competing authored formats and bypass the chosen general installer/package model. M05B3 must map meaningful legacy local/dependency/exclusive/default intent into the accepted common owner, with typed questions for unresolved references and unavailable catalogues. Exact mapping of defaults, underscore/internal names, closure versus choice groups and consumer request placement needs a reader-bound decision; this report does not decide it implicitly.

The source recipe inserts one `[[package.sources]]` row for a normal flow's known boot path and demands an explicit media decision; main has no SourceDescriptor reader in inspected manifest inventory. It belongs with M06A1. The Redbook recipe embeds a fixed historical1.1.0 roster and old `consumer_configuration` identity fields, then appends selected continuity choices; main uses requires-owned configuration intent. It belongs with actual accepted Redbook meaning and M05F2, not a version-literal copy in C1.
