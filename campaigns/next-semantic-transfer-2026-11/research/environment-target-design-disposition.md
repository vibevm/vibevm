# Environment targets: architectural disposition for NST-2

Read B-233 and the owner wording retained in `environment-targets-metadistribution-question.md`. The desired outcome is that a person can select packages, understand the resulting system and operate it through CLI, graphical or agent clients. A container image is not another kind of package manager. An operating system built this way is a direction, not a delivered runtime.

**Reuse.** Keep package identity, source selection, installer choices and the operation plan at their existing owners. `vibe-app/src/operations/install.rs` selects one option and reads prior configuration; `operations/planning.rs` produces its plan, and `operations/mod.rs::OperationContext` supplies caller interactions and execution services. `settings.rs`, `storage/`, `steps/` and `proxies/` own settings, payload placement, steps and command exposure. A different frontend consumes the same plan, decisions, status and receipts; it does not compile an independent Dockerfile from display text.

**Adapt.** For a non-host target, bind the selected root and mounts separately from the host's settings, observed source and cache. Preserve the distinction between target-visible paths and host paths. Planning must label which effects address the target, which need an executor and which are impossible. Do not publish a target launcher into the operator's PATH. M14's target identity, injected layout and physical ownership checks address this gap; a different `HOME` or library directory alone does not.

**New only where necessary.** M15 A–D concern target-compatible payloads, activation and recovery: reuse the existing lifecycle where semantics agree; introduce target-specific realization only where foreign ownership, filesystem metadata or recovery differs. E–G and K concern a package backend, rootfs, image build and executor capability: require an explicit executor and an admitted target, never run a target hook on the host as fallback. H–J add service discovery, image/runtime provenance and client parity: expose these only for supported operations with their own evidence. No new universal lifecycle, store or workflow engine follows from this analysis.

**First discriminating future journey.** Select the same small application in a host plan and a synthetic rootfs plan. Compare package identity and choices, show different effect destinations, then demonstrate that an unavailable executor refuses before host mutation. Image execution, OCI export, native package hooks, service startup and OS recovery each require separate verification; the rootfs planning exercise proves none of them.

Disposition: accept the architecture investigation only, not the implementation of M14/M15. The seven-task M14 source review in `m14-transfer-review.md` and the original M15 A–K contracts remain the evidence index. No container was built or privileged operation performed for this decision.
