## D1: persist requested intent separately from resolved configuration

The original goal is lock replay explaining exact choices, captures and selected technical edges. Its three steps require separate authored authority versus active/dormant closure, exact capture/definition/domain/target/induced-provider edges, and versioned canonical reader behavior. Its positive case is explicit choices **and actual provider edges** surviving offline lock replay; negatives forbid changed definitions/lost request identity being called exact replay and forbid derived selections becoming sole authority. Acceptance requires requested/resolved lock round-trip and source/consumer explanation for every induced edge.

**Transferred app scope:** `configuration/evaluate.rs::evaluate` retains full `input`, normalized consumers, controls/defaults/questions, feature result and fully resolved data separately. `configuration/input.rs::edit` uses submitted original input, otherwise prior evaluation.input, and applies deltas. `configuration/record.rs::validate` validates historical definition/fingerprint and resolved public/secret metadata. ## E1: freshness before fast paths and pure discovery

The original steps require request/definition freshness before bare-install shortcuts, cached discovery through the service boundary, and candidate definition/effects/default inspection without selection/fetch/write. Positive: changing only choice/feature defeats Fresh. Negatives: empty cache performs no provider call, repeated unresolved discovery stops NeedsSelection. Acceptance names identity-based fast-path decisions and purity counters.

**Transferred narrow scope:** the app library description projects a supplied ResolvedPackage's independent package/installer definitions and authored effect/default data. `evaluate` checks expected semantic definition, retains current/historical basis, and produces questions/problems without executable resolution. `plan::prepare` returns structured unresolved state when no attended answer is available; it tracks answered groups and returns instead of polling an unresolved machine client. Actual `missing_choice_is_a_structured_question_and_install_runs_nothing` asserts machine plan has a choice question and no execution/resolved result, then unattended install exits2 without execution sentinel or index. The real journey verifies describe/plan data and no execution from plan. Automatic-basis update refusal is tested before new work/effect/index changes.

**Not transferred:** these are not the generic Fresh branch or cache-only discovery service. CLI `commands/app/describe.rs::show` calls resolve_package before the local library projection; its comment must not be mistaken for no registry/cache activity. Evaluation may validate host paths through supplied facts. No empty-cache provider-call counters, no authored/cache mutation counters or full M16 service route were accepted here. Generic plan's guard before Fresh is an honest unsupported refusal, not successful freshness implementation. Thus the positive bare-install Fresh criterion and complete discovery purity remain open; E1 earns partial local inspection/pre-execution semantics, not a complete cache/freshness subfeature.
