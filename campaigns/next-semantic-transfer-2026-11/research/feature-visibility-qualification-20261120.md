# Ordinary public/internal feature boundary qualification

## Scope and design discriminator

This test-only candidate addresses `PROP-069#FEATURE-VISIBILITY`, not general secret execution or a new capability family. Direct consumer `configuration.features` is a public interface: `ConfigurationDecl::normalize_input` refuses a named internal feature. A package-owned public feature may require an internal backing feature; the closure kernel can select that backing feature without converting it to a public answer. Internal visibility does not make package source confidential or prohibit explicit source reading.

One matched public fixture uses the same exact local Flow declarations and optional dependency effect. The direct world requests `internal-backing`; public `install` refuses with the specific internal-selection diagnostic before publishing a lock, slots or hook effects, preserving the semantic project snapshot. The legitimate world requests `public-entry`, whose declared `requires` selects the internal backing feature and its actual dependency slot, boot contribution and hook. Persisted consumer originals contain only `public-entry`; the persisted definition still marks the backing feature `Internal`. Registry-unavailable cold replay preserves the snapshot and does not rerun the hook. Authored project input remains unchanged in both worlds.

The existing test named `ordinary_secret_boundary_and_diagnostics_qualification` is separate refusal/redaction evidence. The earlier boolean "private" mutation sets `parameter.secret=true`; it is not a feature-visibility receipt. Secret marking does not authorize authored persistent answers or establish an ordinary ephemeral execution channel. That channel remains a distinct open requirement under `PROP-069#SECRET-BOUNDARY`.
