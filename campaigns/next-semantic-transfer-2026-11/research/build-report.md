## Findings that should change transfer design

1. **Safe publication is not a completed end-to-end replacement.** `xtask/src/dist/mod.rs::run_dist` still directly dispatches legacy Prepare, Upload, UploadBuilt and Finalize. `xtask/src/dist/release.rs::prepare_with` can create a tag, delete the existing release, then create a draft without consuming the new prepared subject/approval fence. In contrast, the new `publication_authority::evaluate_publication_authority`, private `publication_full_plan` journal and `calls/owner.rs::drive_one_fixed` are substantial machinery. `calls/driver.rs` explicitly says no live route invokes its production binding. Transfer the exact-subject/approval/preflight invariants, then build one coherent route; copying only the new module tree leaves the old mutation bypass intact.
2. **Existing-file production is not established by the green-shaped creation fixture.** `vibe-lifecycle/src/runner/invocation.rs::comparable_completion` compares the old input witness to the current one and returns `original-inputs-changed` on inequality. The fixture `m_03_a_1_execution.rs` reads `intent.txt`, creates `src/product.rs`, then compiles/tests it. This is useful evidence for creation/verify separation but does not prove modification of an input consumed by the producer. No distinct M-11 pre/post produced/adopted source-transition recipe, outside-write equality join or integrated brownfield fixture was found. Do not transfer a claim that existing-file transitions are done.
3. **Brownfield intake is mostly a historical requirement.** `vibe-scrape/src/inventory.rs` is byte-identical to target main and belongs to terminal scrape. It has deterministic no-follow walking, file identity/digest, and a second directory enumeration; only `.git` is excluded before descent. It has no declared include/exclude intake request, retained byte capture, typed omitted/unstable report or stack proposal/promotion consumer. `fixtures/next/brownfield` and `fixtures/next/transitions` are absent from the pinned tree.
4. **Boot and derivatives have real implementation worth studying.** The boot service has captured graph/occurrences, honest missing mappings, scalar/byte/token measurements, typed query/progress/cancel, an interactive line viewer, pure frozen-world scenarios and shared-dependency comparisons. Derivatives have all five resource families, retained local ownership, inert materialization, exact inventories, compatibility separate from authority, rebase through saved-document CAS/barrier/journal, and source/debugger/deploy joins. These are concrete source/test paths, not just design documents.
5. **Source interpretation migration is incomplete if the intended law is universal explicit classification.** `SourceDescriptor` and declared read paths exist and work through many consumers. But `vibe-specdoc/src/load.rs` is byte-identical to main and still infers semantics from suffix; the public `vibe-facts::observe_authored_source` still enumerates `.md`/`.xml`; progress retains `SourceAdmission::Legacy` and calls the suffix loader. This can be an intentional compatibility contract, but it conflicts with the historical blanket statement “no unclassified semantic path.” Target semantics must state the compatibility boundary explicitly.
6. **Four-client support is not proved by the open map.** Generic file/config, typed command, receipt upgrade/revocation and lifecycle routes exist. The actual-client driver covers Claude Code 2.1.299 and Codex 0.159.3 and requires a physical PodBay namespace. `four-client-contracts.json` explicitly leaves exact OpenCode/Qwen executable/version applicability unresolved. No equivalent M-08-E.2 commissioning driver/matrix was found. Existing standalone Qwen paths are not the complete external lifecycle.
7. **Bridge delivery remains unproved.** `fixtures/next/bridges`, `fixtures/next/native-reuse` and `vibevm/vibespecs/examples/next` have zero tracked files. Shared foreign-content classification and projection closure machinery exist, but the two external wrapper checkouts/pins, actual resource manifests and the two-feat × two-stack reuse journey are not recoverable as implemented from this repository alone.
8. **Smoke skip changed meaning within historical material.** The refined plan requests explicit skip as an allowed publication path. Child M-07-B.2 and `require_apply_ready_default_smoke` deliberately make skipped probes inspectable but not apply-ready under e1; no alternate versioned skip policy was found. Preserve the discrepancy for owner-facing design rather than silently choosing one interpretation.

## Candidates for removing unnecessary indirection, with counterevidence

- **Two publication engines/routes.** Legacy xtask release orchestration plus a much larger private full-plan/call journal is the strongest consolidation candidate. Counterevidence: crash recovery, reobservation, exact asset identity and single-use approval do require retained state; removing those guarantees merely to shorten the implementation is unsound. Preserve semantics and fault cases, redesign the owner boundary and dispatch once.
- **Multiple deploy ownership layers.** Standalone skill receipt, automatic projection receipt, lifecycle deployment receipt, generic adapter receipt and client-command journal overlap physically. Counterevidence: tests prove equal bytes cannot transfer ownership, config members share physical files, revoked providers cannot be used for cleanup, and different before-images matter. A single schema/engine is desirable only if it keeps those distinctions and compatibility readers; deleting receipt distinctions would be a correctness regression.
- **Derivative micro-service versus actual effects.** `DerivativeService` offers tiny passive derive/show/diff/rebase/apply wrappers while real publication lives in `MaterializedDerivative` and real authored apply in `DocumentEditAuthority`. Candidate: keep one user operation facade and reduce duplicate carriers. Counterevidence: inert replacement, durable authored ownership, saved-buffer barriers and activation are genuinely different authorities; merging them into an ambient filesystem operation would violate current tests.
- **Boot DTO/provider/presentation layering.** `FrozenWorld` → protocol → orchestrator → CLI/MCP → viewer is broad. Candidate: keep UI as thin adapter and reduce duplicate serialization/JSON-in-JSON carriers (e.g. `draft_json`, derivative catalog JSON). Counterevidence: actual `m_06_f_1_cases` and `m_06_c_1_cases` test parity, read-only queries and retained snapshot identity; separate preparation from query is a needed boundary.
- **Parallel explicit/legacy source paths.** Universal descriptor-selected loading could replace suffix inference. Counterevidence: target main and existing manifests have legacy behavior; removal needs a deterministic migration and named fallback policy. The current files already supply a comment-preserving migration owner; do not invent a second migration executor.
- **Per-client exact version recipes.** Inspect whether future descriptors can own safe command recipes instead of ever-growing core version branches. Counterevidence: argv construction, executable identity, literal argument handling and explicit unsupported-version refusal are security/effect correctness boundaries; arbitrary package shell templates are not an equivalent simplification.
- **New brownfield abstraction over terminal scrape.** Avoid calling the existing terminal-scrape planner “intake” or adding wrapper-only APIs around it. Counterevidence: no-follow file capture and directory stability checks are reusable; only the terminal export/rewrite/health semantics should remain separate from observation/proposal/promotion.

These are redesign hypotheses, not authorization to delete code, not measured complexity defects, and not proof that additional abstractions are inherently wrong. The absence of a named consumer is evidence against speculative machinery; the source/test counterexamples above identify distinctions with real consumers.

## Existing-main overlap

Pinned blob comparisons show:

- `vibe-scrape/src/inventory.rs` and `vibe-specdoc/src/load.rs` are **byte-identical** to target main. They are existing functionality, not transfer achievements.
- Target main already has `pkgskill/projection.rs`, lifecycle deploy transaction/plugin owners, `runner/verify.rs`, install bootgen and distribution release orchestration; next changes these owners. Semantic transfer should extend/rework their existing ownership rather than import parallel subsystems automatically.
- Main has no `source_descriptor/mod.rs`, `boot_debugger/mod.rs`, `derivatives.rs`, deploy `generic.rs`, deploy `client_deploy.rs`, `client_commands.rs`, `publication_authority.rs`, `publication_full_plan/mod.rs`, or lifecycle `runner/invocation.rs` at the compared paths. Absence at these paths does not prove absence of every equivalent behavior elsewhere; it identifies genuinely new named source owners in next.
- `xtask/src/dist/release.rs` differs only slightly in byte size (21,223 main versus 21,303 next); its legacy direct effect route survives despite the large new publication subsystem.
