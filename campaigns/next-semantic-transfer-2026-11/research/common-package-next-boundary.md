## Why the package effect layer is still missing

1. **Dependency activation needs a concrete declaration contract.** Current `ConfigurationEffect::Dependency`/`Forward` names an existing requires entry (`manifest/configuration.rs:147`, `configuration/validate.rs:208`). `Requires` has no optional declaration bit. `Manifest::resolution_requires` explicitly includes every package requirement (`package/application/requirement.rs:186`), and resolvo `provider.rs:257-285` feeds those requirements unconditionally. Therefore wiring a selected-effect set into today's graph cannot by itself define what an inactive dependency means. The prototype explicitly distinguishes optional declarations (`resolvo_engine/configuration.rs:66-84,457-491`). Root must choose/confirm this narrow normalized source contract. An effect reference must not silently convert an ordinary mandatory requires edge into an optional one.
2. **Real consumer identity and candidate binding are needed.** Main already retains every workspace version constraint and its consumer (`plan/roots.rs`); extend that owner instead of accepting user-supplied domain/instance labels. The configured request and definition/content identity must survive normal solve, held-pin fallback, masked visibility solve and conditional routes. Rejected candidate effects/default basis must not leak. `InstallSource::solve(&[PackageRef])` currently carries only package constraints; the resolvo candidate callback is the existing solver integration seam, not justification for a new solver.
3. **Reuse shared semantics, adapt the app boundary.** `compile_choices`, `normalize_input`, the choice merge and parameter validator are already present. The complete app evaluator is not a generic package evaluator merely because its types are common: `configuration/evaluate.rs:101` names one `installer` consumer and `284-307` rejects non-data effects. Shared evaluation/parameter responsibilities can be extracted or parameterized around their real domains; duplicating the checkbox/choice algorithm or adding an arbitrary “package mode” that bypasses checks is not semantic transfer. Multi-consumer parameter agreement also needs an actual package owner.
4. **Original and derived state are distinct durable obligations.** Main `LockedPackage.features` records effective feature names (`lockfile.rs:421`), while `record.rs:294-337` does not write original consumer input, reviewed default/definition basis or rich selected-effect provenance. A rich extension belongs in this existing lock owner with explicit old/new admission and actual update/reinstall readers. `formats/REGISTRY.toml:1040` currently declares lockfile schema=`none`; copying the generated app record into core is not an established wire/dependency design.
5. **Subskills are effective loading, not selective source copying.** Main deliberately materializes the whole package and leaves legacy `subskills_active` empty; `cli_registry_mgmt.rs:1086-1094` and later loading-model controls document this. The prototype D2 path selects from a durable configuration result and adds eager static content / lazy-push declaration offers / lazy-pull read access from intact captured bytes (`effective_subskills.rs:37,132-164`). Do not revive install-time copying, prune unselected files, or translate these into unrelated `[[skill]]` Agent Skills.
6. **Config-value data needs a real consumer.** PROP-069 explicitly permits data selection for a plan, durable replay and before/after comparison; it does not authorize arbitrary config-file writes. The current non-app path has no such consumed common-data result. Adding a field or serialization alone is not user delivery. A data-only slice is justified only if it is a necessary shared foundation with an identified actual plan/diff/replay consumer; it cannot substitute for the still-required dependency/forwarding/subskill journey.

Current source predicts that this oracle will fail; **no RED was run by this audit**. A legacy 1.1.0 control must still update successfully; ordinary install and whole update are guarded controls.
