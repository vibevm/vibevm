# VN-SOURCE-POLICY: bounded implementation plan

2026-11-07; read-only planning, no runtime verification. Root decisions incorporated: pins address the operation-effective catalog; preference acts at a fixed selected version; exclusions gate managed contacts. Current source-evidence writer owns registry/app edits: this plan does not change them. Hashes are a later observation, not an assertion that the concurrent tree was frozen.

## Concrete vocabulary proposal

```toml
# Project vibe.toml OR user $VIBE_SETTINGS/registry.toml
[source_policy]
prefer_hosting = ["gitverse", "github"]
exclude_hosting = ["github"]

[requires.packages]
"org.example/pkg" = { version = "^1", registry = "gitverse-org" }
```

Use the same strict SourcePolicyDecl in Manifest and GlobalRegistryConfig; keep it separate from existing `[policy]`, which already owns remap unmatched policy. It is an operation policy of the selected project/user, not a policy imported from a dependency manifest. A dependency's **edge pin** participates; its registry declarations or policy do not augment the catalog or override user preferences.

`prefer_hosting`: optional ordered list, distinguish absent from explicit `[]`. Resolve field-wise: invocation list, else project list, else user list, else empty. Highest explicit list replaces the lower list, not concatenation; stable deduplication or duplicate refusal must be deterministic (recommend refuse duplicate entries).

`exclude_hosting`: additive set union of user, project and invocation exclusions. An invocation cannot accidentally reopen a user-excluded hosting. Remove a persisted exclusion in its owning settings to re-enable it; no bypass flag in this increment. This monotonic merge is a proposal requiring root confirmation, not already settled by PROP-073.

Suggested CLI names when the complete vertical is enabled: repeatable `--prefer-hosting <HOSTING>` (occurrence order), `--no-hosting-preference` (explicit empty preference, conflicts with --prefer-hosting), repeatable `--exclude-hosting <HOSTING>`. Preserve current `--registry <PATH>` exactly: it is a local registry override, not a name pin. No new pin mutation CLI is necessary: documented inline `registry` and typed manifest editor meet need1. If later added, use a distinct `--from-registry <NAME>` applying to explicit package arguments and persisting the edge; never reinterpret --registry.

For initial hosting identities use deterministic URL-host classification shared with source evidence: github = github.com, gitverse = gitverse.ru; allow a generic `host:<dns-name-or-ip>` selector for self-hosted sources. Names are not inferred from organization/repository text. Case/IDNA/trailing-dot normalization is one owner function. Do not claim `github` means arbitrary GitHub corporate infrastructure: scope is managed destination hosts; known additional service hosts must be explicit verified classification entries. No new `[[registry]].hosting` override is necessary. Unknown route/SSH alias cannot be treated as safe because its display label is allowed.

## Pin law, selected closure and solver boundary

1. Bind aliases against the operation's immutable merged catalog. Project alias shadows global alias exactly as current merge_effective does. Duplicate alias rows within one scope should refuse ambiguous binding rather than introduce another last-wins rule; check current validation before implementing. Catalog binding is captured, not re-looked-up after project edits.
2. Pin restricts canonical registry identity, not a mirror URL or hosting. Allowed mirror/remap routes serving that registry remain available subject to digest and exclusion. A disabled/excluded pinned registry does not become 'unknown'; failure names the pin and policy reason. Cached matching provenance may satisfy a pin without any contact; cache with absent/conflicting registry evidence does not silently satisfy it.
3. Same declaration cannot carry registry with path/git. An operation override/path/git for a coordinate targeted by an active pin produces typed source-constraint conflict, including when its URL happens to equal the registry URL: route equivalence must not erase declared authority. Unpinned behaviour stays unchanged. Local/embedded precedence never overrides an explicit registry pin. A named local [[registry]] can satisfy its own pin; an ambient embedded copy cannot impersonate it.
4. Current `--registry <PATH>` replaces declared discovery. If any selected edge carries a named pin, refuse the incompatible explicit-local override unless a future explicit binding mechanism exists; do not invent a reserved alias or guess from path equality.
5. Incoming unpinned edges impose no additional source constraint. Equal alias pins unify; different aliases conflict even if URLs match. Error includes package, both requiring edges and catalog bindings. Version constraints still intersect normally; unknown alias/missing version never falls back.
6. Pins from inactive/abandoned solver candidates must not poison the solve. Resolvo currently caches candidates by package name and interns `(name, semver)` solvables; `get_dependencies` reads `manifest.resolution_requires()` then interns only the version constraint. A global accumulating pin hashmap is incorrect: dependencies of a rejected candidate can leave a stale pin and reject a valid solution. Pin constraints must remain attached to solver requirements and their selected candidate/source identity, including backtracking. Conditional and optional edges participate only when activated; all retained active incoming edges are validated before any acquisition.
7. `DepProvider::validate_selected` exists but explicitly cannot change candidate selection. It is useful defense-in-depth, **not** a sufficient pin implementation: post-solve refusal alone can reject a valid alternate version/source solution. `DepProvider`/`VersionEnumerator` currently expose semver and fetch_manifest(group,name,version), with no source constraint. Extending that shared seam is an unavoidable dependent chunk; adapt naive/resolvo/sat, local/embedded providers and metadata/fetch together. No second resolver is justified.

## Where version semantics stay unchanged

`MultiRegistryResolver::list_versions_inner` returns the first registry's nonempty list; `resolve_inner` has override/path/git precedence. Preserve those paths exactly when there is no pin/exclusion. Preference alone must not reorder `sources` before list_versions or choose the highest version across all registries. First select the version under existing semantics; only then rank allowed equivalent source candidates for that exact version by preferred hosting and original registry order. Pin changes the eligible registry intentionally; exclusion changes eligible routes intentionally, so resulting availability/version may differ for those reasons, not preference.

The manifest used to solve dependencies must correspond to the retained source selected for acquisition. Same version text is not proof of equivalent content. Use existing integrity/content identity and captured source evidence to reject incompatible mirrors/copies; never solve metadata from A then silently fetch different same-version dependency metadata from B. Resolvo may select one of several versions during backtracking; fixed-version source selection occurs for each candidate version whose metadata is used, with final retained evidence from the accepted candidate.

### Concrete extension of the existing solver seam

**Design candidate for root evaluation, not an accepted solver architecture.** Accepted constraints are unchanged; the concrete encoding below still needs a bounded check of the existing engine's condition semantics. A prior draft incorrectly required an unpinned edge to retain the default registry's version domain even when another active edge pins the same package. That proposal is rejected: A→X^1 unpinned and B→X^1 pinned to R may select R's 1.5 even if default registry has only 1.2.

Keep resolvo package `NameId` as `group/name`: one chosen candidate per package remains the single-source/single-version invariant. Replace the internal semver-only solvable record with a candidate identity containing version and captured canonical source binding (effective registry identity or the existing direct/local source route). Do not put actual mirror URL into package identity. Keep captured source evidence beside this identity, including immutable metadata observation used to derive dependencies.

Extend the shared provider relation with candidate enumeration and manifest lookup by that candidate, not just `(group,name,version)`. `MultiRegistryDepProvider` routes it to the existing MultiRegistryResolver; local/composite/embedded providers manufacture their existing source-route candidates under the same relation. Extend the existing version-set predicate to include the edge's RegistryPin and its admitted **version domain**. `get_dependencies` interns this edge predicate from Requires, retaining declarant provenance for errors; root requests use the same edge shape. The pool, manifest cache and final ResolvedNode retain candidate identity through graph output and acquisition. `filter_candidates` evaluates a predicate against this captured candidate; it never writes a global pin map. Two aliases' pins then have disjoint candidate sets for the same NameId and produce an ordinary constrained solve conflict, annotated with source reasons. A rejected candidate's requirements disappear with ordinary solver backtracking.

Version-domain distinction is essential: with **no active incoming pin**, admissible versions remain the existing first-nonempty-registry enumeration (plus existing local/embedded precedence); with an active pin, obtain the domain from its named registry. An unpinned edge adds only its declared semver constraint and must not defeat an active pin by imposing the old default registry domain. A superset candidate inventory must not leak registry-only versions into an entirely unpinned solution. Preference is a soft candidate ordering **within the same version**, never a hard filter that would defeat an incoming pin.

Therefore source-aware candidate records and ordinary version-set filters are necessary but not by themselves sufficient. The solver relation also needs an active-edge source-authority condition: a candidate outside the default version domain is eligible only under an incoming pin witness selected in the same solve. Encode that implication in the existing solver's constraint/condition layer, scoped to the requiring solvable, so backtracking removes the witness. Do not approximate it with global discovery of any pin in any fetched manifest. Before coding, inspect the existing resolvo condition/version-set adapter to confirm the exact encoding; if the current adapter cannot represent the implication, extend that adapter's constraint representation, not a second resolver. This is a specific implementation verification point, not permission to change the semantics.

Candidate discovery must accommodate a pin introduced by a later dependency without stale NameId caches. Design the source-aware candidate inventory as the operation's stable allowed source domain before caching candidates for that name; enumerate permitted registry/source alternatives while retaining the default-domain and active-pin eligibility conditions above. Do not lazily append candidates behind resolvo's cached get_candidates result. The legacy adapter path can remain for operations known to carry no pins; merely seeing no root pin is insufficient to know that. Extra allowed-source discovery in the source-aware path is explicit, gated, and reported; it is not evidence of availability on excluded routes. This is an extension of the existing provider, not a second solve.

The existing `DepProvider::validate_selected` then checks retained constraint/source coherence without reselection. Conditional fixpoint passes carry edge constraints and captured candidate identity forward. The naive/sat engines must consume the same relation in their own execution models; otherwise capability admission must refuse that solver before any effects. Do not silently route a requested solver elsewhere. Exact internal predicate/engine file paths are referenced by inspected imports but were outside this packet; inspect them in the implementation packet before specifying edits.

Two focused alternatives for the next design review:

* **A — candidate source identity plus active-edge implication (preferred candidate).** One solve contains source-aware candidates and active pin witnesses; default source/version eligibility holds only in the absence of selected incoming pins. Rejected parent candidates remove their witness by backtracking. Benefits: dependencies read from exact selected source, no re-solving loop state to leak. Required proof: the engine's existing condition/conflict vocabulary can encode “outside default domain requires a selected incoming pin to this source” with exact support, not a free witness variable the solver may invent. Candidate universe must be stable before engine caching. Inspect this proof before implementation; semver+registry record alone is insufficient.
* **B — explicit assumption-scoped passes using the same engine/provider.** An immutable pin assignment is a solve assumption; derive the next assignment only from selected active edges and discard all source-dependent metadata/caches when assumptions change. Crucially, a plain fixed-point loop is insufficient: cycles and a conflicting selected candidate must produce an engine conflict/no-good that allows selecting another parent candidate. The retained state is an explored assumption branch with justification, never a union of encountered pins. This avoids implementing source choice as a second registry resolver, but adds orchestration and termination/completeness obligations; therefore less attractive unless A cannot be expressed. Must prove it can discover a pin that makes an otherwise unsatisfiable default-source graph satisfiable, not just recheck already solved graphs.

Both require tests for alternate parent versions with different pins, conflicting diamond pins with a valid backtracking alternative, optional/disjunction candidates that introduce then discard a pin, and a pinned-only satisfying version shared with an unpinned requirement. Neither authorizes preference to widen version domain. If neither proof holds, stop at design; do not ship a post-solve-only approximation.

## Schema and compatibility work

* `vibe.toml` adds `[source_policy]` and inline `registry`; global registry.toml adds `[source_policy]`. Existing strict serde readers reject new fields, so declare a minimum compatible release for manifests using them; omission keeps old manifests valid. No automatic rewrite of unrelated manifests or default registry config.
* No numeric manifest/global schema field was observed in these declaration types. Do not invent an epoch solely for two fields. Record the format change and minimum reader requirement in the existing compatibility/release mechanism; exact version is root/release owner's decision.
* Registry pin **intent** must survive root snapshots/reinstall/migration: inspect lockfile's existing root-dependency snapshot and any declaration lowering that reduces Requires to PackageRef before implementation. The chosen source fields already exist on LockedPackage and are evidence, not a substitute for pin intent. A lock wire bump is necessary only if its persisted intent shape must expand; do not gratuitously bump source evidence again.
* New generated operation input/error payloads must follow the existing generated schema epochs/capability negotiation; policy strings in authored TOML are not permission to hand-edit generated Rust or invent a parallel JSON envelope. Exact schema paths for shared operation inputs are not in this packet; inspect when P3 begins. L0 does not need an application inventory schema bump.
* Rust structs with new public fields and provider signatures are source-API changes. Update construction sites and provider implementations atomically when their chunk lands. Generated source-evidence changes belong to the active writer; avoid overlapping edits before review.
