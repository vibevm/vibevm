## User-facing command split

The original client is a general VibeVM terminal workbench, not an application owned by Hermes. `vibe ui` and `vibe hermes` initially select the same shell, default Hermes adapter, project and navigation policy. `vibe agent hermes [args]` stays native-facing; its supported `--tui` opens upstream Hermes. Interactive `vibe tree` becomes a launcher for `vibe ui --tree`, not a subprocess or second UI loop. Preserve explicit path selection, plain/JSON and non-TTY behavior. Show the entry points separately in help and exercise them in real terminals and pipes. See `PROP-076#HERMES-ENTRYPOINTS`.

### Shared workbench: initial architecture map and research contract

IntelliJ IDEA Islands is the reference for fitting a great deal of information on one screen without obscuring the active task: distinguish the primary working area from surrounding context without spending a terminal cell on every decorative border. Claude Code is the reference for reading a dialogue vertically: follow a streaming answer, distinguish tool activity from speech, inspect a result, and return to the draft. Benchmark both wide and narrow terminals, including monochrome. These are references for outcomes, not designs or assets to copy.

Working dependency map: command entry → shell (focus, layout, navigation history, draft presentation) → contributed views, actions and search providers → existing domain owners. Agent adapters expose only supported dialogue capabilities and retain native conversation identity; tree, operations and specs work without Hermes. Contributions must not infer permissions from visibility, own a second history or bypass normal operation admission. Prove the seam by mounting and removing an independent test contribution and substituting a minimal test agent without changing the shell or tree. Unsupported capabilities must be visible as unavailable; a test adapter is not shipped support for a second agent. A dynamic binary plugin ABI or marketplace is not a prerequisite.

Before selecting an implementation, extend these four source samples into versioned architecture maps of both official open-source trees: trace one contributed view and action from declaration through activation, context, dispatch, disposal and failure; compare extension trust and process boundaries, then record which mechanisms are worth their cost in a terminal. Inventory VibeVM feature areas and their current owners; coverage of all functions is the workbench direction, not a first-release parity claim. First integrated journey: open the tree with no agent, find a specification, navigate to a linked operation result, then return to the same draft in a linked Hermes conversation. No re-execution, inference or implicit approval on navigation. The shell migration starts after consolidation, not in the bounded SYS milestone.

## Original terminal client: research, feature matrix, implementation

Owner direction, superseding the earlier overlay-first proposal: design a new Vibe/Hermes terminal frontend, not a fork or skin of `ui-tui`. Preserve the backend authorities; do not preselect a toolkit, panel layout, key binding or base client. This shared work belongs to the IDE parent and its ordered children after consolidation. Canon: `PROP-076#HERMES-TUI-ORIGINAL-DESIGN` and `#HERMES-TUI-PROJECT-TREE`.

1. **Build the comparison set at execution time.** Download the then-current official Hermes TUI sources into a fresh isolated research directory. Record upstream origin, tag/commit, release, license and inspected entry points. Identify leading comparable agent terminals and useful specialist tools for tree navigation, diffs and long-running jobs. Explain inclusion by the user journey they do particularly well, not popularity alone. For closed-source products, use permitted black-box trials and official documentation; distinguish observed, documented, absent and untested behavior. Do not vendor their code or assets.
2. **Run the same journeys.** Start and resume a conversation; switch projects and sessions; type while streaming; interrupt; handle approval; inspect a tool call and diff; trace a failed check from notification to task to evidence; return to an unfinished draft. Compare keyboard-only use, mouse support, discoverability, narrow/wide terminals, resize, accessibility/plain fallback, reconnect, long transcripts and large trees. Record both wins and failure modes, with versioned evidence. Count actions and lost context; do not score screenshots as proof of usability.
3. **Publish the feature matrix before choosing the design.** Each row names a user outcome, reference implementations, evidence, strengths/trade-offs, current Hermes/Vibe gap, intended behavior in the new client, domain owner and acceptance test. Include capabilities unique to the combination: an authoritative campaign tree distinct from the package/spec tree and agent activity; operation receipts and spec references linked from the conversation. Resolve conflicting treatments as explicit design decisions, retaining the underlying user needs. The result is a versioned target matrix, not a list from which only the easiest features are implemented.
4. **Design and implement from the matrix.** Prototype materially different interaction models and compare them on the same journeys. Choose layout, navigation, pseudographics, focus and rendering only after this comparison. Deliver every target row in testable slices against the consolidated owners. Track each row through implementation and verification; removing or deferring a target is a visible scope decision, not a silent PASS. Preserve history, drafts and pending approvals across navigation. Opening the tree must not run a job, query a model or change task status.
5. **Exit criterion.** Provide the matrix with evidence for every target row and real terminal demonstrations of the joined-up journeys. Establish where the new client improves on the references and where trade-offs remain. Do not call a widget prototype a completed TUI or infer cross-platform support from a headless rendering test.

## Product-scale plan navigation and Search Everywhere

Add `PROP-076#HERMES-PRODUCT-PLAN-VIEW` and `#HERMES-SEARCH-EVERYWHERE` to the research and delivery matrix. Optimize for orientation in a large plan, not more bookkeeping. Use an existing real campaign as the benchmark: starting deep at a failed check, can a reader name the user scenario, read the stage's purpose, see what else must happen to achieve it, and return to the draft? Starting from the top, can they find the current frontier without expanding every leaf? Preserve native node descriptions; show unknown links as unknown rather than inventing an ancestry. Inspect the canonical multi-user-planning `plan-hierarchy.xml` and actual dashboard behavior for missing context or awkward navigation. Prefer a view change over a schema change. No plan-integrity redesign in this slice.

Baseline the existing `vibe-actions` search engine and `vibe tree` package/field/action providers (`crates/vibe-actions/src/search/mod.rs`, `crates/vibe-cli/src/commands/tree/tui/search/providers.rs`). Use a small query corpus: goal in the user's words, exact task/spec ID, duplicate names in different branches, and absent results. Inspect discoverability, ranking, result labels and return navigation; do not prescribe fixes for unverified bugs. Compare feasible reuse with the original client's UI during research; do not implement a second index of project truth. In a context explicitly linked to Hermes, exercise both directions on the same entities, retaining query, focus and conversation draft; without a link, prove a useful standalone result and no automatic launch. Cross-navigation must obey local access boundaries. Renderer, grouping and key bindings remain design decisions, not conclusions of this brief.
