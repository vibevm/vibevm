# SYSTEM — воспроизводимый системный промпт и живая загрузка сессии

Статус: **проект спецификации для обсуждения**, 2026-11-07. Функция не реализована. Это новый запрос владельца, не одна из реализованных возможностей прототипа. Исследование и место в плане подготовлены; реализация не начинается автоматически от наличия этого документа.

## 1. Что получит пользователь

Пользователь создаёт `vibevm/vibespecs/boot/SYSTEM-TEMPLATE.md` и пишет собственные постоянные инструкции. Vibe собирает `vibevm/vibespecs/boot/SYSTEM.md`, пригодный для передачи в инструкционную часть API-запроса. В рассматриваемом checkout это `/home/olegchir/git/vibevm/vibevm/vibespecs/boot/SYSTEM.md`; абсолютный путь не является частью формата.

**Рекомендуемое решение: стабильный SYSTEM плюс проверяемое живое продолжение загрузки.** SYSTEM содержит пользовательскую рамку, инструкции выбранного entrypoint и уже скомпилированную статическую полосу. Runner передаёт текущие INDEX-входы после этого префикса, затем контекст задачи. Система использует существующую модель загрузки, а не второй компилятор промптов.

Преимущества: большой повторяемый текст доступен API без повторного чтения STATIC агентом; одинаковые входы дают одинаковые байты; изменение задачи не меняет системный префикс; устаревший артефакт обнаруживается до отправки запроса. Это создаёт условия для экономии на кэше, но не гарантирует попадание в кэш или фиксированный процент экономии.

## 2. Что обнаружено в существующей архитектуре

- PROP-009 уже задаёт selected-node effective boot, наследование, видимость, static linking, INDEX и транзакционную публикацию. Их надо переиспользовать.
- В этой репозитории текущая статическая полоса — `STATIC.xml`, не `STATIC.md`. Оба варианта определяются действующим форматом потребителя.
- `INDEX kind = "static"` означает безусловное чтение динамически связанного файла. Это **не** разрешение компилировать его навсегда в префикс. `kind = "dynamic"` и `when` также не должны терять runtime-смысл.
- Собственный authored boot сейчас динамически связан. В частности, изменения `00-core.xml`/`90-user.xml` нельзя скрыть до следующего изменения списка пакетов.
- Legacy own-boot scan исключает STATIC/INDEX, но пока не знает SYSTEM и SYSTEM-TEMPLATE. Наивное добавление этих файлов создаст самовключение или двойную загрузку.
- AGENTS содержит не только постоянную политику: там есть загрузочные указания, центральный/worker режимы, условные harness-правила и ссылки на локальное состояние. Автоматически обходить все ссылки и считать их постоянными инструкциями нельзя.
- `vibe show effective` имеет другой состав отображаемых файлов; его конкатенация не заменяет модель boot.
- Существующий unit fingerprint не доказывает неизменность всех исходных байтов. Новому артефакту нужны реальные input witnesses, а не сравнение одного списка пакетов.

Кодовые основания и хэши: `../research/system-prompt-boot-audit.{md,json}` и `../research/system-prompt-design-review.{md,json}`. Основные владельцы: `vibe-core::layout`, `vibe-workspace::boot`, `boot_artifacts`, `install::bootgen`, существующие captured source / installed binding / publication owners.

## 3. Граница SYSTEM и runtime-контекста

```text
SYSTEM-TEMPLATE (пользовательская постоянная рамка)
  + export выбранного entrypoint, по умолчанию AGENTS.md
  + существующая compiled STATIC-полоса
  + постоянный протокол продолжения загрузки
  = SYSTEM.md                         ← стабильный префикс

проверенный актуальный INDEX и его применимые входы
  + явно предоставленный session/task context
  + история диалога и новый запрос
                                      ← живое продолжение
```

Граница принципиальна: SYSTEM сам по себе не объявляется полным снимком всей сессии. Пара prefix/suffix покрывает **вычисляемую общую загрузку**. Дополнительные обязанности из произвольного authored AGENTS — например, прочитать локальный план после выбора контекста — не становятся автоматически выполненными: их выполняет агент с инструментами или явный context provider runner-а. API без доступа к файлам требует, чтобы вызывающая программа предоставила необходимые материалы; экспортер не притворяется, что прочёл их.

В первой версии не предлагается второй режим «заморозить весь INDEX». Он конфликтует с текущим смыслом динамической загрузки и усложняет доказательство свежести. Такой snapshot-export можно рассматривать отдельно при появлении конкретного сценария.

## 4. Пользовательские и генерируемые файлы

| Файл | Владелец и смысл |
|---|---|
| `boot/SYSTEM-TEMPLATE.md` | Пользователь. Литеральный текст постоянной рамки. Наличие включает генерацию для данного consumer node. |
| `boot/SYSTEM.md` | Vibe. Готовый стабильный UTF-8 текст. Ручное редактирование не является поддерживаемым способом настройки. |
| `boot/SYSTEM.meta.json` | Vibe. Версионированный манифест входов, границ и свежести. Не отправляется целиком модели и не содержит текущее состояние пользователя. |

Для первой версии шаблон не является программой: нет shell, чтения env/HOME, произвольных INCLUDE, сетевых запросов или языка вычислений. Пользователь пишет обычный текст; Vibe автоматически добавляет определённые контрактом блоки. Фигурные скобки и Markdown-примеры остаются буквальным текстом. Это даёт полезную функцию без нового языка шаблонов. Управляемое размещение блоков можно добавить отдельным расширением, если понадобится.

Отсутствие SYSTEM-TEMPLATE сохраняет существующую загрузку без изменений. Пустой присутствующий шаблон означает opt-in без дополнительной рамки. Init может предлагать явный opt-in; установка не должна самовольно создавать или перезаписывать authored шаблон.

Все три пути получают явные роли в общем layout/source owner: template input и generated outputs. Они не входят в обычный own-boot обход, INDEX и static compilation как случайные файлы каталога. Явное включение output в его собственные входы, в том числе косвенное, отказывается до записи. Это нужно проверить и для declared sources, и для legacy discovery, и для допустимых алиасов путей. Самовключение определяется по реальным семантическим рёбрам/идентичности файлов, а не по упоминанию имени SYSTEM в тексте или примере. Template читается как отдельный явно названный обычный input независимо от того, пуста ли project.sources: наличие этой роли не превращает его в native boot source.

## 5. Как включать AGENTS без второго набора правил

По умолчанию выбирается один repo entrypoint `AGENTS.md` данного узла. Не склеивать одновременно AGENTS/CLAUDE/GEMINI: они могут дублироваться либо различаться по harness. Внешние/родительские инструкции не разыскиваются произвольным filesystem walk; наследование определяется существующим selected-node контрактом, а явно добавленный harness input отражается в манифесте.

Exporter сохраняет authored инструкции без LLM-пересказа, сокращения или эвристического удаления «неподходящих» абзацев. Только известный структурно управляемый `<vibevm>` boot redirect заменяется адаптерным указанием на уже предоставленные материалы. Несовпадающие/повреждённые управляющие маркеры дают понятный отказ, а не regex-починку всего документа.

Некоторые authored абзацы тоже требуют прочитать STATIC. Вместо угадывания таких фраз транспортный контракт явно указывает: содержимое перечисленных embedded источников уже предоставлено; повторное чтение для выполнения **этих же** boot-обязанностей не требуется. Отдельная просьба проверить актуальные файлы по-прежнему допустима. В runtime suffix runner указывает фактически предоставленные INDEX-входы; непредоставленные материалы не помечаются прочитанными. Нельзя обещать абсолютный запрет повторных tool calls только посредством текста: это проверяется поведением адаптера и сценариями агента.

Сам entrypoint является входом сборки. Если его operating ledger изменился, SYSTEM может измениться даже при прежних пакетах. Экспортер не должен скрывать такое изменение ради кэша.

## 6. Идентичность, свежесть и повторяемость

Два разных понятия:

1. `prefix_digest` — хэш действительно отправляемых байтов SYSTEM.
2. Input/boot witness — доказательство, из каких наблюдавшихся входов этот текст получен и к какому selected node / boot plan он относится.

Манифест версии 1 должен хранить относительную идентичность узла, entrypoint/profile, версию recipe, формат static lane, упорядоченные входы с исходными хэшами, хэш output и используемую boot-plan/binding идентичность. Точная схема создаётся через существующий generated wire registry при реализации. Эти хэши доказывают согласованность, не доверие автору или подлинность пакета.

В стабильном тексте нет автоматически вставляемых времени сборки, абсолютного checkout/HOME, Git branch/HEAD, статуса задач, ID сессии, имени текущей модели или результатов environment detection. Authored текст не переписывается ради удаления авторских абсолютных путей: ограничение относится к генератору. Диагностика таких authored зависимостей может предупреждать о непереносимости, но не изменяет политику молча.

Детерминированны порядок, разделители, кодировка и окончания строк. Нет LLM-суммаризации, неупорядоченного обхода map или timestamp-заголовка. Исходные байты и итоговые текстовые байты имеют разные witnesses. Исходный XML compiled stream не передаётся парсеру одиночного authored XML-документа. Допустимо сохранить его XML-текст внутри `.md` оболочки; Markdown-расширение не требует потери XML-семантики.

Не ставить общий хэш сборки перед большим повторяемым содержимым: изменение позднего блока тогда испортит совпадение всего префикса. Хэши и изменяемая диагностическая информация находятся в sidecar, а границы секций в тексте стабильны.

| Изменение | Ожидаемое действие |
|---|---|
| Новый вопрос, время, текущий план или cwd | Меняется только предоставленный runtime context; SYSTEM не пересобирается из этих значений. |
| Байты применимого динамического boot-файла при том же плане | Новый проверенный suffix; prefix может остаться тем же. Existing installed-integrity rules продолжают действовать. |
| Шаблон, entrypoint, static input, влияющий recipe/format | Проверить/пересобрать prefix; устаревшие байты не отправлять как актуальные. |
| Состав/порядок INDEX, visibility, selected node или package binding | Перепроверить общий boot plan; пересобрать metadata/затронутые артефакты. Не смешивать несовместимые поколения. |
| Модель, tools, SDK wrapper или настройки API | Файл может быть тем же; фактический cache prefix провайдера может измениться. |
| Истёк TTL провайдера | Может потребоваться новая запись кэша даже при полностью одинаковом SYSTEM. |

Следовательно, обещание — «одинаковые релевантные входы → одинаковые байты», **не** «вечно неизменно до изменения списка пакетов».

## 7. Подготовка и публикация

Переиспользовать существующие подготовленные планы, source capture, static compilation и boot publication. Сначала рассчитать и проверить весь набор выходов, затем опубликовать через действующую границу согласованной записи. Сбой не должен оставлять новый SYSTEM с metadata от другого поколения или портить прежний пригодный комплект. Перед публикацией используются существующие проверки удержанных входов. Если эта же операция переписывает управляемый redirect AGENTS, в SYSTEM и его witness используется prospective entrypoint того же поколения, а не старый файл до записи; иначе новая сборка сразу оказалась бы устаревшей.

Новые артефакты входят в те же install/reinstall/format-change/staged-publication процессы с сохранением защиты authored package members. Без изменения байтов файл не перезаписывается. Удаление шаблона удаляет только доказанно принадлежащие Vibe outputs; чужой или вручную изменённый файл даёт конфликт. Действия с templates и output roles отражаются в changelog форматов.

Перед API-запросом runner выполняет read-only prepare/check: проверяет static witness, выбранный профиль и boot world, затем получает свежие применимые INDEX-входы. OS-условия используют явный session target, не ОС машины, когда-то собравшей SYSTEM. `installed:` остаётся compile-time решением existing boot owner. Неизвестный selector не превращается в true.

Устаревший prefix не отправляется молча. Проверка возвращает причины и предлагает явную регенерацию; обычный session boot остаётся чтением, не скрытым install/build/network. Runner preflight — операция вызывающего API-приложения до запроса; AGENTS redirect не заменяется приказом агенту выполнить `vibe prompt prepare`. Ручной пользователь может скопировать SYSTEM в любой клиент, но вне поддерживаемого checked adapter гарантии свежести и отсутствия двойной загрузки нет.

Предлагаемый CLI, ещё не существующий: `vibe prompt build`, `vibe prompt check`, `vibe prompt prepare --json`. Build пишет outputs, check/prepare не пишут product/cache/config и не обращаются к сети. Граница read-only действует и на расширения: check/prepare не запускает native/backend compiler для проверки свежести. Разрешены чтение удержанных входов, builtin pure projection и проверка существующего producer witness; если нужное доказательство невозможно без effectful provider, возвращается `freshness_unverifiable`/unsupported с предложением отдельного явного build. Это capability contract, не обещание безопасности произвольного callback.

`prepare` возвращает раздельные prefix/runtime материалы и их наблюдения, а не готовый секретосодержащий API-запрос. Окончательную грамматику закрепить вместе с consumer, не выпускать parse-and-ignore флаги.

## 8. API, полномочия и режимы агентов

Имя SYSTEM.md не выбирает роль API. Адаптер явно размещает доверенные project/application instructions в поддерживаемой инструкционной роли (`system`, `developer` либо соответствующий provider field), сохраняя обязательные внешние инструкции и установленные пользователем границы. Перенос repo текста в другую роль не объявляется семантически нейтральным. Текстовые разделители не создают настоящих role boundaries.

Поддерживаемый adapter не должен одновременно инжектировать SYSTEM и снова автоматически загружать тот же AGENTS/STATIC. Предоставленные источники учитываются явно. Если конкретный агент не даёт управлять своим prefix или auto-loading, он не входит в гарантированно поддерживаемую интеграцию; Markdown-файл не способен исправить это сам.

Для central session выбирается полный соответствующий узлу профиль. Для quiet workers полный центральный prefix **не передаётся вообще**: профиль/packet выбираются до формирования запроса. Поздняя фраза «игнорируй лишние правила» не возвращает потраченный контекст и не восстанавливает границы делегирования.

Содержимое HOME, stewardship settings/plan/custody, handoff, токенов и приватных файлов не подтягивается по ссылкам из AGENTS. Допустимые пользовательские наблюдения подаются отдельно по явному runtime contract. Package boot и обычные документы/примеры не получают одинаковую instruction-authority только потому, что доступны на диске.

## 9. Проверенные свойства API-кэширования

Документация проверена 2026-11-07; конкретные тарифы, TTL и список моделей не становятся постоянным продуктовым контрактом.

- **OpenAI:** кэш зависит от совпадения фактического rendered prefix, включая tools и другие части запроса. Стабильный инструкционный блок полезен; настройки, срок хранения и условия записи зависят от модели. Попадание и эффект надо смотреть в реальном usage. [Официальная документация](https://developers.openai.com/api/docs/guides/prompt-caching).
- **Anthropic:** Messages API поддерживает `cache_control`; учитывается иерархия tools → system → messages. Изменение раннего блока влияет на последующие совпадения; время жизни ограничено. [Официальная документация](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).
- **Gemini:** доступно implicit caching, рекомендуется общий ранний префикс; explicit cache зависит от API/model и не универсален. В частности, текущая документация исключает explicit caching для Interactions API. [Официальная документация](https://aistudio.google.com/docs/caching). Страница получена напрямую после отказа web reader обрабатывать её Markdown content-type.

SYSTEM — текстовый артефакт, не переносимый KV-cache между моделями/провайдерами. Он не уменьшает автоматически объём контекста и не устраняет противоречивые инструкции. Стабилизировать 145k ненужных токенов недостаточно: качество и необходимый объём boot остаются отдельной инженерной задачей.

Экономику считать параметрически: для префикса L токенов, W cache writes и H reads сравнить `L × (W + H) × uncached_rate` с `L × (W × write_rate + H × read_rate) + storage_cost`, если хранение тарифицируется. Добавить некэшируемые запросы и неизменяемую стоимость динамических/выходных токенов. Числа подставляются из текущих тарифов и фактического usage. Первый запрос/частые истечения могут уменьшить или устранить выгоду.

Без вызовов платных API можно доказать повторяемость байтов и request envelope через fake provider. Утверждение о реальной экономии требует отдельного измерения cache hit/write tokens, latency и стоимости на конкретных моделях; такая проверка в рамках этого исследования не проводилась.

## 10. Архитектурный маршрут

Точный граф: `system-prompt.json`. Исторические 222 задачи и 113 прототипных приёмок не меняются. Все implementation nodes пока planned, prototype=false. Дизайн не является приёмкой функции.

| Слой | Узел | Пользовательский результат / основание |
|---|---|---|
| L0 | SYS-CONTRACT | Различаем authored template, generated outputs, стабильную и живую части; исключаем самовключение. |
| L1 | SYS-CAPTURE | Знаем точные входы и можем объяснить устаревание, используя уже существующие source/binding owners. |
| L2 | SYS-COMPOSE | Получаем повторяемый SYSTEM и план runtime-продолжения из одного effective boot. |
| L3 | SYS-PUBLISH | Безопасно обновляем весь комплект; сбой не оставляет смешанную версию. |
| L4 | SYS-OPERATIONS | Генерация при install/reinstall, отдельные build/check/prepare операции. |
| L5 | SYS-ADAPTERS | Использование в API без повторной загрузки и с наблюдаемыми cache metrics. |
| Q | SYS-QUALIFY | Доказательства эквивалентности загрузки и совместимости. |
| R | SYS-DOCS | Примеры и честное руководство по ограничениям/экономике. |

Это расширение уже существующих boot/source/publication оснований, а не зависимость от будущего registry pin или Docker. Первым реализуется L0-контракт и недопущение самовключения, затем capture/composition и публикация. После запроса на реализацию VIBE-NEEDS сохраняет установленный приоритет среди одинаково архитектурно готовых задач, пока владелец не поменяет порядок.

## 11. Условия приёмки

1. Одинаковые входы дают byte-identical SYSTEM в разных checkout locations; повторная генерация не увеличивает файл и не меняет mtime при неизменных байтах.
2. Template/output не становятся обычными boot inputs ни в legacy, ни в declared режиме; прямой/косвенный self-include отказывается.
3. Дифференциальные сценарии подтверждают static-first и исходный порядок runtime INDEX, installed visibility и условия для Linux/macOS/Windows.
4. XML/Markdown/mixed/generated stream обрабатываются действующими owners; authored literal directives и примеры не превращаются в исполняемые imports.
5. Root/member/specspace профили не получают области вне selected effective scope; разрешённая агрегация subtree у root сохраняется; quiet worker не получает полный central prefix даже временно.
6. Изменение dynamic bytes меняет только свежий suffix, если план совместим; изменение static/template/entrypoint обнаруживает stale SYSTEM без скрытого rebuild.
7. Missing/unsupported/mutated input, invalid marker и output conflict не портят предыдущий согласованный комплект.
8. Sentinel-файлы HOME/plan/custody/token не открываются и не появляются в output без отдельного явного runtime input; текущая задача/время не меняет prefix.
9. Fake provider видит точные роли, порядок blocks/tools, prefix boundary и отсутствие двойной AGENTS-инъекции. Это не засчитывается как live cache hit.
10. CLI read-only check/prepare подтверждается filesystem/network sentinels и provider-call sentinels; effectful callback не вызывается даже при cache miss; install/reinstall/publish используют общий transaction owner.
11. Metadata format и invalidation reasons версионированы; old consumers не обязаны читать новый артефакт; обычный boot без opt-in остаётся прежним.
12. Заявление об экономии делается только после отдельного provider measurement; нет искусственного добавления бесполезного текста ради cache threshold.

## 12. Рекомендуемые решения для обсуждения

Предлагается принять stable prefix + live suffix, простой literal template без DSL, AGENTS как default entrypoint, opt-in наличием шаблона и обязательную checked prepare границу поддерживаемых API adapters. Условные runtime-файлы не запекаются в SYSTEM. Изменять текущую boot-политику или создавать SYSTEM в рабочем boot-каталоге до реализации защит нельзя.

Если нужен именно **один полностью автономный файл без runner и без файловых инструментов**, это другой контракт: потребуется явно снимковый/target-bound полный контекст с ограничением свежести. Его нельзя обещать одновременно с текущим late-bound boot и живыми пользовательскими настройками. Для предложенной основной функции такой режим не требуется.
