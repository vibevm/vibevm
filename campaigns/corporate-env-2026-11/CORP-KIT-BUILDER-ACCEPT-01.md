# Accept the producer against an existing installation

Applies to the existing `CORP-KIT-BUILDER-ACCEPT` node after the bounded BUILD in `CORP-KIT-BUILDER-FIRST-01.md`. This is a test contract, not a test receipt. It adds no campaign node. A fresh install and a reinstall of identical bytes do not establish an upgrade.

1. From a clean synthetic user and unrelated working directory, initialize and edit two recipes naming distinct, supported local versioned inputs A and B. Use the public producer for both new output directories. Record the input and output hashes, producer and installer identities, and actual bundle version and target. Use no private corporate directory, host profile, credentials, external download or system PATH change.
2. Establish a real installation of A through a supported A installation path. For a compatible A, dry-run then install with the real native installer. For historical `v1.0.11` (`e9d6e6fabc8b75c4febc05509189ff9880ad722a`), the modern installer invokes `self apply`, which did not exist in that CLI. Use its historical installation/import command and explicitly record this distinction; do not patch A or claim that the modern installer installed A. Confirm A by executing the installed shim's compiled version, not by reading the kit label. Independently inspect the active version and at least one version-distinguishing owned artifact. Place an unrelated marker in the install area and record its bytes. Keep this installation intact for the rest of the test.
3. With a corrupted B input, require refusal from the responsible verifier. Check that no usable new kit was published and that A remains active with its owned artifact and unrelated marker unchanged. This tests producer refusal, not installer rollback.
4. Build valid B and use the supported update procedure against the same A installation. Record commands and exit status, then independently observe B active, B's expected owned artifact and the unchanged unrelated marker. No empty-home reset, relabelling one bundle as a second version, or use of a separately hand-assembled kit. If the relevant assets or supported update path are missing, identify which premise is missing rather than substituting a reinstall.

BUILD baseline for this gate: builder commit `f11bb6033ba149a16266e405fb16c4abc831003c`, exact seven Git blobs checked against manifest SHA-256 `b699f87349c074817b1f240b92947455e588265ccfc3b5692de6c2473381fe4c`. The independent Linux x86_64 `build::kit_producer_publishes_and_native_consumer_installs_exact_output` run passed (1 selected, 4 filtered). It establishes that the emitted installer consumed the produced kit in dry-run and fresh-install modes and that the installed CLI reported its version. It used synthetic index/proxy/source payloads; it is neither a full release test nor an upgrade. Use this baseline rather than rerunning it as a substitute for A-to-B.

### Observed failure and bounded repair

On November 20, 2026 the builder and independent reviewer both ran the genuine historical `vibe 1.0.11` and produced B kit with `vibe 1.0.12`. Corrupt B was refused without changing A's active selector, installed executable digest or foreign marker. With valid B, the native installer returned success but invoking the installed shim still printed `vibe 1.0.11`. Independent receipt: `architect-versioned-upgrade-1795198323272010357.log`, test `produced_kit_native_upgrade_preserves_existing_install_on_corrupt_input`, fixture SHA-256 `1454b228170d05b55220d4579b60f6a84a6be83d84ffca0ac8950a1d95c42cdf`. This is a failed upgrade, not a failed fresh install. Ordinary site profile application intentionally skips import when a managed instance is active.

An upgrade must be explicitly requested from the verified kit; unattended operation alone is not upgrade consent. Use the existing full-distribution importer and activation owner in the selected install root; do not change generic `self apply` into an updater or import only the CLI file. Revalidate the expected active instance and strictly newer target before mutation; reject downgrade. Dry-run leaves A active, and success requires the installed shim, active selector and actual bytes to identify B. Preserve A's immutable instance and the unrelated marker. Test this on the same genuine A/B inputs; retain the failing receipt for the former behavior.

### Accepted Linux upgrade behavior

The explicit offline upgrade from the genuine installed `1.0.11` to the produced `1.0.12` kit passed independently in `architect-r3-upgrade-1795199258547629984.log` (one exact test, 113.02 s); the builder panel in `kit-upgrade-repair-runtime-r3.log` passed all six tests. The installed shim reported `1.0.12` and its payload hash matched B; immutable A and the unrelated marker remained. Corrupt B did not change A, an intact dry-run left the inventory and pointer unchanged, a pending journal was preserved on refusal, and a same-version upgrade was refused. This accepts the Linux upgrade criterion on the tested binaries, not a cross-platform verdict or an aggregate NST verdict.

Reuse the BUILD receipt for facts it already proves (fresh consumption, output collision, checked local inputs). Keep the platform verdicts separate: a successful Linux run does not establish Windows/macOS runtime. Document the actual repeatable offline invocation and secret boundary without real values. The existing `campaigns/corporate-env-2026-11/accept.sh` is not a suitable isolation wrapper here: its network namespace still binds the host root. Use a fresh isolated filesystem with only the required read-only inputs and synthetic writable directories. Do not provision a manual runner or publish a kit.
