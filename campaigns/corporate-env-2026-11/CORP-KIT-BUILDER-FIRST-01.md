# Corporate kit producer: local recipe, not another installer

Existing plan nodes CORP-KIT-BUILDER-{DESIGN,INIT,BUILD,ACCEPT}. Architect spec/user-project-root; builder task/user-project-delivery product baseline 5b4378072a72c91305a2b8689266f31f3d1e71ea. The current native installer consumes a kit; receipts for consumption do not establish production. Reuse xtask dist bundle/installer outputs, bootstrap bundle verifier, native SiteProfile parser and existing registry mirror/drop formats. No accessing the owner's corporate kit, credentials or host config, implicit build/download, publication or global install. No consolidation/global repair in this packet.

Public entry points: `vibe kit init [--file PATH]`, `vibe kit validate --file PATH`, then `vibe kit build --file PATH --out NEW_DIR`. Default init destination is `vibe-kit.toml` in the explicit cwd. Init writes an editable commented TOML recipe via exclusive create, does not overwrite or create missing parents. Recipe schema_version=1: closed kit metadata (name, canonical dist target, version), explicit relative paths and SHA-256 for bundle, native installer and site profile. The template's example values and hashes are placeholders, not verified artifacts. In recipe v1 the native installer is a trusted input explicitly selected by the recipe author: its SHA-256 verifies the bytes copied, not its role, version, target or publisher. The distribution fragment's bootstrap digest is for the vibe CLI, not the separate native installer. The producer must not execute supplied binaries to identify them. Verify bundle version and target from the bundle manifest; establish usability of the particular accepted installer/bundle pair separately by actual synthetic installation from the produced kit. Keep profile semantics with the existing profile owner. Do not invent a second mirror config; qualify optional external input manifests only if a real existing owner verifies them. All paths anchored at recipe directory; reject absolute/traversal, escape, input-output overlap, ambiguous names and stale hashes. No environment/secret interpolation. Read-only validation distinguishes bad shape from missing or mismatched inputs and returns useful value-free errors. Register the durable recipe at the project format owner and reference the existing corpus conventions.

First executable gate: real init from empty non-project directory with isolated HOME, no PATH mutation/network; second init preserves bytes; invalid/unknown field and unsafe path refuse; valid synthetic recipe passes appropriate validation. Build gate separately: consume already built versioned local artifacts, verify exact hashes and actual bundle target/version, reproduce canonical bootstrap layout/checksums, stage then publish only to a new directory; do not overwrite old output. Distinguish construction from installation and test successful consumption of produced kit, refusing missing, corrupt or colliding inputs. Linux correction from the first producer trial: the existing OwnedDirectory exclusive creation implementation returns Unsupported on non-Windows platforms; do not treat its API presence as operational support. Use the existing SafeFS cooperative Linux `Pinned::retire_directory_noreplace_to` checked move only on the producer's own exclusively created private stage under a held trusted output parent. For this Linux implementation the existing output parent must belong to the calling user and have mode 0700. Document this prerequisite in the build help/example; an unsuitable parent is a refusal, not permission to chmod it. Test with a private parent for success and a synthetic non-private parent for refusal without changing its mode or publishing output. Check the complete expected names and bytes before and after no-replace publication in that same parent, as well as final directory identity. Fail closed on unsupported filesystems and never delete a foreign destination. Authorization comes from the explicit build request for a new directory, not retirement policy; source identity is observed before/after, not atomically compared by rename. No new unsafe backend is needed. Do not claim cross-platform leases or crash recovery. Use the existing bootstrap's dry-run and actual install separately. Preserve eligibility of the existing update/delta path; do not imply that deferred multi-platform, wizard, mirror or upgrade coverage has passed. Report exact code/fixtures and runtime commands. A parser unit test, rendered plan or manually assembled kit is not evidence of successful production.
