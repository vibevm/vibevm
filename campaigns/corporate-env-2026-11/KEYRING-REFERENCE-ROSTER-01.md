# Public logical removal with a complete reference inventory

Queued after the package-default qualification handover; do not preempt it. The accepted r4 CLI deliberately supplies no inventory. Preserve that binary as a negative compatibility control. Deliver a real public `vibe secrets remove` success for an unreferenced synthetic item without giving any client permission to claim that the roster is empty.

Ownership: the generic keyring owns coordination, storage-version admission and logical deletion; each reference consumer owns the meaning and durable location of its bindings. The trusted composition root enumerates supported consumer owners, not all files in HOME. Use the existing `ReferenceInventory`/`ReferenceGuard`, store mutation lock and protected filesystem primitives. No second reference database standing in for consumer truth. No force flag, secret getter, provider, network, actual credential or private settings. Allowed builder writes: `vibe-secrets`, its narrow CLI composition and focused tests, the corporate format ledger and receipt. Stop and report before touching external consumers or general-purpose filesystem semantics.

Compatibility decision before enabling deletion: identify the durable fact that routes all cooperating binaries sharing this settings store through the same reference protocol. Verify with an older actual reader/writer and a newer test consumer. A version tag known only to the current executable, a missing marker, or a constant empty list is not an attestation. Reject unknown versions, missing participants, incomplete reads and ambiguous legacy state before publishing. If a new format is needed, bind the version in the existing admitted store format so old writers cannot silently drop it on rewrite. Specify initialization and interruption ordering; no automatic assumption that legacy settings are reference-free. Preserve legacy read behavior where feasible and report intentional incompatibility before enabling format writes. Do not implement a competing registry merely to turn the positive test green.

Serialize reference creation and deletion across *processes*: inventory guard first, then existence/revision check under the keyring contract, keep protection through publication. A newly admitted consumer must participate before any binding can exist. Refuse removal on unreadable or unsupported owner inventory. Presence of safe reference IDs can explain a refusal; it cannot reveal values. Preserve reserved item directories and old revision bytes after deletion; no physical erasure claim.

Acceptance: in isolated synthetic settings, run the public CLI end to end, observe successful logical removal only for a verifiably complete unreferenced store, then NotFound on fresh details and repeated remove. Show referenced/unknown/stale/no-consent refusal and byte-for-byte unchanged index, retained old value revision, unaffected foreign neighbor and no sentinel in output. Run independent-process binding-vs-removal with a synchronized barrier; exactly one mutation wins, no dangling reference. Test both client-version orderings, incomplete initialization and unsupported future participant. If no compatible protocol can yet be demonstrated, deliver the precise compatibility blocker and keep production removal fail-closed. No broader product or Windows claim. Return exact candidate manifest, format decision, gate outputs and observed compatibility limits before acceptance.

### Old-client compatibility control — Linux, 2026-11-20

The architect ran the accepted `c05ebc333` CLI (SHA-256 `57ab4b49463ab549e85e2f5429fcdb71777fc4adbe4e70c4302aa0a649443ad3`) read-only mounted into a fresh unshared namespace, with an empty temporary HOME and synthetic settings. Against a private index containing `schema = 2` and `store_revision = 9`, both `secrets list` and `secrets create --value-stdin` exited 1. The same two calls refused schema 1 with an unrecognized top-level `future_roster = []`. In each case the exact index bytes survived and no item directory appeared. A schema-1 control without the extra field admitted both calls (exit 0). This demonstrates an old-client refusal boundary; it neither proves that a roster is complete nor authorizes an automatic legacy migration. The fresh-store positive removal, mixed-version races and consumer checks above remain required.

### Accepted implementation boundary (not acceptance of implementation)

New private stores may initialize index schema 2 / reference protocol 1 with an empty durable participant list only on proven fresh genesis, serialized with the existing store lock. Recheck the actual state under lock. Missing index bytes alone, a pre-existing directory, or interrupted creation do not attest genesis. Valid schema 1 remains readable and mutable as before; its public deletion remains unknown. No automatic conversion. An unsupported epoch is intentionally unavailable to the old CLI; record that compatibility decision in the format ledger before enabling writes.

Registered participant IDs are monotonic in this slice. Registration is internal trusted composition, not a public command or caller input. Publish a participant durably before its first binding, coordinate every binding under the inventory guard, recheck the item and preserve the guard through publication. An older schema-2 client encountering an unknown participant refuses removal. A synthetic later consumer belongs only to tests. Check competing old/new first writers as well as competing binding/removal.
