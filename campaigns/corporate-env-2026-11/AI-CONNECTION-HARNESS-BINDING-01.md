# Per-agent connection binding — qualification before activation

Scope is metadata only. Do not launch a harness, contact a provider, inspect its native credential store, decrypt or resolve a key. Do not change provider compatibility claims. Begin at the accepted selection baseline and locate the production harness identity registry, alias resolver and protocol capability owner. Inventory evidence separately for each selectable harness; a package, proxy test or executable name is not a protocol admission. In particular do not claim Claude Code OpenAI compatibility.

Characterize three independent modes: native/unmanaged (including absence), explicitly inheriting the user's chosen default, and explicitly bound to a particular connection. Use only admitted real harness identities and isolated synthetic connections. A default selection alone must change no harness behavior. For inheritance with no default, or an unavailable explicit connection, return actionable unavailable; never silently fall back to ambient credentials. No side effect on navigation or metadata reads.

For the first test-only atom find the public command/metadata field that can set/show each mode; if absent, document the first missing owner/format/verb and how old readers and writers behave. Do not assume that general add/default commands create per-agent bindings. Test a pair of connections and distinct harness identities if supported. A default switch changes only inheritance resolution; explicit binding stays attached to its ID; native remains native. A future removal path must refuse deleting an explicitly bound connection and may not silently retarget it. Do not change the product until the registry/capability boundary and persistence contract are documented. Allowed initial writes: focused CLI fixture and campaign receipt. Return exact baseline, test evidence and any not-reached rows; no AR/IDE or global publishing work.
