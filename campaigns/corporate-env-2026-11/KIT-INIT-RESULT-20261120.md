## Concrete owners and boundaries

- Public `vibe kit init [--file PATH]` defaults to `./vibe-kit.toml`; `validate --file PATH [--structure-only]` reads that explicit subject. CLI arguments and command dispatch use existing CLI/progress owners. The new command does not discover a project or initialize one.
- Recipe v1 is authored strict TOML with kit name, canonical first target `x86_64-unknown-linux-gnu`, canonical SemVer, and distinct recipe-directory-relative path/SHA-256 pairs for bundle, installer and site profile. Unknown fields refuse. The registered `kit-recipe` epoch1 and JSON Schema describe this data model; codegen owns generated format identifiers. No existing wire or lock epoch changes.
- Existing SafeFS `publish_new_in` owns whole-file exclusive publication; existing occupants, links and missing parents refuse. Existing no-follow directory walks, bounded snapshots and streaming two-pass digest proofs own input observations. Paths reject absolute/traversal/ambiguous components and interpolation is not performed. Errors omit raw TOML/profile contents.
- Existing `SiteProfile::parse` owns profile schema and policies. Recipe pins its exact bytes instead of duplicating its contents. No HOME/settings/cache discovery or writes, credential reading/import, provider, network, automatic Cargo build or publication is added.
- Existing `xtask dist` remains producer of reviewed versioned bundle, installer and fragments. Existing registry mirror/config/payload owners and drop layout remain separate reusable mechanisms, not a second recipe policy solver. No optional mirror/drop manifest is admitted without its existing verifier.
- The next bounded `kit build --file PATH --out NEW_DIR` must verify actual distribution target/version and named installer, assemble canonical bootstrap layout/checksums, stage and publish only to an absent output. It is **not implemented or accepted by INIT**. Input/output overlap, actual distribution compatibility and successful consumption of produced output belong to that gate; synthetic hash-input acceptance is not distribution acceptance.

## Three user-visible steps

1. `vibe kit init` creates a documented editable template with explicitly demonstrated paths and placeholder hashes. No inputs are promised present.
2. `vibe kit validate --file vibe-kit.toml --structure-only` checks closed structure and lexical pins only. Without that flag validation additionally checks actual local file hashes and profile semantics, and explicitly does not claim kit construction or bundle compatibility.
3. `vibe kit build --file vibe-kit.toml --out NEW_DIR` is the next required producer operation; it cannot be substituted by native installer receipts.
