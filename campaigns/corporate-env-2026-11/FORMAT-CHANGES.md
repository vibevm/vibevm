# Corporate-env campaign: format and behaviour changes

Append-only log of user-visible changes made by the campaign in `PLAN.md`, material for release notes. Entries are `CORP-FMT-NNN`; numbers are never reused.

## CORP-FMT-001 — Consented durable-PATH repair core; `self doctor --fix` error text (Phase 8)

Status: **in development** (uncommitted worker change, 2026-11-08).

- New internal entry `ensure_shim_dir_on_durable_path` (`crates/vibe-cli/src/commands/vvm/env_path_fix.rs`) that the coming `vibe self apply` calls: it reports whether the shim directory is on the durable PATH and changes it only with consent. Precedence: explicit flag (`--fix-path` / its negation) → site-profile `[path] fix = "ask" | "always" | "never"` → an interactive question (default **yes on Windows, no elsewhere**); unattended without a flag or `always` never writes. Its JSON observation (for the future `apply` report): `shim_dir`, `outcome` (`already_on_path` | `applied` | `skipped`), `was_on_durable_path`, `on_durable_path`, `consent` (`flag` | `profile` | `interactive` | null), `skip_reason` (`flag_declined` | `profile_never` | `not_interactive` | `declined` | null), `changed`, `activation_hint`, `fix_hint`, `durable_environment` (the existing observation object). No command emits it yet.
- `vibe self doctor --fix` now writes PATH through that core with its existing consent (`--yes` or an interactive yes; unchanged). Visible difference: when the durable write fails, the error now reads ``putting `<shim dir>` on the durable PATH at <target> failed: <cause> (violates REQ spec://org.vibevm.core/vibevm/common/PROP-019#path); fix: …`` instead of the bare cause. A target that is already canonical is no longer rewritten (it was already a byte-level no-op).
- Windows: `HKCU\Environment` logic now sits behind a user-registry seam; real behaviour is unchanged (direct `RegSetValueExW`, kind preserved, `WM_SETTINGCHANGE`, no child process). Manual test: `vibevm/vibespecs/manual-tests/MT-07-windows-user-path.xml`.

## CORP-FMT-002 — `cargo xtask dist gitverse-publish`: mirror a release onto GitVerse (Phase 5b)

Status: **in development** (uncommitted worker change, 2026-11-08). Release tooling only; no `vibe` format changes.

- New explicit step `cargo xtask dist gitverse-publish --version V [--from-dir DIR] [--dry-run] [--replace] [--api-base URL] [--owner O] [--repo R]`. No other `dist` command (and no CI workflow) runs it, so the owner decides when a release appears on GitVerse. Defaults: `https://api.gitverse.ru`, `vibevm/vibevm`; `--api-base` points it at an on-prem GitVerse.
- Source: the published GitHub release `vV`, read anonymously, or a local directory holding the same 19 assets (`--from-dir`). Nothing is sent until `DISTRIBUTIONS.json` names `vV` and every bundle, bootstrap and fragment matches it byte for byte (the `dist finalize` verification); the three installers must be present and non-empty.
- Target: the release for tag `vV` is reused when it exists (by tag, else found in the release list, which also sees a draft) and created otherwise as a public release (`draft: false`, `is_authorized_only: false`, `target_commitish` = the manifest's source commit). Assets go up through `POST /repos/{owner}/{repo}/releases/{id}/assets?name=…` (multipart field `attachment`), `DISTRIBUTIONS.json` last; a final listing checks every name and size.
- Idempotent: a same-named asset of the same size whose downloaded SHA-256 matches is skipped; any other same-named asset stops the run before any upload unless `--replace`, which deletes the differing assets (`DISTRIBUTIONS.json` first) and uploads them again. Duplicate remote names stop the run. Extra remote assets are reported and left alone.
- Token: `VIBEVM_PUBLISH_TOKEN_GITVERSE`, then legacy `VIBEVM_PUBLISH_TOKEN`, then `~/.vibe/gitverse.publish.token`, then legacy `~/.vibe/git.publish.token` (the existing per-host convention), sent as `Authorization: Bearer` with `Accept: application/vnd.gitverse.object+json;version=1`; output names where the token came from, never its value, and error bodies are redacted. `--dry-run` loads no token, contacts no GitVerse endpoint and prints every request it would send.

## CORP-FMT-003 — Artifact drops: `[artifacts]`, package payload drop, `file://` targets, `vibe artifacts where` (Phase 4)

Status: **in development** (uncommitted worker change, 2026-11-08).

- New `~/.vibe/config.toml` table `[artifacts]` with `vibe = "<dir>"` (release drop, see CORP-FMT-004) and `packages = "<dir>"` (application payloads). Paths must be absolute; a relative one is ignored with a warning.
- `packages` lowers into one `local`-layer remap row (provenance source `[artifacts] packages`, key `prefix = ""`, kind `app-input` only) — visible in `vibe remap list` / `explain`. It is the weakest row a user can have: every user, project or invocation row still wins; the declared origin stays the last candidate.
- Lookup for an input `url + sha256` of package `G/N@V`, file name `F` = last URL path segment: `<drop>/G/N/V/F`, `<drop>/G/N/F`, `<drop>/<sha256>/F`, `<drop>/F`. The digest is always verified (`digest_mismatch`, file not kept). A miss is `fetch_failed` naming `F`, the digest and every searched path; when the origin's host is excluded by source policy the drop's miss is now reported first (before: only the `source_contact_refused` refusal).
- Remap behaviour change: a `prefix` row with a `path` target now joins the URL remainder onto the directory (mirror layout; query/fragment dropped, `..` dropped). For application inputs the directory itself is still searched by digest afterwards, so existing digest-layout stores keep working.
- One location rule (`ByteLocation`, PROP-066 `#locations`): `https://`/`http://` remote; `file://` URL and `path` local; anything else refused. A remap `url = "file:///…"` target for an application input is now read locally (before: refused as not package-relative).
- New command `vibe artifacts where [<package>] [--registry DIR] [--json]`; JSON protocol `vibe-artifacts-where/1`: `release {source, location, from, example_dir, files}`, `packages`, `inputs[] {option, step, input, file, sha256, url, searched[], status: present|mismatch|missing|no-drop}`.
- `vibe remap explain <url>` asks about a URL under `https://github.com/vibevm/vibevm/releases` as a `distribution` artifact (before: `app-input`), so release rows show.

## CORP-FMT-004 — Release sources: `[self]`, `vibe self source show|set|reset`, `vibe self releases`, drop/mirror-aware update (Phase 5)

Status: **in development** (uncommitted worker change, 2026-11-08).

- New `~/.vibe/config.toml` table `[self]`: `source = "github" | "gitverse" | "nexus" | "localdir"` (case-insensitive, written lower-case), `url` (nexus base / gitverse repository web URL), `api` (gitverse API base, default `https://api.<host>`), `path` (localdir; default `[artifacts] vibe`).
- Precedence: `$VIBEVM_RELEASE_ORIGIN` → `[self]` → `[artifacts] vibe` → GitHub. The environment variable keeps its invocation-layer row (prefix `https://github.com/vibevm/vibevm/releases`, provenance `VIBEVM_RELEASE_ORIGIN`); its row `reason` text is now `release source \`mirror\` from $VIBEVM_RELEASE_ORIGIN` (was `$VIBEVM_RELEASE_ORIGIN`). `localdir`/`nexus` add one `local`-layer row (prefix `https://github.com/vibevm/vibevm/releases/download`, `distribution` only, source `[self] source` or `[artifacts] vibe`). An unusable source is a warning on every command and a refusal on release verbs.
- `vibe self source` with no subcommand still prints the source tree (unchanged); new `show` (`vibe-self-source/1`: `source, location, from, row{prefix,target,layer}`), `set <type> [--url] [--path] [--api]` (validates, rewrites `config.toml` via the config serializer — comments in that file are not preserved), `reset`.
- New `vibe self releases [--all]` (`vibe-self-releases/1`: `source`, `releases[] {version, installed, active, running}`, `truncated`); newest ten without `--all`.
- Release drop layout `<drop>/v<version>/` with the release page's files; listing = directory scan (a `v<version>/` with `DISTRIBUTIONS.json` or this target's zip, or a bare `vibevm-<version>-<target>.zip` at the root). A bare zip is installed from its embedded `DISTRIBUTION.json` with a hint that it was verified against the embedded manifest only.
- Raw repository listing: optional `<base>/RELEASES.json` (new document: `{"schema_version": 1, "releases": [{"version": "X.Y.Z"}]}`; bare strings / bare array accepted), else Nexus search REST, else refusal. GitVerse: `GET <api>/repos/<owner>/<repo>/releases[?page,per_page]`, `…/releases/tags/v<V>`, assets via `browser_download_url`, `Accept: application/vnd.gitverse.object+json;version=1`, bearer from the per-host token chain when present (never printed, never sent to another origin).
- `self update` on `nexus`/`localdir`/`gitverse` takes the highest listed version (GitHub and `$VIBEVM_RELEASE_ORIGIN` still use `latest/download`).
- Transport: release downloads now go through the operation's controlled transport (the `install -g` client) instead of a private reqwest client: `exclude_hosting = ["github"]` refuses `self update` before contacting github.com; in the controlled posture the bound client's no-implicit-proxy rule applies (as for `install -g`). Requests no longer send `Accept: application/octet-stream`/`Cache-Control`/a `User-Agent` on payload downloads (the cache-busting nonce stays); list API requests send `User-Agent: vibevm/<version>`.
- One location rule for bootstrap/update/install: a remapped release base may be `https://`, `http://` (newly accepted for `self bootstrap`), `file://` or a `path`; local release files carry no `?vvm_nonce` and are read under `--offline` (before: every release verb was refused offline).

## CORP-FMT-006 — Registry `type`, the project-local `registry.local.toml` layer, `vibe registry add|list|remove --scope/--type` (Phase 1)

Status: **in development** (uncommitted worker change, 2026-11-08).

- Every `[[registry]]` (in `vibe.toml`, `~/.vibe/registry.toml` and the new `<project>/.vibe/registry.local.toml`) accepts `type = "github" | "gitverse" | "git" | "monorepo" | "localdir"`, case-insensitive on input, written lower-case. Absent, it is inferred: `file:` url → `localdir`, host `github.com` → `github`, host `gitverse.ru` → `gitverse`, anything else → `git`; `monorepo` is never inferred, so every existing file keeps its meaning. An unknown value is refused with the list of values; `type = "localdir"` with a remote url is refused. An explicit `type` now chooses the backend (`git` on a `file:` url clones it as Git; `localdir` on a bare path reads it as a directory).
- New layer `<project>/.vibe/registry.local.toml` (same grammar as `registry.toml`; `vibe init` already ignores it — `.vibe/.gitignore` is `*` and the root `.gitignore` carries `/.vibe/*.local.toml`). Precedence, highest first: invocation `--registry <dir>` → `registry.local.toml` → `vibe.toml` → `~/.vibe/registry.toml` → site profile (reserved, Phase 7) → built-in defaults. A registry `name` in a higher layer hides the same name below; mirrors concatenate in layer order; overrides dedupe by `pkgref`. Applies to install/update/resolution and to the `[[mirror]]` rows the remap Locator reads.
- `vibe registry add|remove registry|remove mirror` gain `--scope project|local|user` (default `project`, today's behaviour); `vibe registry add` gains `--type`, refuses `--naming` for `monorepo`/`localdir`, and accepts a `file:` url for `localdir`. Writing `user`/`local` re-serialises that TOML file (comments in it are not kept). `--scope site` is refused (the site profile is applied as a whole).
- `vibe registry list` without `--scope` now lists the effective rows of every layer (also outside a project: the user file alone) instead of only `vibe.toml`; `--scope X` lists one layer. Each JSON `registries[]` row gains `type` (effective) and `scope` (`local|project|user|site`); `adapter` follows the type (`github`, `gitverse`, `monorepo`, `localdir`; `null` for `git`). Human output gains `type:` and `scope:` lines.
- `vibe registry publish` chooses its target from the same effective layers (project-local, `vibe.toml`, `~/.vibe/registry.toml`); before, only `vibe.toml` was read. A project with no `[[registry]]` of its own now publishes to the first user-file registry instead of refusing.
- Spec: `spec://org.vibevm.core/vibevm/modules/vibe-registry/PROP-002#registry-type`, `#registry-layers`.

## CORP-FMT-007 — `monorepo` registries: resolution, lock rows, replay (Phase 2a/2b)

Status: **in development** (uncommitted worker change, 2026-11-08).

- `type = "monorepo"`: one Git repository (any url Git accepts; SSH uses the ordinary `~/.ssh` configuration) holding packages at `<group>/<name>/v<version>/` on `ref` (default `main`). Cloned on first use — through the Locator (`[[remap]]` rows, then the canonical url) and the operation's Git backend, so source policy and admission apply; under a controlled transport (any `exclude_hosting`/`prefer_hosting`) it is captured with native preparation into an operation-owned snapshot. `--offline` never contacts it. `auth = "token-env"` is refused (`MonorepoTokenAuth`).
- **Lock row format (new meaning, no new field):** `source_kind = "registry"`, `registry = "<name>"`, `source_url = "<registry url verbatim>#<group>/<name>/v<version>"`, `source_ref = "<branch>"`, `resolved_commit = "<commit read>"`. The url is kept byte-for-byte (an scp-form `git@host:path` stays home-relative). A registry row whose `source_url` carries such a fragment matching its own coordinate is a monorepo row.
- Replay (PROP-073 `#LOCKED-SOURCE-LAW`): a held monorepo row installs from the store, or reads its directory at the held commit (never the branch tip; a mismatching hash or commit refuses); `vibe install <pkg>@<req>` / `vibe update` move the version on the held repository and branch (the fragment and commit follow); `vibe update --sources-only` moves a row from another registry onto a monorepo keeping version and bytes. In-place materialisation is refused (`InPlaceUnsupported`).
- The legacy library type `GitMonorepoRegistry` now records provenance on fetch: `registry_name` (when named), `source_ref` = branch, `resolved_commit`, `fetched_from` when a candidate other than the canonical url served; its `source_uri` changed from `git+ssh://host/path#…` to the verbatim url `+ #<group>/<name>/v<version>`.
- Test fixture: `ssh_fixture.py` honours `VIBE_SSH_FIXTURE_WRITABLE=1` (also admits `git-receive-pack` on its one repository).

## CORP-FMT-008 — Publishing into `monorepo`, `localdir` and generic `git` registries; `--replace` (Phase 2b/3)

Status: **in development** (uncommitted worker change, 2026-11-08).

- `vibe registry publish` dispatches on the target registry's type. `monorepo`: shallow-fetch the branch, write `<group>/<name>/v<version>/`, commit (`publish: <group>/<name>@<version>`, or `replace: …`; the user's Git identity, else `vibevm publisher <publish@vibevm.local>`), `git push <url> HEAD:refs/heads/<ref>` — no host API, no organisation, no tag; an empty repository gets the branch. A non-fast-forward rejection is refetched and retried once, then refused (`MonorepoRaceLost`, nothing pushed). `localdir`: copy into a hidden sibling `.v<version>.incoming-*` and rename into place (a replaced version is renamed aside first, then removed); no locking. `git` (generic server): push into the package's existing repository `<url>/<repo name>.git` per `naming`, as `--repo-url` does; before, publish refused the unknown host.
- Immutable versions for `monorepo`/`localdir`: identical content (by content hash, so `.git` and build output never differ) is a no-op reported `unchanged`; different content is refused with `VersionExists` unless `--replace` (new flag). `--dry-run` decides and writes nothing. `--index-checkout`/`--push-index` are refused for these two types.
- New JSON report for these two types: `{ok, command: "registry:publish", mode: "monorepo"|"localdir", registry, target, package, version, package_path, action: "created"|"replaced"|"unchanged", commit?, retried, content_hash, dry_run}`.

## CORP-FMT-009 — `[[mirror]]` rows reach every command (integration fix)

Status: **in development** (uncommitted integration change, 2026-11-08).

- Bug (since the deferred registry catalog, before this campaign; made visible by the drop and release rows): on a verb that reads no registry catalog up front (`install`, `update`, `reinstall`, the lifecycle verbs, …) the clone chain of a registry used the `[[mirror]]` tables only when the invocation's remap Locator was empty — and in the CLI it never is (the built-in single-file rows, a `[[remap]]` row, the `[artifacts] packages` drop row or the release-source row). Every mirror was silently ignored there; only catalog verbs (`registry`, `search`, `outdated`, `cache`, `init`) honoured them.
- Now the catalog composes its effective `[[mirror]]` tables into the invocation Locator's `[[mirror]] / [[override]]` slot whenever it builds a registry's clone chain (`Locator::with_registry_tables`; one lowering, `vibe_core::remap::rows_from_registry_tables`, shared with the composition root). Precedence is unchanged and the same on every verb (`PROP-066#precedence`): the most specific key first; among equals the higher layer, then the later row — so an explicit `[[remap]]` row of the local layer naming the same registry beats the mirror, an invocation `--remap` row beats both, and the drop (`app-input` only) and release (`distribution` only) rows never apply to a registry clone. The declared registry url stays the last candidate.
- Locked replay is unchanged: a held row still consults operator remap rows only (`PROP-073#LOCKED-SOURCE-LAW`).

## CORP-FMT-010 — Comment-preserving writes of `config.toml`, `registry.toml`, `registry.local.toml`

Status: **in development** (uncommitted integration change, 2026-11-08). Supersedes the "comments are not kept" notes of CORP-FMT-004 and CORP-FMT-006.

- `vibe self source set|reset`, `vibe init` (the remembered `[init] last_author`) and `vibe registry add|remove registry|remove mirror --scope user|local` rewrite only the keys and tables whose value changed (`vibe_core::toml_preserve`, over `toml_edit`): unchanged tables, `[[registry]]`/`[[mirror]]` elements and keys keep their bytes, comments and quoting; a removed element disappears with its own lines; a new element is appended after its array; a changed key keeps its trailing comment. Saving an unchanged value is a byte-identical no-op. If the patched text would not read back as exactly the saved value (or the existing file is malformed), the plain serialisation is written as before.
- `--scope project` (`vibe.toml`) keeps its existing decoration-merge writer.

## CORP-FMT-011 — `registry_layout_publish_report` schema; monorepo publish transfer classification

Status: **in development** (uncommitted integration change, 2026-11-08).

- The CORP-FMT-008 JSON report of `vibe registry publish` into `monorepo`/`localdir` is now a registered wire format: `schemas/registry_layout_publish_report.jtd.json`, `formats/REGISTRY.toml` `[format.cli-registry-layout-publish-report]` (epoch 1), generated type `vibe_wire::generated::registry_layout_publish_report::RegistryLayoutPublishReport`. `mode` (`monorepo` | `localdir`) and `action` (`created` | `replaced` | `unchanged`) are closed vocabularies; `commit` is optional (`x-default: null`). Publish paths do not consult source policy (none of them does; the target is the registry the operator named).


## CORP-FMT-012 — The index inside a `monorepo` / `localdir` registry (`_index/`) (Phase 2c)

Status: **in development** (uncommitted worker change, 2026-11-08).

- New in-registry layout: `<registry>/_index/` is a vibe-index data directory (`hello.json`, `repomd.json`, `primary.jsonl`, `primary.jsonl.gz`, `by-name/`, `by-cap/`, `by-purl/`), plus `_index/listing.txt` (line 1 `# vibe layout-registry listing 1`, line 2 `# journal sha256:<hex>` over the journal shards' names and bytes, then one `<group>/<name>/v<version>` per line, sorted) and `_index/.gitignore` (`/state/*`, `!/state/journal/`). The fact journal `_index/state/journal/<YYYY>-<MM>.ndjson` is **committed** (unlike a standalone vibe-index data dir, whose `state/` is never published). `_index` is not a legal group, so it never collides with a package; `vibe_core::layout_registry::version_dirs` skips it.
- Projection (`vibe_index::layout::project`, PROP-005 `#layout-registry`): tree entries (`source_url = <registry url>#<path>`, `source_ref` = monorepo branch / `v<version>` for localdir, `indexed_at`/`indexed_by` = the journal's `Initialised` record, or the Unix epoch and the reader's identity without a journal) folded with the journal; a `Published` fact is used (keeping its provenance) only while its `content_hash` equals the tree's; `Yanked`/`Buried` apply in journal order.
- Writers: `vibe registry publish` into `monorepo` now commits `_index/` with the version in one commit (`git add -f -A -- <version dirs>` so a package's own `.gitignore` cannot drop files; the race retry refetches, `git clean -fdx`es and re-projects); into `localdir` it rewrites `_index/` after the rename (listing last). A first publish appends `Initialised {registry: <[[registry]].name>, registry_url: <url>, naming: fqdn}`. An unchanged publish into a registry whose index is absent or stale now writes the index (commit `index: refresh`) instead of being a pure no-op.
- Readers: `vibe search` covers `monorepo`/`localdir` registries (hits `source: "index"`) and now reads the effective registry layers (`.vibe/registry.local.toml`, `vibe.toml`, `~/.vibe/registry.toml`), not only `vibe.toml`; `--registry NAME` errors name all three files. Short-name lookup (`MultiRegistryResolver::resolve_name_candidates`) now includes `localdir`/`monorepo` sources (before: they contributed nothing) — from `_index/by-name/<name>.json` when current, else the directory listing. `vibe registry test` reads the effective layers and appends `index: current|stale (<why>)…|absent` to a reachable layout registry's `note`. `vibe registry sync` reads the effective layers; a lock row of a `monorepo` registry is refreshed by one fetch of the clone (before: skipped as an unknown registry), a `localdir` row is skipped as "read in place".
- `vibe-index` refactor (no format change): `scanner::tree_entry::entry_from_tree` is now the one tree→`VersionEntry` projection used by the org scanner, `vibe-index add` and the layout scanner.
- No `vibe registry yank` exists; yanks enter a layout registry's journal through `vibe registry mirror` (carried from the source) or `vibe-index` tooling.

## CORP-FMT-013 — `vibe registry mirror` and the batch layout publisher (Phase 2d)

Status: **in development** (uncommitted worker change, 2026-11-08).

- New command `vibe registry mirror <source> --into <target> [--package G/N]… [--group G]… [--update-snapshots] [--dry-run] [--branch B] [--name N] [--path DIR]`. `<source>`: a configured registry name (any type). `<target>`: a `monorepo`/`localdir` registry name; a Git url (`://` or scp form) or bare-repository path → temp clone, one commit `mirror: <what> from \`<source>\` (<url>)`, push, one retry on non-fast-forward; an existing working copy → commit, no push, refused when `git status --porcelain --untracked-files=all` is non-empty (`PublishError::DirtyWorkingCopy`). A plain non-Git directory is refused with the hint to declare it as a `localdir` registry.
- Listing: source index `primary.jsonl` (`listing: "index"`; tombstones from `by-name/` files of names absent from `primary`), a layout source's index (`"layout"`), or the `v<semver>` tags of `--package` packages (`"tags"`; required when no index answers). Source reads go through the operation's controlled transport/source policy/remap (`vibe_package_source::registry_resolver`, new).
- Decisions per version (report `action`): `copied`, `unchanged` (same content hash — not fetched when the source records a hash), `snapshot-differs`, `updated` (`--update-snapshots`), `alarm` (frozen at source/target/manifest and different, or fetched bytes ≠ the source index's hash). Any alarm: exit non-zero, `ok: false`, nothing written.
- Provenance: a mirrored version's journal `Published` entry carries the upstream `source_url` (the source repository), `source_ref` (the tag) and `resolved_commit`; yanks become `Yanked`, tombstones `Buried` facts (only those the target does not already reflect).
- New JSON report `schemas/registry_mirror_report.jtd.json`, `formats/REGISTRY.toml` `[format.cli-registry-mirror-report]` (epoch 1), generated `vibe_wire::generated::registry_mirror_report::RegistryMirrorReport`.
- Library: `vibe_publish::layout_publish::publish_batch(BatchConfig { target, registry, items: [PublishItem {group, name, version, tree, provenance, replace}], facts, message, dry_run })` is the one publication operation (`publish` = a batch of one); new `LayoutTarget::WorkingCopy`, `LayoutRegistry`, `Provenance`, `BatchOutcome`, `read_target`. `LayoutPublishConfig` gains `registry: LayoutRegistry` (library API change). `vibe-publish` now depends on `vibe-index` (already linked by `vibe-cli`; the binary gains no dependency).

## CORP-FMT-014 — Site profile, `vibe self apply`, `self bootstrap --site` (Phase 7)

Status: **in development** (uncommitted worker change, 2026-11-08). Spec: `spec://org.vibevm.core/vibevm/common/PROP-019#site-profile`.

## CORP-FMT-035 — A launcher may name a command on PATH instead of a payload file

Status: **in development** (uncommitted worker change, 2026-11-09, codkit challenge). Spec: PROP-065 `#launcher-command`; refines PROP-059 `#launcher-paths`, `#proxy`.

- Manifest: `[[installer_options.launchers]] executable = "command:NAME"` — the spelling of `needs = ["command:NAME"]` — names a command resolved on PATH when the launcher runs, instead of a file in the payload. `NAME` must be a bare command name; a directory separator, a template variable (`$`), a `:`, whitespace or a control character is refused (``[[launchers]] `id` executable `…` must name a bare command after `command:` …``). The template grammar and the containment-under-`app_root` rule do not apply to such an executable. Packages using it declare `min_vibe_version = "1.0.12"`.
- Resolution (identical in `vibe app run` / `app launchers` and in the standalone `vibe-app-proxy`, which shares no code with `vibe-app`): the `PATH` entries in order; on Windows the name as it stands when it already ends in a listed `PATHEXT` extension, otherwise the name with each of them appended and never the bare name (Windows cannot start an extensionless file, and a payload directory on PATH may hold one — Node ships `npm` beside `npm.cmd`); `.COM;.EXE;.BAT;.CMD` when the environment carries no `PATHEXT`; the first executable file winning. Exactly one file is never chosen — the running proxy's own image — so a proxy for `NAME` whose launcher runs `NAME` falls through to the host's own instead of re-entering itself. Its siblings in that directory are chosen like any other entry, so a runtime the user installed by name (its public commands are proxies in the same `opt/bin`) is what such a launcher finds.
- Plan: a launcher naming a command the host does not have adds a warning — ``launcher `X` runs the command `NAME`, which is not on PATH; the installation succeeds, but the launcher needs `NAME` when it runs …`` — and the install proceeds. The `vibe-app-plan/1` document is unchanged (the text is the warning block that already existed for skipped agent steps).
- Launch failure: `vibe-app-proxy: command `NAME` is not on PATH, so launcher `X` cannot run; put a `NAME` on PATH, or install an application package whose public commands include it (`vibe install -g GROUP/NAME`)`, exit 127.
- `vibe app launchers`: such a row is `available` with the located file as its `executable.resolved`, or ``unavailable: command `NAME` is not on PATH``. Its `executable.base` is `"path"` instead of `"app_root"` (the field is free-form text in `vibe-app-launchers/2`; the wire schema is unchanged). `describe` and `app installers` report the `command:NAME` spelling unchanged.
- The application index format is unchanged: the `command:NAME` spelling travels in the launcher's existing `executable` string. An older vibe reading such a record resolves it as a relative payload path and reports the launcher unavailable; it never runs the wrong file.

## CORP-FMT-036 — `pac = "system"` is resolved by vibe on Windows; `[proxy] revocation`

Status: **in development** (uncommitted worker change, 2026-11-09). Spec: PROP-068 `#proxy-system`, `#proxy-revocation`; amends `#proxy-px`, `#proxy-doctor`.

- `[proxy] pac = "system"` no longer means "px, detect it yourself". vibe reads the logged-in Windows user's proxy configuration and starts px with the explicit `--pac=<url>` it found — or `--proxy=<host:port>` when the configuration names a fixed proxy instead. Before, px was started with no `--pac` at all, and on a managed desktop its own detection finds nothing: the PAC URL lives inside the `DefaultConnectionSettings` blob of the user's `Connections` key (flags `0x0D` = direct | auto-config URL | auto-detect) while the plain `AutoConfigURL` value is absent.
- Spelling: `system` stays canonical and is what every report prints; `windows` is accepted as an alias for it (`PacSource::SYSTEM_SPELLINGS`). Both were already accepted by the site profile's validation, so no profile needs changing.
- Resolution order, first hit wins, read per operation when px starts: the group-policy `AutoConfigURL` (`HKCU`, then `HKLM`, under `Software\Policies\Microsoft\Windows\CurrentVersion\Internet Settings`) → `WinHttpGetIEProxyConfigForCurrentUser` → (only when that answers nothing) the `AutoConfigURL` value and then the `Connections\DefaultConnectionSettings` blob of `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings`, parsed directly → `WinHttpDetectAutoProxyConfigUrl(DHCP | DNS_A)` when auto-detection is on and no URL was named → the configured proxy server as px's upstream (`https=` over `http=` over a bare `host:port`; `socks`/`ftp` are left out) with that setting's bypass list as px's `--noproxy` when `[proxy] no_proxy` names none. A configured `no_proxy` or `upstream` outranks what Windows said.
- Nothing found: px is **not** started, and the refusal names every setting that was read with what each said, plus the fix (``set `[proxy] pac = "<your PAC URL>"` or an absolute PAC file path, or `[proxy] upstream = "host:port"```). A reader that fails is listed among the settings checked. New `PxError::SystemProxy`.
- Reporting: `vibe dl --test-proxy`'s `pac` row and `vibe self doctor --network`'s `pac` check now read `system → https://… (from user Internet Options)` (or `system → proxy host:port · bypass … (from …)`), instead of "px reads Windows Internet Options / WPAD"; a PAC URL that came from the settings is then fetched and checked like any other. `vibe self apply --show` gains `pac_resolved` in `vibe-self-apply/1` (`proxy_row`) and prints it after the `pac` line. Off Windows `pac = "system"` keeps its existing refusal and its `self apply` warning.
- Library API: new `vibe_core::net::system_proxy` (`WindowsProxySource` seam, `resolve_with`, `install_source`/`installed_source`, `SystemProxy`, `SystemProxyOrigin`, `SystemProxyError`, `IeProxyConfig`, `ConnectionSettings`, `parse_connection_settings`, `pick_upstream`, `bypass_list`, `CONNECTION_*`) and `vibe_net::system_proxy::{resolve, host_source}` (the Windows reader, which needs `unsafe`). `vibe-net` gains a `cfg(windows)` `windows-sys` dependency (`Win32_Foundation`, `Win32_Networking_WinHttp`, `Win32_System_Registry`).
- New `[proxy] revocation = "check" | "best-effort" | "off"` (default `check`, which adds nothing — today's behaviour exactly), switchable by `VIBEVM_PROXY_REVOCATION` over the user's file over the site profile. `off` adds `-c http.schannelCheckRevoke=false` to a child `git` fetching over HTTPS, `best-effort` adds `-c http.schannelCheckRevoke=best-effort`. It exists because a TLS-inspecting corporate CA publishes CRL/OCSP endpoints that the inspected network cannot reach, so Windows schannel fails the handshake — the failure `curl` needs `--ssl-no-revoke` for. The certificate chain is still verified; only the revocation lookup is relaxed.
  - `best-effort` is Git for Windows' own third value for that key (2.26 and newer, where it is that build's default); an upstream git parses the key as a boolean and would refuse the word, so vibe sends it only to a git whose `git --version` reports a Git for Windows 2.26+ (asked at most once per process, only for `best-effort`, only on Windows) and otherwise falls back to `off` with a warning. git honours the key only when `http.sslBackend` is `schannel`; vibe does not set that, so an OpenSSL build is unaffected, as is every non-Windows host (where the key adds nothing at all).
  - vibe's own HTTP clients are rustls and perform no online revocation check, so the key does not reach them. px is unaffected: its libcurl uses schannel on Windows but exposes no revocation option, and for an HTTPS target px only tunnels (`CONNECT`) — the handshake that fails this way is the client's own.
  - A failure that looks like one (`CRYPT_E_NO_REVOCATION_CHECK` / `0x80092012`, `CRYPT_E_REVOCATION_OFFLINE` / `0x80092013`, "the revocation function was unable to check…") is classified `revocation` by `vibe_net::doctor::cause_of` and reported as a TLS failure by `vibe dl` (`dl_tls`, exit 13 — no new exit code); the fix line names the key. New `vibe_net::doctor::REVOCATION_MARKERS`.
  - `vibe self apply --show` gains `revocation` and `revocation_origin` in `proxy_row` and prints a `proxy revocation:` line when a layer asked for one; `vibe dl --test-proxy`'s `config` row says `· revocation <value> (<layer>)` likewise. Library API: `vibe_core::user_config::RevocationCheck`, `ProxyConfig::revocation`, `vibe_core::net::effective_revocation`, `ProxyRoute::{revocation, revocation_origin, with_revocation}`, `vibe_net::git::{revocation_config, version_takes_best_effort, for_remote_with}`.

## CORP-FMT-037 — Whole payload directories on PATH (`path_dirs`) and the per-slot off switch

Status: **in development** (uncommitted worker change, 2026-11-09, Node/npm challenge). Spec: PROP-059 `#path-directories`, `#slot-off`; amends `#alternatives`, `#proxy`, `#session-selection`; reuses PROP-065 `#env-step`.

- Manifest: new `[[installer_options]] path_dirs = ["bin"]` — an explicit opt-in naming payload directories to expose **whole** on the user's PATH, in search order. Each entry is a payload-relative directory template with the launcher-`executable` rules (containment under the application root, no `..`, no absolute literal, `.` names the root itself) minus the variables that leave the payload: `$project_root` and `$vibe_home` are refused with a message naming `$app_root`, `$app_bin` and `.`. A duplicate entry is refused. An option may declare `public_commands`, `path_dirs`, or both. It exists because a runtime's own tooling writes new commands into its own directory *after* installation — `npm install -g` puts them beside `node` — which a per-command proxy set fixed at install time can never reach.
- Exposure: one link per slot and per declared directory index at `<settings>/opt/paths/<slot>/<i>` (`<store>/paths/<slot>/<i>` under `[self] install_root`, the sibling of the proxy `bin`). POSIX writes a symlink; **Windows writes a directory junction** through `FSCTL_SET_REPARSE_POINT`, because a Windows symlink needs `SeCreateSymbolicLinkPrivilege` while a junction needs no privilege and no Developer Mode. A junction stores a local absolute path, so a payload on a UNC/network path is refused with a message naming `vibe storage move` (new code `path_link_target_unsupported`).
- The link points at the slot's **default** provider's directory, so two providers of one slot never collide and `vibe app use` repoints a link instead of rewriting PATH. The number of link directories of a slot is the widest `path_dirs` any exposed provider declares, so switching between providers that declare different counts never changes what is on PATH. The links are derived from the index and reconciled after every index write, which is what repoints them on: first install of a slot, `vibe app use`, uninstall, `expose` / `hide`, update, rollback, modify, a storage move, an import and a project materialisation. A hidden installation exposes no link. The links are repointed in place (sibling + rename on POSIX; remove + create under the home mutation lock on Windows).
- Ownership, like `applications/proxies.toml`: new `<home>/applications/paths.toml` (`schema = 1`, `[[link]] slot` + `index` + `target`) records every link vibe wrote. A real file or directory at a link's name — or a link vibe has no record of — refuses the whole reconciliation **before the first change**, with new code `foreign_path_link`; nothing foreign is ever repointed or removed.
- Durable PATH, through PROP-065 `#env-step`: the slot's link directories are added to the user's durable PATH when the slot first gains `path_dirs` and removed exactly when its last such provider goes — `HKCU\Environment` on Windows (kind preserved, change broadcast), the managed `<settings>/env.sh` / `env.fish` lines on POSIX. The lines are tagged `slot:<name>` instead of an installation key, and the applied entries are recorded per slot in the index so removal takes out exactly them. They are applied from the last declared directory to the first, because every implementation *prepends*: directory `0` therefore ends up first on PATH, **ahead of `opt/bin`** and ahead of the system directories — a payload command wins over a per-command proxy of the same name and over the program it replaces.
- New off switch: `vibe app use SLOT --none` removes the slot's links and the proxies of its public commands, so every lookup falls through to the system program; the PATH entries stay, so nothing has to be re-sourced. `vibe app use SLOT --default` puts both back at the remembered default, and `vibe app use SLOT KEY` both switches the slot on and makes KEY the default. Installations, index records and the remembered default are kept throughout. Passing a key together with a switch, or neither, is a usage error naming the three spellings.
- Session: `vibe shell --use SLOT=KEY` for a `path_dirs` slot prepends that installation's **real** payload directories, shadowing the global link without repointing it. `vibe shell --use SLOT=none` starts the child with exactly that slot's link directories removed from PATH and `VIBE_APP_USE=SLOT=none` set; a proxy of an off slot (globally or for the session) then executes the next same-named command on PATH *after its own directory*, reusing the own-image exclusion of `command:NAME` resolution. The chain it already walked travels in `VIBE_APP_PROXY_SKIP` (internal plumbing between proxy images), so a second proxy for the same slot keeps moving forward and the walk terminates. With no other such command the proxy exits 127 naming `vibe app use SLOT --default`.
- Reports: `vibe app alternatives --json` gains `off` (slot level) and `path_dirs` per provider, and its text says `[off: the system program answers; …]`; `vibe app list --json` gains `slot_off` and `path_dirs` per row, and its text shows the state words `slot off` and `path dirs`; `vibe app describe --json` gains `pathDirs` per installer option; `vibe app home` lists each slot's link directories; `vibe self doctor` reports every link directory with its target and whether it is on PATH, exactly as it does for the shim directory, and `--json` gains `application_path_dirs[] {slot, dir, on_path, target}`.
- `command:NAME` launchers (CORP-FMT-035) keep working through a link directory: resolution is PATH-based and a junction or symlink resolves to the payload file.
- **Wire epoch.** `schemas/application/e5/index.jtd.json`, protocol tag `vibe-user-applications/6` (`formats/REGISTRY.toml`: `application-index` epoch 4 → 5, corpus `formats/corpora/application/e5`; the previous epoch is retained as `application-index-v5`). New members: `installations.<key>.pathDirs` (optional, omitted when empty) and, per slot, `off` (optional, omitted when false) and `pathEnv` (optional, omitted when empty). - Test seam (Windows only, PROP-019 `#path`): `$VIBEVM_ENV_REGISTRY_SUBKEY` names another `HKEY_CURRENT_USER` subkey for every durable-environment read and write, so a test on a real Windows machine never touches the user's own `Environment`. Unset, nothing changes.

A home that never uses `path_dirs` or the off switch is byte-identical to before.

## CORP-FMT-038 — `vibe tool px exec | serve | status`: vibe's px, lent to another tool

Status: **in development** (uncommitted worker change, 2026-11-09). Spec: PROP-068 `#proxy-tool`.

- New command group `vibe tool <tool>`, with one tool today: `px`.
- `vibe tool px exec [--port N] [--env NAME=VALUE]… [--proxy-env NAME]… [--allow-direct] -- <command> [args…]` starts the vibe-managed px exactly as vibe's own operations do — the same effective `[proxy]` table and its layers, the same `pac` resolution (including the Windows `system` resolution of CORP-FMT-036), `upstream`, `px_port`, `px_args`, `px_path`, the same px companion lookup, and the same lifetime (the invocation's operation resource, killed and reaped by the existing supervisor / job object after the child exits) — and runs `<command>` through it.
- The child receives `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY`, `http_proxy` = `http://127.0.0.1:<port>` and `NO_PROXY` / `no_proxy` = `localhost,127.0.0.1,::1` plus `[proxy] no_proxy`. `--proxy-env NAME` also sets `NAME` to that URL (for `npm_config_proxy`, `PIP_PROXY` and friends, which cannot be told the address in advance); `--env NAME=VALUE` adds a literal variable and is applied last, so a caller can override any of the above.
- `<command>` is resolved on PATH as the operating system resolves it — on Windows with `PATHEXT`, and never the bare extensionless name, so `npm.cmd` is found and an extensionless `npm` beside it is not started. A name containing a separator is a path and is run as written. A name that is not on PATH is a refusal naming it, and px does not start.
- stdin, stdout, stderr and the terminal's signals belong to the child and vibe writes nothing to them, so `exec` can stand inside a pipeline (`pxpip freeze > requirements.txt` holds the child's bytes alone); the route it lent is named on stderr only under `--verbose`. **The child's exit code is vibe's** — so a wrapper fails exactly as the tool it wraps does. A child killed by a signal answers 130 when the invocation was stopped and 1 otherwise, and a command that is not on PATH answers **127**, the shell's own code for it.
- `mode = "explicit"` lends the configured proxy URL as the table wrote it (a bare `http://host:port` without the trailing `/` that parsing adds) and starts no px (a credential in it travels in the environment, never in a printed line). No proxy configured at all is a refusal naming `--allow-direct`, which runs the child with the proxy variables removed rather than inherited.
- `vibe tool px serve [--port N] [--json]` runs px in the foreground until the invocation is stopped, printing the listen address, the resolved PAC or upstream and the bypass list. New wire document `vibe-px-serve/1` (`url`, `pac`, `upstream`, `no_proxy`) — printed by the command, not a registered schema.
- `vibe tool px status` is byte-identical to `vibe self px status`.
- `--stop-file` is now accepted for `vibe tool …` (it was project install/update, `registry publish` and `dl`).
- Library API: `vibe_core::net::ProxyRoute::{explicit_urls, with_px_port}`.

## CORP-FMT-039 — `pac = "system"` on Linux and macOS

Status: **in development** (uncommitted worker change, 2026-11-09). Spec: PROP-068 `#proxy-system` (extended), `#proxy-px` (amended); PROP-019 `#site-profile` (the Windows-only note drops `proxy.pac`).

- **No wire or JSON shape change.** `vibe-self-apply/1`'s `proxy_row.pac_resolved` (CORP-FMT-036) keeps its type and its optionality; what changes is the set of values it can carry off Windows — a resolution phrase instead of only the `not Windows` refusal. `vibe dl --test-proxy`'s `pac` row and `vibe self doctor --network`'s `pac` check likewise. No schema, no epoch, no corpus.
- `[proxy] pac = "system"` (alias `windows`) is accepted and resolved on every host. `ProxyRoute::from_config` no longer refuses it off Windows, and `SiteProfile::windows_only_notes` no longer reports `proxy.pac` as Windows-only, so a site profile that selects auto validates and applies everywhere with no warning.
- macOS order, first hit wins: the `SCDynamicStoreCopyProxies` dictionary of the current network service (obtained as `scutil --proxy`) — `ProxyAutoConfigEnable` + `ProxyAutoConfigURLString` → `--pac`; `ProxyAutoDiscoveryEnable` → WPAD; `HTTPSEnable` + `HTTPSProxy` + `HTTPSPort`, else the `HTTP*` triple → `--proxy` (a missing port reports `:80`); `ExceptionsList` → `--noproxy`. Then the environment, then the refusal. An `…Enable` that is off is ignored, as macOS ignores it.
- Linux / other Unix order, first hit wins: (1) GNOME — `gsettings list-recursively org.gnome.system.proxy`: `mode 'auto'` → `autoconfig-url` (empty → WPAD), `mode 'manual'` → the `https` child's `host`/`port` else the `http` child's, `ignore-hosts` → bypass; (2) KDE — `[Proxy Settings]` of `$XDG_CONFIG_HOME/kioslaverc` (else `$HOME/.config/kioslaverc`): `ProxyType` 2 → `Proxy Config Script`, 3 → WPAD, 1 → `httpsProxy` else `httpProxy` (KDE's `http://host port` spelling accepted), 4 → defer to the environment, `NoProxyFor` → bypass; (3) the environment — `https_proxy`/`HTTPS_PROXY`, then `http_proxy`/`HTTP_PROXY`, then `all_proxy`/`ALL_PROXY`, reduced to `host:port` so a credential in the value is dropped and never printed, `no_proxy` → bypass, a loopback value skipped as vibe's own px; (4) nothing → refusal.
- WPAD discovery, for a source that asks to auto-discover: `http://wpad.<domain>/wpad.dat` for each DNS search domain and the FQDN (`/etc/resolv.conf` `search`/`domain`), walking up the labels, **never to a public suffix** (at least two labels remain), at most 6 candidates, fetched directly with a 3 s timeout each, first `200` whose body declares `FindProxyForURL` wins. A discovery that finds nothing is reported and the order continues.
- Reporting: the `system → … (from <source>)` phrase gains the sources `GNOME settings`, `KDE settings`, `macOS network settings`, `environment https_proxy` / `http_proxy` / `all_proxy` and `WPAD discovery`. The refusal names every source that was looked at with what each said.
- Error-type change: `SystemProxyError::NotWindows` → `SystemProxyError::Unsupported` ("neither Windows, macOS nor another Unix"), and `NotConfigured` gains `looked_in` and `configure_hint` (`&'static str`) so each host kind names its own subject and its own way to configure a proxy. **The Windows `NotConfigured` message is byte-identical to CORP-FMT-036's.**
- Library API: new `vibe_core::net::{UnixProxySource, resolve_unix_with, resolve_mac_with, install_unix_source, installed_unix_source, install_mac_source, installed_mac_source, looks_like_pac}`; new `vibe_net::system_proxy::{unix_host_source, HostKind, FIXTURE_ENV, KIND_ENV}`. `WindowsProxySource`, `resolve_with`, `install_source` and `SystemProxy`/`SystemProxyOrigin` are unchanged apart from the new origin variants. No new crate dependency (the macOS reader runs `scutil`; the WPAD fetch reuses the `reqwest` blocking client already linked).
- Test seam: `$VIBEVM_SYSTEM_PROXY_FIXTURE` names a directory whose `gsettings`, `kioslaverc`, `scutil-proxy`, `dns-domains` and `wpad` files stand in for this machine's desktop, and `$VIBEVM_SYSTEM_PROXY_OS` (`unix` / `macos` / `windows`) names the order to run — so a whole `vibe` can be driven over a stated configuration on any host and no test reads the developer's own desktop or network. Both unset, nothing changes. A test's fixture answer for WPAD is honoured only when it is one of the generated candidates.

## CORP-FMT-041 — TLS is verified by the operating system's own verifier; `[tls] extra_ca` is additive on top of it

Status: **in development** (uncommitted, 2026-11-11). Spec: PROP-068 `#proxy-trust` (rewritten), `#proxy-git`, `#proxy-doctor`, `#dl` (amended); PROP-019 `#site-profile` (`[tls]`, `SITE-PROFILE-LAYER`). Wire formats `vibe-dl/1` (`schemas/dl_report.jtd.json`) and `cli-self-apply-report` (`schemas/self_apply_report.jtd.json`), both additive, epoch unchanged, corpus `none`.

- **The verifier changed.** Every TLS client vibe builds is now given one pre-configured `rustls` configuration whose verifier is `rustls-platform-verifier` (0.7.1, published 2026-09-24; it asks for rustls `^0.23.27`, rustls-webpki `^0.103` and windows-sys `>=0.52,<0.62`, all of which this lock file already satisfies at 0.23.39 / 0.103.13 / 0.61.2, so it adds no second copy of any of them). `reqwest`'s own root handling no longer runs: `route_in` hands the configuration over with `use_preconfigured_tls`, which is the single construction point for downloads, `vibe dl`, the `--test-proxy` probe, the px reachability check, the registry HTTP clients and the release fetch.
- **What this changes in practice.** On Windows chains are built by the CryptoAPI chain engine over every store the machine and the user have — the intermediate `CA` stores included — with enterprise policy and AIA issuer fetching. A corporate chain `site ← inspecting CA ← subordinate CA ← root CA` whose two middle certificates live only in `CA` now verifies with no configuration at all; before, only root stores were read and it failed `dl_untrusted_certificate`. On macOS the Security framework decides. Off those two the behaviour is as before (webpki over the platform bundle) **and** vibe still consults the public roots it ships; on Windows and macOS it no longer does, because those platforms run a root programme of their own, including the roots they distrust. Revocation is unchanged for vibe's own clients (rustls checks nothing online) and `best-effort` in the Windows engine (end certificate checked, unretrievable state accepted), which matches the existing `[proxy] revocation` default for a child `git`.
- **New config key `[tls] extra_ca`** in `config.toml` and in a site profile: a string **or** a list of strings; each entry is a certificate file (PEM with one or many certificates, or a single DER) **or a directory**, whose `*.pem`, `*.crt` and `*.cer` files are all read in name order. `[proxy] ca_file` keeps its exact meaning and shape and is the first entry of the effective list; the two are merged without repeats (`vibe_core::user_config::effective_extra_ca`). Each key layers on its own key, user over site, as every other key does. An entry that cannot be read, holds no certificate, or is a directory with no certificate file is a configuration error naming the path and the fix.
- **Extra certificates are additive and can pin.** An authority among them is an extra trust anchor (so an intermediate the server never sends completes a chain); any of them, authority or not, is also an exact-byte pin for a server's own certificate — the only way a self-signed server certificate can be trusted, since webpki refuses an end-entity certificate as an anchor. A pin is honoured only when the presented leaf's DER is byte-identical, the certificate is current, and it is for the host contacted (`subjectAltName`, or the common name when there is no `subjectAltName`; one leading wildcard label).
- **Wire, `vibe-dl/1`:** `tls.trusted_by`'s value set changes from `system` | `ca_file` to `system` | `extra_ca` | `pinned`, and the new optional `tls.trusted_by_source` carries the configured file or directory that accepted the chain (absent for `system`). A reader that only passed the string through is unaffected; one that compared it to the literal `ca_file` must now compare to `extra_ca`.
- **Wire, `cli-self-apply-report`:** `proxy_row` gains `extra_ca` (array of strings, always emitted, possibly empty) — the whole effective list. `proxy_row.ca_file` is unchanged in type and meaning (the one key as written).
- **Child `git`.** `http.sslCAInfo` is passed only when extra certificates are configured, and the bundle it names now carries this machine's own certificates first: on Windows everything in `ROOT` **and** `CA` of both `CurrentUser` and `LocalMachine` (the previous bundle read only `CurrentUser\ROOT`, so naming a CA file silently took the intermediates away), elsewhere the platform bundle. Windows names the backend explicitly, `-c http.sslBackend=schannel -c http.schannelUseSSLCAInfo=true`: Git's own documentation says a bundle "would override the Windows Certificate Store", and `http.sslBackend=openssl` is documented as ignored when the build's libcurl cannot choose a backend at runtime. **New file location:** the bundle is content-addressed at `<settings-dir>/tls/<sha256>.pem` (it used to be written per operation into a temporary directory), written through a temporary file in the same directory.
- **Human output.** The `TLS` row of `vibe dl` reads `trusted by system`, `trusted by extra CA: <file>` or `pinned self-signed: <file>` (it was `trusted by system` / `trusted by ca_file`). The fix of `dl_untrusted_certificate` is now per operating system: the PowerShell export over `Root` and `CA` of both Windows store locations, `security find-certificate` on macOS, the distribution's CA directory elsewhere — and it names `[tls] extra_ca`. `vibe self doctor`'s `trust` row counts the certificates in the machine's own stores and the extra anchors and pins. `vibe dl --test-proxy`'s `config` row prints `extra_ca <paths>` instead of `ca_file <path>`. Three `vibe dl` golden captures change accordingly.
- **Default log filter.** With `$VIBE_LOG` unset the filter is `warn,rustls_platform_verifier=off`: that crate logs every refused chain at ERROR through the `log` bridge, including the trial verifications the probe makes to work out which part of the trust set accepted a server, which would otherwise print an error line on a successful download. `$VIBE_LOG`, when set, still decides everything.
- **Library API:** new `vibe_net::{TrustSet, TrustSource}` and `vibe_net::trust::system_certificates`; `vibe_net::git::bundle_config`; `vibe_core::net::ProxyRoute::{extra_ca, with_extra_ca}`; `vibe_core::user_config::{TlsConfig, ExtraCa, effective_extra_ca}`; `vibe_core::settings::tls_cache_dir`. Removed: `vibe_net::NetworkSession::extra_roots`, `vibe_net::probe::TrustSource::{CaFile, as_str}` (the enum moved to `vibe_net::trust` and gained `kind`/`source`/`describe`). `vibe_net::http::RouteBuilder::with_root` is replaced by `with_tls`. `ManagedHttpClient::captured`/`captured_in` take the captured registry trust as PEM bytes rather than as `reqwest::Certificate` values, so that trust can replace the installation's rather than being silently ignored under a pre-configured TLS configuration.
- **New dependencies of `vibe-net`:** `rustls-platform-verifier` 0.7.1, `sha2` (workspace), and `schannel` 0.1.29 on Windows only (already in the lock file as `rustls-native-certs`'s own dependency).
