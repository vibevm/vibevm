## Ответы

### 1. Рабочая команда floor из корня пакета

**`vibe bin exec typescript-ai-native -- floor` работает, но одной сборки из
корня хоста для этого мало.** Проверено три предусловия, каждое обязательно:

1. **`--assume-yes` при сборке.** Группа `org.vibevm.ai-native` не в
   allow-list, поэтому `vibe bin build typescript-ai-native` падает с
   `EXIT=1` (см. свидетельство С-1). Рабочая форма —
   `target/debug/vibe.exe bin build typescript-ai-native --assume-yes`
   (из корня хоста: 28 с общего времени, из них `cargo build --release`
   24.59 с; собирает 10 крейтов слота, артефакт —
   `vibevm/vibedeps/org.vibevm.ai-native.typescript-ai-native-lang/1.0.0/target/release/typescript-ai-native.exe`,
   печатается `vibe bin path typescript-ai-native`).
2. **Lockfile схемы 7 в самом пакете.** `bin exec` резолвит через lockfile
   ТОГО проекта, из корня которого запущен. Скопированный `research/ts-demo`
   несёт `vibe.lock` схемы 6 → отказ (С-2). Лечится `vibe install` в пакете
   (6 с, offline, из `vibevm/vibepacks`).
3. **Сборка инструмента в слоте самого пакета.** После `vibe install`
   `bin exec` снова отказал тем же consent-текстом, что и в пункте 1:
   хостовая сборка не видна пакету, у него свой
   `vibevm/vibedeps/.../1.0.0/target/release/`. После
   `vibe bin build typescript-ai-native --assume-yes` **из корня пакета**
   (23 с) `vibe bin exec typescript-ai-native -- floor` отработал за 5 с с
   кодом выхода **0** (С-3).

Итоговая последовательность для web-пакета, который сам является vibe-проектом:

```sh
vibe install --path . --registry <repo>/vibevm/vibepacks --offline --assume-yes
vibe bin build typescript-ai-native --assume-yes      # из корня пакета, ~25 с
vibe bin exec typescript-ai-native -- floor           # из корня пакета
```

**Более дешёвые маршруты (проверены, все три дают `all green`, код 0):**

- A. Готовый бинарник хоста из корня пакета:
  `<repo>/vibevm/vibedeps/org.vibevm.ai-native.typescript-ai-native-lang/1.0.0/target/release/typescript-ai-native.exe floor`
  — не требует ни `vibe install`, ни второй сборки слота.
- B. Тот же бинарник с `--path`, из любого каталога:
  `… typescript-ai-native.exe floor --path <пакет>` (есть и `--quiet`,
  и `--keep-going`).
- C. Маршрут из boot-сниппета:
  `cargo run --manifest-path <repo>/vibevm/vibedeps/org.vibevm.ai-native.typescript-ai-native-lang/1.0.0/Cargo.toml -p typescript-ai-native-cli --bin typescript-ai-native -- floor --path <пакет>`
  — 19 с (отдельный debug-профиль в том же слоте).

Для web-пакета внутри этого репозитория маршрут A/B строго дешевле: слот
хоста уже собран, второй копии `vibedeps/` не нужно.

### 2. Семь шагов floor на копии `research/ts-demo`

Порядок и имена шагов зафиксированы в коде —
`vibevm/vibedeps/org.vibevm.ai-native.typescript-ai-native-lang/1.0.0/crates/typescript-ai-native-cli/src/floor.rs:26-34`:
`prettier` → `tsc` → `tests` → `eslint` → `conform` → `specmap` → `test-gate`.
Что делает каждый шаг (по `floor.rs` и наблюдаемому выводу):

| шаг | команда | периметр |
| --- | --- | --- |
| `prettier` | `node_modules/.bin/prettier --check <roots>` | `[typescript].roots` из `conform.toml` |
| `tsc` | `node_modules/.bin/tsc --noEmit` | корневой `tsconfig.json` пакета (без `-p`) |
| `tests` | `node --test <root>/**/*.test.ts <root>/**/*.spec.ts` | те же roots; globs захардкожены в `tools.rs:56` |
| `eslint` | `node_modules/.bin/eslint <roots>` | те же roots |
| `conform` | встроенный `typescript-ai-native-conform check` | `conform.toml` + baseline |
| `specmap` | встроенный `specmap --check` (байтовое сравнение индекса + orphan-ratchet) | `specmap.toml` |
| `test-gate` | `node --test --test-reporter=tap` + diff против `discipline/registry/tests-baseline.json` | те же roots |

Инструменты ищутся **только** в `node_modules/.bin` пакета
(`tools.rs:15-44`, на Windows через `.cmd`-шим); отсутствие инструмента — не
пропуск, а падение шага с рецептом установки.

**Что реально происходит на нетронутой копии.** Прогон
`floor --keep-going` на копии `research/ts-demo`, воспроизводящей раскладку
репозитория (тот же относительный путь до `vibevm/vibepacks/...`, `npm ci` по
закоммиченному lock): **красных шага три — `prettier`, `eslint`, `specmap`**
(С-4, С-5, С-6). Зелёные: `tsc`, `tests` (5 тестов), `conform`
(1 находка, 1 заморожена в baseline, 0 новых), `test-gate`.

Причины:

- `prettier`: `research/ts-demo/src/main.ts:11` — строка импорта длиной 81
  символ при `printWidth` 80 (`.prettierrc.json` пуст, `{}`). Lock пинует
  ровно ту же prettier 3.9.4, что стоит у меня, то есть это не дрейф версий.
- `eslint`: плагин `@org.vibevm/eslint-plugin-ai-native` подключён как
  `file:`-зависимость и материализуется симлинком на
  `vibevm/vibepacks/.../tools/eslint-plugin-ai-native`; node резолвит импорты
  плагина от его realpath, где нет ни своего `node_modules`, ни родительского
  с `@typescript-eslint/utils` → `ERR_MODULE_NOT_FOUND` (С-5). Лечится
  `npm install` внутри каталога плагина (проверено: после этого шаг зелёный).
- `specmap`: `export function compose` в `src/main.ts` не помечен
  ни `@implements`, ни файловым `@scope` → orphan-ratchet блокирует (С-6).

После трёх исправлений в scratch (prettier --write; `npm install` в каталоге
плагина; `@scope spec://ts-demo/PROP-001#root` в шапке `src/main.ts` +
`typescript-ai-native specmap` для перевыпуска индекса) floor даёт
`floor: all green (7 step(s) run, 0 disabled by policy).`, код выхода 0.

**Отключение шагов политикой** (для web-пакета это ключевой рычаг):
в `conform.toml` секции `[[typescript.floor_disable]]` с полями `step` и
`reason`; каждая печатается на каждом прогоне, неизвестное имя шага — жёсткая
ошибка со списком допустимых (С-9).

### 3. Обязательные флаги `tsconfig` и как floor их проверяет

**Список из GUIDE §1** (`…/vibevm/vibespecs/typescript/GUIDE-AI-NATIVE-TYPESCRIPT.xml:51-55`),
точные имена:

- `"strict": true` — включает восемь базовых (`strictNullChecks`,
  `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`,
  `noImplicitAny`, `noImplicitThis`, `alwaysStrict`,
  `useUnknownInCatchVariables`);
- сверх `strict`, всё обязательное: `noUncheckedIndexedAccess`,
  `exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`,
  `noImplicitOverride`;
- «ловцы дефектов»: `noUnusedLocals`, `noUnusedParameters`,
  `noFallthroughCasesInSwitch`, `noImplicitReturns`,
  `"allowUnreachableCode": false`;
- флаг стирания: `erasableSyntaxOnly`.

Boot-сниппет стека (`…/vibevm/vibespecs/boot/20-stack-typescript-ai-native-lang.xml:29-32`)
называет «строгим полом» сокращённую четвёрку: `strict` +
`noUncheckedIndexedAccess` + `exactOptionalPropertyTypes` +
`erasableSyntaxOnly`; ослабление любого обязательного флага требует
`deviates` + причину.

**`conform.toml` про `tsconfig` не знает ничего.** Полный набор ключей
таблицы `[typescript]` (структура `TsConfig`,
`…/crates/vendor/core-ai-native-conform/src/config.rs`): `roots`,
`skip_dirs`, `exclude_substrings`, `gated`, `exempt` (таблицы-массивы с
`unit`/`reason`), `cells_dir`, `seam`, `composition_root`, `floor_disable`.
Корневые ключи: `max_file_lines` (600), `invariant_comment_markers`,
`invariant_comment_min_file_lines`, `sarif_reports`. Ни одного ключа про
компиляторные флаги.

**Как floor их проверяет: механической проверки нет.** Поиск имён флагов по
всему слоту даёт только GUIDE, boot-сниппет, SKILL терраформа и тестовую
фикстуру `tools/ts-oracle/test/fixtures/proj/tsconfig.json` — ни одной
проверки в коде. Эксперимент: я подменил `tsconfig.json` копии на
заведомо ослабленный (`"strict": false`, без трёх флагов пола) и прогнал
`floor --keep-going` — **ни один шаг не сказал ни слова про tsconfig**
(С-7). Шаг `tsc` там всё же покраснел, но по другой причине: без
`strictNullChecks` перестало сужаться дискриминированное объединение
демо-кода (`TS2339: Property 'error' does not exist…`). То есть флаги
работают только через то, что после них отвергает `tsc --noEmit` (шаг 2), а
сообщение при нарушении — обычная диагностика TypeScript, например для
`enum` под `erasableSyntaxOnly`:
`src/cells/probe/index.ts(2,13): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.`
Дисциплинарный статус `tsconfig` держится ревью и картами («versioned
artifact of the discipline», GUIDE §1), не гейтом.

### 4. Совместимость с Qwik 2.x

Базовый `tsconfig` Qwik 2 взят из стартера апстрима
(`https://raw.githubusercontent.com/QwikDev/qwik/main/starters/apps/base/tsconfig.json`,
получен WebFetch): `jsx: "react-jsx"`, `jsxImportSource: "@qwik.dev/core"`,
`moduleResolution: "Bundler"`, `module: "esnext"`, `target: "es2020"`,
`lib: ["es2022","DOM","WebWorker","DOM.Iterable"]`, `allowJs`,
`resolveJsonModule`, `allowImportingTsExtensions`, `esModuleInterop`,
`isolatedModules`, `incremental`, `outDir: "tmp"`, `noEmit`, `skipLibCheck`,
`paths: {"~/*": ["./src/*"]}`, плагин `typescript-plugin-css-modules`.
Имя `@qwik.dev/core` подтверждено установкой: latest = 2.0.0-beta.43.
Находки P0-O5 (`findings/A0.10-qwik-probe.md`) на момент работы не было.

**Объединённый `tsconfig` собран и проверен: `tsc --noEmit` даёт код 0** на
пробе из двух компонентов (`component$`, `useSignal`, `useStore`, `Slot`,
брендированный проп, `process.env` в композиционном корне). Полный файл —
`…\P0-O6\qwik-probe\tsconfig.json`; слитая часть дисциплины добавлена к
стартеру целиком, включая семь флагов, которых нет в `ts-demo`
(`noPropertyAccessFromIndexSignature`, `noImplicitOverride`,
`noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`,
`noImplicitReturns`, `allowUnreachableCode: false`), плюс
`verbatimModuleSyntax` и `types: ["node"]`.

Конфликты, найденные эмпирически:

- **К-1. `exactOptionalPropertyTypes` против необязательных JSX-пропов.**
  Передача `string | undefined` в необязательный проп даёт `TS2375`
  (С-8). Это не поломка Qwik: типы пропов Qwik проходят через
  `Omit<Props, …> & _Only$<Props>`, и требование дисциплины просто
  запрещает «передать undefined вместо отсутствия». Лечение — условный
  рендер/условный спред; после правки проба зелёная. Цена: шум на каждом
  необязательном пропе.
- **К-2. `erasableSyntaxOnly` — с Qwik не конфликтует.** В пользовательском
  коде Qwik нет ни `enum`, ни `namespace`, ни параметров-свойств; `component$`
  — обычный вызов функции, JSX стирается. Запрет ловит `enum` (TS1294), что
  и требуется. Типы самого `@qwik.dev/core` не проверяются: стартер (и
  `ts-demo`) держат `skipLibCheck: true`.
- **К-3. Тесты `.tsx` не запускаются шагами 3 и 7.** `node --test`
  (v24.18.0) на `.tsx` падает:
  `TypeError [ERR_MODULE_NOT_FOUND]`… точнее `ERR_UNKNOWN_FILE_EXTENSION`
  (С-10) — node стрипает типы, но не JSX. Плюс globs шага жёстко заданы как
  `**/*.test.ts` и `**/*.spec.ts` (`tools.rs:56`), то есть `.tsx`-тест даже
  не будет найден. Это главный практический конфликт для web-пакета.
- **К-4. Расхождение модульной модели.** `ts-demo` живёт на
  `module/moduleResolution: "nodenext"` (чтобы `node --test` исполнял `.ts`),
  Qwik требует `esnext` + `"Bundler"`. Дисциплина модульную модель не
  предписывает, так что это не нарушение, но прямое копирование
  `tsconfig` из `ts-demo` в web-пакет невозможно.
  `allowImportingTsExtensions` присутствует в обеих конфигурациях —
  здесь конфликта нет, импорты вида `./cells/hello/index.tsx` проходят.
  `verbatimModuleSyntax: true` с `Bundler` отработал без ошибок, хотя в
  стартере Qwik его нет.
- **К-5. `noPropertyAccessFromIndexSignature` + `process.env`.** Чтение
  среды в композиционном корне обязано писаться как `process.env["SITE_MODE"]`
  и требует `types: ["node"]` (в стартере Qwik их нет — там `vite/client`).
- **К-6. Структурный гейт `.tsx` понимает.** Экстрактор берёт
  `[".ts", ".tsx", ".mts", ".cts"]` кроме `.d.ts`
  (`tools/ts-extract/extract.ts:45,882-883`), и на пробе `conform` нашёл мой
  умышленный `"Hello" as Title` прямо в `src/main.tsx:9` (С-11). `specmap`
  так же индексирует `.tsx` (`@scope`/`@implements` в JSDoc работают).
- **К-7. Мусор сборки Qwik.** `outDir: "tmp"` и `incremental: true` из
  стартера обязаны попасть в `.prettierignore` и `ignores` eslint, иначе
  шаги 1 и 4 пойдут по артефактам.

**Предложение по развилке F-18.** Держать флаги дисциплины полностью
(они с Qwik совместимы, проверено), брать у Qwik блок `jsx` / модульной
модели / `paths`, а тестовые шаги развести:

- юнит-тесты чистой логики оставить `.test.ts` без JSX — они проходят
  шагами 3 и 7 как есть;
- компонентные тесты вести на vitest и **отключить** шаги `tests` и
  `test-gate` через `[[typescript.floor_disable]]` с честной причиной,
  вызывая vitest отдельной командой (`npm run test:component`) рядом с
  floor. Вывод при этом (С-9) явно печатает, что пол урезан, — «reduced
  floor can never masquerade as the full one» (`floor.rs:1-6`).

Альтернатива (не пробовал): поднять прогон `.tsx`-тестов на node через
загрузчик, стрипающий JSX; шаги 3/7 всё равно не найдут `.tsx` из-за
захардкоженных globs, так что это потребует правки стека.

### 5. Какие файлы дисциплины должен нести web-пакет

`typescript-ai-native init` создаёт шесть артефактов (проверено на
Qwik-пробе, С-12): `conform.toml`, `specmap.toml`,
`typescript-ai-native-conform-baseline.json`,
`discipline/registry/tests-baseline.json`, `discipline/registry/debt.json`,
`discipline/registry/intent.json`. Он же сам находит ячейки под `cells_dir`
и заносит их в `[[typescript.exempt]]` («pre-adoption»), а namespace берёт по
имени каталога. Рекомендуемый порядок для web-пакета — **сгенерировать
`init`-ом и подправить**, а не копировать из `ts-demo`.

Сверх сгенерированного пакет должен нести:

- `tsconfig.json` — собранный вручную (см. §4), не копия `ts-demo`;
- `.prettierrc.json` — переносится из `ts-demo` дословно (`{}`);
- `.prettierignore` — из `ts-demo` по смыслу, со строками `vibedeps/`,
  `.vibe/`, `node_modules/`, `target/`, `specmap.json`, `package-lock.json`,
  `discipline/`, плюс Qwik-специфичные `tmp/`, `dist/`, `server/`;
- `eslint.config.js` — из `ts-demo` дословно (flat config,
  `tseslint.configs.recommended` + правило `ai-native/diagnostic-cites-req`),
  меняются только `ignores`; блок плагина можно опустить, если не решать
  проблему его резолва (см. §2);
- `package.json`: `"type": "module"`, `"engines": {"node": ">=22.6"}`,
  скрипт `"floor": "typescript-ai-native floor"` (дословно из `ts-demo`),
  devDependencies `typescript`, `prettier`, `eslint`, `typescript-eslint`
  (рецепт из `init` и GUIDE §15 WIRE-3);
- `specmap.json` — коммитится, шаг 6 сверяет его байт в байт;
- `vibe.toml` + `vibe.lock` — только если web-пакет оформляется как
  отдельный vibe-проект (нужно для маршрута `vibe bin exec`; для маршрута
  A/B не требуется);
- каталог спеков: текущий `init` пишет `spec_roots = ["vibevm/vibespecs"]`
  (в `ts-demo` — устаревшее `spec_roots = ["spec"]`).

Дословно из `ts-demo` переносятся: `.prettierrc.json`, `eslint.config.js`
(с заменой `ignores`), скрипт `floor` в `package.json`, форма
`conform.toml`/`specmap.toml` (комментарии-шапки и порядок ключей).
Не переносятся: `tsconfig.json` (модульная модель), `vibe.lock`
(схема 6 устарела), `package-lock.json`.

## Расхождения с решениями

- `REVIEW:` пакет называет `research/ts-demo` «образцом web-пакета под
  дисциплиной», но на дереве b1291b06 он **не зелёный**: три шага floor
  красные (`prettier`, `eslint`, `specmap`, см. С-4…С-6) при точном
  воспроизведении раскладки репозитория и `npm ci` по закоммиченному
  lockfile. Как источник форм файлов он годится, как доказательство
  «дисциплина работает из коробки» — нет.
- `REVIEW:` `research/ts-demo/vibe.lock` имеет `schema_version = 6`, а
  `vibe.exe`, собранный из этого дерева, требует 7 (С-2). Маршрут
  `vibe bin exec` в самом демо сейчас нерабочий до `vibe install`.
- `REVIEW:` `research/ts-demo/tsconfig.json` ниже пола GUIDE §1: в нём нет
  семи обязательных флагов (`noPropertyAccessFromIndexSignature`,
  `noImplicitOverride`, `noUnusedLocals`, `noUnusedParameters`,
  `noFallthroughCasesInSwitch`, `noImplicitReturns`, `allowUnreachableCode`),
  и ни `deviates`, ни причины при нём не записано. Boot-сниппет стека
  называет полом сокращённую четвёрку — расхождение между GUIDE §1 и
  boot-сниппетом само по себе стоит решения.
- Правило R-16 («floor до каждого коммита») с найденным состоянием
  совместимо: гейт запускается и работает, но у web-пакета он пройдёт
  только после явного решения по шагам `tests`/`test-gate` (К-3).
