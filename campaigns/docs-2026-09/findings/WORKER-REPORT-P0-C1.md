## Решения и как разрешились неоднозначности пакета

- Пакет A0.1 просил таблицу "файл · тип матча · тест/продукт · действие" на
  каждый файл с совпадением. При 114 файлах это интерпретировано как ОДНА
  строка таблицы на файл (с диапазоном/списком строк внутри), а не строка на
  каждое отдельное вхождение (иначе таблица вышла бы на 300+ строк) — так
  прочитано требование "Для каждого файла с матчами открыть и записать
  таблицу".
- Для файлов без "test"/"tests" в имени, но живущих внутри
  `#[cfg(test)] mod tests` (24 файла) — статус "тест" не предполагался, а
  проверялся отдельным `grep -n "cfg(test)|mod tests"` по каждому такому
  файлу и сверкой номера строки совпадения против номера строки `mod tests`.
  Два файла без "test" в имени и без `cfg(test)` внутри
  (`vibe-lifecycle/src/mechanism/package/support.rs`,
  `vibe-spec/.../transform/lowering_worlds.rs`) классифицированы как
  тест-support по факту их собственных заголовочных доккомментариев
  ("Shared fixtures for the package-phase suites" / "for the T10B lowering
  tests") — цитаты в A0.1 "Свидетельства".
- A0.2 п.3 (нужна ли break-заметка) пакет предполагал ответ «нет» с
  подтверждающей цитатой. Буквальное чтение PROP-044 §4.7/§8 (G7) не даёт
  чистого «нет» — гейт break-заметки завязан на непустоту golden wire-diff,
  а не на "лёгкость" изменения; §4.2a/§4.6 поддерживают дух "не нужна", но
  явного исключения для открытых словарей в тексте нет. Ответ дан с обеими
  цитатами и явной пометкой, что ожидание пакета не подтверждено буквой
  текста — не подгонялось под ожидаемый ответ.
- A0.3 п.4 просил "перечислить структуры, куда лягут" ещё не существующие
  поля — по определению это не наблюдаемый факт кода, а перенос по аналогии
  с существующими секциями того же формального вида (`[[skill]]` →
  прецедент для `[[documents]]`, `describes: Option<Purl>` → прецедент для
  `[translates]`, и т.д.); в самой находке это явно помечено как аналогия
  с цитатами прецедентов, не как найденный код.

## Отклонения от буквы пакета (с причинами)

- A0.2 читал `crates/vibe-index/src/cli/kinds.rs` (не входил в явный список
  "Читать" пакета для A0.2, но входил в явный список для… нет, не входил и
  туда) — добавлено, потому что `crates/vibe-index/src/types/kinds.rs`
  (который пакет просил прочитать) оказался прямым ре-экспортом
  `vibe-wire`'s типа без собственной логики, а именно `cli/kinds.rs`
  содержит единственную продуктовую функцию (`parse_kind_flag`), важную для
  ответа на вопрос 1 A0.2 (как открытый словарь превращается в тип). Без
  этого файла ответ был бы неполным.
- A0.2/A0.3 расширили grep за пределы явно названных в пакете крейтов
  (`vibe-core`, `vibe-registry`, `vibe-publish` для `min_vibe_version`;
  `crates`, `xtask` для `vocabularies.json`) на соседние крейты
  (`vibe-workspace`, `vibe-install`, `vibe-cli`, `vibe-resolver`,
  `vibe-lifecycle`), когда изначальный список не дал функции проверки
  версии — иначе ответ "проверяется здесь" был бы недостоверным (не
  установлено ли на самом деле в непроверенном крейте).
- В A0.1 добавлен раздел "Дополнительно" про `BootCategory::App`
  (`vibe-core/src/manifest/package.rs`) — формально это не матч по
  `PackageKind` и в перепись не входит, но напрямую релевантно для того, кто
  спроектирует `PackageKind::App` (имя уже занято соседним enum, уже
  разведено по его собственным матчам). Оставлено как отдельный
  промаркированный блок, не смешано с основной таблицей.
- Пакетный `vibevm/vibespecs/common/PROP-044-change-native-formats.xml`
  прочитан ЦЕЛИКОМ (555 строк), а не только §4-5, т.к. заголовки секций в
  файле не размечены как `<h1..6>`/`<section>` — потребовался бы отдельный
  проход, чтобы понять разметку, а файл достаточно мал для прямого чтения;
  §6-10 не цитировались в находках, кроме одного факта в открытых вопросах
  A0.3 (§6.2 про манифест) — использован, т.к. напрямую относится к
  вопросу A0.3.5.
- Ни один из этих отходов не переписывает решения кампании (`D-NN`); все —
  расширение источников для более точного ответа на уже заданные пакетом
  вопросы.
