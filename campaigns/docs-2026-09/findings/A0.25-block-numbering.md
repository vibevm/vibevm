## Ответы

### 1. Идентичность блоков в пивоте и обход дерева бэкендами

#### 1.1 У блоков идентичности нет

`Block` (`crates/vibe-specdoc/src/doc.rs:96-119`) — пять вариантов
(`Paragraph`, `List`, `Table`, `Fence`, `Quote`), **ни один не несёт
поля id**. Деривы — `#[derive(Debug, Clone, PartialEq, Eq)]`
(`doc.rs:96`): равенство блоков структурное, «тот же блок» в пивоте
означает «те же данные», а не «то же место».

Адресуемые сущности всего три, и все — не блоки:

| что | поле | строка |
| --- | --- | --- |
| якорь заголовка документа | `Title::id: Option<String>` | `doc.rs:54` |
| якорь секции | `Section::id: Option<String>` | `doc.rs:80` |
| id факта в юните | `Fact::id: Option<String>` | `doc.rs:146` |

Как считаются якоря: XML-читатель чеканит их в **одно общее
пространство имён** — `mint_heading` (`xml_in.rs:472-483`, проверка
«якорь выразим в Markdown»), `mint_fact` (`xml_in.rs:485-498`, проверка
через `progress_core::parse::take_fact_id` — та же грамматика, что в
Markdown), дубли ловит `check_ids` (`xml_in.rs:500-515`) с сообщением
progress-core дословно. В Markdown те же якоря пишутся как `{#id}` у
заголовка (`md_out.rs:27`, `:49`) и `@fact:<ID>` у юнита
(`md_out.rs:184-191`).

Отсюда прямое следствие для `pNN`: **опереться на существующую
идентичность нельзя** — абзац без факта не имеет в пивоте ничего, чем
его можно назвать. Номер должен рождаться из позиции в обходе, что и
предписывает D-22 (номер — свойство проекции).

#### 1.2 Обход дерева — три реализации, один порядок

Порядок совпадает у писателя XML, писателя Markdown и у хостового
сборщика фактов; это и есть «канонический обход», который надо
воспроизвести в `vibe-doc`.

| шаг | `to_xml` | `to_markdown` | `authored_facts` (хост) |
| --- | --- | --- | --- |
| заголовок | `xml_out.rs:75-81` | `md_out.rs:23-30` | — |
| статус документа | `xml_out.rs:82-84` | `md_out.rs:31-34` | — |
| блоки преамбулы, по порядку | `xml_out.rs:85-87` | `md_out.rs:35` | `report.rs:30` |
| секции верхнего уровня, по порядку | `xml_out.rs:88-90` | `md_out.rs:36-38` | `report.rs:31-33` |
| в секции: статус → блоки → подсекции | `xml_out.rs:109-117` | `md_out.rs:52-59` | `report.rs:59-64` |

(хостовый обход — `crates/vibe-facts/src/report.rs:28-35` и `:59-64`.)

То есть обход — **предпорядок в глубину**: преамбула, затем каждая
секция: сначала её собственные блоки, потом её подсекции. Уровень
заголовка нигде не хранится и вычисляется из глубины (`md_out.rs:42`
принимает `level`, `xml_in.rs:359-366` — тоже).

Внутри блока бэкенды спускаются в юниты: список — `items` по порядку
(`xml_out.rs:197-219`, `md_out.rs:114-132`), таблица — строки, в строке
ячейки (`xml_out.rs:220-230`, `md_out.rs:133-157`). Юниты **не** блоки:
у списка один блок на весь прогон пунктов (`doc.rs:100-102`), у таблицы
один блок на всю таблицу (`doc.rs:103-107`).

### 2. Место и сигнатура присвоения `pNN` в `vibe-doc`

Крейта `vibe-doc` в workspace сегодня нет (`Cargo.toml`, секция
`members`) — площадка чистая.

#### 2.1 Адрес блока

Позиция блока в документе выражается двумя числами-путями; ничего
другого в IR нет.

```rust
/// Детерминированный адрес блока в документе: путь секции от корня
/// (0-базные индексы) плюс индекс блока в списке блоков своего
/// владельца. Преамбула документа — пустой путь секции.
#[derive(Debug, Clone, PartialEq, Eq, PartialOrd, Ord, Hash)]
pub struct BlockPath {
    /// `[]` — преамбула; `[0]` — первая секция; `[0, 2]` — её третья
    /// подсекция.
    pub section: Vec<u16>,
    /// Индекс блока внутри `SpecDoc::preamble` или `Section::blocks`.
    pub block: u16,
}
```

Лексикографический порядок `BlockPath` **не совпадает** с порядком
чтения (у секции сначала её блоки, потом подсекции — а пути подсекций
лексикографически больше её блоков, что верно; но блоки родителя, идущие
после подсекции, в диалекте невозможны — читатель это запрещает,
`xml_in.rs:436-447`: «`<p>` cannot follow a nested `<section>`»). Поэтому
`Ord` на `BlockPath` **совпадает** с документным порядком, и это свойство
даёт бесплатную детерминированность; его надо закрепить тестом.

#### 2.2 Функция обхода и результат

```rust
/// Присвоить `pNN` каждому нумеруемому блоку документа, в документном
/// порядке. Чистая функция: `doc` только читается — нумерация есть
/// свойство проекции, а не состояние пивота (D-22, R-26).
///
/// Вызывается в `vibe-doc` ПОСЛЕ раскрытия `derived` и ДО любого
/// бэкенда, ровно один раз на документ.
pub fn number_blocks(doc: &SpecDoc) -> Numbering;

/// Готовая нумерация: адрес → номер, плюс обратная выборка.
pub struct Numbering { /* BTreeMap<BlockPath, u32> + Vec<BlockPath> */ }

impl Numbering {
    /// Номер блока, если он нумеруемый.
    pub fn get(&self, path: &BlockPath) -> Option<u32>;
    /// Готовая метка — `"p12"`. Одно место, где живёт написание.
    pub fn label(&self, path: &BlockPath) -> Option<String>;
    /// Адрес по номеру — для ссылок «см. p12» и для переводов.
    pub fn path_of(&self, n: u32) -> Option<&BlockPath>;
    pub fn len(&self) -> usize;
    /// Пустая нумерация — нейтральный элемент для вызывающих, которым
    /// номера не нужны.
    pub fn none() -> Numbering;
}
```

Обход — тот же предпорядок, что в §1.2:

```rust
fn number_blocks(doc: &SpecDoc) -> Numbering {
    let mut n = 0u32;
    let mut out = Numbering::default();
    walk_blocks(&doc.preamble, &mut Vec::new(), &mut n, &mut out);
    for (i, s) in doc.sections.iter().enumerate() {
        walk_section(s, &mut vec![i as u16], &mut n, &mut out);
    }
    out
}
// walk_section: сначала walk_blocks(&s.blocks, path, …), затем
// рекурсия по s.sections с путём path + [i].
```

#### 2.3 Какие блоки получают номер — предлагаемое правило

**Правило: один номер на блок, сквозной счётчик на весь документ,
нумеруется каждый элемент списка блоков; юниты внутри блока
собственных номеров не получают.**

| конструкция | номер | почему |
| --- | --- | --- |
| `Paragraph` | да | абзац — базовая единица ссылки |
| `List` (весь прогон) | да, один на список | в IR список — один блок (`doc.rs:102`); пункт адресуется `p12.3`, если понадобится, но в `pNN` не входит |
| `Table` (вся таблица) | да, один | то же (`doc.rs:107`) |
| `Quote` | да | это отдельный блок потока |
| `Fence` | да | код цитируют в обсуждении так же часто, как прозу |
| `Example`, `Note`, `Figure`, `Prompt`, `Rule` (жанр документации) | да | это блоки потока |
| `Derived` | да — **после** раскрытия | к моменту нумерации это уже обычный блок с текстом (D-22) |
| пункт списка, ячейка таблицы, дети `prompt` | нет | не блоки |
| заголовки секций | нет | у них своя адресация — якорь (`Section::id`) |

Мотив «нумеровать всё подряд»: любое исключение надо помнить и
воспроизводить в каждом бэкенде и в каждом переводе; сквозной счётчик
без исключений проверяется одним тестом и не даёт расхождений между
языковыми версиями (номер — общий якорь оригинала и перевода).

Нерешённое, требующее слова владельца, — взаимодействие с `when`
(см. «Открытые вопросы», п. 1).

#### 2.4 Как номера попадают в бэкенды

**Рекомендация: номера не попадают в бэкенды `vibe-specdoc` вообще.**
Собственные бэкенды документации живут в `vibe-doc` и принимают два
параметра:

```rust
pub fn render_html(doc: &SpecDoc, numbering: &Numbering) -> String;
```

`Numbering` — отдельное значение, не поле `SpecDoc`. Бэкенд, которому
номера не нужны, получает `Numbering::none()`.

Почему не карта внутри документа и не обёртка над `SpecDoc`: любое
хранение номера рядом с IR немедленно втягивает его в `PartialEq`
(`doc.rs:96`), а на равенстве IR держатся все законы пивота
(`convert.rs:93-97`; `redbook_roundtrip.rs:179-208`). Вторая пара
параметров — единственная форма, которая ничего не втягивает.

#### 2.5 Почему это не ломает round-trip пивота

Три независимых довода, каждый — из кода:

1. **Номер не является состоянием `SpecDoc`.** Законы round-trip
   сравнивают значения `SpecDoc` (`from_xml(to_xml(d)) == d`,
   `lib.rs:16-18`, `:45-46`; корпусные законы —
   `tests/redbook_roundtrip.rs:179-208`). `Numbering` в `SpecDoc` не
   входит, в `PartialEq` не участвует, из бэкендов пивота не пишется.
2. **Номер не может просочиться в XML незаметно.** Словарь атрибутов
   закрыт: `only_attrs` (`xml_support.rs:67-85`) отвергает всё вне
   белого списка, а у `<p>`/`<quote>` белый список **пуст**
   (`xml_blocks.rs:20`). Попытка записать `<p p="12">` — громкая ошибка
   чтения, то есть «тихая» утечка нумерации в пивот технически
   невозможна.
3. **Нумерация — чистая функция от IR.** Один и тот же IR даёт одну и ту
   же карту при любом числе вызовов; порядок обхода совпадает с
   порядком, который уже воспроизводят три независимых реализации
   (§1.2). Значит нумерация не вводит нового источника
   недетерминизма — в отличие от, например, хеша или времени.

Ограничение, которое стоит записать прямо: `pNN` **позиционен**, поэтому
вставка абзаца сдвигает номера ниже по документу. Это принято D-22 (номер
— свойство рендера, а не адрес факта); для устойчивой адресации остаётся
якорь факта (`Fact::id`), который от нумерации не зависит.

### 3. Развилка F-43 — если параметр всё же придётся отдать в `md_out`/`xml_out`

Сигнатуры сегодня — одноместные:

- `pub fn to_xml(doc: &SpecDoc) -> String` (`xml_out.rs:69`, ре-экспорт
  `lib.rs:90`);
- `pub fn to_markdown(doc: &SpecDoc) -> String` (`md_out.rs:21`,
  ре-экспорт `lib.rs:84`).

Менять их **нельзя дёшево**: 16 внешних вызовов в восьми файлах
(`vibe-check/src/checks/wal_wellformed.rs`,
`vibe-spec/src/compiler/emit/attribution.rs`,
`vibe-spec/src/compiler/emit/static_xml.rs`,
`vibe-workspace/src/vibedeps/derived.rs` и четыре тестовых модуля), плюс
внутренние вызовы в `load.rs:131` и `convert.rs:46,55,68,77`, плюс
doctest в `lib.rs:37-48` и `load.rs:115-124`.

**Минимальная правка — аддитивный сосед, а не смена сигнатуры:**

```rust
// xml_out.rs / md_out.rs
pub fn to_xml(doc: &SpecDoc) -> String { to_xml_numbered(doc, &Numbering::none()) }
pub fn to_xml_numbered(doc: &SpecDoc, numbering: &Numbering) -> String;
```

Последствия такой правки, если на неё пойти:

- `Numbering` (или хотя бы трейт «дай метку для этого пути») переезжает
  в `vibe-specdoc` — иначе крейт получит зависимость от `vibe-doc` и
  сломает закон отделимости (`lib.rs:50-52`: крейт зависит только от
  `progress-core` и `quick-xml`). Это единственная неустранимая цена, и
  она — довод в пользу §2.4 (не отдавать номера в пивот совсем).
- Нумерованный вывод перестаёт быть байт-идемпотентным как XML: любая
  запись номера в документ ломает `redbook_readme_golden_xml_is_pinned`
  (`tests/redbook_roundtrip.rs:211`) и
  `canonical_form_is_pinned` (`xml_out.rs:362`), и потребует расширения
  закрытого словаря атрибутов на **каждом** блочном элементе
  (`xml_blocks.rs:20`, `:31`, `:90`, `:178`; `xml_facts.rs:18`).
- Для Markdown-проекции (`load.rs:125-135`) номера пришлось бы либо
  прятать, либо печатать — первое делает вывод неоднозначным, второе
  меняет текст, который хостовые сканеры хешируют
  (`vibe-cli/src/commands/progress/grounding.rs:118-122` — хеш берётся
  ровно от текста проекции).

**Вывод по F-43: правка не нужна.** Номер требуется только бэкендам
документации, а они — в `vibe-doc`, где `(doc, numbering)` передаются
рядом. Сигнатуры `to_xml`/`to_markdown` остаются нетронутыми, и
нумерация никак не касается законов пивота. Аддитивный сосед описан выше
как запасной путь, если появится требование печатать номера прямо в
канонический Markdown.

## Расхождения с решениями

Нет. D-22 («`pNN` — свойство проекции, присваивается в `vibe-doc`
детерминированным обходом после раскрытия `derived`, до бэкендов») и
R-26 кодом подтверждаются: у блоков нет идентичности, которую можно было
бы принять за номер (`doc.rs:96-119`), закрытый словарь атрибутов не даёт
записать номер в пивот незаметно (`xml_blocks.rs:20`,
`xml_support.rs:67-85`), а канонический порядок обхода уже существует в
трёх реализациях и совпадает (§1.2).

## Открытые вопросы

1. **`when` и нумерация — до или после фильтрации.** Если нумеровать
   *до* отбрасывания блоков с невыполненным `when`, номера одинаковы во
   всех вариантах сборки (Windows/macOS, агент A/агент B), но в выводе
   будут пропуски. Если *после* — нумерация плотная, но `p12` в
   Windows-сборке и в macOS-сборке указывают на разные абзацы.
   Рекомендация — нумеровать до фильтрации (номер должен значить одно и
   то же в баг-репорте и в переводе), но решение за владельцем; в D-22
   этого нет.
2. **Показывается ли `pNN` читателю и где.** От этого зависит, нужен ли
   `Numbering::path_of` (обратная выборка) и попадает ли метка в якоря
   HTML (`#p12`). На пивот не влияет.
3. **Нумерация в переводах.** Если перевод — отдельный документ с тем же
   деревом блоков, номера совпадут автоматически; если переводится
   выборочно (форма `example ref=`), совпадение нужно проверять тестом.
   Требует решения по структуре переводов, которого в прочитанном коде
   нет.
4. **Ширина счётчика.** `u16` в `BlockPath` и `u32` в номере выбраны с
   запасом; предельные размеры документа нигде в коде не заданы (глубина
   секций ограничена шестью уровнями — `xml_in.rs:367-371`).
