тест в `crates/vibe-check/src/checks/snippet_presupposition/tests.rs` —
ячейка PROP-049 §4 (концепты boot-сниппета не должны presupposing чужую
дисциплину без структурной оговорки). Список всех ячеек:
`ls crates/vibe-check/src/checks` → `activation_conflict.rs`,
`boot_directory.rs`, `bridge_provenance.rs`, `facts_sync.rs`,
`features_graph.rs`, `i18n_coverage.rs`, `local_source_freshness.rs`,
`lockfile_files.rs`, `manifest_epoch.rs`, `manifest_validity.rs`,
`redirect_block.rs`, `review_aging.rs`, `snippet_presupposition.rs` (+
подкаталог `snippet_presupposition/`), `subskill_structure.rs`,
`visibility_hygiene.rs`, `wal_freshness.rs`, `wal_wellformed.rs` — один
файл = одна ячейка, `crates/vibe-check/src/checks/mod.rs:1-7` формулирует
это явно: "one module per `CheckId`… never a sibling cell".

**Сигнатура ячейки (unit-struct + макро-атрибут).**
`crates/vibe-check/src/checks/snippet_presupposition.rs:24-25`:
```rust
#[cell(seam = "Check", variant = "snippet-presupposition")]
pub struct SnippetPresuppositionCheck;
```
`cell` — атрибут-макрос из `specmark::cell`. Реализует трейт `Check`
(`crates/vibe-check/src/lib.rs:394-399`):
```rust
pub trait Check {
    fn id(&self) -> CheckId;
    fn run(&self, project_root: &Path, opts: &CheckOptions, report: &mut CheckReport);
}
```

**Регистрация в списке проверок.** Единственная точка —
`crates/vibe-check/src/lib.rs:414-434`, `pub fn all_checks() -> Vec<Box<dyn
Check>>`; ячейка добавляется одной строкой `Box::new(SnippetPresuppositionCheck)`.
Комментарий над функцией (`lib.rs:402-405`) фиксирует: порядок вектора —
порядок находок в отчёте (наблюдаемый вывод), новые ячейки дописывать в
конец, а не переставлять существующие.

**Форма одной диагностики.** `Finding`
(`crates/vibe-check/src/lib.rs:237-247`):
```rust
pub struct Finding {
    pub check: CheckId,
    pub severity: Severity,
    pub path: Option<PathBuf>,
    pub line: Option<usize>,
    pub message: String,
}
```
`Severity` = `Error | Warning | Info` (`lib.rs:202-206`). `CheckReport`
(`lib.rs:268-270`) хранит `findings: Vec<Finding>` и даёт три
приватных-крейту конструктора — `err`/`warn`/`info` (`lib.rs:285-330`),
например `warn` (`lib.rs:300-306`):
```rust
pub(crate) fn warn(
    &mut self,
    check: CheckId,
    path: Option<PathBuf>,
    line: Option<usize>,
    msg: impl Into<String>,
)
```
Код диагностики = вариант `CheckId` (например `CheckId::SnippetPresupposition`,
`lib.rs:80-…`, у некоторых вариантов есть doc-комментарий с привязкой к
PROP); отдельного enum "кода ошибки" сверх `CheckId` нет — весь остальной
контекст (какая рекомендация, какой владелец концепта) живёт текстом в
`message`. Пример вызова —
`crates/vibe-check/src/checks/snippet_presupposition.rs:268-279`:
`report.warn(CheckId::SnippetPresupposition, Some(rel.clone()),
Some(line_number), format!("{rel_label}:{line_number}: foreign concept ..."))`.

**Устройство теста ячейки.** Вынесен в соседний файл
`checks/<cell>/tests.rs` (не inline), подключается одной строкой в конце
основного файла — `crates/vibe-check/src/checks/snippet_presupposition.rs:354`:
`#[cfg(test)] mod tests;`. Шапка тестового файла поясняет причину —
"out-of-line per the file-length budget", при этом позиция в дереве
модулей (и значит `use super::…`) не меняется относительно inline-формы.
Тест строит фиктивный проект во временном каталоге (`tempfile::tempdir()`),
пишет туда `vibe.toml`/файлы локальными помощниками (`write`, `write_owner`,
`write_consumer` в `tests.rs:18-92`), прогоняет ячейку через локальный
хелпер `run(root: &Path) -> CheckReport` (`tests.rs:94-98`:
`SnippetPresuppositionCheck.run(root, &CheckOptions::default(), &mut
report)`), затем ассертит на `report.findings`: количество, `.check ==
CheckId::…`, `.severity`, `.line`, `.message.contains(...)`.

## Открытые вопросы

- Задание не называло конкретный `D-NN`, с которым сверять doc-kind
  правила, поэтому раздел выше — фактическое описание формы ячейки, а не
  проверка совместимости с уже принятым решением по картинкам/переводам/
  карточке doc-kind.
- Не проверял процедуру добавления нового варианта `CheckId` (сам enum,
  `crates/vibe-check/src/lib.rs:80` и далее) построчно за пределами
  процитированных диапазонов — по структуре похоже на обычное добавление
  варианта плюс doc-комментарий со ссылкой на PROP, но это не подтверждено
  чтением всего enum.
- `vibe-check` в списке "Читать" не имеет отдельного файла с описанием, как
  `all_checks()` вызывается снаружи (`vibe check` CLI-команда) — не входило
  в задание, не проверялось.
