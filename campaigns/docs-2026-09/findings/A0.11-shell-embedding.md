## Ответы

### 1. `rust-embed` против `include_dir`

Ни того, ни другого в дереве сейчас нет: `grep -rn "rust-embed\|rust_embed\|include_dir"`
по `*.toml` и `*.rs` не дал ни одного вхождения. Встраивание в дереве
делается вручную через `include_str!` — шаблоны `vibe init`
(`crates/vibe-cli/src/commands/init/helpers.rs:152-158`).

Версии, лицензии и графы получены `cargo add` + `cargo metadata` +
`cargo tree` в пробном проекте.

| | `rust-embed` 8.12.0 | `include_dir` 0.7.4 |
|---|---|---|
| Лицензия | MIT | MIT |
| Репозиторий | `https://pyrossh.dev/repos/rust-embed` | `https://github.com/Michael-F-Bryan/include_dir` |
| Лицензии всего графа | MIT / Apache-2.0 / Unlicense — copyleft нет | то же |
| Транзитивных крейтов | 23 (`rust-embed-impl`, `rust-embed-utils`, `syn`, `sha2` + 6 крейтов RustCrypto, `walkdir`, `same-file`, `winapi-util`, `windows-sys`, `windows-link`, `mime_guess`, `mime`, `unicase`, `proc-macro2`, `quote`, `unicode-ident`) | 4 (`include_dir_macros`, `proc-macro2`, `quote`, `unicode-ident`) |

| Размер release-бинарника | 131 072 Б | 131 072 Б (обе +1 КиБ к `include_str!`: 130 048 Б) |
| Фича-гейты | `debug-embed`, `compression` (→ `include-flate`), `deterministic-timestamps`, `include-exclude`, `interpolate-folder-path`, `mime-guess`, плюс интеграции `actix`/`axum-ex`/`poem-ex`/`rocket`/`salvo-ex`/`warp-ex`; по умолчанию ни одной | `default = []`, `metadata`, `nightly`, `glob` |

| ETag/хэш | `Metadata::sha256_hash()`, `last_modified()`, `created()`, `mimetype()` (`rust-embed-utils-8.12.0/src/lib.rs:67-141`) | только mtime под фичей `metadata`; хэша нет |
| Сжатие | фича `compression` (deflate внутри бинарника через `include-flate`) | нет |
| Обход путей | точное совпадение по списку; есть тест `tests/path_traversal_attack.rs` | точное сравнение путей в `Dir::get_entry` (`include_dir-0.7.4/src/dir.rs:40-56`) — `..` не совпадает ни с чем |
| Абсолютный путь сборки в release-бинарнике | не найден | не найден |

**Рекомендация: `include_dir` 0.7.4.** Причины, по убыванию веса:

1. **Отладочная сборка `rust-embed` не самодостаточна.** Измерено: бинарник,
   собранный в debug, отдал файл, добавленный в каталог *после* сборки, и
   перестал его отдавать, когда файл удалили, — то есть читал с диска по
   абсолютному пути. Release тот же файл отдавал из себя. Для читателя,
   который обязан быть автономным (D-09: «всё в бандле»), это постоянная
   ловушка: фичу `debug-embed` придётся помнить вечно и в каждом месте.
   У `include_dir` такого режима нет вовсе.
2. **Граф зависимостей.** 4 крейта против 23, чистая сборка 2,95 с против
   6,53 с. `rust-embed` тянет `sha2` и `walkdir` в обычные (не build-only)
   зависимости, `syn` и `mime_guess` — в proc-macro.
3. **Что даёт `rust-embed` сверх — здесь не нужно.** SHA-256 на каждый файл
   был бы полезен для `ETag`, но по D-12 п. 5 пинуется **один** content hash
   всей оболочки; его считает `build.rs` и отдаёт константой, а `ETag` для
   всех ассетов — этот же один идентификатор сборки (имена файлов у
   бандлера и так контент-хэшированные, им нужен `cache-control: immutable`,
   а не поштучный ETag). Сжатие лучше делать заранее файлами `.gz` рядом:
   дерево уже применяет ровно этот приём
   (`crates/vibe-index/src/server/routes/index_files.rs:62-66` ставит
   `content-encoding: gzip` вручную), а для оболочки из store его умеет
   `ServeDir::precompressed_gzip()`.

Риски `include_dir`, записаны честно: версия 0.7.x (0.x-схема версий),
сопровождается вяло, интеграции с axum нет. Если владелец предпочтёт
активнее сопровождаемый крейт, приемлемая альтернатива — `rust-embed` с
**обязательным** набором фич `features = ["debug-embed",
"deterministic-timestamps"]` (первая закрывает пункт 1, вторая убирает
mtime-шум из воспроизводимой релизной сборки). Оба варианта по лицензиям
чисты.

**Общий вывод, не зависящий от выбора крейта:** ни один из них не отличает
пустой каталог от полного и ни один не заказывает пересборку при изменении
каталога. Значит `build.rs` с `cargo:rerun-if-changed=shell` и явной
проверкой обязателен в любом случае — а раз он всё равно нужен, отсутствие
у `include_dir` отслеживания изменений ничего не стоит.

### 2. Проба фичи `embedded-shell`

Пробный крейт: `<scratch>/vibe-docs-phase0\P0-O3\probe\`.
Три сценария, все выполнены:

| Сценарий | Команда | Код выхода | Что произошло |
|---|---|---|---|
| Без фичи, каталога `shell/` нет | `cargo build` | 0 | собралось, работает запасная голая оболочка |
| С фичей, каталог пуст | `cargo build --features embedded-shell` | 101 | `build.rs` остановил сборку своим сообщением (дословно ниже) |
| С фичей, каталог с файлами | `cargo build --features embedded-shell` | 0 | собралось; `/` отдаёт встроенный `index.html`, `/shell/app.js` — встроенный ассет |

Макет `build.rs` (31 строка, компилируется как есть):

```rust
//! Build script: the `embedded-shell` gate. Off — nothing is required and no
//! shell directory has to exist. On — the built shell must be present and
//! non-empty, or the build stops with a message that names the fix.

use std::path::PathBuf;

fn main() {
    let shell = PathBuf::from(std::env::var("CARGO_MANIFEST_DIR").unwrap()).join("shell");
    println!("cargo:rerun-if-changed=shell");
    println!("cargo:rustc-env=DOCSHELL_DIR={}", shell.display());

    if std::env::var_os("CARGO_FEATURE_EMBEDDED_SHELL").is_none() {
        println!("cargo:rustc-env=DOCSHELL_STATE=fallback");
        return;
    }

    let index = shell.join("index.html");
    if !index.is_file() {
        eprintln!(
            "error: feature `embedded-shell` is on, but the built doc shell is missing: \
             `{}` does not exist.\n\
             note: the shell is produced by `cargo xtask embed-doc-shell` (pnpm build with \
             the embeddable adapter).\n\
             fix: run `cargo xtask embed-doc-shell` before a release build, or build without \
             `--features embedded-shell` to get the fallback bare shell.",
            index.display()
        );
        std::process::exit(1);
    }
    println!("cargo:rustc-env=DOCSHELL_STATE=embedded");
}
```

Проверка на `index.html`, а не на «каталог непустой», сделана намеренно: она
ловит и пустой каталог, и каталог с мусором без точки входа. Реальному
`build.rs` стоит дополнительно посчитать sha256 всего каталога и отдать его
`cargo:rustc-env=VIBE_DOC_SHELL_SHA256=…` — это и есть пин D-12 п. 5.

`eprintln!` + `exit(1)` вместо `panic!` выбраны ради чистого сообщения: с
`panic!` вывод содержит ещё `thread 'main' panicked at build.rs:19:9` и
`note: run with RUST_BACKTRACE=1` (проверено обоими способами). Сам `cargo`
в обоих случаях завершается кодом **101**.

Дословное сообщение при пустом каталоге:

```
error: failed to run custom build command for `docshell-probe v0.0.0 (…\probe)`

Caused by:
  process didn't exit successfully: `…\build-script-build` (exit code: 1)
  --- stdout
  cargo:rerun-if-changed=shell
  cargo:rustc-env=DOCSHELL_DIR=…\probe\shell

  --- stderr
  error: feature `embedded-shell` is on, but the built doc shell is missing: `…\probe\shell\index.html` does not exist.
  note: the shell is produced by `cargo xtask embed-doc-shell` (pnpm build with the embeddable adapter).
  fix: run `cargo xtask embed-doc-shell` before a release build, or build without `--features embedded-shell` to get the fallback bare shell.
```

Макет `lib.rs` — файл `probe/src/shell.rs`, строки 1-57 (функция
`safe_join`, строки 59-72, приведена целиком в находке A0.7 и здесь опущена,
чтобы уложиться в лимит):

```rust
//! Shell surface: one type, three sources. Nothing else knows where bytes live.
use std::path::{Component, Path, PathBuf};

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Provenance {
    Embedded,
    Store,
    Fallback,
}

#[cfg(feature = "embedded-shell")]
mod embedded {
    use include_dir::{Dir, include_dir};
    pub static DIR: Dir<'_> = include_dir!("$CARGO_MANIFEST_DIR/shell");
}

/// The bare shell a Node-less `cargo build` ships (D-12 п. 2).
pub const FALLBACK_INDEX: &[u8] =
    b"<!doctype html><meta charset=utf-8><title>vibe doc</title>{island}";

/// `store_root` = `…/opt/vibevm/doc-shell/<sha256>` when the pinned shell was
/// downloaded by explicit consent (D-12 п. 3), otherwise `None`.
pub struct Shell {
    store_root: Option<PathBuf>,
}

impl Shell {
    pub fn new(store_root: Option<PathBuf>) -> Self {
        Shell { store_root }
    }

    /// What `vibe doc serve` reports it is carrying (D-12 п. 5).
    pub fn provenance(&self) -> Provenance {
        if cfg!(feature = "embedded-shell") {
            Provenance::Embedded
        } else if self.store_root.is_some() {
            Provenance::Store
        } else {
            Provenance::Fallback
        }
    }

    pub fn index(&self) -> Vec<u8> {
        self.asset("index.html")
            .unwrap_or_else(|| FALLBACK_INDEX.to_vec())
    }

    /// Embedded lookup is an exact match against the compile-time list, so
    /// `..` cannot resolve; the store lane is joined lexically and rechecked.
    pub fn asset(&self, rel: &str) -> Option<Vec<u8>> {
        #[cfg(feature = "embedded-shell")]
        if let Some(file) = embedded::DIR.get_file(rel) {
            return Some(file.contents().to_vec());
        }
        std::fs::read(safe_join(self.store_root.as_deref()?, rel)?).ok()
    }
}
```

Три источника закрыты одним типом: встроенная оболочка, оболочка из store и
запасная. Ни сервер, ни конвейер не знают, откуда пришли байты; `provenance()`
— это и есть ответ на «`vibe doc serve` умеет сообщить, что несёт» (D-12 п. 5).

### 3. Релизные активы, store версий и место оболочки в них

**Откуда `vibe self` берёт релизные активы.**

- Корень: `const GITHUB_RELEASE_ROOT: &str =
  "https://github.com/vibevm/vibevm/releases/download"`
  (`crates/vibe-cli/src/commands/vvm/bundle.rs:37`); база релиза —
  `{GITHUB_RELEASE_ROOT}/v{version}` (`bundle.rs:168`). Для `self bootstrap`
  база берётся аргументом и валидируется до единственной канонической формы:
  схема `https`, хост ровно `github.com`, без пользователя, пароля, порта,
  запроса и фрагмента, путь ровно
  `/vibevm/vibevm/releases/download/{tag}` (`bundle.rs:336-350`).
- Порядок: сперва скачивается агрегатный манифест `DISTRIBUTIONS.json`
  (`DISTRIBUTION_AGGREGATE_MANIFEST_FILENAME`,
  `crates/vibe-publish/src/release_manifest.rs:23`; скачивание —
  `bundle.rs:167-177`), из него выбирается фрагмент по цели платформы
  (`select_platform`, `bundle.rs:314-334`; цель — `current_target()`,
  `bundle.rs:432-441`), и только затем скачивается сам бандл
  `vibevm-<version>-<target>.zip` (`xtask/src/dist/build.rs:129-131`).
- Транспорт: анонимный `reqwest::blocking` с `user-agent vibevm/<version>`,
  `connect_timeout` 20 с, общий таймаут 30 мин (`bundle.rs:39-40, 388-395`),
  заголовки `accept: application/octet-stream`, `cache-control: no-cache`,
  `pragma: no-cache` и cache-busting-параметр `?vvm_nonce=…`
  (`bundle.rs:360-366`). Токен не используется — релизы публичные
  (PROP-019 §5 `SEC-TOKEN`).
- Каждое скачивание ограничено заявленным размером: `copy_download` читает
  `maximum + 1` байт и падает при превышении (`bundle.rs:421-427`); временный
  файл создаётся `create_new` и удаляется `DownloadCleanup` при любом исходе
  (`bundle.rs:371-378`).

**Как считается и проверяется хэш.**

- Форма актива — `DistributionAsset { name: String, size: u64, digest: String }`,
  где `digest` — строчный `sha256:<64 hex>`
  (`crates/vibe-publish/src/release_manifest.rs:117-123`).
- Проверка — одна функция на всё: совпасть должны **и размер, и дайджест**
  (`require_digest`, `crates/vibe-cli/src/commands/vvm/bundle/archive.rs:440-453`).
  Бандл хэшируется потоково при открытии
  (`open_hashed_regular_exact`, `archive.rs:69-80`), затем ZIP проверяется
  структурно: встроенный `DISTRIBUTION.json` обязан быть **равен** выбранному
  фрагменту агрегата (`archive.rs:89-94`), пути компонентов канонические
  (`validate_platform_paths`, `archive.rs:257-282`), а набор записей ZIP —
  **закрытое множество** (`validate_outer_structure`, `archive.rs:284-315`):
  лишний файл в архиве останавливает установку.
- `vibe self bootstrap` дополнительно проверяет сам загрузочный бинарник
  против агрегата до всего остального (`verify_file_asset`, `archive.rs:47-59`).
- Идентичность уже установленного экземпляра держится на
  `payload_sha256` и `distribution_manifest_sha256` в `InstallRecord`
  (`archive.rs:142-143`), а `installed_bundle_intact` перепроверяет их перед
  повторным использованием (`archive.rs:167-254`).

**Store версий.** Корень — `$VIBEVM_INSTALL_ROOT/opt`, по умолчанию
`~/.vibe/opt` (`crates/vibe-cli/src/commands/vvm/mod.rs:49-53, 86-101`;
PROP-019 §2.4 `ROOT-DEFAULT`). Раскладка (методы
`crates/vibe-cli/src/commands/vvm/store.rs:135-215`, фенс PROP-019 §2.4):

```
~/.vibe/opt/
├─ bin/                                  шимы на PATH
└─ vibevm/
   ├─ current, previous                  указатели на активный экземпляр
   ├─ state.toml                         инвентарь InstallRecord
   ├─ versions/<kind>/<id>/<instance>/    неизменяемые экземпляры
   │     bin/{vibe,vibe-index}[.exe]
   │     source/, vibevm-source.zip, DISTRIBUTION.json
   ├─ build/                             общий cargo --target-dir
   └─ src/.mirror/                       общий клон исходников
```

`<instance>` — монотонный счётчик, не хэш (PROP-019 §9.2, §9.4). Любая
мутация пути внутри store проходит `guard_mutation_path` /
`guard_mutation_tree` — лексическое containment плюс отказ на симлинки,
reparse-точки и специальные файлы (`store.rs:110-132`).

**Как добавить оболочку отдельным активом с хэшем.**

1. **Имя актива:** `vibevm-doc-shell-<version>.zip`, **без цели платформы**.
   Оболочка — JS, CSS и woff2, одинаковые на всех четырёх целях
   (`SUPPORTED_DISTRIBUTION_TARGETS`,
   `crates/vibe-publish/src/release_manifest.rs:52-57`), поэтому четырёх
   копий в релизе не нужно. Собирается тем же шагом
   `cargo xtask embed-doc-shell`, выкладывается рядом с бандлами
   (`xtask/src/dist/build.rs:79-88` — место, куда добавляется четвёртый
   выходной файл).
2. **Манифест: отдельный, а не поле в существующем.** Добавлять поле в
   `PlatformDistributionFragment` или `AggregateDistributionManifest`
   **нельзя без слома старых клиентов**: обе структуры объявлены
   `#[serde(deny_unknown_fields)]`
   (`crates/vibe-publish/src/release_manifest.rs:116, 125, 143`), а
   `validate_schema` принимает ровно
   `DISTRIBUTION_SCHEMA_VERSION = 1`
   (`crates/vibe-publish/src/release_manifest/validation.rs:13-21`,
   константа — `release_manifest.rs:49`). Любое новое поле — это версия
   схемы 2, и тогда каждый установленный `vibe 1.0.0` откажется читать
   манифест нового релиза и потеряет `self update`. Поэтому: отдельный
   актив `DOC-SHELL.json` рядом с `DISTRIBUTIONS.json`, который читает
   только `vibe doc serve`; старые клиенты его не запрашивают. Форма —
   зеркало уже существующей: `{ schema_version, product, repository,
   version, tag, source_commit, asset: { name, size, digest } }`, где
   `digest` — тот же `sha256:<64 hex>`, и та же проверка `require_digest`.
3. **Где хранится пин** (D-12 п. 5 — «lock-файл рядом с `vibe`»). Два слоя,
   оба неизменяемы после создания:
   - константа в бинарнике: `build.rs` отдаёт
     `cargo:rustc-env=VIBE_DOC_SHELL_SHA256=…` — это «рядом с `vibe`» в
     самом сильном смысле, пин нельзя подменить, не пересобрав `vibe`;
   - человекочитаемая копия `DOC-SHELL.lock.toml` в каталоге экземпляра,
     **записанная во время стейджинга**, то есть при рождении экземпляра
     (`archive.rs:113-121` создаёт staging, `placer::publish_staged_instance`
     публикует его целиком). Дописывать что-либо в уже существующий
     экземпляр нельзя: экземпляры объявлены неизменяемыми (PROP-019 §2.4), а
     `state.toml` — это изменяемый инвентарь, и в него поля под отдельные
     возможности класть не стоит (`record_install` отказывает на любое
     изменение метаданных существующего `#N`, `store.rs:275-297`).
   - **Сама оболочка** кладётся не в экземпляр, а в новый общий
     контент-адресуемый каталог рядом с `build/` и `src/`:
     `~/.vibe/opt/vibevm/doc-shell/<sha256>/`. Так одна закачка обслуживает
     все экземпляры, пиннущие этот хэш, неизменяемость экземпляра не
     нарушается, а `guard_mutation_tree` применяется к новому каталогу без
     изменений.
   - Self-check сверяет константу бинарника с содержимым каталога по хэшу
     (D-12 п. 5); `vibe doc serve` печатает `provenance()` и пин.
4. **Какой командой скачивается.** Явная подкоманда
   `vibe doc shell install [--assume-yes]` плюс предложение при первом
   `vibe doc serve` без оболочки. Согласие обязательно и берётся уже
   существующим приёмом: `Confirm::new().default(false)` с отказом при
   отсутствии TTY и обходом только по явному `--assume-yes` / `--json` /
   unattended (`crates/vibe-cli/src/commands/install/confirm.rs:22-45`).
   Никогда не автоматически (D-12 п. 3). Скачивание переиспользует
   `Downloader`-шов (`bundle.rs:377-380`) — с тем же ограничением по
   размеру, тем же `create_new`-временным файлом и той же проверкой
   `require_digest`.
5. **Если оболочки нет.** `Shell::provenance() == Fallback`: `vibe doc serve`
   поднимается и работает, отдаёт `FALLBACK_INDEX` — голый HTML без
   скриптов и стилей, в который вклеен тот же остров, — и сообщает, что

## Расхождения с решениями

Нет. D-12 п. 1 допускает и `rust-embed`, и `include_dir` — выбран второй с
изложенными основаниями; п. 2, 3, 4, 5 воспроизведены как есть.

Одно уточнение внутри принятого решения, не меняющее его: D-12 п. 3 говорит
«кладёт в store версий VVM», и буквальное прочтение — каталог экземпляра.
Экземпляры объявлены неизменяемыми (PROP-019 §2.4), поэтому предложено
класть оболочку в общий контент-адресуемый `opt/vibevm/doc-shell/<sha256>/`,
то есть в store версий, но не внутрь экземпляра; в экземпляре остаётся
только пин, записанный при его создании. Это исполнение решения, а не его
пересмотр.

## Открытые вопросы

- Реальный размер собранной оболочки Qwik неизвестен (пакета `web` ещё нет),
  поэтому вклад в размер `vibe.exe` оценить нельзя; измерена только накладная
  стоимость кода библиотеки (+1 КиБ). Текущий `target/debug/vibe.exe` — 98 МиБ,
  но это debug.
- Нужен ли для актива оболочки отдельный шаг проверки при публикации релиза
  (по образцу `xtask/src/dist/release.rs`, который «requires and remotely
  verifies all twelve platform assets» — PROP-019 §2.18): один актив на
  релиз ломает счёт «двенадцать», и эту проверку придётся расширять.
- Политика обновления: что делает `vibe doc serve`, когда пин экземпляра
  указывает на хэш, которого нет в `doc-shell/`, а сеть недоступна.
  Предложение — падать в запасную оболочку с предупреждением, но решение не
  записано ни в D-12, ни в PROP-019.
- Сборка `cargo xtask embed-doc-shell` требует Node и pnpm; проверка их
  наличия и пинов (D-12: версии Node и pnpm запинены) в этой пробе не
  трогалась.
