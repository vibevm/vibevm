Парные `*_at`-ядра берут корень явным параметром и видны только внутри крейта
(`pub(crate)`): `lookup_at` (`:504`), `list_versions_at` (`:515`),
`list_all_at` (`:533`), `insert_at` (`:353`), `recorded_hash_at` (`:435`),
`record_hash_at` (`:456`), `remove_entry_at` (`:265`), `remove_name_at` (`:298`).
Снаружи крейта они недоступны — потребитель вызывает root-less-обёртки.

Ключевое ограничение для развёртывания: **собственного env-переключателя у store
нет**; корень движется только вместе с `$VIBE_SETTINGS`
(`crates/vibe-registry/src/store.rs:30–37`, `:79–83`;
`vibe_core::settings::SETTINGS_DIR_ENV = "VIBE_SETTINGS"`,
`crates/vibe-core/src/settings.rs:36`, `settings_dir()` — `:46`).

Раскладка (`crates/vibe-registry/src/store.rs:7–19`, `:89–93`, `:110–120`):

```text
<store>/<group>/<name>/v<version>/        — распакованное дерево пакета (без .git)
<store>/<group>/<name>/v<version>.sha256  — sidecar рядом, не внутри записи
```

Дисциплина записи — write-once для нашего кода (`:21–28`, `:353–432`): запись
делается копией в соседний `v<version>.tmp-<pid>` и атомарным `rename`;
существующая запись возвращается как `InsertOutcome::AlreadyPresent` и не
переписывается. Исключение — мутабельный источник: `insert_current_at`
(`crates/vibe-registry/src/store/refresh.rs:24`) сравнивает записанный sidecar с
хэшем живого источника и при расхождении удаляет запись и вставляет заново. Его
вызывают пути реальной выборки: `crates/vibe-registry/src/local_registry.rs:197`,
`crates/vibe-registry/src/multi_registry_resolver/dispatch.rs:154`,
`.../sources.rs:236`, `.../redirect_follow.rs:279`,
`crates/vibe-registry/src/git_registry.rs:197`.

### 2. Как `cache add` резолвит замыкание зависимостей и откуда берёт реестр

Команда целиком — `crates/vibe-cli/src/commands/cache/add.rs`.

- Замыкание: `resolver.solve(&roots)` — `crates/vibe-cli/src/commands/cache/add.rs:56–58`.
  Это метод трейта `InstallSource::solve` (`crates/vibe-install/src/lib.rs:148`),
  реализованный для `InstallResolver`
  (`crates/vibe-package-source/src/source.rs:187`). Собственного обхода в команде
  нет — комментарий `add.rs:53–55` это фиксирует: «The closure walk is the
  existing solve — it already follows each package's `[requires]`».
- Выборка каждого узла: `resolver.resolve_and_fetch(&exact_pinned_pkgref(node), &store_root, None)`
  — `add.rs:72` (трейт-метод `crates/vibe-install/src/lib.rs:139`). Корень store
  берётся один раз: `vibe_registry::store_root()` — `add.rs:59`.
- Реестр: `cache_resolver(&args.path, root_offline)` — `add.rs:96`. Внутри
  проекта (есть `vibe.toml`, `add.rs:104`) собирается
  `build_install_resolver(...)` — `add.rs:115–122`; вне проекта —
  `projectless_resolver(&global, offline)` (`add.rs:134`) поверх
  `GlobalRegistryConfig::load()` (`add.rs:107`), то есть
  `~/.vibe/registry.toml` (`vibe_core::settings::registry_config_path`,
  `crates/vibe-core/src/settings.rs:77`).
- **Важно:** третьим позиционным аргументом `build_install_resolver` идёт
  `embedded_root`, и `cache add` передаёт `None` (`add.rs:118`). То есть
  «vibe-embedded»-реестр PROP-030 §2 (производный от VVM-установки) для
  `cache add` не подключается никогда. Локальный источник у `cache add`
  ровно один — **project-local** `<project_root>/vibevm/vibepacks`
  (`crates/vibe-package-source/src/builder.rs:187–198`,
  `crates/vibe-package-source/src/project_local.rs:31`,
  `vibe_core::layout::current_packages_root()` —
  `crates/vibe-core/src/layout.rs:165`, возвращает `vibepacks_root()` — `:90`).
- Флага `--registry` у `cache add` нет (проверено на `--help`; в заглушке
  аргументов `registry: None`, `add.rs:168`).

### 3. Раскладка store живьём

Проверено в изолированном окружении (см. «Свидетельства», проба 1). Дерево
после `cache add` одного in-tree пакета:

```text
<tmp>/home/settings/cache/
└── org.vibevm.world/
    └── multi-user-planning/
        ├── v1.0.0/            (27 файлов, дерево пакета дословно, .git отсутствует)
        └── v1.0.0.sha256      («sha256:e1a1…a051\n», одна строка)
```

Sidecar — родной брат каталога версии, не файл внутри него (иначе хэш покрывал
бы сам себя): `crates/vibe-registry/src/store.rs:99–120`.

### 4. Функции трёх источников для `vibe-doc`

Крейта `vibe-doc` в дереве ещё нет (`ls crates/` даёт только `vibe-specdoc`),
поэтому ниже — точки вызова, которые он должен использовать.

**Источник «store».** `vibe_registry::store::{list_all, list_versions, lookup,
recorded_hash, entry_dir, store_root}` — таблица в п. 1. Типичный сценарий
читателя: `list_all()` даёт инвентарь, `lookup(group, name, version)` даёт
`PathBuf` корня дерева пакета, дальше — обычное чтение файлов. Ничего, кроме
каталога, читать не нужно: раскладка **и есть** индекс
(`crates/vibe-registry/src/store.rs:13–19`). Машиночитаемый эквивалент из CLI —
`vibe cache list --json` (поля `root`, `count`, `packages[].{group,name,version}`).

**Источник «lock проекта».**

- Тип: `vibe_core::manifest::Lockfile` — `crates/vibe-core/src/manifest/lockfile.rs:81`;
  имя файла `Lockfile::FILENAME = "vibe.lock"` — `:493`.
- Чтение: `Lockfile::read(path: impl AsRef<Path>) -> Result<Self>` — `:511`
  (запись — `write`, `:537`; пустой — `empty`, `:495`).
- Строки: `Lockfile::packages: Vec<LockedPackage>` — `:85`; `LockedPackage` —
  `:306`, поля `kind` (`:307`), `name` (`:308`), `group` (`:312`),
  `version` (`:313`), `content_hash` (`:358`), `registry` (`:333`),
  `source_url` (`:341`), `source_ref` (`:347`), `resolved_commit` (`:353`).
- Материализованное содержимое лежит не в локе, а в слоте:
  `vibe_workspace::vibedeps::slot_abs_path(workspace_root, group, name, version)`
  — `crates/vibe-workspace/src/vibedeps.rs:69`, то есть
  `<root>/vibevm/vibedeps/<group>.<name>/<version>/`. Портируемый
  относительный путь — `slot_rel_path` (`:63`), проверка наличия —
  `is_materialised` (`:82`).

**Источник «реестр».**

- Трейт `vibe_registry::Registry` — `crates/vibe-registry/src/lib.rs:114`, три
  вопроса: `list_versions` (`:115`), `resolve` (`:121`), `fetch` (`:123`).
  Реализации: `LocalRegistry` (`crates/vibe-registry/src/local_registry.rs:45`,
  `list_versions` `:58`, `resolve` `:141`, `fetch` `:191`),
  `GitMonorepoRegistry`, `GitPerPackageRegistry`.
- Обход нескольких реестров: `vibe_registry::MultiRegistryResolver`,
  конструктор `open(registries, mirrors, overrides)` —
  `crates/vibe-registry/src/multi_registry_resolver/mod.rs:420`; билдеры
  `with_offline`, `with_store_root`, `with_git_packages`,
  `with_locked_packages`, `with_strict_auth` (применяются в
  `crates/vibe-package-source/src/builder.rs:81–89`).
- «Резолвить и положить в store» одним вызовом:
  `InstallSource::resolve_and_fetch(pkgref, store_root, expected_hash) -> Result<CachedPackage, RegistryError>`
  — `crates/vibe-install/src/lib.rs:139`. Результат `CachedPackage` —
  `crates/vibe-registry/src/lib.rs:204`: `cache_dir` (`:208`, абсолютный путь
  записи в store), `manifest` (`:210`), `content_hash` (`:214`),
  `source_uri` (`:217`), `registry_name` (`:222`).
- Готовая сборка резолвера из манифеста проекта:
  `vibe_package_source::build_install_resolver(options, manifest, embedded_root, project_root, global, offline, locked)`
  — `crates/vibe-package-source/src/builder.rs:136`.
- Текстовый поиск по реестрам (`vibe search`) — отдельный слой
  `crates/vibe-registry/src/search/` (индекс-серверы PROP-005 и
  `full_scan_github_org`, `crates/vibe-registry/src/search/full_scan.rs:128`);
  для получения пакета он не нужен.

**Store как самостоятельный источник резолюции.** Это не отдельный API, а
поведение резолвера (PROP-010 §2.6): `store_root` прокидывается в
`MultiRegistryResolver` (`crates/vibe-package-source/src/builder.rs:79–87`), и
`crates/vibe-registry/src/multi_registry_resolver/offline.rs` обслуживает
попадания в store — `resolve_offline` (`:32`), `store_availability_fallback`
(`:84`), `store_hit` (`:97`), `fetch_from_store` (`:134`). Два ограничения,
важных для сайта: попадание в store **ездит на пине из lockfile** (`offline.rs:92–103`:
версия берётся из локальной lock-строки), и манифест записи store обязан нести
таблицу `[package]` (`offline.rs:145`). Наконец, при пустом наборе реестров и
`--offline` непустой store сам по себе снимает отказ
(`crates/vibe-package-source/src/builder.rs:253–258`).

## Расхождения с решениями

`REVIEW:` **`vibe cache add` печатает «already present — bytes untouched
(write-once)» даже тогда, когда байты записи в store были заменены.**
`crates/vibe-cli/src/commands/cache/add.rs:70` вычисляет `was_present` через
`lookup(...)` *до* выборки, а сама выборка (`add.rs:72`) уходит в
`insert_current_at`, который при расхождении хэша удаляет и перевставляет запись
(`crates/vibe-registry/src/store/refresh.rs:24–56`). Живая проба B2/B4 (см.
`A0.20-host-from-source.md`): отчёт — `0 fetched, 1 already present`, а
содержимое записи изменилось с `REVISION-ONE` на `REVISION-TWO` и затем на
`REVISION-THREE`. Ни одного решения вижена это не нарушает — фиксируется как
дефект вывода CLI, на который сайт не должен опираться: признак «обновилось ли
содержимое» надо брать из sidecar-хэша, а не из строки отчёта.

## Открытые вопросы

- Гарантия свежести git-источника. Константа
  `DEFAULT_FRESHNESS_SECS = 3600` (`crates/vibe-registry/src/registry_cache.rs:20`)
  расходуется только в `should_pull` (`crates/vibe-registry/src/git_registry.rs:121`,
  `:294`), то есть в монорепозиторном реестре; per-package-путь обновляет клон
  в месте (`BringIntent::RefreshExisting`,
  `crates/vibe-registry/src/git_package_registry/fetch.rs:64`, `:275`). На пробе
  повторный `cache add` через считанные секунды подхватил новый коммит ветки.
  Не установлено, есть ли путь, где TTL всё-таки задержит новый HEAD ветки.
- Не проверялось живьём чтение store после переноса `$VIBE_SETTINGS` на другую
  машину/том (гипотеза «корень движется с VIBE_SETTINGS» взята из кода и
  подтверждена только в пределах одной машины).
