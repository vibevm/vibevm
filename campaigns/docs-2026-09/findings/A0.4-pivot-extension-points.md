### 1. Как устроено сегодня

#### 1.1 `Block` и соседние типы (`crates/vibe-specdoc/src/doc.rs`)

`SpecDoc` (`doc.rs:36-49`) — четыре поля: `title: Option<Title>` (`:41`),
`status: Option<StatusEl>` (`:43`), `preamble: Vec<Block>` (`:45`),
`sections: Vec<Section>` (`:48`). `Section` (`doc.rs:76-87`): `id:
Option<String>` (`:80`), `title: String` (`:82`), `status:
Option<StatusEl>` (`:84`), `blocks: Vec<Block>` (`:85`), `sections:
Vec<Section>` (`:86`). Уровень заголовка не хранится — он равен глубине
вложенности (`doc.rs:73-75`).

`Block` (`doc.rs:96-119`) — пять вариантов, ровно:

| вариант | поля | строка |
| --- | --- | --- |
| `Paragraph(Unit)` | один юнит | `doc.rs:99` |
| `List { ordered: bool, items: Vec<Unit> }` | плоский прогон пунктов | `doc.rs:102` |
| `Table { rows: Vec<Vec<Unit>> }` | `rows[0]` — шапка, если была | `doc.rs:107` |
| `Fence { lang: Option<String>, fact: Option<String>, text: String }` | info-строка, привязка `@fact/code:<ID>`, дословный текст | `doc.rs:112-116` |
| `Quote(Unit)` | один юнит без префиксов `>` | `doc.rs:118` |

Деривы: `#[derive(Debug, Clone, PartialEq, Eq)]` (`doc.rs:96`). **Нет**
`#[non_exhaustive]`, **нет** serde — ни один проволочный формат от
`Block` не зависит, добавление вариантов ломает только `match`-ы (см.
п. 5.3).

`Unit` (`doc.rs:124-136`) — `fact: Option<Fact>` + `text: String`; инлайн
остаётся Markdown'ом дословно (`doc.rs:129-135`, закон
`##INLINE-STAYS-MARKDOWN`, `doc.rs:10-14`). `Fact` (`doc.rs:141-150`) —
`id: Option<String>`, `requirements: Option<ArtifactRequirements>`,
`status: Option<StatusEl>`; `Fact::is_meaningful` (`doc.rs:155-157`)
решает, сериализуется ли факт вообще.

**Идентичность блока: её нет.** Ни один вариант `Block` не несёт id.
Адресуемы только: якорь заголовка документа (`Title::id`, `doc.rs:54`),
якорь секции (`Section::id`, `doc.rs:80`) и id факта внутри юнита
(`Fact::id`, `doc.rs:146`). Все три чеканятся в одно общее пространство
имён: `Parser::mint_heading` (`xml_in.rs:472-483`), `Parser::mint_fact`
(`xml_in.rs:485-498`), проверка дублей — `check_ids`
(`xml_in.rs:500-515`). Это прямо влияет на A0.25.

### 2. Черновик вариантов `Block` для словаря документации и атрибута `when`

Словарь D-10 даёт **шесть блочных элементов** (`example`, `rule`,
`derived`, `note`, `figure`, `prompt`) и **пять детей** (`run`, `expect`
у `example`; `needs`, `outcome`, `assert` у `prompt`); форма
`example ref="…"` — седьмой вариант, если держать её отдельным
конструктором (пакет говорит «семь элементов» — черновик ниже даёт ровно
семь вариантов, считая `ExampleRef`; альтернатива — свернуть её в
`Option<String>` внутри `Example`).

```rust
/// Блоки жанра документации (D-10). Легальны только когда читатель
/// работает в словаре документации; в словаре спек эти имена сохраняют
/// нынешний смысл (именованная секция либо громкая ошибка).
pub enum Block {
    // … пять существующих вариантов без изменений …

    /// `<example>`: команда и её золотой вывод.
    Example {
        /// `<run>` — командная строка, дословно.
        run: String,
        /// `<expect>` — золотой вывод; `None`, когда пример показывает
        /// только команду. Сравнение — по правилам нормализации, которые
        /// живут в `vibe-doc`, не в пивоте.
        expect: Option<String>,
    },
    /// `<example ref="<якорь>"/>`: форма перевода — тело берётся из
    /// примера источника по этому якорю, своего текста нет.
    ExampleRef { r#ref: String },
    /// `<rule address="spec://…#якорь"/>`: живая цитата текущего текста
    /// спеки. Пинов ревизий нет: проверяется только существование якоря.
    /// Сам текст цитаты НЕ состояние пивота — он подставляется на сборке.
    Rule { address: String },
    /// `<derived command="vibe --help" lang="text"/>`: вывод команды,
    /// порождаемый на сборке. Текст не хранится (D-10).
    Derived { command: String, lang: Option<String> },
    /// `<note kind="…">`: врезка — один юнит, как абзац.
    Note { kind: NoteKind, body: Unit },
    /// `<figure media="…">`: картинка из `[media]` пакета с подписью.
    Figure { media: String, caption: Unit },
    /// `<prompt>`: промпт агенту.
    Prompt {
        /// Тело промпта, дословно (как `Fence::text`).
        body: String,
        /// `<needs>` — скилл, MCP, сеть; закрытая лексика на уровне
        /// `vibe-doc`, в пивоте строки.
        needs: Vec<String>,
        /// `<outcome>` — что увидит человек; один юнит.
        outcome: Unit,
        /// `<assert>` — одна и более шелл-проверок после работы агента.
        asserts: Vec<String>,
    },
}
```

Замечания к черновику, вытекающие из кода:

- Тексты `run`/`expect`/`body`/`asserts` ведут себя как `Fence::text`
  (`doc.rs:112-116`): дословные, многострочные, без инлайн-грамматики.
  Их писатель обязан экранировать через `esc_text` (`xml_out.rs:284-296`)
  или CDATA — сегодня CDATA разрешена **только** внутри `<fence>`
  (`xml_blocks.rs:263-266`), это придётся расширить на новые текстовые
  дети явным списком, а не отменой проверки.
- `Note`/`Figure` держат `Unit`, а не `String`: это даёт им бесплатно
  якорь и статус (`Fact`), то есть `<note>` можно адресовать
  `spec://…#якорь` тем же механизмом, что и абзац.
- `NoteKind` — закрытый enum в `vibe-specdoc` с `parse`/`Display`, по
  образцу `Stage`/`State`; подсказки «did you mean» бесплатны через
  `progress_core::model::nearest`, который уже используется в
  `xml_support.rs:170-193`.

#### Где держать `when`

Три варианта, с ценой по коду:

1. **Поле в каждом новом варианте** (`when: Option<Cond>` в `Example`,
   `Note`, …). Дёшево, ничего не ломает. Цена: `when` нельзя повесить на
   `<p>`, `<list>`, `<table>` — а именно это обычно и нужно странице
   («этот абзац только на Windows»). Формулировка D-10 «атрибут `when`
   **на блоках**» при таком выборе выполняется частично.
2. **Обёртка слота блока** — `Section.blocks: Vec<BlockNode>`,
   `SpecDoc.preamble: Vec<BlockNode>`, где
   `pub struct BlockNode { pub when: Option<Cond>, pub block: Block }`.
   Семантически честно: условие — свойство позиции в потоке, а не рода
   блока; одинаково работает для `p` и для `example`. Цена: 48
   упоминаний `Block::` внутри крейта плюс две внешние сигнатуры
   (`vibe-facts/src/report.rs:66`, `vibe-workspace/src/vibedeps/derived.rs:477`)
   — правка механическая, её ведёт компилятор.
3. **Вариант-обёртка** `Block::Guarded { when: Cond, inner: Box<Block> }`.
   Сохраняет `Vec<Block>`, но допускает бессмысленную вложенность
   `Guarded(Guarded(…))` и заставляет каждый обход рекурсировать.

**Рекомендация: вариант 2.** Он единственный выполняет D-10 буквально и
не создаёт нелегальных состояний. `Cond` — закрытый список (ОС, агент),
такой же enum с `parse`, как `NoteKind`.

### 3. Где включать «режим жанра документации» (развилка F-08)

**Рекомендация — параметр читателя, пробрасываемый загрузчиком; ожидание
пакета подтверждается, с одной поправкой.**

Поправка: `load.rs` **не может** взять kind сам. Загрузчик чист и
решает по одному расширению файла (`project_spec_text`,
`load.rs:125-135`; «Pure: no filesystem access, no clock, nothing but
`path`'s extension and `raw`», `load.rs:108-109`), а крейт по закону
отделимости не зависит ни от одной подсистемы vibevm — только от
`progress-core` и `quick-xml` (`lib.rs:50-52`, `Cargo.toml`
`[dependencies]`). Значит `PackageKind` (`crates/vibe-core/src/package_ref/kind.rs:31-54`)
в `vibe-specdoc` не приходит никогда; в пивоте живёт **свой** маленький
тип, а отображение «kind пакета → словарь» делает вызывающая сторона.

Предлагаемая форма (аддитивная, ни один существующий вызов не ломается):

```rust
/// Какой словарь открыт читателю.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub enum Vocabulary {
    /// Словарь спек — сегодняшний закрытый набор (умолчание).
    #[default]
    Spec,
    /// Словарь спек плюс жанр документации (D-10).
    Doc,
}

pub fn from_xml(xml: &str) -> Result<SpecDoc>;                       // = from_xml_with(xml, Vocabulary::Spec)
pub fn from_xml_with(xml: &str, vocab: Vocabulary) -> Result<SpecDoc>;
pub fn load_spec_text_with(path: &Path, vocab: Vocabulary) -> Result<(String, SourceKind), LoadError>;
pub fn project_spec_text_with(path: &Path, raw: &str, vocab: Vocabulary) -> Result<(String, SourceKind), LoadError>;
```

Путь параметра внутри: `load_spec_text_with` → `project_spec_text_with`
→ `from_xml_with` → поле `Parser::vocab` (структура `Parser`,
`xml_in.rs:74-82`) → три плеча диспетчера (`xml_in.rs:322`, `:436`,
`xml_blocks.rs:18`). Ни один обход бэкендов не трогается.

Кто выставляет `Vocabulary::Doc`: та сторона, что знает пакет. Данные
уже на месте — `PackageManifest.kind`
(`crates/vibe-core/src/manifest/package.rs:87`) и `LockedPackage.kind`
(`crates/vibe-core/src/manifest/lockfile.rs:307`). Ближайшая точка, где
имя пакета уже в руках у конвертера:
`crates/vibe-workspace/src/vibedeps/derived.rs:410` (параметр
`package: &str`, вызовы пивота — `:441`, `:456-457`). Всего сайтов
вызова `load_spec_text` / `project_spec_text` / `from_xml` вне крейта —
37 упоминаний, из них 15 не тестовых; аддитивные `*_with` оставляют их
как есть.

**Что будет, если элемент словаря документации встретится в обычном
пакете — рекомендация: ошибка, а не игнор.** Обоснование по текущему
поведению:

- Неизвестный элемент сегодня — громкая ошибка с именем и позицией
  (`xml_in.rs:344-351`, `:456-463`, `xml_blocks.rs:163-166`); тихих
  пропусков в диалекте нет вообще (`xml_in.rs:12-15`). Игнор был бы
  первой дырой в этом законе.
- Проверено эмпирически: `<note>` в обычном документе уже отвергается
  (см. Свидетельство 2). То есть «ошибка» — это не новое поведение, а
  сохранение нынешнего; менять придётся только **текст** сообщения:
  вместо «the dialect has no `<note>` element» — «`<note>` принадлежит
  словарю документации; он открыт только в пакетах kind `doc`».

**Но сама закрытость словаря ломается на четырёх именах — это главный
риск расширения.** Имена `example`, `rule`, `derived`, `run` **уже
заняты** в живом корпусе: они читаются как *именованные секции*
(`<example title="…">`). Список фактов — в Свидетельстве 1 и 3. Следствия:

- Плечо `match` с литеральным именем стоит **выше** плеча именованной
  секции (`xml_in.rs:322` против `:335`, `:436` против `:448`), поэтому
  добавление литерала `"example"` в блочный список молча переопределит
  смысл этих файлов — если словарь открыт. Гейт по kind закрывает этот
  риск для `flow`/`feat`-пакетов (где все находки и живут), но **не**
  внутри пакета документации.
- Писатель симметрично сломается: `anchor_is_elementable`
  (`xml_out.rs:28-61`) сегодня возвращает `true` для `example`, и секция
  с якорем `#example` внутри doc-пакета выедет как `<example title=…>` —
  документ, который собственный читатель прочтёт неоднозначно. Значит
  чёрный список (`xml_out.rs:44-60`) обязан пополниться всеми именами
  словаря, **и** этот предикат тоже становится зависимым от
  `Vocabulary` (иначе doc-пакет и spec-пакет пишут по-разному один и тот
  же IR).
- Дешёвая страховка, уже используемая диалектом: различать не по имени,
  а по **атрибуту-дискриминатору** — так сделано для фактов
  (`fact="true"`, `xml_facts.rs:78-99`). Симметричное правило для жанра:
  блок документации **не несёт** `title=`, а именованная секция его
  несёт всегда (`xml_in.rs:383-388` — `title` обязателен). Тогда даже
  при открытом словаре `<example title="…">` остаётся секцией, а
  `<example>` без `title` — блоком. Это снимает конфликт полностью и
  ничего не стоит.

### 4. Нужен ли `md_in` для новых элементов — **нет, подтверждено**

`from_markdown` — адаптер, а не парсер: всю лексику делает
`progress_core::parse::parse_document` (`md_in.rs:2-9`, `:37`), а
`Adapter::run` (`md_in.rs:70-140`) лишь перекладывает результат. Единицы,
которые может отдать сканер, перечислены в `BlockKind`
(`crates/progress-core/src/doc.rs:100-111`): `Text`, `Code`, `Comment`,
`MarkerOnly`, `Heading` — пяти достаточно ровно для пяти нынешних
вариантов. Нового блочного рода в Markdown не существует, и придумать его
в `vibe-specdoc` нельзя: пришлось бы менять грамматику `progress-core`,
то есть закон «XML-диалект — подмножество Markdown»
(`doc.rs:4-8`, `lib.rs:31-33`). Вывод: `md_in` не расширяется; авторинг
документации — только XML.

**Однако у этого есть цена на стороне `md_out`, и её надо принять
осознанно.** Загрузчик хостовых потребителей проецирует любой `.xml` в
Markdown (`load.rs:95-101`, `:125-135`) — «XML never reaches a scanner
raw» (`load.rs:4-5`). Значит:

- либо `md_out` получает проекцию для каждого нового блока (например,
  `example` → fence с командой + fence с выводом), и тогда проекция
  **не** переживёт обратный разбор в тот же IR — `from_markdown` вернёт
  `Fence`, а не `Example`;
- либо doc-документы просто не ходят через хостовый загрузчик.

В первом случае закон (а) из `redbook_roundtrip.rs:179-193` для
doc-жанра не выполняется, и `convert(…, Direction::ToMarkdown)`
классифицирует такой документ как `Conversion::IrDivergent`
(`convert.rs:93-97`: `if ir != back_ir`). Корпусные тесты при этом
останутся зелёными — они стартуют от Markdown и новых блоков не
порождают. Рекомендация: закрепить это тестом-ожиданием («doc-жанр
необратим через Markdown»), а не открыть молча.

## Расхождения с решениями

`REVIEW: четыре имени словаря D-10 — example, rule, derived, run — уже
имеют в живом корпусе другой смысл (именованные секции, 8 канонических
файлов, 32 файла с копиями зависимостей; Свидетельство 1 и 3), против
D-10.` Решение не переписываю. Конфликт снимается без изменения словаря
двумя мерами, обе внутри духа D-10: (1) гейт по kind (уже в решении)
закрывает spec-пакеты; (2) дискриминатор «блок жанра не несёт `title=`»
— по образцу `fact="true"` — закрывает и doc-пакеты. Нужно решение
владельца, принимается ли мера (2) как часть словаря.

`REVIEW: kind пакета doc в коде отсутствует — PackageKind = flow | feat |
stack | tool | mcp | lang (crates/vibe-core/src/package_ref/kind.rs:31-54,
ALL :68-75), против D-10 «включаемый по kind содержащего пакета (doc)».`
Это не противоречие, а недостающая предпосылка: седьмой kind придётся
завести (манифест, лок, валидация, `vibe list` и т. д.) — отдельная
работа вне пивота.

Прочее расхождений не даёт: секция `[media]` пакета, на которую ссылается
`figure`, в манифесте тоже пока отсутствует (grep по
`crates/vibe-core/src/manifest/` — совпадений нет).

## Открытые вопросы

1. **Проекция doc-жанра в Markdown.** Решить явно: `md_out` получает
   лучшую-возможную проекцию (и doc-документ становится необратимым,
   `Conversion::IrDivergent`), либо doc-документы не ходят через
   `load_spec_text` вовсе, и это правило записано. Сейчас загрузчик
   один на всех (`load.rs:4-5`), обойти его молча нельзя.
2. **Зависит ли писатель от словаря.** Если `anchor_is_elementable`
   сделать жанрозависимым, один и тот же IR будет писаться в разные
   байты в doc- и spec-пакете. Если не делать — doc-пакет может выдать
   неоднозначный документ. Нужна развилка (кандидат на отдельный F-номер).
3. **Нумерация пунктов `assert`/`needs`** и вообще адресуемость детей
   (`spec://…#якорь` внутри `prompt`) — в D-10 не определена; пивот
   сегодня умеет адресовать только юнит-носитель.
4. **Куда попадают правила нормализации `expect`.** В пивоте их держать
   нельзя (он не сравнивает, он моделирует); ожидание — `vibe-doc`.
   Подтверждения в коде нет, крейта `vibe-doc` в workspace нет
   (`Cargo.toml`, `members`).
