# A0.28 Цена рендера хоста

Дата: 2026-09-11
Дерево: b1291b06

## Ответы

### 1. Откуда `vibe self install latest` берёт «последнюю» версию

**Из текущего рабочего дерева, а не из тегов.** Внутри чекаута селектор
`latest` без `--mirror` включает ветку in-tree: сборка идёт из корня
найденного дерева как есть, git читается только ради ярлыка версии.

- `crates/vibe-cli/src/commands/vvm/model.rs:232` — `"latest" => Selector::Latest`;
  теги разбираются отдельными ветками (`looks_like_semver_tag`, `Kind::Tag`).
- `crates/vibe-cli/src/commands/vvm/mod.rs:222` —
  `let prefer_in_tree = matches!(selector, model::Selector::Latest) && args.mirror.is_none();`
  и `mod.rs:225–232` — при найденном корне источником становится сам
  `root` (`Origin::External`), никакого `checkout`/`fetch` нет.
- `crates/vibe-cli/src/commands/vvm/source.rs:77` — `find_source_root` ищет корень
  вверх по каталогам по признаку «есть `Cargo.toml` и `crates/vibe-cli`».
- `crates/vibe-cli/src/commands/vvm/source.rs:88–96` — `label_in_tree`: `git rev-parse HEAD`
  плюс имя текущей ветки. Это **ярлык и провенанс**, не выбор исходников:
  незакоммиченные правки рабочего дерева попадают в бинарник.
- Теги читаются только на других путях: `stable` → `highest_semver_tag`
  (`source.rs:176–179`), `X.Y.Z` → `Kind::Tag`. Для `latest` вне дерева (клон
  зеркала) — `source.rs:166–175`: `refs/remotes/origin/main`, то есть тоже
  ветка `main`, а не тег. Спецификация: PROP-019 §2.3 `##SEL-LATEST` —
  «`latest` → tip of branch `main`» (`PROP-019-version-manager.xml:144`).
- Бинарное исполнение с `latest` запрещено:
  `mod.rs:200–207` → `VvmError::BinaryFetchUnavailable`.

Практическое следствие для рендерера: «текущее состояние `main`» на сервере —
это буквально то, что лежит в выкладке. Чтобы это было именно `main`, выкладку
надо синхронизировать явно (свежий клон или жёсткая синхронизация с
`origin/main`); сам `vibe`/`cargo` за этим не следит.

### 3. Влезает ли пересборка раз в час на четырёхъядерном сервере

Да, с запасом. Это **оценка порядка величины**, а не факт: пересчёт по числу
ядер груб, модель серверного процессора здесь не известна и не выяснялась.

- Холодная сборка параллелится хорошо (354 крейта): переход 16 → 4 потока даёт
  примерно ×2.5–3.5, плюс более медленное ядро — **порядка 20–40 минут**.
  Платится один раз на прогрев контейнера, дальше кэш живёт.
- Инкрементальная сборка после коммита в `crates/` упирается в одну
  последовательную кодогенерацию (`codegen-units = 1`) — число ядер почти не
  меняет её, важна скорость ядра. 9800X3D — очень быстрое десктопное ядро;
  серверное обычно в 1.5–2.5 раза медленнее → **порядка 6–16 минут**.
- Коммит, не трогающий `crates/` (обычный случай кампании документации), стоит
  **no-op**: 6 с здесь, порядка 15–30 с там. Отличать такие коммиты вручную не
  нужно — cargo сам решает это по отпечаткам.

То есть при худшем сценарии (каждый час — коммит в код) сборка занимает
меньше четверти часа из часа; при типичном — секунды.

### 4. Два варианта для `derived` с ценой

**(а) Сборка в контейнере-рендерере с дебаунсом — рекомендация.**

- Рендереру не нужен `vibe self install`: достаточно
  `cargo build --release -p vibe-cli`. `self install` дополнительно собирает
  `vibe-index` (+6 минут по замеру) и меняет пользовательский стор.
  (Если он всё же используется, кэш сборки у него общий:
  `crates/vibe-cli/src/commands/vvm/store.rs:190` — `<root>/vibevm/build`.)
- Разумный дебаунс при измеренном времени: **10 минут на профиле `release`**.
  Тогда серия коммитов схлопывается в одну сборку, а отставание сайта от `main`
  в худшем случае — дебаунс плюс сборка, порядка 25 минут. Меньше 5 минут
  ставить бессмысленно: сама сборка длиннее.
- **Профиль `dev` вместо `release` — самый дешёвый рычаг.** Вывод `vibe --help`
  у обоих бинарников совпадает побайтово, а инкрементальная сборка дешевле в
  10 раз (23 с против 231 с), холодная — в 4 раза (1m 42s против 6m 42s). На
  `dev` разумен дебаунс **3–5 минут**, отставание — порядка 5–7 минут. Цена:
  бинарник 103 МБ вместо 74 МБ и кэш 7.2 ГБ вместо 2.1 ГБ. Это выбор
  реализации рендерера, решения D-07/D-16 он не затрагивает.
- Требования к контейнеру: тулчейн Rust (канал `stable`, `rustc 1.93.1`),
  постоянный том под `CARGO_TARGET_DIR` (2.1 ГБ на `release`, 7.2 ГБ на `dev`)
  и под кэш реестра, сеть для первой загрузки 573 пакетов. Нужен
  single-flight: две сборки одновременно cargo сам сериализует на блокировке
  каталога, второй рендер просто ждёт — это надо учесть в таймаутах.
- Что в замеры не вошло и добавится на сервере: `git fetch`/синхронизация
  выкладки, первая загрузка зависимостей, старт контейнера.

**(б) Артефакт `derived.json` от сборки продукта — только по слову владельца.**
Здесь лишь перечень того, что потребовалось бы; ничего не предлагается к
внедрению.

1. Манифест derived-команд (что запускать, с какими аргументами, в каком
   каталоге и окружении), доступный сборке продукта, а не только сайту.
2. Производитель на стороне продукта (например, цель `cargo xtask`), который
   после сборки прогоняет каждую команду в чистой песочнице и пишет
   `derived.json`: команда, код выхода, stdout, stderr.
3. Транспорт артефакта до сайта и правило на случай, когда артефакта нет или
   он старше документации: отказ сборки сайта или явный откат к сборке.
4. Выигрыш: сайту не нужен ни тулчейн Rust, ни 2–9 ГБ кэша, ни минуты сборки —
   рендер становится чистыми данными. Цена: новый derived-блок нельзя добавить
   без пересборки продукта, репозитории связываются через манифест.
5. Отдельный вопрос владельцу: чем помечать артефакт. Идентичность сборки в
   нём недоступна (D-27), остаётся только коммит, который производитель знает
   из собственной выкладки, а не из бинарника.

## Открытые вопросы

- Модель процессора и реальное число ядер сервера не выяснялись (правило R-25),
  поэтому пересчёт на четыре ядра — только порядок величины. Разница
  Windows/NTFS против Linux в Docker не измерена; обычно Linux несколько
  быстрее на той же машине.
- В (а) не входит первая загрузка 573 пакетов из реестра: кэш crates.io на
  дев-машине был прогрет. Сколько это минут и мегабайт на холодном контейнере —
  не измерено.
- Не проверено, как ведёт себя инкрементальная сборка после коммита, который
  трогает нижний крейт (например `vibe-core`): замер сделан для правки в самом
  `vibe-cli`. Правка нижнего крейта пересоберёт всех его потребителей и будет
  дороже 3m 50s, но дешевле холодных 6m 42s.
- `derived.json` (вариант б) не прототипировался: описан только перечень
  требований.
