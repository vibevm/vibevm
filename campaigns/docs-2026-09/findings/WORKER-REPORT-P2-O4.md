## A2.0 — крейт по чеклисту §2.8 (`f8220dd1`)

Семь пунктов чеклиста, по порядку:

1. `cargo xtask add-cell --help` — глагола `add-cell` в `xtask` нет
   (`cargo xtask --help` перечисляет `conform`, `codegen`, `specmap`,
   `sync-engines`, `wire-diff`, `bridge`, `dist`, …). Крейт заведён по
   образцу ближайшего тонкого библиотечного крейта, `vibe-trace`.
2. Член workspace в обоих списках (`members` и `default-members`),
   `license-file.workspace = true`, `publish = false` буквально.
3. Первая строка `lib.rs` после doc-комментария —
   `specmark::scope!("spec://org.vibevm.core/vibevm/common/PROP-057#PIPE-LIBRARY")`.
4. Один `thiserror`-enum на слой (`DocError`, девять вариантов); каждое
   сообщение цитирует нарушенный `spec://` и несёт `fix:`; `#[spec(implements
   = …)]` на самом enum (этого потребовал conform);
   `unwrap`/`expect` в доменной логике нет (конформ-гейт `no-unwrap-in-domain`
   по крейту чист).
5. Публичные швы несут doctest: `pages::read_package`, `DocError`,
   `examples::command::{split, parse}`, `examples::normalize::replace_path_spellings`,
   `examples::jtd::{validate, with_vocabulary, split_documents}`, крейт целиком.
6. **Периметр conform: крейт вошёл в `gated`**, не в `exempt`. Основание —
   предпосылки гейта выполнены с первого коммита (швы доктестированы,
   слой ошибок несёт REQ-ребро), так что откладывать было бы нечего.
   `cargo xtask conform check` по путям `crates/vibe-doc/**` и
   `crates/vibe-cli/src/{cli,commands}/doc.rs` — **ноль находок**.
7. `cargo xtask specmap` — **0 suspects**, 0 неразрешённых хостовых рёбер;
   адрес `PROP-057#PIPE-LIBRARY` резолвится. Сам `specmap.json` я **не
   коммитил** — см. «Что не сделано».

В скелете открыт ровно один модуль — `pages`: единственное место, где
делается выбор словаря пивота по виду пакета (`Vocabulary::Doc`). Пивот

Обход возвращает **обе** половины — прочитанные страницы и непрочитанные с

проверка, падающая на первом дефекте, показывает один дефект за прогон.

## A2.9 — раннер примеров (`5c472381`)

### Форма фикстуры

Фикстура — **рецепт**, а не закоммиченное дерево: `examples/<фикстура>/example.toml`
называет родителя (`from`) и шаги, превращающие его состояние в это.
Шагов четыре вида, и три файловых появились потому, что их требует сама
таблица фикстур кампании:

| Шаг | Зачем |
|---|---|
| `run` | команда из того же закрытого набора программ, что и примеры |
| `copy = { from, to }` | `hello-deploy` — копия проекта под другим именем |
| `append = { path, text }` | `workspace-root` и `hello-deploy` дописывают таблицу, которую печатает сама страница, в файл, сгенерированный продуктом |
| `edit = { path, from, to }` | `hello-vibe-scrape` меняет два значения в сгенерированном `contract.toml` |

Альтернатива — написать сгенерированный файл руками в `tree/` — отвергнута:
тогда фикстура проверяла бы не продукт, а его транскрипцию.

Файлы, которых рецепт произвести не может (два манифеста участника
workspace и `NOTES-FLOW.md`), лежат в `examples/<фикстура>/tree/` и
накладываются поверх состояния родителя.

Заведено **семнадцать** фикстур: `none`, `empty`, `hello-vibe-empty`,
`hello-vibe`, `hello-vibe-relay`, `hello-vibe-removed`,
`hello-vibe-registry`, `hello-vibe-cwd`, `hello-cargo`, `hello-deploy`,
`hello-vibe-scrape`, `project`, `flow-slot`, `package-spec`,
`workspace-root`, `workspace`, `host`. Не заведены `package-notes` и
`docs-store`: единственные примеры на них объявлены отложенными, и раннер
до фикстуры не доходит.

### X-025 — реестр внутри фикстуры

`examples/none/tree/registry/org.vibevm.world/wal/v1.0.0/` — копия девяти
файлов пакета; `home/registry.toml` фикстуры объявляет
`url = "file:///${REGISTRY}"`, и подстановка даёт этот каталог внутри
песочницы. Установка резолвится без сети и **без чтения дерева, которое
раннер как раз проверяет**.

Цена решения — ровно одна строка на одной странице: `vibe list --json`
печатает `source_url` реестра, из которого пакет пришёл, и она сменилась с
`file:///<REPO>/vibevm/vibepacks/org.vibevm.world/wal/v1.0.0` на
`file:///<TMP>/registry/org.vibevm.world/wal/v1.0.0`. См. «Разбор
расхождений».

### Изоляция и трипвайр

Окружение ребёнка: выставляются `VIBE_SETTINGS` (в нативном написании) и
`NO_COLOR`; **удаляются** `VIBE_OFFLINE`, `VIBE_UNATTENDED`,
`VIBE_INVOKED_BY`, `VIBE_NO_DEFAULT_REGISTRY`, `VIBETERM`, `VIBEFRAME`,
`VIBE_REGISTRY_CACHE`, `VIBEVM_SEARCH_CACHE_DIR`, `VIBEVM_INSTALL_ROOT`.
`--offline` и `--assume-yes` стоят в самой команде примера.

Трипвайр (по образцу `tools/user-home-tripwire.sh`) снимает состояние **до**
прогона и сверяет **после**, по двум предметам:

- настоящий `~/.vibe` целиком (путь, размер, mtime по каждому файлу);
- в дереве-исходнике — не всё дерево (чекаут с `target/` — миллионы файлов,
  обход дороже прогона), а ровно те места, куда `vibe`, как наблюдалось,
  пишет: `vibevm/vibedeps`, `.vibe`, `vibe.lock`, `vibe.toml`, плюс
  **имена** верхнего уровня, чтобы новый посторонний файл в корне был
  замечен. Страницы самого doc-пакета трипвайр намеренно не покрывает:
  туда пишет `--accept`.

За все прогоны трипвайр не срабатывал ни разу.

### Раннер — не оболочка

Команда разбирается самим раннером и диспетчеризуется в закрытый набор:
`vibe` (собранный бинарник), `cargo` (только для рецептов фикстур) и
собственный `cat` (страница показывает содержимое файла, а не вывод
программы; на Windows `cat` попросту нет). Всё прочее — громкий отказ с
именем программы; конвейер или редирект отвергаются словами «нужна
оболочка, а раннер ею не является». Причина в читателе: страница, которой
нужна оболочка, показывает команду, которую читатель не может скопировать в
свежий терминал на другой платформе и получить тот же результат.

### Нормализация

Порядок жёсткий и он несущий: `crlf` → `ansi` → **`paths`** → `slashes` →
имя исполняемого файла → версия продукта → объявленные `replace` →
`sort_blocks` → хвостовые пробелы. Пути заменяются **до** унификации
слэшей, сортировка блоков — **после** всех текстовых замен.

Три решения, которых в макете A0.12 не было и которые пришлось принять по
живому выводу:

1. **Замена пути нечувствительна к разделителю.** Настоящий поток их
   мешает: значение `VIBE_SETTINGS`, переданное с прямыми слэшами,
   возвращается с нативным хвостом (`C:/a/b\cache`), и игла, написанная
   любым одним способом, не находит ничего. Совпадение ищется по
   свёрнутому ключу (`\` ≡ `/`, регистронезависимо), а замена ставится
   **в том написании, в котором нашлась**, — иначе ретаргет песочницы
   молча оставлял бы копию указывающей на родителя (этот дефект я поймал:
   в TOML `\f\empty` читается как `<FF>mpty`, и реестр уезжал в
   несуществующий каталог).
2. **JSON-написание пути (`C:\\a\\b`) обрабатывается отдельной иглой**, а
   не глобальным схлопыванием `\\` → `\`: схлопывание портит экранирование,
   не имеющее к путям отношения. Шаг `slashes` при этом сначала переводит
   `\\` в один `/`, иначе каждый разделитель в `--json`-примере удваивался
   бы.
3. **Windows-префикс `\\?\` снимается** вместе с путями: `\\?\C:\…` и
   `C:\…` — один каталог, и какое из двух написаний напечатала команда,
   зависит от того, как она канонизировала путь, а не от содержания.
   (Виден в `vibe scrape contract init`.)

Версия продукта (`vibe 1.0.0` → `vibe <VERSION>`) **включена** по умолчанию
и применяется к обеим сторонам; версии пакетов (`wal@1.0.0`) правило не
трогает — оно привязано к слову `vibe`. Принятая цена: пример `vibe
--version` больше не может поймать регрессию самой строки версии. Правило
названо в `PIPE-EXAMPLE-RUNNER`, и без него каждый bump версии красил бы
четыре примера.

`match`-шаблонов нет. Ни одному примеру корпуса не понадобилось ни одного
`replace`-правила и ни одного `sort_blocks` — вся недетерминированность
закрылась именованными классами.

### `--accept` и почему он не перезаписывает

`--accept` **заполняет пустой** `expect` и отказывается заменять
непустой: перезапись золотого образца, который кто-то однажды подписал, —
ровно тот ход, которым красная проверка становится зелёной без чьего-либо
решения. Перезапись требует второго, громкого флага `--force` и говорит об
этом в отказе.

Правка **хирургическая**: только `<expect>` (и `<stderr>` с атрибутом
`exit`, когда команда ими воспользовалась), ни байта больше. Через писателя
пивота страница не перегоняется сознательно — это канонизировало бы
написания, которые выбрал автор, и превратило бы снятие в переформатирование;
пакет говорит «только `expect` и ничего больше». Поэтому список
`NOT_CANONICAL` в `crates/vibe-specdoc/tests/docs_corpus.rs` **не
сокращён** — ни одна страница не канонизирована, и тест
`non_canonical_pages_are_exactly_the_recorded_ones` это подтверждает.
Каждая запись проверяется: страница перечитывается пивотом и сверяется, что
пример несёт ровно захваченный текст, что `stderr` и код выхода совпали и
что документ вообще разбирается; неподтверждённая правка не сохраняется.

Экранирование — дословно как у писателя (`&`, `<`, `>`, `\r`).

### X-026 — статус «снимается на релизе»

Назван так, как просил пакет («`captured="release"` или эквивалент — назови
в отчёте»). **Эквивалент:** атрибута на странице нет; отложенные примеры
объявлены в файле пакета `examples/deferred.toml` — по строке на пример:
`page`, `id`, `captured = "release" | "blocked"`, `reason`.

Почему не атрибут на `<example>`: PROP-045 §7 перечисляет атрибуты примера
закрытым списком (`id`, `fixture`, `lang`, `exit`, `when`), добавление
шестого — правка нормы и пивота, а пакет запрещает и то, и другое. Почему
не пустой `<expect></expect>`: пивот читает его как утверждение «команда
ничего не печатает» — утверждение, которого никто не делал. Объявленный
пропуск говорит, чего не хватает и что его снимет; пустой золотой образец
говорит неправду.

Сегодня в файле десять строк: одна `release` (установщик Windows) и девять
`blocked`.

### JTD

Валидатор принесён с собой (в `vibe-wire` его нет и быть не может: схемы
там — вход кодогенерации). Восемь форм RFC 8927, плюс подмешивание
**общего словаря** `formats/vocabularies.json` в `definitions` схемы:
без него `ref: "package_kind"` читался бы как «неопределённое определение»
для совершенно валидного документа. Документ, которому фикстура не назначила
схему, сообщается как **непроверенный**, не как прошедший.

### Панель

Шаг добавлен ровно с текстом пакета:
`run_step "documented examples run and match"` — после шага 4
(`cargo run -p vibe-cli -- check`), через `cargo run`, с коротким корнем
песочницы. Полную панель я по указанию оркестратора не гонял.

## A2.10 — генераторы `derived` (`e2a05ce9`)

| Вид | Что делает |
|---|---|
| `cli-help` | печатает `vibe <команда> --help` собранным бинарником; снимает `\r\n` и суффикс `.exe`. Ссылка, которая не про `vibe` или не просит help, — отказ: иначе `derived` был бы шагом сборки, спрятанным в странице |
| `jtd-schema` | таблица полей (имя, обязательность, форма, описание из самой схемы) по пути `*.jtd.json` **или** по `FormatId` через `formats/REGISTRY.toml`; каждое `definitions`-определение получает свою таблицу после корневой |
| `manifest-field` | грамматика X-030 целиком (см. ниже) |

**X-030 реализован буквально:** `abstract` (без координаты) — поле
манифеста документирующего пакета; `org.vibevm.core/vibevm-docs`
(координата одна) — **весь** манифест; `org.vibevm.core/vibevm-docs#package.title`
— одно поле. Чужая координата — отказ по имени, а не догадка: чужой
манифест приходит через store, которого сборка здесь не открывала.
Дополнительно: `title` и `package.title` — один и тот же путь, потому что
заставлять страницу писать имя таблицы ради собственного заголовка — обряд.
Манифест читается как данные TOML, а не через типизированную модель: у формы
«весь манифест» типа нет, а форма «поле» обязана доставать любой ключ,
который манифест когда-нибудь отрастит.

**Запись построения** — `maintenance/derived.json` в самом пакете: строка
на блок, `sha256` и размер, **текста нет**. Это и есть механизм «сообщает
расхождение с последним построением», не кладущий дрейфующую вещь в
репозиторий. Двигает запись только явный `--accept`
(`ROW-DOCVOCAB-DERIVED-CHECK`). Тест
`the_record_keeps_a_hash_and_a_size_and_never_the_text` прибивает это.

**Детерминизм доказывается, а не предполагается:** `check` строит каждый
блок **дважды** и отказывается, если два прогона разошлись. Генератор, не
являющийся функцией дерева, сделал бы запись бессмысленной, и сделал бы это
молча.

Панель получила второй шаг —
`run_step "derived references build to what the record holds"`. Он отдельный,
а не флаг к шагу A2.9, потому что пакет фиксирует текст шага примеров
дословно, а красная строка «help уехал» и красная строка «пример разошёлся»
— разные работы для разных людей.

**Важно интегратору:** запись снята с бинарника этого дерева на
`e2a05ce9`. Любая правка `--help` любой команды (а в фазе параллельно
работают четыре воркера) сделает этот шаг красным — это и есть его смысл;
лечение — прочитать, что уехало, и `vibe doc check --derived --accept`.

## Разбор расхождений — «страница или продукт»

### 1. `reference/machine-formats--list-json` — ни то, ни другое: решение X-025

Расхождение ровно в одной строке:

```
- "source_url": "file:///<REPO>/vibevm/vibepacks/org.vibevm.world/wal/v1.0.0",
+ "source_url": "file:///<TMP>/registry/org.vibevm.world/wal/v1.0.0",
```

Прежний `expect` снят в фазе P, когда реестр песочницы указывал на in-tree
реестр **хоста**. Пакет P2-O4 предписал закрыть X-025 — реестр-копию
**внутри фикстуры**, — и адрес источника закономерно сменился. Продукт не
менялся, проза страницы не менялась; устарел золотой образец, и устарел он
по решению, принятому этим же пакетом.

Поэтому это единственное место, где я применил `--force`, и применил
точечно: `--accept --force --only "machine-formats.xml#list-json"`. Диф —
одна строка (`git show 5c472381 -- …/reference/machine-formats.xml`).
Формально это отступление от буквы «иначе — разбор в отчёте, не правка
`expect`»; выбор между двумя требованиями пакета (это и «новый шаг
зелёный») сделан в пользу зелёной панели, потому что красная строка тут не
сообщает ничего, чего не сообщает эта запись. Если центральная сессия
считает иначе — откат этой строки тривиален и панель станет красной ровно
на ней.

### 2. `lifecycle/build-package-deploy--package`, `--deploy-plan`, `lifecycle/phases--deploy-plan` — **страница**

Манифест, который страница печатает в шаге 1, продукт отвергает:

```
error: invalid manifest: duplicate artifact id `hello` (output of
```

## Что не сделано и почему

1. **`bash tools/self-check.sh` до конца не гонялся** — прямое указание
   оркестратора («полную панель не гоняй — это сделает центральная сессия
   после посадки всех пакетов»). Оба новых шага проверены их собственными
   командами, дословно теми же, что стоят в скрипте, и оба зелёные (вывод
   выше). Шаг панели гоняет `cargo run -p vibe-cli`, то есть пересобирает
   бинарник в общем `target/` — на этом дереве это и есть причина запрета.
2. **`cargo build --workspace` и `cargo test` тронутых крейтов целиком** не
   гонялись по той же причине: в середине работы `crates/vibe-wire`
   не собирался из-за незавершённой правки соседнего воркера
   (`missing fields abstract_, documentation, documents … in initializer of
   VersionEntry`). После того как тот воркер закончил, `cargo build -p
   vibe-cli` (а значит и весь граф до него) собирается; `cargo test -p
   vibe-cli` полностью не гонял — он порождает сотни процессов `vibe.exe`
   и блокирует перелинковку у всех.
3. **`specmap.json` не закоммичен.** Гейт выполнен (0 suspects), но
   регенерация в общем дереве втягивает дрейф чужих коммитов: сверка
   показала сдвиги строк и фингерпринтов в файлах, которых я не трогал.
   Файл возвращён к HEAD. **Интегратору:** после посадки всех пакетов фазы
   — один прогон `cargo xtask specmap` и один коммит `specmap.json`
   (панель гейтит его шагом 6c). Это то же указание, что оставил P2-O2.
4. **`NOT_CANONICAL` не сокращён** — и не должен был: `--accept` правит
   только `expect`, страниц не канонизирует (разбор выше).
5. **Фикстуры `package-notes` и `docs-store` не заведены** — их
   единственные примеры отложены, рецепт был бы мёртвым кодом.
6. **PROP-файлы не менялись**, зона кампании тронута только этим отчётом и
   `EXAMPLES-TODO.md` (колонка «Состояние», правило 3 песочницы, строка
   `hello-vibe-registry`, таблица «что не снимается сейчас»). `git push`
