Дата: 2026-09-11
Дерево: b1291b06

Сокращение: `ENGINE/` = `vibevm/vibepacks/org.vibevm.ai-native/core-ai-native/v1.0.0/crates/core-ai-native-specmap/`

## Ответы

### 1. Становится ли цитата `spec://` внутри спек-документа ребром карты

**Нет. Сегодня ни один документ (`.md` или `.xml`) не производит ни одного
ребра.** Документы дают только узлы (`spec_units`) и предупреждения.

Разделение жёсткое и видно в одной строке сборки индекса:

- `ENGINE/src/index.rs:72` — `mdspec::scan_spec_tree(root, cfg)` возвращает
  `(Vec<SpecUnit>, Vec<Warning>)`. Рёбер в сигнатуре нет
  (`ENGINE/src/mdspec/walk.rs:93`).
- `ENGINE/src/index.rs:73` — `scanner.scan(root, cfg)` возвращает
  `(Vec<CodeItem>, Vec<Edge>, Vec<Warning>)`. **Единственный источник рёбер.**
- Скан документов (`ENGINE/src/mdspec.rs`, `ENGINE/src/xmlspec.rs`) не
  импортирует `Edge` вовсе: `use crate::generated::specmap::{SpecUnit,
  SpecUnitKind, SpecUnitStatus, Warning};` (`ENGINE/src/mdspec.rs:13`).

Кто производит рёбра сегодня — ровно два сканера, собранные в
`DefaultScanner` (`ENGINE/src/scanner.rs:84-118`):

1. `RustScanner` — атрибуты `#[spec(verb = "spec://…")]`, `#[verifies(…)]`,
   `specmark::scope!(…)` через `syn` (`ENGINE/src/rscan.rs:71-81`);
2. `JtdScanner` — блок `metadata.spec` в `*.jtd.json`
   (`ENGINE/src/jtd.rs:97-132`).

Глагол `documents` **существует и работает** — он один из пяти в закрытом
наборе (`ENGINE/src/generated/specmap/mod.rs:84-99`;
`core-ai-native-specmark-grammar/src/lib.rs:40-68`). В сегодняшней карте
хоста 243 ребра `documents`, но все они исходят из кода, не из документации:
242 из `.rs` и 1 из `.jtd.json`. Рёбер, чей `file` оканчивается на `.md` или
`.xml`, — ноль.

Обратный запрос «какая документация покрывает этот факт» уже реализован и
бесплатен, как только ребро появится:

- `vibe explain <spec://…>` печатает `edges in:` — все рёбра, входящие в узел
  (`ENGINE/src/explain.rs:101-110`);
- `vibe select --where 'lacks:documents …'` — предикат по глаголу
  (`crates/vibe-cli/src/cli/select.rs:19-24`;
  `crates/vibe-trace/src/select.rs:310-315`). Это готовый источник гейта
  покрытия.

**Структура записи ребра в `specmap.json`** (цитата из живого файла,
`specmap.json` в корне дерева — ребро с глаголом `documents`):

```json
{
  "file": "schemas/package_skill_receipt.jtd.json",
  "from_symbol": "package_skill_receipt::package_skill_binding",
  "line": 32,
  "provenance": "authored",
  "uri": "spec://org.vibevm.core/vibevm/common/PROP-018#PROJECTION-DEF",
  "verb": "documents"
}
```

Wire-тип (`ENGINE/src/generated/specmap/mod.rs:101-134`), поля
`pinned_r` и `reason` опускаются при сериализации, когда `None`:

```rust
pub struct Edge {
    pub file: String,          // #[serde(rename = "file")]
    pub fromSymbol: String,    // "from_symbol"
    pub line: u32,             // "line"
    pub provenance: EdgeProvenance,  // authored | generated | proposed
    pub uri: String,           // "uri" — БЕЗ пина (см. §2)
    pub verb: EdgeVerb,        // implements|verifies|documents|deviates|informs
    pub pinnedR: Option<Box<u32>>,     // "pinned_r", skip_serializing_if None
    pub reason: Option<Box<String>>,   // "reason", обязателен для deviates
}
```

Как ребро попадает в файл: `index::build_with_scanner` собирает
`Specmap { schema, specUnits, codeItems, edges, suspects, warnings }`
(`ENGINE/src/index.rs:211-219`), сортирует рёбра по
`(fromSymbol, verb_key, uri, file, line)` (`ENGINE/src/index.rs:195-203`), затем
`to_canonical_bytes` пишет pretty-JSON + завершающий `\n`
(`ENGINE/src/index.rs:222-226`). Хост вызывает это из
`xtask/src/specmap.rs:18` через `rust_ai_native_specmap::run_specmap`.

**Важно для нас:** у ребра *обязателен* хвост `from_symbol`, и он должен
присутствовать в `code_items`, иначе связь односторонняя. Прецедент для
не-кодового хвоста уже есть: JTD-сканер выдаёт `CodeItem` с сентинельным
именем крейта `crate_name = "<schema>"` (`ENGINE/src/jtd.rs:71`,
`ENGINE/src/jtd.rs:138-148`) и без `fingerprint`. Страница документации может
использовать тот же приём — менять wire-схему не требуется.

### 2. Пин ревизии `~rN` на ребре и условия «suspect»

**Пин умеет. Он не нужен нам, и его тривиально не ставить.**

Грамматика (`core-ai-native-specmark-grammar/src/lib.rs:19-25`) допускает пин
двумя способами, которые обязаны совпадать:

- внутри URI: `spec://<package>/<doc-path>#<anchor>~r<N>` — разбор на
  `lib.rs:198-205`, поле `SpecUri::pinned_r` (`lib.rs:82-98`);
- атрибутом: `#[spec(implements = "…", r = 2)]`;
- сверка двух пинов — `reconcile_pins` (`lib.rs:264-270`): расходящиеся
  пины — ошибка компиляции.

В самом ребре хранится **адрес без пина** плюс отдельное числовое поле:
`uri: edge.uri.without_pin()`, `pinnedR: edge.r.map(Box::new)`
(`ENGINE/src/rscan.rs:75,79`).

**Как считается suspect** — `ENGINE/src/index.rs:96-148`. Для каждого ребра
берётся ревизия целевого узла (`unit_revisions`, собран из узлов проекта
*и* внешних спек, `ENGINE/src/index.rs:89-94`) и разбирается четыре случая:

| состояние узла | пин на ребре | результат |
|---|---|---|
| узла нет вовсе | любой | `Warning{code:"dangling-edge"}` (`index.rs:98-108`) |
| узел есть, `revision` отсутствует | есть пин | `Warning{code:"pin-into-unmarked-unit"}` (`index.rs:109-121`) |
| узел есть, `revision` отсутствует | **нет пина** | **ничего** |
| узел на `rN` | пин `p < N` | **`Suspect`** (`index.rs:122-132`) |
| узел на `rN` | пин `p > N` | `Warning{code:"pin-ahead-of-unit"}` (`index.rs:133-144`) |
| узел на `rN` | пин `p == N` | ничего |
| узел на `rN` | **нет пина** | **ничего** |

Запись `Suspect` (`ENGINE/src/generated/specmap/mod.rs:223-246`) несёт
`current_r`, `pinned_r`, `from_symbol`, `uri`, `file`, `line`.

**Что пометит наши рёбра suspect'ом: только наличие пина.** Строка
`if let Some(p) = e.pinnedR.as_deref()` — единственный вход в обе ветки. Ребро
с `pinnedR: None` физически не может попасть ни в `suspects`, ни в
`pin-into-unmarked-unit`, ни в `pin-ahead-of-unit`, ни в строку
`now SUSPECT:` дрейф-отчёта (`ENGINE/src/index.rs:293-300`), какие бы
ревизии ни ставила спека.

**Как этого избежать:** выдавать рёбра с `pinned_r: None`. Ровно так уже
делает JTD-сканер, и его комментарий формулирует правило дословно —
`ENGINE/src/jtd.rs:115-119`: «no revision pin … so an edge minted here is
unpinned (it cannot go suspect)». Это полностью согласуется с D-18: изменение
содержимого узла на рёбра не влияет (хэш узла сравнивается только между
узлами, `classify_drift`, `ENGINE/src/index.rs:269-284`).

Практическая мера: чтобы `~rN` не появился случайно из авторского текста,
адрес в атрибуте `rule` следует отбрасывать по `without_pin()` (или
отвергать пин предупреждением) на входе сканера страниц.

### 3. Как doc-пакет несёт свою карту

**`vibe specmap` для пакета** — `crates/vibe-cli/src/commands/specmap.rs`:

- вход: `vibe specmap --path <dir>` (`SpecmapArgs`,
  `crates/vibe-cli/src/cli/specmap.rs:16`);
- opt-in: пакет участвует в трассируемости тогда и только тогда, когда в его
  корне лежит `specmap.toml`; иначе — тихий no-op, не ошибка
  (`commands/specmap.rs:88-94`);
- карта строится тем же движком, `build(dir, &cfg)`
  (`commands/specmap.rs:105`), под локальным «никнеймом» из `specmap.toml`,
  а затем **все URI собственного пространства имён перекладываются на
  координату пакета** `<group>/<name>` (`commands/specmap.rs:106-107`,
  `remap_namespace` — `:128-163`), после чего порядок рёбер и suspects
  восстанавливается по канону движка;
- выход: файл `package.specmap.json` в корне пакета
  (`MAP_FILENAME`, `commands/specmap.rs:39,111`). Имя отличается от
  `specmap.json` намеренно: `specmap.json` — собственный dev-артефакт
  кодового пакета.

**Форма `specmap.toml`** — тип `specmap_core::config::Config`
(`ENGINE/src/config.rs:46-152`), имя файла в `Config::REL_PATH`
(`ENGINE/src/config.rs:253`). Критично: `#[serde(default,
deny_unknown_fields)]` (`ENGINE/src/config.rs:46`) — **любой новый ключ в
`specmap.toml` требует правки движка**, иначе парсинг падает. Ключи:
`namespace`, `scan_roots`, `spec_roots`, `root_spec_docs`, `spec_exclude`,
`schema_roots`, `schema_vocabulary`, `[[external_specs]]` (`namespace` +
`root`), `exempt`, `dispositioned`, `max_connections_per_item`,
`max_section_lines`, `section_grain`.

Минимальный живой образец — `vibevm/vibepacks/org.vibevm.fractality/fractality/v1.0.0/specmap.toml:1-11`:

```toml
namespace = "fractality"
scan_roots = ["crates/*"]
spec_roots = ["vibevm/vibespecs"]
root_spec_docs = []
exempt = []
dispositioned = []
```

**Где карта пакета встречается с картой хоста: НИГДЕ. Объединения нет — ни при
`install`, ни при `cargo xtask specmap`.** Три отдельные точки соприкосновения,
и ни одна не сливает карты:

1. **`cargo xtask specmap`** строит карту хоста только из `scan_roots` /
   `spec_roots` / `schema_roots` своего дерева. `package.specmap.json`
   пакетов он не читает вовсе (`grep -rn "specmap" crates/vibe-install/src/
   crates/vibe-workspace/src/install.rs` — пусто; `install` никогда не
   вызывает `vibe specmap`).
2. **`[[external_specs]]`** читает не карту, а **исходные спек-документы**
   установленного пакета, и только для *разрешения адресов*: их узлы
   попадают в `unit_revisions` (`ENGINE/src/index.rs:79,89-94`), но
   **никогда не сериализуются** в `specmap.json` хоста
   (`ENGINE/src/index.rs:74-78`, `ENGINE/src/mdspec/walk.rs:78-89`). Именно
   это держит карту хоста байт-воспроизводимой.
3. **`vibe explain` / `vibe requirements`** отвечают на чужой адрес из
   *второй, некоммитимой* карты, построенной в памяти в момент запроса:
   `vibe_trace::foreign::resolve_foreign` (`crates/vibe-trace/src/foreign.rs:94-119`)
   находит слот `vibevm/vibedeps/<group>.<name>/<version>/` и читает оттуда
   `package.specmap.json` (`foreign.rs:198,249`); `crates/vibe-trace/src/lib.rs:142-152`
   диспетчеризует. Тот же файл питает провайдер связей для
   `vibe requirements` через доказательную лестницу по slot-record
   (`crates/vibe-trace/src/relations.rs:18-27`).

Как карта пакета попадает в `vibedeps/`: никакого особого шага нет —
`package.specmap.json` лежит в каталоге пакета как обычный файл и
материализуется вместе со всем деревом пакета. Резолвер просто проверяет
`slot.join(MAP_FILENAME).exists()` (`foreign.rs:198`).

Наблюдение на этом дереве: `package.specmap.json` существует ровно один —
`vibevm/vibepacks/org.vibevm.fractality/fractality/v1.0.0/package.specmap.json`;
ни один слот в `vibevm/vibedeps/**` его не несёт (в том числе
`org.vibevm.ai-native.core-ai-native/1.0.0/`, где `specmap.toml` есть, а карты
нет). То есть доставка карты в слот сегодня не автоматизирована.

### 4. Какой код сканирует документы: хостовый `vibe-trace` или вендоренный движок

**Вендоренный движок. `vibe-trace` не сканирует ничего — он только вызывает
движок.** Ни один байт разбора документов не живёт в хостовом дереве
`crates/`.

Цепочка:

- `crates/vibe-trace/src/lib.rs:158-167` — вся работа делегирована:
  `specmap_core::config::Config::load(root)` → `specmap_core::index::build(root, &cfg)`
  → `specmap_core::explain::explain_text|explain_json`.
- `xtask/src/specmap.rs:18` — `rust_ai_native_specmap::run_specmap(&root, check)`;
  `xtask/src/specmap.rs:58` — `specmap_core::index::build(root, &cfg)`.
- `crates/vibe-cli/src/commands/specmap.rs:105` — тот же `build`.

Что такое `specmap_core` для хоста — **вендоренная копия, не авторская**
(`Cargo.toml:153`):

```toml
specmap-core = { package = "core-ai-native-specmap", path = "vibevm/vibepacks/org.vibevm.ai-native/rust-ai-native-lang/v1.0.0/crates/vendor/core-ai-native-specmap" }
```

`sync-engines.toml:19-31` объявляет авторский источник
`…/core-ai-native/v1.0.0/crates` и цели — в том числе именно тот
`rust-ai-native-lang/v1.0.0/crates/vendor`, в который смотрит хост. Итого
**7 копий крейта `core-ai-native-specmap` под
`vibevm/vibepacks/org.vibevm.ai-native/**`: 1 авторская + 6 вендоренных**
(3 `*-ai-native-lang` + 3 `*-ai-native-mcp`; наборы `[[sync]]` на строках
19-31, 39-48, 66-75, 102-111). Ещё 6 копий лежат внутри `vibedeps/`
спекспейса fractality — это регенерируемые копии зависимостей, не цели
синхронизации (`xtask/src/sync_engines.rs:95` — `SCAN_DENY` исключает
`vibedeps`).

Согласованность держит `cargo xtask sync-engines`: инкрементальное зеркало +
`--check` в `tools/self-check.sh:504`. Правило сформулировано в
`sync-engines.toml:12-13`: «the fix surface is ALWAYS the authored copy, never
a vendored one». Проверено фактически: `diff -r` авторской и хостовой
вендоренной копии — идентичны (код выхода 0).

**Кто главный:** авторская копия
`vibevm/vibepacks/org.vibevm.ai-native/core-ai-native/v1.0.0/crates/core-ai-native-specmap/`.
Правка вендоренной копии — красный `sync-engines --check`, затем откат при
следующем `sync-engines` (перезапись зеркалом).

#### Где именно будет читаться элемент `rule`

Элемента `rule` в диалекте **нет**: `grep -rn '"rule"'` по
`…/core-ai-native/v1.0.0/crates/` — ноль вхождений. Словарь диалекта закрыт и
реализован **дважды, независимо**:

- **движок** — `ENGINE/src/xmlspec/blocks.rs:18-39` (`p`, `quote`, `fence`,
  `facts`, `list`, `table`; всё прочее — `«the dialect has no <X> element —
  the vocabulary is closed»`), `ENGINE/src/xmlspec/doc.rs:30-46` (список
  зарезервированных имён);
- **хост** — `crates/vibe-specdoc/src/xml_in.rs:322,436,348,460` и
  `crates/vibe-specdoc/src/xml_blocks.rs:19,165`. Это отдельная реализация
  того же диалекта (IR PROP-045, `md ↔ xml` пивот); паритет двух реализаций
  закреплён **тестами, а не общим кодом** — `ENGINE/src/xmlspec/doc.rs:12-13`
  («Mirror of vibe-specdoc's named-section boundary. The engine stays
  separable, so parity is pinned by tests instead of shared code»),
  `ENGINE/src/xmlspec/tests.rs:121`.

Прецедент, прямо относящийся к развилке: хостовый `vibe-spec` **осознанно не
переиспользует** вендоренную грамматику — `crates/vibe-spec/src/lib.rs:9-14`:
«it is a sync-engines–gated snapshot that must not be edited from the host
tree. The flat-anchor kebab rule is reproduced here segment-by-segment». То
есть в проекте уже принята практика: когда нужно расширение, хост пишет
собственный читатель, а движок не трогают.

Второй прецедент: **рёбра документ→документ в хосте уже есть** — сканер
директив `#use` / `#source` / `#embed` / `@spec://…`
(`crates/vibe-spec/src/directives.rs:1-21`) и граф `LinkTable`
(`crates/vibe-spec/src/link_table.rs:1-32`), полностью хостовый, вне
`specmap.json`. Его собственный комментарий: «A persisted on-disk format
(a `specmap.json` sibling) … are follow-ups».

#### Рекомендация: хостовая сторона (F-10/F-28 — вариант «хост»)

**Рекомендую читать `rule` на хостовой стороне и не трогать движок вообще.**
Это выполнимо с нулём правок в `vibevm/vibepacks/org.vibevm.ai-native/**` при
трёх условиях:

1. страницы документации лежат **вне** `spec_roots` (иначе движковый
   `xmlspec` встретит `<rule>` и уронит документ с предупреждением
   `xml-dialect`, `ENGINE/src/xmlspec.rs:20-23`);
2. политика скана страниц живёт в **своём** хостовом файле (в `specmap.toml`
   новый ключ положить нельзя: `deny_unknown_fields`,
   `ENGINE/src/config.rs:46`);
3. хост внедряет свой сканер через **уже публичный** шов `CodeScanner`,
   созданный ровно для этого (`ENGINE/src/scanner.rs:1-11`, «per-language
   stacks ship their own»): `index::build_with_scanner`
   (`ENGINE/src/index.rs:67`), `index::check_with_scanner`
   (`ENGINE/src/index.rs:373`), `index::write_with_scanner`
   (`ENGINE/src/index.rs:346`) + `CompositeScanner` (`ENGINE/src/scanner.rs:45-71`).

**Цена варианта «хост» — файлы под правку:**

| файл | что делает |
|---|---|
| новый модуль/крейт (напр. `crates/vibe-docmap/src/lib.rs`) | читает страницы, разбирает `rule`, выдаёт `(CodeItem, Edge, Warning)`; `pinned_r: None`, `crate_name = "<doc>"` по образцу `ENGINE/src/jtd.rs:71,115-119` |
| `crates/vibe-specdoc/src/xml_in.rs`, `xml_blocks.rs`, `xml_out.rs`, `doc.rs` | только если страницы пишутся в том же закрытом диалекте и проходят через пивот; если страницы — собственный формат, правка не нужна |
| `xtask/src/specmap.rs:18` | перестать делегировать `run_specmap` (он зовёт бесшовные `index::check`/`write`) и вызвать `check_with_scanner`/`write_with_scanner` с композитом; орфан-гейт вызвать отдельно (`rust_ai_native_specmap::run_gate`) |
| `xtask/src/specmap.rs:58` | **не забыть**: resolve-гейт строит карту вторым, независимым вызовом `index::build` — без той же инъекции он не увидит рёбра страниц и гейт покрытия будет зелёным по пустоте |
| новый хостовый конфиг (напр. `docmap.toml` или секция `docs/SITE-MANIFEST.toml`) | корни страниц |
| `specmap.json` в корне | регенерируется (диффы большие, но это данные) |
| `tools/self-check.sh` | при желании — отдельный шаг гейта покрытия |

Правок под `vibevm/vibepacks/**` — **ноль**, `cargo xtask sync-engines`
запускать не нужно, R-21 не задействовано.

### Дополнительно: как выглядит «неразрешённое» ребро и куда ляжет проверка якоря

Слова `unresolved` в движке нет; там это называется **`dangling-edge`**.

- **Движок, мягкий слой.** Если адреса нет ни среди узлов проекта, ни среди
  узлов `[[external_specs]]`, ребро остаётся в карте, а рядом появляется
  `Warning` (`ENGINE/src/index.rs:98-108`):
  `edge `<from_symbol>` --<verb>--> `<uri>`: no spec unit carries this anchor`.
  В сегодняшней карте таких ровно одно
  (`crates/vibe-trace/src/fragment.rs:22`, адрес
  `spec://org.vibevm.ai-native/core-ai-native/mechanisms/PROP-014#addressing-code`).
- **Хост, жёсткий слой (B-076).** `run_resolve_gate`
  (`xtask/src/specmap.rs:46-94`) поднимает предупреждение до блокировки, но
  **только для адресов собственного пространства имён** —
  `e.uri.starts_with("spec://{namespace}/")` (`xtask/src/specmap.rs:59,63`).
  Чужие адреса считаются «вне юрисдикции» и проходят молча
  (`xtask/src/specmap.rs:78-80`). Под `--check` ненулевой счётчик — `bail!`
  (`xtask/src/specmap.rs:86-92`).

**Как проверка существования якоря без пина ляжет в существующую проверку:
никак дорабатывать не нужно — это ровно то, что уже сделано.** Проверка
существования — это ветка `None` в `unit_revisions.get(e.uri.as_str())`
(`ENGINE/src/index.rs:97-98`); пин в ней не участвует вовсе (пин читается
только в ветках `Some(...)`). Наши рёбра будут цитировать
`spec://org.vibevm.core/vibevm/…`, то есть **собственное пространство имён
хоста**, значит попадут в жёсткий гейт `run_resolve_gate` автоматически:
опечатка в якоре страницы покраснит `cargo xtask specmap --check` с точным
`file:line` страницы. Дополнительный гейт для этого писать не нужно.

Единственная оговорка — пункт «не забыть» из таблицы выше:
`run_resolve_gate` строит карту **своим** вызовом `index::build`
(`xtask/src/specmap.rs:58`), не тем, что построил основной проход. При
хостовом сканере инъекцию нужно продублировать в обеих точках, иначе гейт
покрытия будет зелёным по пустоте — тот же класс ошибки, против которого в
движке заведено `vacuity_warning` (`ENGINE/src/index.rs:453-463`).

## Расхождения с решениями

Нет. Проверено по трём решениям, названным в пакете:

- **D-18 (пинов ревизий на рёбрах нет, проверяется только существование
  якоря)** — реализуемо без правок: `pinned_r` опционален и опускается при
  сериализации; проверка существования якоря (`dangling-edge` +
  `run_resolve_gate`) пином не пользуется.
- **Глагол `documents`** — существует в закрытом наборе и уже применяется
  (243 ребра), в том числе из не-Rust источника (JTD-схема).
- **R-21 (движок карты вендорится; правки — в авторскую копию + `sync-engines`)**
  — подтверждено фактически: хост зависит от вендоренной копии
  (`Cargo.toml:153`), гейт `cargo xtask sync-engines --check` стоит в
  `tools/self-check.sh:504`, правило «the fix surface is ALWAYS the authored
  copy» записано в `sync-engines.toml:12-13`.

## Открытые вопросы

1. **Хвост ребра — `CodeItem`.** Wire-схема допускает у ребра только
   `from_symbol`, и для полноты графа этот символ должен присутствовать в
   `code_items`, чей doc-комментарий гласит «A tagged code item (fn, struct,
   enum, trait, impl, mod)» (`ENGINE/src/generated/specmap/mod.rs:33-34`).
   JTD-сканер уже растянул это понятие сентинелью `"<schema>"`, так что
   менять схему не требуется, но страница документации в `code_items` —
   решение по смыслу, а не по технике. Нужен вердикт вижена: страница как
   `code_item` с `crate_name = "<doc>"`, или отдельная таблица узлов (что
   уже потребует правки JTD-схемы движка и, следовательно, R-21).
2. **Формат страниц.** Не установлено, будут ли страницы документации
   писаться в том же закрытом XML-диалекте PROP-045 (тогда затрагивается
   `crates/vibe-specdoc/**` и, при попадании в `spec_roots`, движковый
   `xmlspec`) или в собственном формате (тогда ни то, ни другое). От этого
   зависит примерно половина строк в таблице цены.
3. **Доставка карты doc-пакета.** Установлено, что `install` не запускает
   `vibe specmap` и что ни один слот `vibedeps/**` в этом дереве не несёт
   `package.specmap.json` — значит, публикация карты пакета сегодня ручная
   (`vibe specmap --path <pkg>` перед публикацией). Кто и когда будет это
   делать для doc-пакета — вне спайка.
4. **Состояние гейта на HEAD.** `cargo xtask specmap --check` на b1291b06
   **красный** и без каких-либо моих изменений (см. отчёт). Это фон, на
   который лягут будущие правки; причина — несведённый `specmap.json`
   (20 новых узлов, 3 новых ребра, 8 `unbumped-hash`).
