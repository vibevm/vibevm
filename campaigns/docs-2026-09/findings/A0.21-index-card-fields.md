## Ответы

**1. Путь поля манифеста в запись индекса сегодня.**

- Парсинг: `crates/vibe-index/src/scanner/manifest.rs:52` (`parse_manifest`, через `vibe_core::manifest::Manifest::parse_str`) и `:61` (`require_package` — без `[package]` нет записи индекса).
- Простые скаляры (`name`, `group`, `version`, `license`, `authors`, `description`, `homepage`, `keywords`, `bridge`, `frozen`) копируются **напрямую** в литерал `VersionEntry{..}` в двух местах, не через `manifest.rs`:
  - `crates/vibe-index/src/scanner/org_walk.rs:240-276` (сканирование из org/git-клонов),
  - `crates/vibe-index/src/cli/add.rs:98-129` (ручной `vibe index add`) — побайтово то же самое, оба места придётся трогать при добавлении любого нового скаляра.
- Вложенные/структурные поля идут через хелперы-проекции в `manifest.rs` (`compatibility_from`, `provides_from`, `requires_from`, `requires_any_from`, `obsoletes_from`, `conflicts_from`, `features_from`, `i18n_from`, `boot_snippet_from`, `embedded_sources_from`, `workspace_origin_from`, `collect_subskills`), вызываемые из тех же двух литералов. Закон модуля (manifest.rs:82-85): пустая секция всегда даёт `None`, никогда `{}` на wire — пинуется тестом `empty_projection_tables_never_reach_the_wire` (manifest.rs:426-469).
- `VersionEntry` **не рукописный тип** в vibe-index — это `pub use vibe_wire::generated::shared::VersionEntry;` (`crates/vibe-index/src/types/entry/mod.rs:39`), сгенерированный код (шапка: `// Code generated by jtd-codegen for Rust v0.2.1`, `crates/vibe-wire/src/generated/index/e1/entry/mod.rs:1`). Поведение (`SCHEMA_VERSION`, `sort_key`, `minimal`) живёт отдельно в `vibe_wire::behaviour` из-за orphan rule (types/entry/mod.rs:9-17).
- Схема одной строки `primary.jsonl`: `schemas/index/e1/entry.jtd.json:6` — это не сама схема, а `{"ref": "version_entry"}`, отсылка в общий вокабуляр. **Реальный источник истины полей** — `formats/vocabularies.json:57`, ключ `"version_entry"`: там и `properties` (required), и `optionalProperties` (с `x-default`/`x-empty` метаданными).
- Генерация кода: пайплайн `xtask/src/codegen/{vocabulary.rs, shared_module.rs, optional_shapes.rs, reader_projection.rs, empty_policy.rs, wire_order}` читает `formats/vocabularies.json` + `schemas/**/*.jtd.json` и пишет `crates/vibe-wire/src/generated/**` — руками этот код не редактируется.
- Сборка `Vec<VersionEntry>` в файл: `crates/vibe-index/src/index/primary.rs:28` (`serialise`, сортировка по `sort_key()`, JSON Lines) и `:44` (`write`, плюс детерминированный gzip-сиблинг `primary.jsonl.gz`).
- Тест соответствия схема↔код: `crates/vibe-wire/tests/vocabulary_parity.rs` — образец жанра «читаем `formats/vocabularies.json` напрямую и сверяем со сгенерированным Rust» (сегодня пинует `package_kind`, не `version_entry`, но это тот же механизм, которым нужно будет пинать новые поля). Более жёсткий и уже существующий guard — тестовый хелпер `entry()` в `primary.rs:142-182`: он строит **полный** литерал `VersionEntry{..}` по имени поля, так что добавление любого нового обязательного поля **не скомпилируется**, пока хелпер не обновят — то же верно для `crates/vibe-index/src/index/memory/tests.rs`.

## Расхождения с решениями

`REVIEW:` пакет вводит `[translates]` и `[translations]` без глоссы (в отличие от `documents`/`documentation`, для которых глосса дана явно). В коде нет реализации ни одного из двух — экстраполировать их форму по аналогии рискованно: если `[translations]` не «обратное ребро», а список файловых вариантов внутри одного пакета, то это другая структура и другое место в схеме (ближе к `i18n.available`, чем к новому `XxxEntry`-списку). Выведено как открытый вопрос.

Других расхождений с зафиксированными решениями не найдено — пакет не процитировал ни одного `D-NN` для сверки.

## Сравнение двух мест ответа на обратный запрос

**(а) На стороне сайта, по `primary.jsonl`, при сборке.**
В этом дереве генератора сайта нет вообще — `Cargo.toml` не содержит `vibe-site`/аналога, есть только `docs/SITE-MANIFEST.toml` (манифест, не генератор). Технически всё уже готово для такого подхода без единой новой строчки бэкенд-кода: `primary.jsonl`/`primary.jsonl.gz` уже отдаются целиком одним запросом (`GET /v1/index/primary.jsonl[.gz]`, маршруты `crates/vibe-index/src/server/mod.rs:67-72`, реализация `index_files.rs:31-78`) и читаются с диска без сервера вовсе (`primary.rs:76` `read`/`read_gz`). Обратный индекс «кто документирует X» / «какие переводы есть у Y» — одна свёртка `Vec<VersionEntry>` в `HashMap` в момент сборки сайта, целиком в памяти генератора. Правка: 0 строк в vibe-index, вся работа — новый код в генераторе сайта. Ограничение: нужно скачать/распарсить весь каталог целиком даже ради одного обратного запроса (сегодня малый файл, но не таргетированный запрос); подходит для build-time/офлайн-режима — что устраивает и локального офлайн-читателя (тот же код пути).

**(б) Маршрутом индекса, по образцу `by-cap`.**
`by-cap` — **не** запрос, вычисляемый на лету. Это статический файл, посчитанный один раз при переиндексации:
- агрегация всех `VersionEntry.provides.capabilities` в `BTreeMap<slug, Vec<CapabilityRow>>` — `crates/vibe-index/src/index/inverted.rs:95-186`;
- запись одного файла `by-cap/<slug>.jsonl` на capability — `inverted.rs:196-233` (`by_cap_dir`, `capability_file`, `write_capability`);
- HTTP-маршрут `crates/vibe-index/src/server/routes/index_files.rs:80-94` (`by_cap_jsonl`) не считает ничего — тот же `serve_file`, что для `hello.json`/`repomd.json`/`by-name/<name>.json` (index_files.rs:128-163): читает готовый файл с диска, ставит `Cache-Control: no-cache`. Зарегистрирован в `crates/vibe-index/src/server/mod.rs:79-84`.
- `repomd.json` (`crates/vibe-index/src/index/repomd.rs`) по имени упоминает только `primary.jsonl` (строка 56); `by-cap`/`by-purl` там **не** перечисляются как отдельные хэшируемые файлы.

Построить «кто документирует X» так же означает воспроизвести весь стек заново: новый модуль агрегации (аналог inverted.rs) по новым полям; новая JTD-схема (`schemas/index/e1/by_documents.jtd.json` и т. п.) + сгенерированный Rust-двойник; новая директория на диске (`by-documents/<slug>.jsonl`), которую обязана писать каждая переиндексация (`rebuild.rs`); новый маршрут + регистрация в `server/mod.rs`. Заметно больше кода, чем (а). Отдельная сложность для `documentation`: «официальность» по R-23 — **конвергенция** двух рёбер (`documents` ∩ `documentation`), а не значение одного поля; `inverted.rs` агрегирует только один плоский признак одной записи и не содержит прецедента свёртки-пересечения двух полей двух разных записей. Ограничение по размеру: `by-cap`/`by-purl` — уже папки из множества мелких файлов; ещё одна (`by-documents`) — заметный рост числа файлов индекса, чего вариант (а) не создаёт.
