## Решения (интерпретации задания, где оно было неоднозначно)

- **`crates/vibe-core/src/manifest/*.rs` прочитан как весь модуль рекурсивно** (`**/*.rs`), а не только прямые файлы каталога `manifest/`. Причина: поля вроде `[[skill]]` и `[[mcp_server]]` определены в `crates/vibe-core/src/manifest/package/skill.rs` и `.../package/mcp_server.rs` (подтверждено чтением; `mcp_server.rs:1` буквально содержит doc-комментарий `` `[[mcp_server]]` — the MCP servers an `mcp`-kind package declares ``) — подкаталог, не прямой файл. Буквальное нерекурсивное `*.rs` пометило бы явно живые поля как `устарело`.
- **Добавлен пятый паттерн пути — `vibedeps/`** — сверх четырёх названных в задании (`vibevm/…`, `crates/…`, `~/.vibe/…`, `*.toml`/`*.lock`). `vibedeps/` — такой же полноправный, документированный каталог проекта (glossary.md, loading-model.md, lockfile-format.md), но это **генерируемый** каталог (материализуется `vibe install`), а не закоммиченный. Проверка `Path.exists()` по дереву для него систематически давала бы ложный `устарело` в непроинсталлированном чекауте (так и было до правки — 17 строк). Итог: `vibedeps/…` помечается `неизвестно` с объяснением, а не проверяется по дереву — по той же логике, что и `~/.vibe/…`.
- **`~/.vibe/…` проверяется по реальному диску этой машины** (`Path.home()`), а не по дереву репозитория — единственный механический прокси для рантайм-пути. Отсутствие на этой машине → `неизвестно` (не `устарело`): на другой/чистой машине файл может появиться после первого использования.
- **`~/.vibe/*.token` намеренно НЕ проверяется через `.exists()`** — R-12 (секреты) из PACKET-COMMON называет ровно этот шаблон пути; хотя `.exists()` не читает содержимое и не может раскрыть значение токена, из осторожности скрипт вообще не трогает такие пути на диске и сразу возвращает `неизвестно`.
- **Флаги (`--xxx`) проверяются по объединению** всех `--flag`, встретившихся в `--help` живого CLI, обойдённого на глубину 2 (верхний уровень + дети каждой группы: `registry`, `mcp`, `cache`, `self`, `bin`, `prefs`, `vars`, `progress`, `skill`, `agentic`, `workspace`, …), а не привязаны к конкретной подкоманде, рядом с которой флаг упомянут в документе. Упрощение: точная привязка флага к «его» подкоманде потребовала бы куда более тяжёлого разбора контекста; глобальное объединение осталось механическим и быстрым ценой отдельных ложных `живо`, если в документе флаг стоит не при той команде.
- **Разрешение `vibe …`-команды идёт по цепочке подкоманд, шаг за шагом**, и останавливается на первом «листе» — уровне, чья строка `Usage:` не содержит `<COMMAND>`. Эмпирически проверено: `vibe install some-bogus-positional-xyz --help` завершается кодом `0` (`--help` перехватывает вызов ДО проверки позиционных аргументов), т.е. слова после листового уровня — это позиционные аргументы, а не продолжение пути подкоманд, и тестировать их как подкоманды нельзя (иначе `vibe registry redirect sync --help` ошибочно резолвился бы в несуществующее «redirect → sync», хотя `sync` там — просто проглоченный позиционный `<PKGREF>`).
- **Отфильтрованы кандидаты-НЕ-команды**, которые иначе ловились бы наивным правилом «строка начинается с `vibe `» (буквально из задания): вывод-текст с версией (`vibe 1.0.0`, `vibe 0.1.0-dev` — первое слово после `vibe ` начинается с цифры), синопсис-плейсхолдеры (`vibe mcp [OPTIONS] <COMMAND>`, `vibe registry redirect-sync <pkgref>` — токен начинается с `[`/`<`, содержит `...`/`…`), и лог-подобный вывод (`vibe registry add: `private` registered…` — токен оканчивается на `:`). Без этих фильтров все перечисленные примеры ложно резолвились бы в `устарело`.
- **Секции/поля манифеста берутся только из код-блоков и inline-кода**, не из прозы — иначе markdown-ссылки вида `[текст](url)` ловились бы как секции. Дополнительно исключены quadratные скобки со СПЛОШНЫМИ ЗАГЛАВНЫМИ идентификаторами (`PROP-002`, `D-17`, `R-12`, `E-BUG-001`) — все настоящие TOML-секции в проекте строчные (`[package]`, `[[registry]]`, …).
- **Дедупликация — по файлу**, не глобально: одинаковое утверждение (тип + текст), повторённое в одном файле несколько раз, попадает в таблицу один раз (с заголовком первого вхождения); то же утверждение в РАЗНЫХ файлах остаётся отдельной строкой на файл — иначе карта переноса потеряла бы файловую гранулярность, ради которой всё делается.

## Открытые вопросы / известные ограничения (не то же самое, что регрессия — просто предел механики)

- Наивное правило «строка начинается с `vibe `» (буквально из задания) не отличает реальную команду от прозы на естественном языке. Один непочищенный пример остался в таблице: `docs/guides/agent-mcp-quickstart-opencode.md`, раздел Troubleshooting → утверждение `vibe not found` помечено `устарело` (`not`/`found` не резолвятся как подкоманды), хотя это фрагмент текста об ошибке, а не заявление о команде. Не стал добавлять фильтр по английским стоп-словам — это открытый по объёму эвристический костыль для механического скрипта; строка одна, видна в таблице как есть.
- Категория `section` ловит ЛЮБОЙ snake_case-идентификатор или `[скобочный]` токен в код/inline-коде — не только те, что автор имел в виду как поле TOML-манифеста. Часть строк `устарело` в этой категории — это имена внутренних функций/переменных или JSON-полей API, упомянутые в обратных кавычках в прозе, а не поля `vibe.toml`: например `repo_exists`, `auto_init`, `clone_url`, `extract_org_segment`, `extract_host_segment`, `total_registries`, `skill_results`, `query_package`, `materialise_subskill`, `invoked_by` (это JSON-поле конверта, не поле манифеста), `[mcp_servers.vibevm]` (схема конфигурации Codex, не vibevm). Проверка по заданию (grep по `crates/vibe-core/src/manifest` и `vibevm/vibepacks/**/vibe.toml`) для них корректно возвращает «не найдено» — это правда, они не поля манифеста — но это несовпадение категории на этапе извлечения, а не подтверждённый регресс по R-17. Рекомендация центральной сессии: строки типа `section` с меткой `устарело` стоит бегло просмотреть глазами перед тем, как трактовать их как регрессии.
- `vibe vendor` (docs/glossary.md, таблица Anti-vocabulary) резолвится в `устарело` — и это верно: сегодня существует только `vibe registry vendor`. Сам глоссарий уже помечает это как задел на будущее («or `vibe vendor` (when M1.6 ships)»), так что это не ошибка скрипта, а самодокументированный случай.
- Обход дерева CLI для флагов идёт на глубину 2 (верхний уровень + дети каждой группы). Признаков третьего уровня вложенности в этом CLI не встретилось, но это не доказано исчерпывающе отрицательно.
- Полный список причин `неизвестно` (27 строк) сводится к четырём формам, каждая — с объяснением в столбце «как проверено»: `~/.vibe/git.publish.token` / `~/.vibe/search-cache/` (рантайм-путь, не на этой машине, или намеренно не проверялся как секрет), `vibedeps/…` (генерируемый каталог), и текстовые плейсхолдеры `vibe <command> --help` / `vibe <subcmd> --help` / `vibe <version>` / `vibe …`.
