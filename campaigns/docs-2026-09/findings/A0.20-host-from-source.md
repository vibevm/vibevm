# A0.20 Хост из репозитория исходников

Дата: 2026-09-11
Дерево: b1291b06

## Ответы

### 1. Git-источники с `branch`: поддержка и живая проба

**Поддерживаются.** Спецификация: PROP-002 §2.4.1,
`vibevm/vibespecs/modules/vibe-registry/PROP-002-decentralized-registry.xml`:

- грамматика URL — «just git URL», явно включая `file://`
  (`##SHAPE-PLAIN-GIT-URL`, строка 19; для git-источника то же —
  `##ROW-GS-GIT-MEANING`, строка 296);
- `branch` — одна из трёх форм ссылки (`##ROW-GS-BRANCH`, строки 310–312);
  ровно одна из `tag` / `branch` / `rev` обязательна, умолчания «HEAD ветки по
  умолчанию» нет (`##GS-EXACTLY-ONE-REF`, строка 325);
- семантика мутабельности (`##GS-MUTABILITY`, строка 335): `vibe install`
  резолвит ветку в её текущий HEAD и пинит коммит в lock; последующий
  `vibe install` за HEAD не гонится, а `vibe update` перевычисляет.

Код: `GitPackageDep` — `crates/vibe-core/src/manifest/package/deps.rs:33`,
`GitRefKind::{Tag,Branch,Rev}` — `:66`. Резолюция —
`MultiRegistryResolver::resolve_git_source`
(`crates/vibe-registry/src/multi_registry_resolver/sources.rs:18`), вставка в
store — `store::insert_current_at` там же, `:236`. Объявления из манифеста
попадают в резолвер через `with_git_packages(manifest.requires.git_packages)`
(`crates/vibe-package-source/src/builder.rs:85`); при пустом наборе реестров
git-источник сам по себе снимает отказ «no registry configured»
(`crates/vibe-package-source/src/builder.rs:241–243`).

Локальность пути для `--offline` считается по схеме URL:
`vibe_core::url_is_local` — `crates/vibe-core/src/global_registry.rs:350`;
локальны и `file:`-URL, и голый путь, включая `C:\…` (docstring `:337–344`).

**Живые пробы (все — `vibe.exe cache add`, изолированное окружение).**

| проба | источник | ref | результат |
|---|---|---|---|
| A | `file:///C:/…/host.git` (bare-клон хоста) | `branch = "main"` | exit 1 — манифест хоста не пакет (см. п. 2) |
| B1 | `file:///C:/…/pkgrepo` (обычный репозиторий) | `branch = "main"` | exit 0, в store `REVISION-ONE` |
| B2 | тот же, после нового коммита в `main` | `branch = "main"` | exit 0, в store `REVISION-TWO` (та же версия 0.1.0) |
| B3 | тот же, правка в рабочем дереве **без коммита** | `branch = "main"` | exit 0, в store по-прежнему `REVISION-TWO` |
| B4 | `C:/…/pkgrepo` — **голый путь, без схемы** | `branch = "main"` | exit 0, в store `REVISION-THREE` |
| B5 | тот же голый путь, **с `--offline`** | `branch = "main"` | exit 0, в store `REVISION-FOUR` |

Из этого следует, по пунктам:

- `file://` и голый локальный путь как git-источник работают одинаково;
- `branch` действительно даёт **текущий HEAD ветки**, а не тег: содержимое в
  store менялось от коммита к коммиту при неизменной версии пакета `0.1.0`;
- обновление одной и той же версии проходит: путь выборки зовёт
  `insert_current_at`, который сносит устаревшую запись и вставляет новую
  (`crates/vibe-registry/src/store/refresh.rs:24–56`, PROP-011 §2.6). При этом
  `cache add` печатает «already present — bytes untouched (write-once)» —
  вывод врёт, см. «Расхождения»;
- git-источник видит только **закоммиченное** состояние ветки: правка в рабочем
  дереве без коммита в store не попадает (проба B3);
- `--offline` локальному git-источнику не мешает (проба B5).

Клон-кэш: git-источник разворачивает полный клон в
`$VIBE_REGISTRY_CACHE/__git_sources__/<group>.<name>/clone/` (наблюдено в
scratch). Для неудачной пробы A клон **не создавался**: чтение манифеста на
ветке идёт отдельным дешёвым путём (`fetch_manifest_at_ref`,
`crates/vibe-registry/src/multi_registry_resolver/sources.rs:35`) и падает до
выборки содержимого.

### 2. Читается ли корень хоста как пакет `org.vibevm.core/vibevm` (B-031)

**Нет — и это не дефект, а форма записи B-031.**

- В корне есть `vibe.toml`, но его первая таблица — `[project]`, не `[package]`:
  `vibe.toml:1–8` (`name = "vibevm"`, `group = "org.vibevm.core"`,
  `version = "1.0.0"`, `spec_format = "xml"`).
- Разбор различает две формы: `Manifest::require_package()` требует `[package]`
  и иначе даёт «expected a [package] table — this manifest is not a publishable
  package» (`crates/vibe-core/src/manifest/document.rs:427–432`);
  `require_project()` требует `[project]` (`:436–440`).
- То есть B-031 дал корню **полностью квалифицированное имя**
  (`org.vibevm.core/vibevm` как `group` + `name` в `[project]`), но не сделал
  корень публикуемым пакетом. `BACKLOG.md:769–773` помечает B-031 как closed и
  отсылает к коммиту `1ef63a37`; его сообщение: «the root project takes a
  fully-qualified name, host addressing exceptions die with the short notation».
- Что печатает CLI для корня: `vibe show config` (полный аналог «show» для
  проекта; отдельной команды `vibe show <package>` для корня нет —
  `vibe show` имеет подкоманды `effective` / `config` / `features` /
  `subskills` / `purls` / `source-path`). Первая строка вывода:
  `Project: vibevm 1.0.0 (C:\Users\olegc\git\v\vibevm-docs)` — имя и версия без
  группы.
- Живая проверка «корень как пакет» — проба A выше: объявление
  `"org.vibevm.core/vibevm" = { git = "file:///…/host.git", branch = "main" }`
  падает ровно на этом: манифест на `main` не несёт `[package]`.

### 3. Путь, по которому сайт получит текущее состояние `main` без публикации

**Рекомендация: project-local реестр рабочей копии, без git-источника и без
реестра вообще.**

Команда (выполняется из корня выкладки, где уже лежит репозиторий после
`git pull`):

```bash
vibe cache add --offline <group>/<name>@<version> [ещё пакеты…]
```

Почему именно так:

- источник — `<корень>/vibevm/vibepacks`, открытый как `LocalRegistry`
  (`crates/vibe-package-source/src/builder.rs:187–198`,
  `crates/vibe-package-source/src/project_local.rs:31`); подробности —
  `A0.17-intree-to-store.md`;
- он читает **живой каталог на диске**, а не коммит: проба C (пакет в
  `<tmp>/localproj/vibevm/vibepacks/org.probe/probe-local/v0.1.0/`, каталог
  вообще не под git) — правка `README.md` в месте и повторный `cache add`
  обновили содержимое в store с `LOCAL-ONE` на `LOCAL-TWO` при той же версии;
- клон не нужен: репозиторий уже на диске, второй копии git не создаётся
  (в отличие от git-источника, который поднимает полный клон в
  `$VIBE_REGISTRY_CACHE/__git_sources__/…`; для этого дерева это ≈175 МиБ
  объектов);
- сети нет: `--offline` отсекает объявленные в корневом `vibe.toml` сетевые
  реестры (`https://github.com/vibespecs`, `https://gitverse.ru/vibespecs`),
  которые иначе опрашиваются ради объединения версий (PROP-030 `##ENUM-UNION`);
- публикации нет: `cache add` ничего не материализует в проект и не пишет lock
  (`crates/vibe-cli/src/commands/cache/add.rs:1–7`).

Ограничения этого пути, которые сайт обязан учитывать:

1. **Хост сам по себе так не берётся.** Через project-local доступны только
   пакеты из `vibevm/vibepacks`. Документация *самого* репозитория (файлы
   `vibevm/vibespecs/**`, `*.md` в корне) пакетом не является — её сайт читает
   прямо из выкладки, файлами. Пока doc-пакет ядра не собран, «хост как пакет»
   недоступен ни одним из трёх источников.
2. **Состояние определяется рабочей копией, а не веткой.** `cache add` возьмёт
   ровно то, что лежит на диске, включая незакоммиченное. Соответствие
   «текущему `main`» обеспечивает сам деплой (`git checkout main && git pull`,
   чистое дерево), а не vibe.
3. **Версия не меняется.** In-tree пакеты — мутабельные слоты одной версии
   (`vibevm/vibepacks/org.vibevm.world/multi-user-planning/v1.0.0/vibe.toml:1–4`).
   Обновление store опирается на sidecar-хэш, а не на номер версии; значит,
   сайт не должен использовать `(group, name, version)` как ключ кэша
   рендеринга — нужен `recorded_hash` (`crates/vibe-registry/src/store.rs:128`)
   или content-hash пересчётом.
4. **Отчёт `cache add` не говорит, обновилось ли содержимое** — см.
   «Расхождения».
5. Store общий на машину и движется только вместе с `$VIBE_SETTINGS`
   (`crates/vibe-registry/src/store.rs:30–37`). На сервере это единственный
   рычаг, чтобы увести store в каталог сервиса.

**Альтернатива без store вообще.** Раз содержимое и так лежит на диске,
`vibe-doc` может открыть `<корень>/vibevm/vibepacks` как
`vibe_registry::LocalRegistry` (`crates/vibe-registry/src/local_registry.rs:45`)
и читать `list_versions` (`:58`) / `resolve` (`:141`) без выборки, либо просто
ходить по каталогам `<группа>/<имя>/v<версия>/`. Это убирает и `cache add`, и
дисциплину write-once, и рассинхрон отчёта. Store остаётся нужен там, где
пакеты приходят извне (реестр, git-источник).

**Git-источник по ветке** для этой задачи применим только тогда, когда
репозитория на диске сервера нет, и только к репозиторию, корень которого —
публикуемый пакет. Для vibevm ни одно из двух условий сегодня не выполняется.

## Расхождения с решениями

`REVIEW:` **`cache add` сообщает «already present — bytes untouched
(write-once)» в тех случаях, когда байты записи были заменены** (пробы B2, B4,
B5, C2). Причина — в `crates/vibe-cli/src/commands/cache/add.rs:70`:
`was_present` считается до выборки, а выборка уходит в `insert_current_at`
(`crates/vibe-registry/src/store/refresh.rs:24`). Решениям D-07/D-16 это не
противоречит, но прямо задевает их исполнение: если сайт будет решать «надо ли
перерендерить» по строке отчёта `cache add`, он пропустит каждое обновление
мутабельной версии. Признак свежести надо брать из sidecar
`<store>/<group>/<name>/v<version>.sha256`.

Отдельно отмечаю как факт, не расхождение: решение D-07/D-16 говорит «сайт
рендерит документацию **хоста**», а хост пакетом не является (п. 2). Способа
получить «хост как пакет» сегодня нет ни через store, ни через lock, ни через
реестр; путь к текущему `main` — это чтение файлов выкладки, а не выборка
пакета. Doc-пакет ядра, о котором говорит фаза 3, это и меняет.

## Открытые вопросы

- Полный клон через git-источник на 175-мегабайтном хосте живьём не мерился:
  проба A упала раньше выборки содержимого, и клона не возникло. Стоимость и
  время `clone --recurse-submodules` такого репозитория на сервере неизвестны.
- Не проверялось поведение `vibe update` для ветки-git-источника (`##GS-MUTABILITY`
  обещает перевычисление HEAD). Для `cache add` это не нужно — он и так
  перевыбирает при каждом запуске, — но если сайт пойдёт через реальный
  `vibe install` в проект, разница «install не гонится за HEAD, update гонится»
  станет значимой.
- Не установлено, существует ли способ адресовать корень хоста как пакет,
  который планируется фазой 3 (отдельный doc-пакет с собственным `[package]` или
  добавление `[package]` в корневой `vibe.toml`): это вопрос к владельцу, а не
  к коду.
