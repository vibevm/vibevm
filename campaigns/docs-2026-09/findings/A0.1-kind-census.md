# A0.1 Перепись матчей по kind

Дата: 2026-09-11. Дерево: b1291b06 (`vibevm-docs`, ветка `research-preview-1-docs`).

Команда переписи (сохранена в `findings/kind-census.txt`, 114 файлов):

```
grep -rn -E "PackageKind::(Flow|Feat|Stack|Tool|Mcp|Lang)\b" crates xtask --include='*.rs' \
  | cut -d: -f1 | sort | uniq -c | sort -rn
```

Для получения строк и контекста каждого совпадения использован
`grep -rn -B2 -A1 -E "PackageKind::(Flow|Feat|Stack|Tool|Mcp|Lang)\b" crates xtask --include=*.rs`
(вывод — `context-dump.txt` в scratch, не публикуется), плюс точечное чтение
исходников для неоднозначных файлов и проверка `grep -n "cfg(test)|mod tests"`
для файлов без "test" в имени.

### 2. Полная таблица (все 114 файлов)

Условные обозначения типа матча: **ИСЧЕРП-ЯДРО** / **ИСЧЕРП-ПРОД** /
**ИСЧЕРП-ГЕН** (сгенерирован) / **ИСЧЕРП-ТЕСТ** — настоящий исчерпывающий
`match`; **СЛОВАРЬ** — открытый матч с явным `Unknown`/`_` хвостом (это
структурно не "скрывающий kind" `_ =>`, а сам механизм открытого словаря);
**СПИСОК** — статический массив (`ALL`, `known()`); **FIXTURE** —
struct-literal/`vec![]` со значением kind как данными; **ASSERT** —
`assert_eq!`/`assert_ne!` на одно значение; **CMP** — целевое сравнение
`==`/`!=` с одним конкретным kind вне матча; **DOCTEST** — пример внутри
`///`/`//!`; **МАТЧ-СТРОКА** — `match` по `&str`, не по `PackageKind`;
**КОДГЕН-ОБРАЗЕЦ** — строковый литерал, изображающий сгенерированный код
внутри теста самого генератора (xtask), не настоящий матч в этом файле.

"Т/П": Т = тест (включая тесты, встроенные в продуктовый файл через
`#[cfg(test)] mod tests`, что проверено отдельно — см. "Свидетельства");
П = продуктовый путь выполнения.

### 3. Дополнительно (вне регекса переписи, но напрямую относится к задаче)

`BootCategory` (`crates/vibe-core/src/manifest/package.rs:482-498`) — **другой**
enum (порядковая полоса `[boot_snippet]`, не `PackageKind`) — уже содержит
вариант `App` (строка 494: «An `app` package's contribution.») и упомянут в
доккомменте (466-471: "`flow` / `stack` / `tool` / `app` are package
contributions"). Есть свой исчерпывающий матч
`crates/vibe-index/src/scanner/manifest.rs:211-219` (`fn boot_category_str`) —
**уже** содержит ветку `BootCategory::App => "app"` — и
`crates/vibe-workspace/src/boot.rs:414-419` (`fn band_for`) уже трактует
`BootCategory::App` наравне с `Flow`/`Stack`/`Tool`. У `Doc` аналогичной
заготовки в `BootCategory` нет. Это НЕ матч по `PackageKind` (в перепись не
входит), но релевантно для того, кто будет проектировать `PackageKind::App`:
имя "app" уже занято в соседнем enum и уже разведено по всем матчам этого enum.

## Расхождения с решениями

Нет. Контекст решений кампании гласит: «Ядро (vibe-core) держит закрытый enum
PackageKind; индексная сторона (vibe-index) — открытый словарь с
Unknown(_)». Перепись подтверждает это буквально:
`crates/vibe-core/src/package_ref/kind.rs` — обычный закрытый Rust `enum`,
без генерации, без `Unknown`; `crates/vibe-wire/src/generated/shared/mod.rs` —
сгенерированный `enum PackageKind { Feat, Flow, Lang, Mcp, Stack, Tool,
Unknown(String) }`, и `crates/vibe-index/src/types/kinds.rs` — не отдельный
тип, а прямой ре-экспорт этого сгенерированного типа
(`pub use vibe_wire::generated::shared::{NamingConvention, PackageKind};`).
Код уже соответствует описанной архитектуре; расхождений с D-NN не найдено.

## Открытые вопросы

1. `crates/vibe-cli/src/commands/extensions.rs:311-318,340-348` конвертирует
   `vibe_core::PackageKind` в два ЛОКАЛЬНЫХ CLI-enum — `ManifestKind` и
   `ReportPackageKind`. Не установлено (не входило в спайк, требует отдельного
   чтения) — объявлены ли эти два enum с `#[non_exhaustive]`/явным списком
   вариантов и придётся ли добавлять `ManifestKind::Doc`/`App` и
   `ReportPackageKind::Doc`/`App` тоже — вероятно да, но файлы их определения
   не открывались.
2. `crates/vibe-index/src/cli/kinds.rs:23-36` (`parse_kind_flag`) — продуктовая
   функция, НЕ исчерпывающий матч (это `if let PackageKind::Unknown(_) =
   &kind { refuse }`), поэтому формально вне охвата переписи по регексу
   задания — но напрямую зависит от результата A0.2: если
   `vibe-wire/src/behaviour/vocabularies.rs`'s `from_str`/`known()` не
   пополнить, `--kind doc` при вызове CLI будет распознан как
   `PackageKind::Unknown("doc")` и ОТКАЗАН этой функцией с сообщением
   "unknown to this build", даже если "doc" уже есть в
   `formats/vocabularies.json`. Дальше разобрано в A0.2.
3. Не открывались (вне пределов регекса и вне заявленного объёма спайка):
   определения `ManifestKind` и `ReportPackageKind` (см. вопрос 1). Если
   владельцу нужен их матч-статус — отдельный маленький грep
   (`grep -n "enum ManifestKind\|enum ReportPackageKind" -r crates/vibe-cli`).
