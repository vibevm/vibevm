## Ответы

### 1. Открытый словарь → Rust-тип с `Unknown(_)` (индекс) и закрытый enum (ядро)

Это **два независимых, не связанных кодом пути** — общего у них только
человеческая дисциплина (одинаковые шесть строк) и общая ссылка на
VIBEVM-SPEC §4.1 в доккомментариях. Кодогенерация связывает только
open-vocabulary-сторону; закрытый enum ядра пишется от руки и не читает
`formats/vocabularies.json` вовсе.

**Открытая сторона (index/wire):**
1. Источник истины: `formats/vocabularies.json:2` —
   `"package_kind": {"metadata": {"x-vocabulary": "open", ...}, "enum":
   ["flow","feat","stack","tool","mcp","lang"]}`.
2. Генерирующая команда: `cargo xtask codegen` (`xtask/src/main.rs:85,396`,
   `Cmd::Codegen => run_codegen()`); парсинг словаря — `xtask/src/codegen/vocabulary.rs`
   (доккомментарий строки 11: "vocabularies live once in
   `formats/vocabularies.json`"; путь строится в `vocabulary.rs:44`
   `root.join("formats").join("vocabularies.json")`). Есть также
   `cargo xtask check-codegen` (`Cmd::CheckCodegen`, `main.rs:90,397`) — вероятно
   CI-проверка "регенерировано и совпадает", не открывалась подробно (вне
   объёма спайка).
3. Результат генерации: `crates/vibe-wire/src/generated/shared/mod.rs:2013-2025`
   — `pub enum PackageKind { Feat, Flow, Lang, Mcp, Stack, Tool, Unknown(String) }`
   — плюс рукописные `impl Serialize`/`Deserialize` в том же файле
   (2027-2039, 2041-2058), которые сериализуют шесть известных строк и
   заворачивают всё прочее в `Unknown`.
4. `crates/vibe-index/src/types/kinds.rs:12` — НЕ отдельный тип, а прямой
   ре-экспорт: `pub use vibe_wire::generated::shared::{NamingConvention,
   PackageKind};`. Доккомментарий файла (строки 1-8) явно говорит: "PROP-005
   §3.2's deliberate duplicate is retired: the parity test that watched the
   two copies for divergence watched a distance that no longer exists" —
   то есть раньше был отдельный копия+parity-тест, сейчас — просто ре-экспорт,
   расхождение структурно невозможно.
5. `crates/vibe-index/src/cli/kinds.rs:14` — ещё один ре-экспорт того же типа
   (`pub use crate::types::kinds::{NamingConvention, PackageKind};`), плюс
   продуктовая функция `parse_kind_flag` (строки 23-36) — граница CLI-аргумента:
   парсинг `PackageKind::from_str` тотален (открытый словарь), но
   ЛЮБОЙ `PackageKind::Unknown(_)` результат ЗДЕСЬ отклоняется с сообщением
   `"package kind '{value}' is unknown to this build — known kinds: {...}"`
   (строки 28-34), где список "known kinds" берётся из
   `PackageKind::known()`.
6. Отдельный рукописный поведенческий слой:
   `crates/vibe-wire/src/behaviour/vocabularies.rs:12-44` добавляет к
   сгенерированному типу `as_str()` (16-26), `known()` (33-43, статический
   массив из ШЕСТИ значений) и `impl FromStr` (60-74) — **это НЕ
   сгенерировано**, это рукописный код, повторяющий ту же таблицу строк,
   что и генерируемый `Serialize`/`Deserialize` в `generated/shared/mod.rs`.
   Он расходится с генератором по механизму синхронизации: генератор
   регенерируется автоматически из JSON; `vocabularies.rs` — вручную.

**Закрытая сторона (ядро):**
`crates/vibe-core/src/package_ref/kind.rs:31-97` — обычный, полностью
рукописный `#[derive(...)] pub enum PackageKind { Flow, Feat, Stack, Tool,
Mcp, Lang }` (без `Unknown`, без `#[non_exhaustive]`), с ручными `as_str`,
`ALL`, `FromStr` — **никакой кодогенерации, никакой связи с
`formats/vocabularies.json`**. Доккомментарий строки 18: "This enum is
closed; adding a fifth kind is a spec change, not a code change" — то есть
пополнение этого enum есть осознанно ручная, не автоматизированная операция.

### 2. Тест, пинующий совпадение двух копий словаря

Для **`package_kind` конкретно — такого теста сейчас нет**, и не может быть
структурно: `vibe-index/src/types/kinds.rs` — не копия, а ре-экспорт (см.
п.1.4), поэтому раздваиваться нечему. Раньше (PROP-005 §3.2) была отдельная
копия + parity-тест — доккомментарий кода прямо говорит, что это "retired"
(строка 6-8 файла), т.е. эта защита выведена из эксплуатации, потому что
предмет защиты исчез, а не потому что кто-то её удалил по ошибке.

Что действительно ПИНУЕТ форму словаря — три теста, ни один из которых не
сверяется с `formats/vocabularies.json` напрямую (все сверяются с
собственным зашитым списком):
- `known_kinds_round_trip_their_wire_strings` — `crates/vibe-wire/src/behaviour/vocabularies.rs:119-126`.
- `known_list_names_every_variant_and_nothing_else` — та же секция,
  строки 144-154, буквально `assert_eq!(known.len(), 6)` — жёстко зашитое
  число, при появлении `Doc`/`App` придётся вручную поправить на 8.
- `every_known_value_reads_named_and_writes_identical_bytes` —
  `crates/vibe-wire/tests/open_vocabulary.rs:33-51` — тоже перечисляет шесть
  строк буквально (`for wire in ["feat","flow","lang","mcp","stack","tool"]`,
  строка 36) и внутри держит исчерпывающий матч (39-46, см. A0.1 №12).

Отдельно найден похожий, но **другой** словарь (`naming_convention`), для
которого `formats/vocabularies.json:4` заявляет buквально: "Two copies exist
in code (`vibe-index/src/types/kinds.rs` and `vibe-core/src/manifest/project.rs`)
with identical strings today; the index-side test
`naming_convention_serde_matches_vibe_core_wire` pins them". В реально
прочитанном `vocabularies.rs` тест называется
`naming_convention_serde_matches_the_registry_wire` (строка 165) — имя не
совпадает буквально с тем, что цитирует метаданные JSON (возможно, тест был
переименован, а описание в JSON не обновили — не проверялось глубже, не
входит в объём: A0.2 просит `package_kind`, а не `naming_convention`).
Упомянуто как факт, найденный по пути, а не как ответ на вопрос про
`package_kind`.

**Вывод:** сегодня совпадение "формы словаря" держится на ТРЁХ статических
тестах, каждый из которых надо будет вручную расширить (добавить "doc"/"app"
в перечисления/массивы), а не на автоматической сверке с JSON. Дрейф между
`formats/vocabularies.json` (если туда добавят "doc"/"app") и рукописным
`vibe-wire/src/behaviour/vocabularies.rs` (`known()`/`from_str`) — если
кто-то забудет обновить второе — **не будет пойман кодогеном** (тот сам не
проверяет рукописный поведенческий слой) и не гарантированно будет пойман
тестами (см. открытый вопрос 1 ниже).

### 3. PROP-044: нужна ли break-заметка для нового значения в открытом словаре

Пакет ожидал «нет». Буквальное прочтение PROP-044 не даёт чистого «нет» —
результат неоднозначный, привожу обе стороны фактами:

**За «не нужна» (дух механизма):**
- §4.2a (`M-OPEN-ENUM-FROM-CLOSED`, xml-id, строки 249-256): "From a *closed*
  schema enum the generator emits an *open* Rust type: `enum {
  …known…, Unknown(String) }`. Compiler-checked exhaustiveness survives (the
  `Unknown` arm is mandatory), the original string is preserved through any
  rewrite, and tolerance of future values is structural." — открытый словарь
  специально спроектирован поглощать новые значения без последствий для
  старых читателей.
- §4.6 (`M-EPOCHS`, строки 309-315): "Light breaks (a new capability under
  must-understand) need no epoch at all." — добавление значения похоже по
  профилю на "light break", для которого явно не нужна эпоха.

**За «формально нужна» (буква гейта):**
- §4.7 (`M-BREAK-WINDOW`, строки 316-327): "**Any wire-visible change requires
  a break note** (`formats/breaks/NNN.md`: what · epoch · who fixes · sunset ·
  user recipe), **and the golden-corpus wire-diff must be empty or covered by
  one** — the gate does not forbid breaks, it makes an *unannounced* break
  impossible." Формулировка не делает исключения по "лёгкости" изменения —
  критерий механический: пуст ли wire-diff золотого корпуса. Добавление
  "doc"/"app" меняет сгенерированный код (новые именованные ветки вместо
  `Unknown`) и, вероятно, минимум один golden-фикстур/корпус (см. п.4 ниже) —
  то есть diff, скорее всего, НЕ будет пустым.
- §8 (`AGENT-GATES`, строка 469): "G7: schema/format changes demand a break
  note; golden wire-diff empty or covered (L3)." — тот же механический
  триггер продублирован в списке гейтов для агентов, отдельно от G8 ("schema
  changes refused while the break window is closed") — то есть требование
  break-заметки (G7) и требование эпохи/окна (G8) — **разные** гейты; "не
  нужна эпоха" (§4.6) не значит автоматически "не нужна break-заметка" (G7).

Прямой фразы вида "открытый словарь освобождён от break-заметки" в
прочитанном тексте PROP-044 НЕ найдено. Рекомендация по фактам кода:
ожидание пакета «нет» подтверждается ДУХОМ архитектуры (§4.2a), но не
подтверждается буквой единственного найденного правила, привязывающего
необходимость break-заметки к результату wire-diff (§4.7, G7) — это стоит
пересверить с владельцем как открытый вопрос, а не считать закрытым.

### 4. Корпуса `formats/corpora/**`, которым нужны образцы `doc`/`app`

`formats/vocabularies.json` называет `package_kind` (по `x-vocabularies`)
только у ДВУХ схем: `compatibility_entry` (строка 46) и `version_entry`
(строка 57, `"kind": {"ref": "package_kind"}`). Корпуса, реально построенные
на `version_entry` (то есть типизированные как `package_kind`, а не просто
несущие поле по имени "kind"):

- `formats/corpora/index/e1/by-name/wal.json`
- `formats/corpora/index_cli/e1/capabilities_report.json`
- `formats/corpora/index_cli/e1/get_report.json`
- `formats/corpora/index_cli/e1/list_report.json`
- `formats/corpora/index_cli/e1/outdated_report.json`
- `formats/corpora/index_cli/e1/purls_report.json`
- `formats/corpora/index_cli/e1/search_report.json`
- `formats/corpora/index_http/e1/capabilities_response.json`
- `formats/corpora/index_http/e1/package_list_response.json`
- `formats/corpora/index_http/e1/package_search_response.json`
- `formats/corpora/index_http/e1/package_upsert_response.json`
- `formats/corpora/index_http/e1/package_versions_response.json`
- `formats/corpora/index_http/e1/purls_response.json`

Это 13 файлов — кандидаты первой очереди на добавление образцов с
`"kind": "doc"` / `"kind": "app"` (round-trip проверка новых именованных
вариантов).

Второй, более слабый круг — корпуса с полем `"kind"`, объявленным в схеме
как ОБЫЧНАЯ строка (`{"type": "string"}`), а не `{"ref": "package_kind"}` —
`project` (строка 17), `world_package` (строка 18), `artifact` (строка 22),
`slot_target` (строка 23), `reply_artifact` (строка 25) — в рантайме несут
те же шесть значений по факту, но формально не завязаны на словарь:
`formats/corpora/extensions/e1/report.json`,
`formats/corpora/lifecycle/e1/{context,plan,report}.json`,
`formats/corpora/native/e1/{compile_request.valid,compile_request.invalid,context.valid}.json`.
Им расширение желательно для полноты, но не обязательно с точки зрения
самого словаря `package_kind`.

    let kind = match PackageKind::from_str(value) { Ok(kind) => kind, Err(u) => match u {} };

## Расхождения с решениями

Нет прямого расхождения с D-NN campaña. Отмечено внутреннее расхождение
между `formats/vocabularies.json`'s описанием `naming_convention` (называет
тест `naming_convention_serde_matches_vibe_core_wire`) и реальным именем
теста в коде (`naming_convention_serde_matches_the_registry_wire`,
`vocabularies.rs:165`) — это про ДРУГОЙ словарь (не `package_kind`), к
задаче A0.2 впрямую не относится, зафиксировано как найденный по пути факт,
не как REVIEW против решения кампании.
