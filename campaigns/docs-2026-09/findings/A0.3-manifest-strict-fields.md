## Ответы

### 1. Верхний уровень `vibe.toml` пакета; где живут `[boot_snippet]`, `[[skill]]`, `[compatibility]`, `[i18n]`

Верхнего уровня фактически **два** сцепленных типа, а не один:

- **`ManifestWire`** — `crates/vibe-core/src/manifest/package/visibility.rs:299`
  (`pub(crate) struct ManifestWire`, `#[serde(deny_unknown_fields)]` строка 298)
  — это структура, в которую TOML парсится НАПРЯМУЮ (`toml`/`serde` видят
  именно её). Она приватна для крейта.
- **`Manifest`** — `crates/vibe-core/src/manifest/document.rs:76`
  (`pub struct Manifest`) — публичный, эргономичный домен-тип, на который
  всё остальное дерево ссылается. Сам НЕ парсится напрямую:
  `#[serde(try_from = "ManifestWire")]` (document.rs:75), конверсия —
  `impl TryFrom<ManifestWire> for Manifest` (visibility.rs:384-451) и обратно
  `impl TryFrom<Manifest> for ManifestWire` (visibility.rs:453-524).

Из этого следует главное для A0.3.4 (см. ниже): **новое поле верхнего
уровня надо добавлять в ОБЕИХ структурах** (`ManifestWire` и `Manifest`) и
в обоих направлениях `TryFrom`, иначе оно либо не распарсится (нет в
`ManifestWire`), либо распарсится, но не долетит до остального кода (нет в
`Manifest`).

Адреса секций, которые спрашивает пакет:

| Секция | Тип | Файл:строка (само определение) | `deny_unknown_fields`? | Поле на `Manifest` | Поле на `ManifestWire` |
|---|---|---|---|---|---|
| `[boot_snippet]` | `BootSnippet` | `crates/vibe-core/src/manifest/package.rs:567` | да (566) | `document.rs:202` `pub boot_snippet: Option<BootSnippet>` | `visibility.rs:359` `boot_snippet: Option<BootSnippet>` |
| `[[skill]]` | `SkillDecl` | `crates/vibe-core/src/manifest/package/skill.rs:61` | да (60) | `document.rs:138` `pub skills: Vec<SkillDecl>` (rename="skill") | `visibility.rs:328-329` `skills: Vec<SkillDecl>` (rename="skill") |
| `[compatibility]` | `Compatibility` | `crates/vibe-core/src/manifest/package.rs:397` | да (396) | `document.rs:198` `pub compatibility: Compatibility` | `visibility.rs:356-357` `compatibility: Compatibility` |
| `[i18n]` | `I18nDecl` | `crates/vibe-core/src/manifest/i18n.rs:49` | да (48) | `document.rs:242` `pub i18n: I18nDecl` | `visibility.rs:376-377` `i18n: I18nDecl` |

`Compatibility` (package.rs:395-403) сама по себе: `min_vibe_version:
Option<String>` + `requires_kinds: Vec<PackageKind>` — именно тут будущий
`Doc`/`App` появится как значение `requires_kinds`, если пакету документации
понадобится потребовать другой пакет конкретного kind (не сам факт
добавления kind — это уже разобрано в A0.1/A0.2).

### 2. Где и как проверяется `min_vibe_version`

**Нигде.** Поле объявлено (`package.rs:399`), копируется как есть в
индексную запись (`crates/vibe-index/src/scanner/manifest.rs:88`:
`min_vibe_version: c.min_vibe_version.clone()`) и в пейлоад
post-publish-хука (`crates/vibe-publish/src/post_hook.rs:253`:
`"min_vibe_version": manifest.compatibility.min_vibe_version`) — оба раза
чисто транзитом, без сравнения с текущей версией `vibe`. Единственная
логика вокруг поля — проверка "пусто ли" (`Compatibility::is_empty`,
package.rs:405-408, и зеркально `crates/vibe-wire/src/behaviour/projections.rs:21`
для сгенерированного `CompatibilityEntry`). Расширенный grep по
`vibe-resolver`, `vibe-workspace`, `vibe-install`, `vibe-cli`, `vibe-lifecycle`
не нашёл НИ ОДНОГО места, где `env!("CARGO_PKG_VERSION")` (реальная текущая
версия — используется для `--version`, User-Agent строк и `generated_by`)
сравнивался бы с чьим-то `min_vibe_version`. Сообщений об ошибке для этого
случая, соответственно, тоже нет — их негде печатать.

Практическое следствие для F-05 (см. вопрос 5): сегодня старый `vibe`,
встретив пакет с `min_vibe_version` выше своей версии, **не откажет по
этой причине** — он либо примет манифест как есть (поле декларативно), либо
откажет по СОВСЕМ ДРУГОЙ причине — `deny_unknown_fields` на `ManifestWire`,
если новые поля документации (title/documents/…) физически не влезают в
известную схему (см. п.4).

### 4. Какие структуры с `deny_unknown_fields` расширять под новые поля документации

Кода для этих полей ещё нет — ниже перечислена **их вероятная посадка по
аналогии с уже существующими полями того же типа** (факт: аналогия точная и
цитируемая), а не наблюдение существующего кода.

- **`title`, `abstract`, `lang`** (скалярные, простые) — по форме совпадают
  с уже существующими скалярными полями `PackageMeta`
  (`crates/vibe-core/src/manifest/package.rs:81-159`,
  `#[serde(deny_unknown_fields)]` строка 80): `description: Option<String>`
  (122), `homepage: Option<String>` (124), `keywords: Vec<String>` (126) —
  `title`/`abstract` естественно лягут туда же, новыми
  `Option<String>`-полями с `#[serde(default, skip_serializing_if =
  "Option::is_none")]`. **`lang` — коллизия смысла, не просто добавление**:
  в манифесте уже есть `[i18n]` → `I18nDecl.canonical` (`i18n.rs:53`,
  "Default language for this manifest") — ровно та же идея ("на каком языке
  этот файл"). Открытый вопрос: новое поле `lang` на `PackageMeta` дублирует
  `i18n.canonical`, или означает что-то более узкое (например, "язык
  ИСХОДНОГО, недокументного контента", отдельно от i18n-машинерии
  переводов)? Решение — не моё (не пересуживаю), но сам факт пересечения
  стоит зафиксировать.
- **`[[documents]]`** (множественная таблица) — по форме как `[[skill]]` /
  `[[binary]]` / `[[mcp_server]]`: новый `Vec<DocumentDecl>` (например,
  `pub use document::DocumentDecl;` из нового подмодуля `package/document.rs`
  — по образцу `package/skill.rs`), новое поле на ОБЕИХ структурах
  (`Manifest` и `ManifestWire`, см. п.1), `#[serde(default, rename =
  "document", skip_serializing_if = "Vec::is_empty")]`, сам `DocumentDecl`
  — новая структура с `#[serde(deny_unknown_fields)]`.
- **`[documentation]`** (одиночная таблица) — по форме как `[compatibility]`
  / `[boot_snippet]`: новое поле `documentation: Option<DocumentationSection>`
  (или `DocumentationSection` с собственным `is_empty()`, как `Compatibility`)
  на обеих структурах верхнего уровня; новая структура с
  `#[serde(deny_unknown_fields)]`.
- **`[translates]`** (единственное число — "этот пакет переводит/описывает
  вон тот") — концептуально это **уже существующее поле** `PackageMeta.describes:
  Option<Purl>` (`package.rs:127-131`, доккомментарий: "PURL of the upstream
  library this package documents (PROP-003 §2.5.6)... ties the package's
  version to a specific upstream artefact"). Если "переводит" должно
  указывать на ДРУГОЙ vibevm-пакет (а не внешний PURL), `describes` в
  текущем виде не подходит по типу (`Purl`, не `PackageRef`) — тогда
  `translates` нужен как отдельное поле того же смыслового слота на
  `PackageMeta`, рядом с `describes`, а не как что-то с нуля.
- **`[translations]`** (множественное число) — по форме ближе всего к
  списку `i18n_entry`-подобных записей (`formats/vocabularies.json:49`,
  `available: Vec<String>`/`default: Option<String>` в `I18nDecl`,
  `i18n.rs:49-73`), но если каждая запись перевода несёт не только язык, а
  ещё путь/файл — тогда это отдельная новая структура
  `Vec<TranslationEntry>` (аналог `embedded_source_entry`-списка,
  `package.rs:123-131` `embedded_sources: Vec<EmbeddedSourceDecl>`) внутри
  нового `[documentation]` или на верхнем уровне.
- **`[media]`** — прямого прецедента в текущем манифесте не нашлось; ближе
  всего по форме — `[[binary]]`/`[[skill]]` (список файловых артефактов
  пакета), то есть вероятно `Vec<MediaDecl>` в новом подмодуле, с
  `deny_unknown_fields`.

Итог одним списком структур, которые физически придётся написать/расширить:
`PackageMeta` (расширить: title, abstract, возможно lang) — package.rs:81;
новая `DocumentDecl` + `Vec` на `Manifest`/`ManifestWire`; новая
`DocumentationSection` + `Option` на `Manifest`/`ManifestWire`; возможно
новое поле на `PackageMeta` рядом с `describes` (translates); новая
`TranslationEntry` + `Vec`; новая `MediaDecl` + `Vec`. Каждая новая
структура — по конвенции всего файла — со своим `#[serde(deny_unknown_fields)]`
(без исключений: ни одна из семи существующих package-role структур,
прочитанных в этом спайке, не оставляет "дыры").

### 5. Какую `min_vibe_version` ставить пакетам с новыми полями — открытый вопрос владельцу F-05

Ключевой факт, meняющий рамку вопроса: **`min_vibe_version` сегодня ничего
не гейтит** (п.2) — реальная защита старого `vibe` от нового манифеста уже
существует и работает независимо от этого поля: `ManifestWire`'s
`#[serde(deny_unknown_fields)]` (visibility.rs:298) откажет распарсить файл
с незнакомыми ключами (`title`, `[[documents]]`, ...) ЛЮБОЙ версией `vibe`
старше добавления этих полей, вне зависимости от того, что написано в
`min_vibe_version`.

**Вариант 1 — поднять версию `vibe`.** Новая возможность манифеста (kind
doc/app + пакет новых полей) — по обычной семверной дисциплине как минимум
minor bump. Новые пакеты документации ставят `min_vibe_version` на новую
версию. Функционального эффекта на старый `vibe` сегодня это не даёт (он и
так откажет по `deny_unknown_fields`), но поле остаётся честным для
будущего, когда проверка появится, и для реестра/UI, показывающих "требует
vibe ≥ X" человеку уже сейчас.

**Вариант 2 — оставить `1.0.0`, принять, что старый `vibe` отвергнет
манифест.** Ничего не менять в `Cargo.toml`; писать `min_vibe_version =
"1.0.0"` (или не писать вовсе) в новых пакетах — раз поле сейчас не
проверяется, разницы в поведении нет. Цена — поле становится вводящим в
заблуждение метаданными (говорит "1.0.0 достаточно", хотя фактически старый
`1.0.0` физически не распарсит файл).

**Рекомендация по фактам кода:** вариант 1. Поле `min_vibe_version` и вся
инфраструктура вокруг него (`Compatibility`, `CompatibilityEntry` на wire,
`env!("CARGO_PKG_VERSION")` везде) уже существуют и используются как ЧЕСТНАЯ
декларация версии в других местах (`generated_by`, User-Agent) — заполнить
её правильно сейчас не стоит ничего, а вариант 2 оставляет намеренно ложное
число в машинно-читаемом поле. Отсутствие сегодняшнего runtime-гейта — не
повод писать туда неправду; и то, что реальный отказ старого `vibe` всё
равно идёт через `deny_unknown_fields`, а не через `min_vibe_version`, не
входило в объём принятия решения владельцем и стоит явно проговорить с ним
до правки версии.

## Открытые вопросы

1. Пересекается ли будущий `lang` (уровень `[package]`) с существующим
   `[i18n].canonical` (`i18n.rs:53`) — см. п.4.
2. `[translates]` (ед.ч.) может быть тем же самым слотом, что и уже
   существующий `PackageMeta.describes: Option<Purl>` (package.rs:131), если
   допустить, что "переводимый" объект тоже описывается PURL, а не
   `PackageRef`; либо нужен отдельный тип-ссылка на vibevm-пакет — не решено,
   не мой выбор.
3. `cargo xtask check-codegen` и любые CI-гейты вокруг `deny_unknown_fields`/
   схемы манифеста не проверялись на предмет того, потребуют ли они
   отдельного `formats/breaks/NNN.md` при добавлении новых полей `vibe.toml`
   — судя по `PROP-044` §6.2 (`FMT-MANIFEST`, не процитировано подробно
   здесь — см. A0.2 про соседний break-note вопрос), "every new manifest key
   is a years-long obligation and requires a break note, a codemod, and
   generated documentation" — то есть для `vibe.toml` (в отличие от
   открытого словаря kind) правило сформулировано БЕЗ двусмысленности:
   новое поле манифеста прямым текстом требует break note. Это отдельный,
   более жёсткий факт, чем вопрос про kind в A0.2, и явно относится к
   каждому из шести новых полей (`title`, `abstract`, `[[documents]]`,
   `[documentation]`, `[translates]`, `[translations]`, `[media]`) — семь
   полей, семь потенциальных break notes, если читать PROP-044 §6.2 буквально.
