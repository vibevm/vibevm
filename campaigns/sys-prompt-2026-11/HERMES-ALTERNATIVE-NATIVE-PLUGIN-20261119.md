# Independent Hermes alternative: use the already-serving owner

Research record, 2026-11-19. Native pin `4ae451d4126327c871fd084e60c045dec0c85911`. No change to product, installed Hermes, operator profile, or H1–H3 acceptance. This corrects the earlier inference that a new upstream authority-side RPC is necessarily required. It is not the owner-facing completion blog.

## Reframing

Do not reserve a second runner for a profile which already has a ready local owner. In `hermes_cli/gateway_client.py:330`, `connect_gateway(endpoint=<discovered GatewayEndpoint>)` and setting `HERMES_TUI_GATEWAY_URL` are **different branches**: the former requests a native ticket and uses `gateway_ws_target`; the latter uses the explicit URL without that ticket. `discover_gateway_endpoint` is distinct from ensure/start. In `gateway/session_finite.py` the existing owner/creator/CLI policy continues to govern unattended admission. This distinction does not make a private minimal runner ready or grant it a ticket.

`hermes_cli/plugin_rpc.py:register_rpc` and `gateway/session_plugin_rpc.py:call_plugin_rpc` provide a profile-side plugin RPC. A scoped call runs native session control authorization. The plugin must itself require a session for a binding operation: the API also supports unscoped registration calls. A session ID/client label is not authorization, nor does successful RPC distinguish two viewers submitting to one session. `ctx.register_middleware('llm_request', ...)` is a supported request-replacement extension; unlike `register_system_prompt_section` it is not a 4,000-character section at the volatile after-memory anchor (`hermes_cli/plugins_dispatch.py:98`).

## Executed observations, not product acceptance

Independent inline Python -I/-B experiments ran under bwrap unshare-all/clearenv with read-only pinned source and staged dependencies, synthetic tmpfs home/config, no operator credentials or public provider traffic. Only spawned sandbox-owned daemons were settled. Plugins and synthetic files lived inside ephemeral sandboxes; this record summarizes observations, not hashes of retained raw logs.

1. Native request middleware unit boundary: selected synthetic session accepted 310025 ASCII characters; a different session's payload was unchanged. A deliberately throwing callback also returned the unmodified request. This is affirmative evidence of FAIL-OPEN, not a zero-provider refusal. Native helper copied the original input.
2. In-process authority RPC dispatch: own fixture local session OK; read-only principal denied; another local principal's session denied. First test used raw display user id rather than the native creator subject and was denied even in the intended positive case. Corrected fixture bound the native actor subject as production local session creation does. No identity bypass or authorization change.
3. Stock `gateway.run` in an isolated synthetic profile was started separately as the fixture's ready owner. A local client discovered it, connected through the ticket-bearing branch, created a native `oneshot` session, and bound **its returned ID** through a profile plugin RPC. Stock `hermes_cli.main -z ... --resume <id>` returned 0 and the synthetic server's response. Local HTTP capture: exactly one main request contained 310025 consecutive synthetic bytes once in the system content. A second stock `-z` in an unbound session on the same still-running daemon returned 0, one main request, zero such blocks. No `native_owner` override. This is actual wire/runtime evidence for ready-local-owner H1 + session-scoped H3 happy path, not an implementation of independent invocation leases or a cold terminal-only start.
4. Separate fixture: stock classic `chat --cli --worktree --verbose -Q -q ...` against a ready synthetic gateway returned 0 with the synthetic reply. At the main request middleware both `ctx.session_cwd()` and `agent.runtime_cwd.resolve_context_cwd()` named the actual `/tmp/project/.worktrees/hermes-...`; the gateway's `os.getcwd()` was `/tmp/project`. Main capture contained the full test block. Six other captured calls did not contain the main query or block; they were not classified as six workers or six additional passes. This tests the classic finite query/worktree path, not Ink/TUI, every classic option, or a production handoff mechanism. In this separate fixture selection used a test project marker, **not** per-invocation authorization.

In the two real-CLI experiments the fixture altered a synthetic project-context marker within a text system message. That establishes placement/size at the local receiver, not the correct stable/volatile boundary for a real Vibe prefix, native file/resource equivalence across providers, cache hits, cost savings, token budgeting or multi-turn/compaction parity. Do not ship the marker trick.

## Remaining decision and discriminating next test

Do not start a maintained fork on the strength of the prior blocker packet. A pre-enabled owner plugin can keep native command dispatch, worktree selection and unattended authorization intact. Next evaluate the actual Vibe Rust composition at the authoritative turn cwd, exact invocation and native child exclusion (including a second viewer of the *same* session), and failure enforcement. `agent/turn_context.py:1362` accepts an explicit `pre_llm_call` block before turn-start compaction; exception or unloading is not a reliable veto for a later failed `llm_request`. The latter runs after provider kwargs/cache decoration (`agent/turn_api_request.py`); merely catching an exception or checking successful registration earlier does not guarantee that the admitted request contains the prefix. Required negative: the plugin loses its binding or fails between verification and dispatch; no external submission for that Vibe invocation, with ordinary native launches unaffected. Also distinguish retry/fallback/auxiliary paths. No new provider proxy, auth changes, upstream edit or exemption is authorized.

If native mechanisms cannot enforce this invariant, propose a **narrower** upstream requirement: mandatory session/turn-scoped contribution before native cache budgeting and decoration, whose missing contribution refuses only that managed turn. A separate terminal-only lifecycle is still a possible requirement for **cold start when no owner exists and unrelated services must not start**. No operator gateway or real TUI/platform was tested. Pre-existing Vibe support and earlier RED receipts are unchanged.
