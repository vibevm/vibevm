## Native CLI and TUI are the product interface

Owner direction: invest in a Hermes-specific adapter behind the existing `vibe agent <launcher>` entry. Do not reimplement Hermes' renderer, chat loop, slash-command interpreter, session store, or provider policy. Translate only decisions that Vibe owns: trusted executable/profile resolution, project selection and instruction scope, capability negotiation, and an honest delivery/degradation notice. Pin grammar to the admitted installation; upstream documentation describes intended UX, not proof that every command works on the pin.

The ordinary command should follow the user's native interface preference. Explicit `--cli` and `--tui` must choose the actual corresponding Hermes frontend, not a lookalike or the restricted transport viewer. Support native continuation (`-c`/`--continue`, `--resume` by native ID/title where admitted), in-session help and discovery/picking of sessions without requiring a database query, streaming replies, approval/clarification, interrupt/exit, and normal terminal restoration. Preserve profile, selected project/worktree and launcher aliases. Native new/switch changes may not silently carry a project binding into another context. Keep `-q`, `-z`, pipes, output protocols and exit status distinct from the interactive path. No hand-maintained parallel CLI grammar; inventory the supported native families, delegate to their existing owners, and report real gaps rather than swallowing args. Do not proxy service installation or destructive maintenance as incidental launch effects.

Prioritize the actual classic two-window journey first, then the same user outcome through real native TUI (PTY interaction, native selector, response and clean exit) against the pinned runtime. Preserve command help and offer actionable diagnosis if the TUI dependencies are missing. Native help/list smoke tests alone are not interactive-TUI proof. Surface delivery state separately from the interface: do not silently drop project instructions to make a frontend appear supported, and do not force transport-only choices on the user when the promised native route is available. Keep all Hermes-specific behavior local to that adapter; no general-harness framework refactor.
