# Sys-prompt campaign: format and behaviour changes

Append-only log of user-visible changes made by the campaign in `PLAN.md`, material for release notes. Entries are `SP-FMT-NNN`; numbers are never reused.

Regime at writing (`formats/EPOCHS.toml:35-36`, 2026-11-10): `public = false`, `break_window_open = true` — breaking is free and unmigrated, the standing user recipe is «regenerate / re-init / re-fetch», and no break note under `formats/breaks/` is required. Every entry below still states the format registry record it touches and whether its epoch moves, because `FormatId` cannot express an unregistered format (`xtask/src/codegen/format_id.rs:52`, `crates/vibe-wire/tests/format_registry_completeness.rs:32`, and in the other direction `xtask/src/codegen/strictness.rs:131-146`).

Design authority for all of it: `spec://org.vibevm.core/vibevm/common/PROP-076#SYS-FORMAT-CHANGES`.

**Id ranges.** `SP-FMT-001`…`SP-FMT-020` are the ids `PLAN.md` assigned to the phases while planning; a phase fills its own. Ids from **`SP-FMT-101`** up are for a format a phase turned out to need and the plan did not foresee, so two phases running concurrently cannot pick the same number.

**One standing note for every entry below.** The whole feature is **opt-in by the presence of one authored file**. A project with no `vibevm/vibespecs/boot/SYSTEM-TEMPLATE.md` sees no new artifact, no new boot behaviour and no byte of change in its existing `STATIC`/`INDEX`/redirect output — `PLAN.md` phase P5 makes that a golden test over the whole boot directory. Nothing in this campaign changes an existing project's boot.

## SP-FMT-001 — `vibevm/vibespecs/boot/SYSTEM-TEMPLATE.md`, a reserved authored path (Phase 1)

Status: **delivered 2026-11-10** (phase P1). The layout role, the three predicates and the enrolment and admission gates are implemented and tested; no generation exists yet, so nothing reads the template and nothing writes it — which is exactly the reservation this id claims and no more.

- New record `[format.boot-system-template]`, epoch **1**, `schema = "none"` (literal UTF-8 text, no structure to validate), `recoverable = true`, `foreign_parsers = "many"` (a human writes it and any editor may), `corpus = "none"`, `sunset = "none"`.
- **Authored by the user, never generated and never deleted by vibe.** It is the one input the user writes, and `vibe install` neither creates nor overwrites it. `vibe init` may *offer* to create one.
- **Its presence is the entire opt-in.** Absent: no generation at all. Present and empty: opt in with no frame of the user's own, so the prefix is the entrypoint export plus the lane.
- **It is text, not a program.** No shell, no environment or `HOME` read, no `INCLUDE`, no network, no conditionals, no placeholder grammar and no placement directives. Curly braces, fenced examples, Markdown links and the literal strings `SYSTEM.md` or `<vibevm>` are ordinary characters with no effect. Controlled placement is a later extension and deliberately not in this version.
- **New layout role, distinct from "generated".** `crates/vibe-core/src/layout.rs` gains `SYSTEM_TEMPLATE_MD` and `current_boot_system_template()`, plus a **new predicate** `is_reserved_boot_authored_input`. The template is excluded from automatic boot enrolment and from declaration admission as a source row, but it is **not** a member of the private `generated_boot_paths()` list: it is not generated, not owned by publication, never removed as a stale output, and preserved like any authored file. Collapsing the two roles into one list would be the convenient mistake that deletes the user's file on a format change.
- **The hazard this closes, verified at `e2508fc1d`:** `crates/vibe-workspace/src/install/bootgen/own_boot.rs:167` `legacy_entries` admits every immediate boot-directory child that `vibe_specdoc::is_spec_source` accepts — by extension alone, `Some("md" | "xml")` (`crates/vibe-specdoc/src/load.rs:76-81`) — excluding only `STATIC.md`, `STATIC.xml` and `INDEX.md` (`:185-190`). Without this entry the template would be delivered to every session as ordinary boot instructions.
- Refused as a declared source row in any ASCII case spelling, by the same rule `crates/vibe-core/src/manifest/source_descriptor/mod.rs:228` already applies to generated outputs.
- **As delivered.** `layout.rs` gained the three constants, the three `current_boot_system*()` accessors, two more entries in the private `generated_boot_paths()` (now five), a new private `reserved_boot_paths()` (six — the generated five plus the authored template) that `is_reserved_boot_source` reads, and the new `is_reserved_boot_authored_input` predicate. **No existing caller of either public predicate needed an edit**, as `PLAN.md` §5 predicted. `legacy_entries` now asks the two predicates instead of comparing three bare names, so a future reserved name is excluded without touching it. The one message change: `valid_source_path`'s refusal now reads "names a reserved boot path — a generated boot output or the authored system-prompt template", because "generated boot output" became inaccurate once a non-generated path joined the refusal.
- **Hazard measured before the gate, by spike S3** (`PLAN.md` §3): a fixture boot directory holding two authored snippets plus `SYSTEM.md` and `SYSTEM-TEMPLATE.md` produced **four** `INDEX.md` rows, so both new names were delivered to every session as ordinary boot instructions. The predicted *recursive growth* of the generated lane did **not** occur and cannot: own authored boot is unconditionally `LinkType::Dynamic`, so the bytes are never compiled in — the files are only named. A literal template in no spec dialect was admitted **without error**, because an INDEX row is not parsed at generation time. The user-visible failure this id prevents is therefore silent doubled delivery, not a growing artifact.

## SP-FMT-002 — manifest `[system_prompt]` (Phase 1)

Status: **delivered 2026-11-10** (phase P1).

- `[format.manifest]` (`schema = "none"`, authored TOML, `foreign_parsers = "many"`), epoch **1 → 1**. Every addition is optional and omitted when absent, so existing manifests serialise byte-identically.
- New optional top-level table `[system_prompt]`, which must be added to `Manifest` (`crates/vibe-core/src/manifest/document.rs`), to `ManifestWire` (`…/package/visibility.rs`, `deny_unknown_fields`) and to both `TryFrom` arms, or the table is refused as unknown.
- Exactly three optional members in this version, and nothing else is configurable:
  - `entrypoint` — a relative path admitted only from the closed set `CLAUDE.md` / `AGENTS.md` / `GEMINI.md` (the same set `crates/vibe-workspace/src/boot_artifacts/redirect.rs:29` already owns), or the boolean `false` for no entrypoint segment. Default `"AGENTS.md"`.
  - `lane_form` — `"verbatim"`, the default and **the only accepted value in this version**. Reserved so the canonical-Markdown-projection alternative of `PROP-076#SYS-LANE-VERBATIM` needs no format change later; `"projected"` refuses as not-yet-supported rather than silently behaving as verbatim.
  - `recipe` — an integer pinning the generated transport-contract recipe (`SP-FMT-009`). Absent means the current one.
- **Two more keys were added by the owner decision of 2026-11-10** and are recorded under `SP-FMT-101`, not here: `host` (where the agent runs) and `target` (which operating systems the product is for). They are optional and omitted when absent like the three above, so this id's byte-identical claim is unaffected.
- Refusals, each naming its field as a TOML path (PROP-059 `#declaration`): `[system_prompt]` present with no `SYSTEM-TEMPLATE.md` beside it; an `entrypoint` outside the closed set, with the message naming the three legal spellings; `lane_form` other than `"verbatim"`; an unknown member.
- **Why the manifest and not the template:** the template is literal text by `SP-FMT-001`, so it carries no configuration; `[system_prompt]` is the one place a non-text choice lives. The precedent is PROP-075 `#TEMPLATE-SPELLING`, which puts `[template]` in the manifest for the same reason.
- **As delivered, with one naming deviation and one placement choice.** The typed section is `SystemPromptSection { entrypoint: EntrypointChoice, lane_form: LaneForm, recipe: Option<u32> }`, with `EntrypointChoice::{Default, File(EntrypointFile), None}` and `LaneForm::Verbatim`. The closed set is named **`EntrypointFile`**, not `RedirectFile` as `PLAN.md` wrote: `vibe_core::manifest::RedirectFile` already exists and is the unrelated `vibe-redirect.toml` document, so the plan's name would have collided. A test in vibe-workspace (`boot_artifacts/redirect/tests.rs`) pins `EntrypointFile::ALL` to `REDIRECT_FILES`, since the two crates cannot share a constant and vibe-core cannot depend on vibe-workspace.
- **Bad values refuse at deserialisation, not at `validate()`**, following `manifest/package/when.rs`: `lane_form = "projected"` refuses as reserved rather than silently behaving as `verbatim`, an `entrypoint` outside the closed set refuses while naming all three legal spellings, and `entrypoint = true` refuses because it says nothing. The cross-field refusal — the table with no `SYSTEM-TEMPLATE.md` beside it — needs a directory, so it is `Manifest::validate_system_prompt_beside`, called from `Manifest::read`; a manifest parsed from a string is deliberately **not** checked, because inventing a directory would be worse than not checking.
- **The table is legal on every role**, including a bare `[project]`: the prefix is a property of the selected node, so `[system_prompt]` is not a package-role section and does not join the "package-role section without `[package]`" refusal list.

## SP-FMT-003 — `vibevm/vibespecs/boot/SYSTEM.md`, the generated prefix (Phase 3)

Status: **planned**.

- New record `[format.boot-system-prompt]`, epoch **1**, `schema = "none"` (generated UTF-8 text), `recoverable = false` (it is a witnessed generation, not reprojectable from a single source), `foreign_parsers = "many"` (an API caller reads it as bytes), `corpus = "none"`, `sunset = "none"`.
- **Generated, git-tracked and marked generated**, like `STATIC.*` and `INDEX.md` (PROP-009 `#ARTIFACTS-GENERATED`), so a fresh clone needs no build and boot stays pure file reading. Editing it by hand is not a supported way to configure anything; the supported ways are `SP-FMT-001` and `SP-FMT-002`.
- **Three segments, in this order:** the template's bytes, the entrypoint export, the compiled static lane. That is PROP-009 `#SESSION-START-ORDER` with the user's frame prepended, and it is also the cache-optimal order, because a provider cache matches a prefix and the lane is the segment that changes most often while the template changes least.
- **The entrypoint export substitutes the managed block in place.** The vibe-owned `<vibevm>` block's exact byte range (`redirect.rs:128` `locate_block`, `BlockLocation::Present { start, end }`) is replaced by the transport contract of `SP-FMT-009`; **every other byte of the entrypoint is verbatim.** No summarisation, no reordering, no heuristic filtering, no removal of an author's absolute path. A malformed or mismatched marker pair is a named refusal, never a repair. A node whose entrypoint has no managed block gets its bytes whole with the contract as a trailing segment.
- **The lane enters as the admitted bytes, opaque.** It is not re-parsed, not re-compiled as a fresh normal source, and no `#use` marker, provenance comment or `spec://` reference inside it is followed. The `.md` extension is a name and asserts no parse: the segment may hold XML bytes verbatim.
- **Framing and encoding, which is where determinism lives.** UTF-8, no BOM. One fixed frame line per segment, carrying the layer-qualified segment id and nothing variable — no digest, no length, no time, no checkout path. Frames use LF and the file ends with exactly one LF; a segment **body** is verbatim, with one LF inserted before the next frame when the body does not end with one, so an authored CRLF document keeps CRLF inside its own segment. The frame token is never an exactly standalone `<vibevm>` or `</vibevm>` line, so `locate_block` cannot mistake a frame for a marker.
- **Nothing volatile, ever:** no build time, no absolute checkout or `HOME` path, no Git branch/HEAD/dirty state, no task or plan state, no session or run id, no model name, no token estimate, no environment detection. And **no whole-build digest before the content** — a digest at the top would make any late change destroy the whole prefix's match, which is the opposite of the feature. Padding the text to reach a provider's minimum cacheable length is forbidden.
- **No INDEX entry's bytes are in it,** however unconditional the row. `kind = "static"` in INDEX is read timing, not linkage — PROP-009 `#AUTHORED-INDEX-BOUNDARY` in words, `crates/vibe-workspace/src/boot_artifacts.rs:203-207` in code, PROP-072 `#SOURCE-HOST-BOOT-LAW` from the source side.
- **Honest limit:** `SYSTEM.md` alone is not a session. A caller that sends it alone gets an explicitly incomplete boot; obligations an entrypoint states beyond reading files are not discharged by generation and are not reported as discharged.
- Scale on the host repository at `e2508fc1d`, for the release note: the lane is 251,817 bytes and the entrypoint 26,121, so the prefix is **278,092 bytes** and holds **83%** of the 335,832 bytes of boot material; the eight INDEX rows are the remaining 57,894 (17%). *Corrected 2026-11-10 by spike S1, which assembled the prefix by hand: this entry read "~278 KB and holds **92%**", and 92% was an arithmetic slip — `(251,817 + 26,121) / 335,832` is 82.76%, and the assembled prefix is 82.81%. The 75%-is-the-lane figure was right. Corrected in `PROP-076#SYS-SIZE-TODAY` too.*
- Repository prerequisite for the determinism claim: `.gitattributes:7` `* text=auto eol=lf`. A project without it gets a prefix that differs by checkout, which diagnostics report.

## SP-FMT-004 — `vibevm/vibespecs/boot/SYSTEM.meta.json`, `vibe-system-prompt/1` (Phase 3)

Status: **planned**.

- New record `[format.boot-system-meta]`, epoch **1**, `schema = "schemas/system_prompt_meta.jtd.json"` (new), `recoverable = false`, `foreign_parsers = "ours"`, `corpus = "formats/corpora/boot-system-meta/e1"` (one golden document), `sunset = "none"`. Protocol tag `vibe-system-prompt/1`, declared as a constant at the emit site and as an untyped `protocol` member in the schema, the convention the tree already uses.
- Generated and git-tracked beside `SYSTEM.md`. **It is never sent to a model** and carries no user state.
- Holds: the protocol tag; the **relative** identity of the selected node; the entrypoint's relative path or `false`; the recipe version; the lane spelling (`static-md` / `static-xml` / `none`) and the `lane_form`; the `layer` role (`"project"`); an ordered `inputs[]` of the prefix's inputs, each with its role, its node-relative path, the SHA-256 of the bytes **as observed** and their length; `prefix_sha256` and `prefix_len`; a `segments[]` map of id, byte offset, length and whether the segment is a recommended cache boundary; the boot-plan identity the existing owner produces together with the SHA-256 of `INDEX.md`'s bytes; and the `continuation` plan — the ordered rows of the unconditional and gated bands, each with its node-relative path, its band, and for a gated row its `when` string verbatim.
- **Four things it must not hold**, each for a stated reason: a build time or any timestamp, and an absolute checkout/`HOME`/cache path, and the generating host's operating system — all three because the sidecar is a **pure function of its inputs**, which is what makes a second `vibe install` with nothing changed produce byte-identical files and no git diff; and **no content digest for any continuation row**, because a hash of `90-user.xml` here would make every edit of a user boot snippet dirty a committed generated file and demand a rebuild, destroying the one property dynamic linking exists for. Continuation bytes are witnessed **per request**, in `SP-FMT-007`'s response.
- **Two identities, never conflated:** `prefix_sha256` proves byte identity of what is sent; the `inputs[]` witness proves *consistency* between that text and a set of observations. Neither proves authenticity — the existing boot-graph verifier is graph verification, not body authentication (PROP-072 `#SOURCE-BOOT-CHECK-LAW`), and the existing unit fingerprint (`crates/vibe-workspace/src/boot/hybrid/fingerprint.rs:133`) hashes identity, path, version, conditions, fragments, edge modes, child fingerprints and owner-plan digests while reading **no file bytes at all**.
- **Versioned for forward compatibility:** `layer = "project"` and layer-qualified segment ids are present from version 1, although no other layer exists yet, so the later layered-prefix campaign (PROP-074 `#LAYERED-PREFIX`) composes project + user + override with **no change to this format**. An old consumer is never obliged to read the artifact.

## SP-FMT-005 — the boot transaction gains two production roles (Phase 4)

Status: **planned**.

- No registered format: the boot publication transaction's journal is internal (`.vibe-boot-*`), and the only registered boot record is `[format.boot-artifact-transaction]` (`formats/REGISTRY.toml:1202`), whose **schema may need one additive member per new role** — if it does, this entry records an epoch **1 → 1** on that record, since the members are optional and absent means byte-identical documents.
- **The role set is closed and validated today, so this is a real change to that owner, not a new filename riding along.** `crates/vibe-workspace/src/boot_artifacts/transaction/journal.rs` names exactly `INDEX.md` (`:21`), `STATIC.md` (`:22`) and `STATIC.xml` (`:23`), validates at `:62-86` that the selected/stale pair is exactly that distinct `STATIC` pair (`:75-78`), and `transaction.rs:259-282` `common_parent` requires every target to share one directory and be distinct.
- `SYSTEM.md` and `SYSTEM.meta.json` become two new `StageRole`s and two new admitted production targets, staged in `transaction/prepare.rs` and applied beside the INDEX and STATIC roll-forwards. The `common_parent` invariant holds trivially: all five targets live in the one boot directory.
- **Inside the existing commit, not beside it.** A failure must never leave a new prefix paired with a sidecar of another generation, nor damage the previous usable set. The whole output set is computed and validated **before** publication, and the relevant captured inputs are rechecked immediately before the write, as `boot_artifacts.rs:402-404` already does. There is no second journal and no second atomicity story.
- **The entrypoint witness is the prospective one of the same generation.** The same publication can rewrite the entrypoint's managed block — `write_boot_artifacts_inner` compiles first (`:379-391`), then `transaction::write_production_with_selectors` (`:405`) runs the redirect selector **after** the INDEX/STATIC commit (`transaction.rs:245`) — so witnessing the pre-write entrypoint would make a newly published prefix stale the instant it was written. The prospective projection is computed through the same redirect owner, source-before and expected-source-after are retained separately, and the entrypoint is never re-read after publication to manufacture agreeing evidence.
- **Equal bytes are not rewritten**, by the rule already in `transaction.rs:306-310` (`apply_forward` compares present+sha and returns early) and `redirect.rs:267-269`: an idempotent regeneration performs no write, moves no mtime and produces no git diff. A regeneration that *grows* the prefix is a self-inclusion bug by definition.
- **Source-member protection is unchanged and now covers the two new roles:** `crates/vibe-workspace/src/install/bootgen/publication.rs:13` `publish_node_boot` refuses to publish into a nonroot authored package member selected as a dependency by `(kind, group, name)` with version absent from the predicate (`:24-28`).
- Both node seams learn the roles: the builtin `boot_artifacts.rs:365` path and the owner-managed `boot_artifacts/native_managed/write.rs:91` path. The unit-lane seam (`boot_artifacts/publication.rs:171`) does **not** — package slots publish no prefix.

## SP-FMT-006 — `vibe prompt check`, `vibe-prompt-check/1` (Phase 5)

Status: **planned**.

- New record `[format.cli-prompt-check]`, epoch **1**, `schema = "schemas/prompt_check.jtd.json"` (new), `recoverable = true`, `foreign_parsers = "many"`, `corpus = "none"`, `sunset = "none"`. Protocol tag `vibe-prompt-check/1`.
- `vibe prompt check [--node <rel>] [--json]` compares the currently admitted inputs with the published artifacts and answers one of six verdicts, each with its reasons: `equal`, `stale`, `missing`, `conflict`, `unavailable`, `freshness_unverifiable`.
- **The two halves of the band model are observable here, which is the point.** Changing the bytes of an applicable dynamic boot file under an unchanged plan leaves the verdict `equal` — the prefix is still valid and a fresh continuation is read per request. Changing the template, the entrypoint, a static-lane input, the recipe or the `lane_form` gives `stale` naming which. Changing the **plan** — a row added, removed or reordered, a condition changed, visibility changed, a different selected node, a different package binding — invalidates the pairing: it must be recomputed under the current world, never paired blindly with an old prefix.
- `conflict` is the ownership refusal of `SP-FMT-010`. `unavailable` and `freshness_unverifiable` each name the exact `vibe prompt build` that would resolve them.
- **Read-only, and the boundary is a capability contract rather than a sandbox promise.** No product, cache, profile or config write; no network; and — the part that is easy to get wrong — **no effectful native or backend compile provider invoked to recompute freshness**. Reusing an analyse entrypoint is not proof of that: `analyze_node_lane` (`crates/vibe-workspace/src/install/bootgen/analyze.rs:80`) takes no provider and is effect-free, while `analyze_node_lane_bound_native_using` (`:270`), `analyze_effective_bound_native_with_sources` (`:554`) and `compile_node_backend_using` (`:415`) each accept an `OwnerNativeCompileProvider` — the last mandatorily — and hand control to a caller-supplied trait that may spawn a process. What `check` may do is read retained inputs, compare witnesses and run explicitly effect-free builtin preparation; when the proof needs an effectful provider it returns `freshness_unverifiable` instead. It never falls back to an empty transform plan and never quietly repairs while promising no writes.
- One new `vibe check` check id reports a stale or conflicting artifact in the ordinary check report (`[format.cli-check-report]`, epoch **1 → 1**) — see `SP-FMT-008`.

## SP-FMT-007 — `vibe prompt prepare`, `vibe-prompt-prepare/1` (Phase 5)

Status: **planned**.

- New record `[format.cli-prompt-prepare]`, epoch **1**, `schema = "schemas/prompt_prepare.jtd.json"` (new), `recoverable = true`, `foreign_parsers = "many"`, `corpus = "none"`, `sunset = "none"`. Protocol tag `vibe-prompt-prepare/1`.
- `vibe prompt prepare --json [--node <rel>] [--session-target os=<name>]` returns the materials of one request: the **prefix band**, the **unconditional continuation band**, the **gated continuation band** and the unresolved remainder — **separately and ordered, never concatenated** — each band's rows carrying their node-relative path, their observed bytes' SHA-256 and their length, plus the recommended cache-boundary offsets taken from the sidecar's segment map.
- **Why separate bands are the whole value.** The continuation's bytes are byte-stable too — they change only when those files change — so a provider that supports several cache breakpoints caches the prefix *and* the unconditional band, and a task change invalidates neither. Keeping INDEX late-bound therefore costs nothing in cache terms while preserving the runtime meaning of a dynamic entry. The only residual cost is that a runner reads those files per request: 57,894 bytes across eight files on this repository.
- **The continuation's digests live here, in the response, and nowhere else** — they are request-local observations, which is exactly why `SP-FMT-004` holds none.
- **An `os:` gate is evaluated against an explicitly supplied session target, never the generator's host.** The condition grammar is closed (`crates/vibe-core/src/manifest/package/when.rs:71-112`: exactly `os:windows|macos|linux` and `installed:<group>/<name>`, every other prefix a named error), and `installed:` is already resolved at generation time by `crates/vibe-workspace/src/install/bootgen/conditions.rs:86-96`, so only an `os:` gate survives into the gated band. With a non-empty gated band and no `--session-target`, `prepare` reports **unresolved input** and refuses to guess; an unknown selector never becomes `true`.
- **It returns materials and observations, never a ready-to-send request.** It assembles no credentials, chooses no model and constructs no provider envelope. It is the *calling program's* preflight, run outside the model's turn: PROP-009 `#PURE-FILE-READING` and `#REJ-RUN-VIBE` forbid turning boot into a command, and the transport contract never asks an agent to run it.
- Same read-only capability contract as `SP-FMT-006`, proved by filesystem, network and provider-call sentinels.

## SP-FMT-008 — `vibe check` reports a stale or conflicting prefix (Phase 5)

Status: **planned**.

- `[format.cli-check-report]`, epoch **1 → 1**: one new `CheckId` with its finding rows; existing members unchanged.
- A project that has opted in and whose published prefix is stale, missing its sidecar, or in ownership conflict is reported by the ordinary `vibe check`, at the severity the check inventory assigns, with the exact `vibe prompt build` that would resolve it. A project that has not opted in is not reported at all.

## SP-FMT-009 — the transport-contract recipe (Phase 3)

Status: **planned**.

- No separate registry record: the recipe is a versioned surface **inside** `SP-FMT-003`'s bytes and `SP-FMT-004`'s sidecar, pinned by `[system_prompt] recipe` (`SP-FMT-002`). Its number is recorded here because a change to the text changes every prefix digest in the world, and that must be a deliberate, visible act rather than a prose edit.
- The contract is the one piece of generated prose in the prefix, placed at the entrypoint's managed-block byte range. It states, as facts about the request: which sources have been supplied, each by role and node-relative path; that their content is already present and need not be read again **to discharge those same boot obligations**; that the continuation entries actually supplied are named where they appear; and that any entry not named has **not** been supplied and must not be treated as read.
- **Four things it does not do**, each a deliberate limit: it does not forbid tool calls in general — a later instruction to check a file's current state on disk remains valid, and no text can guarantee an agent makes no tool call, which is a property of the adapter proved by `SP-FMT-011`'s tests rather than asserted by prose; it does not instruct the agent to run `vibe` or anything else; it carries no digest, build time, path or counter, so it can never be the thing that makes two otherwise equal prefixes differ; and it speaks **only for its own layer**, which is what lets the later layered-prefix campaign append each layer's contract instead of regenerating one global one.
- Recipe **1** is the initial text. A wording change is a new recipe number, a new `prefix_digest` everywhere, and a new entry amending this one.

## SP-FMT-010 — opting out, and the file that is not ours (Phase 4)

Status: **planned**.

- No format record; behaviour, recorded because it is user-visible and destructive if done wrong.
- **Opting out** is removing `SYSTEM-TEMPLATE.md`. The next install removes exactly the two outputs it can **prove** it owns — proof being the sidecar's own witness of the pair — by the same reasoning publication already uses to delete the *stale* `STATIC` spelling while never touching the selected one (`boot_artifacts.rs:401`, `transaction/prepare.rs:90`).
- **Ownership conflict**, a named refusal that writes nothing and deletes nothing: a `SYSTEM.md` present with no sidecar, with a sidecar that does not describe it, or whose bytes do not match the sidecar's `prefix_sha256`. A file by that name may be a user's own work, so a hand-edited output is never silently blessed as current and never silently overwritten. The message names the file, the mismatch, and the exact command that would regenerate it deliberately.
- Switching the lane spelling, changing the entrypoint or changing the recipe is an ordinary regeneration of a coherent set, not a removal.
- Both `STATIC` spellings present remains `resolve_static_path`'s refusal (`boot_artifacts/format.rs:50-55`), propagated rather than resolved by picking a side; a node with **no** static contributions builds a valid prefix with no lane segment, which is a normal case and not an error.

## SP-FMT-011 — the adapter request capture and its cache diagnostics (Phase 6)

Status: **planned**.

- New record `[format.cli-prompt-capture]`, epoch **1**, `schema = "schemas/prompt_request_capture.jtd.json"` (new), `recoverable = true`, `foreign_parsers = "ours"`, `corpus = "none"`, `sunset = "none"`.
- The envelope a supported adapter builds from `SP-FMT-007`'s materials: the instruction blocks in order, the tool block's position, the message bands, and the declared cache-boundary offsets. It is what the qualification scenarios assert against a **local fake provider**, offline.
- **A filename chooses no API role.** The adapter places the project's trusted instructions explicitly in a supported instruction role (`system`, `developer`, or the equivalent provider field), preserving mandatory external instructions and the user-set boundaries that already apply. The elevation is acknowledged, not assumed away: project instructions, package boot text, examples and operational grants do not acquire provider-level authority by sitting on disk or by being in a file called `SYSTEM.md`, and a text separator inside one message creates no real role boundary.
- **No double injection.** A supported adapter never injects the prefix and then auto-loads the same entrypoint or lane again; supplied sources are accounted for explicitly, which is the only reason `SP-FMT-009`'s contract can say what it says. The test is that the entrypoint's text appears **exactly once** in the captured request. An agent that does not let its caller control its own prefix or auto-loading is simply not part of the guaranteed integration.
- **A quiet worker receives no central prefix at all, not even briefly.** The profile and the packet are selected *before* the request is constructed; there is no "ignore the parts that do not apply to you" clause in the prefix and deliberately no attempt to write one, because a later message cannot return spent context or restore a crossed delegation boundary. A central session gets its own selected node's profile, and a root's legitimate aggregation of its own subtree stays legitimate (PROP-009 `#MATRYOSHKA-SCOPES`).
- **Nothing user-local is pulled in by reference.** An authored instruction that *mentions* a home directory, a stewardship settings or plan file, a custody or handoff record, or a token path is an instruction to a tool-using agent, not permission to embed that file's contents; the exporter opens none of them. The proof is a sentinel test: the files exist and are shown never opened and absent from every output.
- **Cache diagnostics are read, never computed.** `write_tokens`, `read_tokens` and `uncached_tokens` come from a provider's own usage record; there is no constructor that accepts a local estimate, which is a type-level guarantee rather than a comment.
- **What this id does not claim.** A text artifact is not a portable KV cache and does not transfer between models or providers; equal `SYSTEM.md` bytes do not prove identical actual API prefixes, because provider wrapper text, role arrangement, tools and request framing may change independently; and a provider TTL expiry can require a new cache write with a completely unchanged file. The economics are parametric — for a prefix of L tokens with W writes and H reads, compare `L × (W + H) × uncached_rate` with `L × (W × write_rate + H × read_rate) + storage_cost`, then add the uncacheable requests and the unchanged cost of dynamic and output tokens — and every rate is substituted from current pricing, never from this document. **A saving is claimed only after a separate, separately authorised provider measurement**, which this campaign does not perform; the fake-provider capture proves the envelope, not a cache hit. Padding a prefix to reach a minimum cacheable length is forbidden outright.

## SP-FMT-101 — `[system_prompt] host` / `target`, and the `when = "target:<os>"` gate (Phases 1, 2, 3, 5)

Status: **the manifest keys delivered 2026-11-10** (phase P1); the gate spelling is **planned** for P2, the host baking for P3, the host-mismatch warning for P5.

Owner decision of 2026-11-10, which answers and replaces `PROP-076#SYS-OWNER-QUESTIONS` Q3. Design authority: `PROP-076#SYS-HOST-AND-TARGET`. The id comes from the `SP-FMT-101`-and-up range, because the plan did not foresee this format.

- **One axis was really two.** Q3 asked "portable prefix or target-bound prefix?" and had no answer at all for a second question hiding inside it. `[system_prompt]` therefore gains **two** optional keys:
  - `host = "portable" | "linux" | "windows" | "macos"` — **where the agent runs**. Default `"portable"`.
  - `target = ["linux", …]` — **which operating systems the product is for**. Default: every OS.
  The case that proves they cannot be one key is ordinary: a Linux workstation building Windows software.
- **`host` governs the existing `os:` gate**, which has always meant the session's own operating system — a devops, shell or package-manager rule. `"portable"` keeps the designed behaviour: an `os:` row stays in the gated continuation band and is evaluated per session against an explicitly supplied session target. A **fixed** OS resolves those rows at build time and bakes them into the prefix — matching rows included, others dropped — so a fixed-host prefix has an **empty gated band** and `vibe prompt prepare` needs no `--session-target` for it.
- **A host mismatch warns; it never refuses.** When a session's own OS differs from a fixed `host`, `vibe prompt check` and `vibe prompt prepare` say so and continue. The prefix is a deliberate project declaration, and refusing would leave a cross-platform worker unable to read its own project's instructions.
- **`target` introduces a new closed condition spelling, `when = "target:<os>"`**, for a rule about the platform the software itself addresses — a kernel interface, WinAPI, a filesystem semantic. It is a property of the project and never of a session, so it is **always** resolved at build time whatever `host` says: a row is included exactly when its OS is in `target`. It is therefore never a residual `when`, never reaches the gated band, and leaves `prepare_index_body`'s `kind` expression meaning exactly what it means today. `[format.manifest]` and the generated INDEX both move epoch **1 → 1**: the grammar grows by one accepted prefix and no existing document changes.
- **Nothing changes for a project that sets neither key**, which is the compatibility condition the owner stated. An absent `target` selects every OS, so no `target:` row is ever dropped; an absent `host` is `"portable"`, so every `os:` row behaves exactly as designed. P2 asserts this as a byte-identical `INDEX.md` for this repository.
- **A baked host OS is not volatile content.** `PROP-076#SYS-NO-VOLATILE` forbids "the result of environment detection"; nothing is detected here. The OS name is read from the node's own authored manifest, exactly like `entrypoint` or `recipe`, so the prefix stays a pure function of its declared inputs and `#SYS-DETERMINISM` holds unchanged — two checkouts of one commit still produce identical bytes on every host. Detecting the *generating machine's* OS remains forbidden.
- **As delivered in P1**, with `TargetOs` reused as the closed OS set rather than a second enum: `HostChoice::{Portable, Fixed(TargetOs)}` and `TargetSelection::{AllPlatforms, Only(Vec<TargetOs>)}`, both omitted from serialisation when at their default. Refusals, at deserialisation and each naming its field: an unknown or mis-cased OS names the field, all three legal systems **and** `portable` (which is not an OS and is the answer a reader usually wants); `target = []` refuses, because an empty selection and an absent key mean opposite things and `[]` would silently drop every `target:` row — the message says to omit the key instead; a repeated OS refuses. The author's order in `target` is preserved, so the table round-trips byte-stably.
