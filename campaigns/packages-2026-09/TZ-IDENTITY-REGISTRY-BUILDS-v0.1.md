## S1. Двухъярусный publish — обновление без org-прав

### Философия

Сегодня `vibe registry publish` всегда идёт через host-API с publish-токеном
org-уровня — то есть КАЖДАЯ публикация требует прав на организацию, хотя
подавляющее большинство публикаций — обновление уже существующего пакета.
Рулинг (PROP-002 `##TWO-TIER-PUBLISH`): **ветвиться по существованию
репозитория, а не по правам**; права проявляют себя в точке действия. Ярус 1
(обновление) — чистый git: имя репо детерминированно из идентичности,
`ls-remote` — проба существования, пуш обычными кредами (SSH достаточно).
Ярус 2 (создание) — сегодняшний адаптерный путь за явным подтверждением.
Следствия: наименьшие привилегии становятся нормой (автор — коллаборатор
своего репо, org-токен — у модераторов; это механизм поручительства
PROP-008 §2.10), и обновления начинают работать на GitVerse, чей API создавать
репо не умеет (их стаб перестаёт блокировать ярус 1).

### База (проверено 2026-08-13)

| факт | где |
|---|---|
| Оркестратор publish | `crates/vibe-publish/src/orchestrator.rs`; CLI-вход `crates/vibe-cli/src/commands/registry/publish.rs` |
| Выбор адаптера по хосту URL; GitVerse — осознанный стаб с машинным конвертом | `publish.rs:121-141` (`extract_host_segment`, `creator_for_url`; `host_lower == "gitverse.ru"` → stub envelope) |
| Прямой git-путь уже существует | `crates/vibe-publish/src/direct_git.rs` — движок `--repo-url` (`publish.rs:83`: «bypass registries, host adapters, tokens») |
| Композиция имени репо | `NamingConvention::repo_name` — `crates/vibe-core/src/manifest/project.rs:313`, Fqdn → `{group}.{name}` |
| Трейт хоста | `creator.rs`: `host_name`, `repo_exists(org,name)`, `create_repo`, `push_url` |
| Токен-лоадер (4 источника) | `crates/vibe-publish/src/token.rs` |
| Индекс-хук после publish | `crates/vibe-publish/src/post_hook.rs` — не трогать, он яруса не знает |

*База пересверена замером [`harvest/s1-publish-tiers.md`](harvest/s1-publish-tiers.md)

### РЕШЕНО 2026-08-14 — «не найден» переименовывается в «не виден»

Замер нашёл свойство хоста, которое кодом не снимается: GitHub отвечает
`Repository not found` и на приватный репозиторий, невидимый кредам, — тем же
ответом, что и на несуществующий. Значит текст вопроса яруса 2 из S1.3
(«does not exist — create it?») в этом случае ЛЖЁТ, а закон 1 PROP-044
([`##LAW-NO-LYING`](../../spec/common/PROP-044-change-native-formats.xml#laws))
запрещает ровно ту форму отказа, где неверный ответ выглядит верным. Четыре
следствия; исполнитель их НЕ переоткрывает.

1. **Носитель называется по тому, что известно.** Новый вариант на
   publish-стороне — `PublishError::RepoNotVisible { url }`, НЕ `RepoNotFound`:
   зонд яруса 1 устанавливает невидимость, а не отсутствие. Док-комментарий
   варианта перечисляет трихотомию дословно (репозитория нет · репозиторий есть
   и приватен для этих кредов · хост отвечает неразличимо). *Отвергнуто:* имя
   `RepoNotFound` — оно вернуло бы ту же ложь в каждого будущего читателя,
   которому «not found» прочтётся как «нет».
2. **Вопрос яруса 2 не утверждает несуществования.** Форма: «`<group>.<name>`
   не виден в `<org>` — его либо нет, либо твои креды его не видят. создать?
   [y/N]». Рецепт отказа называет ТРИ выхода: `--create`, «попроси модератора»,
   «проверь свой доступ». *Отвергнуто:* сегодняшний текст «does not exist»
   (лжёт на приватном репо); выбор яруса догадкой (закон шага S1.1: при
   неразличимости — остановка, а не угадывание).
3. **«Уже существует» — не ошибка, а позднее свидетельство существования.**
   Отказ создания с «already exists» (GitHub 422 и родня) доказывает то, чего
   зонд увидеть не смог: репозиторий ЕСТЬ. Диспетчер тогда **переезжает на ярус
   1** (Update) и даёт говорить пушу — это и есть
   [`##RIGHTS-CHECKED-AT-THE-ACTION`](../../spec/modules/vibe-registry/PROP-002-decentralized-registry.xml#publish):
   права проявляются в точке действия, а не в предварительном вопросе. Вывод
   честно называет случившееся («репозиторий существовал, но зонду не был
   виден; публикую как обновление»). *Отвергнуто:* печатать сырой ответ хоста
   (оператор остаётся с загадкой); считать «already exists» фатальным (мы
   только что установили, что ярус был выбран неверно, и знаем верный).
4. **Ярус 1 обновляет через fast-forward, а не переписывает ветку.** Замер §5:
   сегодняшний `push_release` ВСЕГДА строит свежую single-commit историю и
   пушит `main` без `--force`, поэтому на непустом remote он отвергается как
   non-fast-forward — то есть посылка шага S1.2 («сегодняшний `--repo-url`-движок,
   URL больше не ручной») неверна: движок умеет первую публикацию в пустой репо
   и НЕ умеет обновление. Ярус 1 обновления: клонировать remote, положить
   содержимое версии поверх, закоммитить, запушить fast-forward, затем запушить
   новый тег. `--force` не появляется нигде. *Отвергнуто:*
   `--force-with-lease` на ветке (перепись опубликованной истории ради нашего
   удобства — красная линия Rule 4 и закон fast-forward-only PROP-016); пушить
   ТОЛЬКО тег поверх существующего `main` (тег указывал бы на коммит, до
   которого из ветки не дойти, — репозиторий перестаёт читаться как история
   пакета).

Что замер снял с цены слайса: трёхсторонний дискриминатор уже построен и
оттестирован — `GitError::{RepoNotFound, AuthFailed, NetworkUnreachable}` плюс
чистая `classify_stderr_message` (`crates/vibe-registry/src/git_backend/shell.rs:492`),
уже работающая на том же примитиве `ls-remote --tags` (`shell.rs:212`).
Недостаёт ровно того, что publish-сторона плющит всё в
`PublishError::Git(String)` (`crates/vibe-publish/src/lib.rs:187`).

### Шаги

**S1.1 — Диспетчер ярусов.** В `vibe-publish` новый модуль `tiers.rs`
(маленький файл): `pub enum PublishTier { Update { repo_url: String }, Create }`
и `pub fn dispatch(...) -> Result<PublishTier>`: составить имя репо
`registry.naming.repo_name(kind, group, name)?`, собрать кандидатные URL
(SSH-форма `git@<host>:<org>/<repo>.git` и HTTPS `<org-url>/<repo>.git`),
пробовать существование `git ls-remote <url>` (через тот же shell-git слой,
что у резолвера; выход 0 = существует). Существует → `Update`; **не виден** →
`Create`. Ошибка сети ≠ «репо не виден»: классификацию НЕ писать заново —
переиспользовать `classify_stderr_message`
(`crates/vibe-registry/src/git_backend/shell.rs:492`), уже разводящую
`RepoNotFound`/`AuthFailed`/`NetworkUnreachable` на этом же примитиве; при
неразличимости СТОП с внятным текстом, не угадывать. Вердикт «не найден»
переводится на publish-сторону как `RepoNotVisible` — см. пункт 1 решения выше.

**S1.2 — Ярус Update.** В CLI-входе: `PublishTier::Update` → путь
`direct_git` с выведенным URL. Кред-порядок яруса 1: если publish-токен
ДОСТУПЕН — HTTPS+токен как сегодня; иначе SSH-URL без токена вовсе (это и есть
«SSH достаточно»). `--repo-url` остаётся как явный override поверх диспетчера.
**Поправка по замеру:** скобка «сегодняшний `--repo-url`-движок» неверна —
`push_release` умеет только первую публикацию в ПУСТОЙ репозиторий; обновление
непустого он отвергает как non-fast-forward. Форму обновления задаёт пункт 4
решения выше (клон → наложение → коммит → fast-forward-пуш → тег), и она —
часть работы этого шага, а не готовый движок.

**S1.3 — Ярус Create.** `PublishTier::Create` → если TTY: вопрос
`package <group>.<name> is not visible in <org> — it may not exist, or your
credentials may not see it. create it? [y/N]`; `--create` — да без вопроса;
`--no-create` ИЛИ не-TTY без `--create` — отказ с рецептом, называющим ТРИ
выхода (флаг `--create`, «попроси модератора», «проверь свой доступ»). Отказ
создания с «already exists» — не ошибка: диспетчер переезжает на ярус 1 и
говорит об этом вслух (пункт 3 решения выше). В остальном — сегодняшний
адаптерный поток без изменений.

**S1.4 — Диагностика прав (не ветвление!).** При 403 на создании — прежде
чем печатать generic-текст, ОДИН запрос `GET /user` + `GET
/orgs/{org}/memberships/{login}`: member/absent → в текст ошибки («ты не
член org / член без права создания — обнови пакет, если он существует, или
попроси модератора»). Fine-grained токены членства не видят — потому это
только диагностика (`##RIGHTS-CHECKED-AT-THE-ACTION`). GitVerse: ярус 2
остаётся стабом; текст стаба дополнить «обновление существующего пакета
работает (ярус 1)».

**S1.5 — Тесты (герметичные).** (а) update-против-локального-bare: seed
bare `<группа>.<имя>.git` в tempdir-org (образец `cli_registry_mgmt.rs`),
publish новой версии БЕЗ токен-файла и БЕЗ env-токена → успех, тег
появился; (б) create-refused-non-tty: нет репо, нет `--create` → exit ≠ 0,
текст содержит `--create`; (в) create с `--create` против file://-org (или
мок-Creator): репо создан, потом контент; (г) `--repo-url` по-прежнему
обходит диспетчер; (д) ярус 1 не читает токен: тест с
`VIBEVM_PUBLISH_TOKEN=битый` — update всё равно успешен по SSH/file-URL.

**S1.6 — Спека и суд.** PROP-002 `##TWO-TIER-PUBLISH`,`##TIER-UPDATE`,
`##TIER-CREATE`,`##RIGHTS-CHECKED-AT-THE-ACTION`,`##LEAST-PRIVILEGE-IS-THE-NORM`
переводятся `spec/plan → impl/done` (правка статуса = правка факта → суд
`--force` с evidence file:line на построенное). Панель; коммиты: диспетчер+
update / create+вопрос / диагностика / спека — по смыслу, не по файлам.

## S2. Переименование живых `_`-репозиториев — СТОП-ВЛАДЕЛЕЦ

### Философия

Композиция стала точечной (`org.vibevm.world.wal`), а в `vibespecs` на
GitHub лежат репо `_`-эры. Пока публика не пришла (D13), переименование
бесплатно: GitHub редиректит старые имена для git-операций, локфайлы хранят
`source_url` и переживут, свежие резолвы уже составляют точечные имена — то
есть КАЖДЫЙ день без переименования это день, когда свежий резолв из
реестра бьёт мимо.

### Шаги (исполняются владельцем или при нём — нужны org-права)

1. `gh repo list vibespecs --limit 200 --json name` → выписать все имена с
   `_`-джойном (`<группа>_<имя>`; НЕ трогать архивные `flow-*` kind-name
   эры — они read-only легаси).
2. По каждому: `gh repo rename <группа>.<имя> -R vibespecs/<группа>_<имя> --yes`.
3. Проверка: `git ls-remote https://github.com/vibespecs/<новое>.git` — ok;
   старое имя тоже ok (redirect).
4. GitVerse-зеркала пакетов (если появились) — переименовать в веб-UI.
5. В хост-репо: `cargo run -q -p vibe-cli --bin vibe -- install` (свежий
   резолв цел), панель, отметить исполнение в этом файле.

**Приёмка:** `vibe install` чистого клона хоста проходит; `gh repo list
vibespecs` не содержит `_`-джойна вне архивных. **Запреты:** ничего не
удалять; не трогать `flow-*`-архив; не делать это агентом без владельца.

## S4. Каналы — авторские указатели версий [ЗАПЕРТО: PROP-044 + Ф1–Ф3]

### Философия

Контракт целиком — PROP-005 §2.18; прочитать его ПЕРВЫМ, он писался как ТЗ.
Суть: канал — плоский авторский указатель `(group,name,канал)→версия`
(npm dist-tags / Docker tags); авторитет — журнал; каталог только проецирует;
манифест декларирует членство КАК ФАКТ ПУБЛИКАЦИИ (`channels = [...]`) — и
потому публикация сама двигает указатели, а ретаргет замороженного — только
журнальный акт; LATEST/STABLE — встроенные каналы с вычисляемым фолбэком;
порядок — semver + natural-sort тай-брейк по `+…`; умолчание резолвера —
STABLE, иначе LATEST, замороженность на выбор не влияет. Почему заперто:
указателям нужен журнал (Ф3 change-native ТЗ) и слоты полей записи (Ф1.4).

### База (проверено 2026-08-13)

| факт | где |
|---|---|
| Схема журнала и события уже со слотами `channel_set`/`channel_unset`/`force_replaced` | `TZ-CHANGE-NATIVE-FORMATS-v0.1.md` Приложение А.2 (строится Ф3.1) |
| `latest_stable` уже фильтрует prerelease — половина фолбэка STABLE | `crates/vibe-index/src/types/entry/aggregate.rs` |
| Кандидаты по имени, куда ляжет мапа каналов | `NameEntry` в `crates/vibe-index/src/types/entry/`; файл `by-name/<name>.json` (PROP-008 §2.8) |
| pkgref-грамматика (позиция версии) | `crates/vibe-core/src/package_ref.rs` (`parse_bare_semver_is_caret_per_cargo` и соседние тесты — образец расширения) |
| Табличная форма зависимости уже есть | корневой `vibe.toml`: `{ version = "...", link = "..." }` — парсинг в `vibe-core/src/manifest` (requires) |
| Локфайл v5, per-package поля | `crates/vibe-core/src/manifest/lockfile.rs` |
| Свежий порядок версий для spec://-слотов | `version_order::newest` в `crates/vibe-spec/src/resolver.rs` окрестность — НЕ переиспользовать напрямую: каноничный порядок каналов живёт в `vibe-core` (см. S4.2) |

### Шаги (суб-фазы; каждая — панель + коммит)

**S4.1 — Манифест.** `PackageMeta` (`vibe-core/src/manifest/package.rs`):
поле `channels: Vec<String>` (default пусто, `skip_serializing_if` пуст).
Валидация имени канала при парсе: `[a-z][a-z0-9-]*` (`##CHANNEL-NAME-GRAMMAR`);
`channel = "…"` (единственное число) — отказ с did-you-mean «channels =
[…]» (образец рефузала: `Materialization` deserialize там же — рецептом, не
alias). Round-trip тест + отказные тесты.

**S4.2 — Порядок версий.** Новый маленький модуль `vibe-core`
(`src/version_rank.rs`): `pub fn rank_cmp(a: &semver::Version, b) -> Ordering`
— semver precedence; при равенстве: без метаданных < с метаданными; между
метаданными — natural sort (прогоны цифр числом, текст лексикографически;
больший = свежее). Юнит-тесты из `##VERSION-ORDERING-WITH-BUILD-TIEBREAK`:
`1.0.0 < 1.0.0+a < 1.0.0+b < 1.0.0+b.2 < 1.0.0+b.10`, таймстемпы. Затем
`aggregate.rs` и все выборы «новейшей» в резолве переводятся на `rank_cmp`
(grep по сравнению версий в `vibe-index`/`vibe-registry`; перечислить в
коммите заменённые точки).

**S4.3 — Журнал и проектор (после Ф3).** Проектор применяет
`Published{entry}` → для каждого `entry.channels` двигает указатель;
`ChannelSet/Unset` — ретаргет/снятие; состояние `authored` хранится в
проекции пер-канально (`##LATEST-AND-STABLE-ARE-BUILT-IN`: authored с
первого акта, до того — вычисляется `rank_cmp`-ом; новая публикация БЕЗ
декларации authored-указатель не двигает). `NameEntry` получает
`channels: BTreeMap<String, ChannelState>` где `ChannelState {version,
authored: bool}` — wire-вид согласовать со схемой Ф4 (если Ф4 уже сел —
через схему и генератор, НЕ рукописный serde: закон 5 PROP-044).

**S4.4 — Резолвер.** По `##RESOLVER-DEFAULT-IS-STABLE-THEN-LATEST`: голый
запрос без req/канала → STABLE если есть, иначе LATEST; явный канал: в
pkgref `@beta` (расширить разбор позиции версии: не начинается с цифры и не
оператор реqа → имя канала) и в манифесте `{ channel = "beta" }`
(взаимоисключимо с `version` — отказ при обоих). Мёртвый авторский
указатель → отказ с рецептом (`##DEAD-POINTER-IS-LOUD`), тексты — из
данных, не литералами по месту. Замороженность НЕ фильтрует выбор.

**S4.5 — Локфайл и update.** Пер-пакетно опциональные `channel`,
`resolved_version` уже есть как `version`; добавить `channel: Option<String>`
(+ то, чего требует `##CHANNEL-RESOLUTION-PINS`). `vibe update` при
запиненном канале перечитывает указатель; `--locked` — громкий дрейф.
Схема локфайла: добавление опционального поля НЕ бамп (v5 читает старые
локи); тест обратного чтения.

**S4.6 — Поверхности.** Обязательство показа (симметрия D14): `vibe
list/show/tree/search/outdated`, machine-JSON, MCP-инструменты показывают
каналы версии там, где показывают версию. Machine-виды — по схеме; человечьи
— рендер всегда.

**S4.7 — Деградация.** По `##CHANNELS-DEGRADED-RESOLUTION`: (1) лок без
каталога — уже так, тест-охрана; (2) кэш каталога — пометка «по снимку от
<даты>»; (3) перечисление провайдера: ls-remote --tags → манифесты на тегах
→ реконструкция каналов из publish-time деклараций, вывод помечен; (4)
отказ с рецептом. e2e на герметичном file://-org.

**Приёмка S4 (сводно):** тесты S4.1–S4.7; `vibe install pkg` в фикстуре с
`stable`-указателем берёт его; с одними prerelease — LATEST; `@beta` и
`{ channel }` работают; дрейф под `--locked` красный; панель зелёная; спека
§2.18 переведена в impl/done фактам, суд тем же заходом.

**Запреты S4:** не заводить рукописный serde на wire-типах каналов после
Ф4; не давать публикации двигать authored-указатели; не делать промоушен
(`beta→stable`) операцией реестра; слово `snapshot` в коде каналов не
употреблять (см. терминологию PROP-044 §2b).

## S5. Жизненный цикл: согласие и объявленная замена [ЗАПЕРТО: Ф1+Ф3]

### Философия

Контракт — PROP-002 §2.13. Имя после удаления свободно, но перерегистрация
ВИДИМА (цепочка `Removed→Published`); каждый громкий отказ идентичности несёт
рецепт из одной команды; согласие пер-пакетное (`--accept-new`, новый пин =
запись согласия); `--force-replace --reason` — объявленная замена: журнал
append-only, история не переписывается, меняются байты по адресу — громко и
с причиной.

### Шаги

**S5.1** (после Ф1.4+Ф3) — `Removed`+tombstone в проекторе; ответ по имени с
надгробием (закон «не молчать»). **S5.2** — маркер разрыва линии в NameEntry
(проектор видит `Removed→Published`); резолвер/установка при пине через
разрыв — отказ с датой и рецептом. **S5.3** — `vibe update <group>:<name>
--accept-new`: принять новую линию/байты, перепин; refuse-текст всех
identity-отказов называет ровно эту команду и пакет; бланкетного форса НЕТ.
**S5.4** — `vibe registry publish --force-replace --reason "…"`:
журнальный `ForceReplaced` + переиздание координаты; реестровая проверка
«замороженная координата с другими байтами» пропускает ТОЛЬКО этот акт;
маркер замены на поверхностях (как frozen). Тесты каждой ступени —
герметично, с фикстурным журналом.

**Приёмка:** e2e «удалили→имя отвечает надгробием→перерегистрировали→
установка с старым пином красная с датой→`--accept-new`→зелёная»; форс-
замена без `--reason` — отказ. **Запреты:** не переписывать журнал; не
делать unfreeze; не давать `--accept-new` принимать больше одного пакета за
вызов.

### РЕШЕНО 2026-08-14 — свежесть заводится сбоку, движок не трогается

Времени прогона нет НИ В ОДНОМ артефакте: SARIF намеренно «no wall-clock»
(`CONF/sarif.rs:12-13`), fact-store ключуется хэшем содержимого, а единственный
КОММИЧЕННЫЙ conform-артефакт (`conform-baseline.json`) хранит отпечатки
`rule|file|carrier` **без номеров строк**, то есть как (file,line)-ключ
непригоден вовсе. Обязательная владельцем оговорка свежести
([`##B019-V-RECOMMENDATION`](../../BACKLOG.md#b-019)) опирается на факт,
которого в данных нет. Три следствия; исполнитель их НЕ переоткрывает.

1. **Свежесть несёт наш сайдкар, а не движок.** Шаг `cargo xtask conform check`
   дописывает рядом с отчётом `target/conform/last-run.json` —
   `{at, exit_code, sarif_sha256}`. Движок дисциплины НЕ трогается (стоячий
   запрет обоих ТЗ), байт-стабильность SARIF не портится, а `sarif_sha256`
   привязывает время к ТОМУ отчёту, который оно описывает. *Отвергнуто:* класть
   время в SARIF (правка вендоренного движка плюс порча его намеренной
   байт-стабильности); довольствоваться одним mtime (файл пересоздаётся каждым
   прогоном и живёт под `target/`; mtime не отличает «прогнали» от «тронули»).
2. **Ответ трёхсоставен, и молчания среди состояний нет.** *(i)* нет ни
   сайдкара, ни SARIF → «качество: не измерено (отчёта нет; прогони
   `cargo xtask conform check`)»; *(ii)* SARIF есть, сайдкар есть и
   `sarif_sha256` сходится → «получено `<at>`»; *(iii)* SARIF есть, сайдкара
   нет или хэш не сходится → «получено не позже `<mtime SARIF>` (прогон не
   наблюдался)». Третье состояние — честная деградация: закон
   [`##FORBID-SILENCE`](../../spec/common/PROP-044-change-native-formats.xml#laws)
   запрещает уронить ответ, закон
   [`##LAW-NO-LYING`](../../spec/common/PROP-044-change-native-formats.xml#laws)
   запрещает выдать *(iii)* за *(ii)*. *Отвергнуто:* сводить *(iii)* к *(i)*
   («не измерено» при лежащем на диске отчёте — выброс данных, которые есть).
3. **Сайдкар — формат, и он входит в реестр форматов.** PROP-044 §6.5: любая
   поверхность, которую читает второй компонент, есть формат. `last-run.json`
   пишет `xtask`, читает `vibe-trace` ⇒ запись в `formats/REGISTRY.toml`:
   `recoverable = true` (перегенерируется прогоном), `foreign_parsers = "ours"`,
   `epoch = 1`. *Отвергнуто:* «это же просто файл в `target/`» — ровно та
   мысль, ради которой §6.5 написан.

### Шаги

1. ~~Замер~~ — **исполнен 2026-08-14**, находка `harvest/s6-conform-artifact.md`;
   свежесть — по решению выше, не по mtime.
2. В поисковом/`explain`-ответе (та самая А5-поверхность): при наличии
   отчёта — рядом с узлами карты по совпадению (file,line∈span) показать
   находки, каждая с «получено <когда>»; при отсутствии отчёта — строка
   «качество: не измерено (отчёта нет; прогони <команда>)».
3. Ни один движок не получает зависимости на другой (архитектурный тест:
   grep-гейт по `Cargo.toml` — `vibe-trace`/`vibe-cli` не зависят от
   conform-крейтов; шаг в self-check).
4. Спека: записать построенное — `BACKLOG.md` строка B-019(в) закрывается
   могильником ТОЛЬКО когда (а)(б) срезы 2–3 тоже закрыты, иначе строка
   живёт; факт `B019-V-RECOMMENDATION` → impl/done с evidence.

**Приёмка:** запрос по цели с известной находкой показывает её с датой;
без отчёта — «не измерено»; grep-гейт зависимостей зелёный; панель.
**Запреты:** не заводить cargo-зависимость между движками; не кэшировать
