## 1. What an obligation is {#record}

A **drift verdict** is a judgement about one anchor: this sentence is false,
here is the evidence. An **obligation** is a unit of *repair*: the set of drift
verdicts that one edit pass clears. The registry is the join between them, and
it is **derived — never hand-edited**. A row carries:

| field | what it holds |
|---|---|
| `id` | `F-NNN`, in the campaign's single finding-id space (see §3.4) |
| `type` | one of the six: `contradiction` · `duplication` · `missing-support` · `terminology` · `relocation` · `reality-mismatch` |
| `rule` | which classification rule assigned that type, by name |
| `merged_by` | which signal put these verdicts in one obligation |
| `anchors` | every `file#anchor` this obligation must clear — the §2 table of its SPEC task |
| `evidence_refs` | what falsifies them: the `to` side of the §2 table |
| `packages` / `files` | the subject surface |
| `cross_package` / `release_event` | whether closing it is a publication (§4.5) |
| `closure_route` | how it can be closed, which decides **who approves** (§1.2) |
| `installed` / `installed_differs` | whether the subject ships to a consumer through `vibedeps/` |
| `reason` | the verdict prose that opened it, verbatim |
| `status` / `wave` | `open` · `resolved` · `deferred`; the wave that touched it |

The SPEC task's §2 table is generated from the row rather than typed:

```bash
python campaigns/packages-2026-09/tasks/drift-registry.py --task F-145
```

**`from` is the package anchor that is false; `to` is what falsifies it** — the
host artefact, the code, or the sibling document the evidence names. That
direction is worth stating because it is the opposite of wave 1's usual case:
there the spec was judged against the host's own code, here a *published
package* is judged against a *consumer*.

### 1.1 The six types, split so the split is decidable {#types}

Wave 1 used three of the six. Wave 2 uses five; `terminology` has no member
yet and stays in the vocabulary rather than being dropped.

- **`reality-mismatch`** — the fact **describes** something that exists, and
  describes it wrongly: a path, a count, a roster, a version, a name, a
  behaviour, a practice the consumer keeps differently. The defect is a
  *discrepancy*.
- **`missing-support`** — the fact **depends on** an artefact, mechanism,
  checker or record that does not exist at all. The defect is an *absence*.
  A rule with no checker is this class, not the one above.
- **`contradiction`** — two written statements disagree: document against
  document, a document against itself, or a package's prose against the host's
  written contract.
- **`duplication`** — one norm authored in two or more places, each with its
  own writer and nothing forcing them to agree.
- **`relocation`** — the content is right and its **address** is not: a pointer
  that resolves inside the package and not from where the consuming session
  stands, a home the consumer does not have. *This is a judgement call and is
  recorded so it can be re-judged:* the `../flows/…` family could equally be
  read as `missing-support` (the address has no support in the consumer's
  layout). It is filed as `relocation` because the repair is an address repair
  and the content is never in question — which is exactly the machinery
  `RULE-ANCHORS-IMMUTABLE` governs.
- **`terminology`** — the same concept under two names. Empty today.

Measured, 2026-07-29:

| type | obligations | drift verdicts |
|---|---:|---:|
| `reality-mismatch` | 119 | 359 |
| `missing-support` | 57 | 142 |
| `contradiction` | 27 | 44 |
| `relocation` | 20 | 49 |
| `duplication` | 5 | 7 |
| **total** | **228** | **601** |

### 1.2 The number that sizes the phase is not the type — it is the route {#routes}

A type says what is wrong. A **closure route** says what closing it costs, and
in particular whether the boss may close it alone. The routes are ordered and
the first that applies wins:

| route | obligations | drifts | who approves |
|---|---:|---:|---|
| `release` | 17 | 59 | **owner**, before publication |
| `sync-from-code` | 52 | 176 | **owner**, on every spec diff |
| `build-or-demote` | 54 | 134 | the boss decides; the owner sees any diff that also reaches code |
| `prose-edit` | 105 | 232 | boss |
| **total** | **228** | **601** | |

**This is the phase's rate limit, and it is worth saying out loud before the
first edit:** 69 of 228 obligations cannot be closed without the owner reading
something, and 176 of the 601 drift verdicts sit behind the `sync-from-code`
gate alone. Editing is not the bottleneck; review is. §4 orders the waves
around that fact rather than around the size of the packages.

## 2. How 601 became 228 {#clustering}

### 2.1 The hypothesis that was wrong, and the measurement that killed it {#failed}

The obvious guess — Phase C workers wrote one reason and pasted it across every
anchor it falsifies, so the drifts cluster by reason text — is **false, and
measurably**: of 601 reasons, only **16 texts repeat at all**, over **54 rows**.
Clustering on text alone produced 552 groups for 601 rows, a reduction of 1.1×.
Phase C wrote a bespoke reason per anchor, which is a compliment to Phase C and
an obstacle here.

### 2.2 What does group them {#signals}

The subject does. One document's drifts of one kind close in one edit pass, so
the primary key is **`(document, type)`**. Three signals then merge *across*
documents, and each is something a script can prove rather than infer:

- **a reason shared almost verbatim** — Jaccard ≥ 0.65 over 5-gram shingles.
  One reason falsifying anchors in two packages is prose copied between
  packages, which is also the release-event signature.
- **a finding id the worker itself cited** — 18 rows carry an `F-NNN` in their
  reason, naming the family in the author's own words.
- **one anchor drifting in two or more packages** — 16 anchors, 48 rows. This
  is the parallel corpus: one fact projected per language (`MOTIVATION`,
  `COMPONENT-THE-PRODUCT-SEAM`, `OP-INIT` across rust/typescript/go) or per
  flow (`sibling-document-pointers` in eight packages,
  `full-protocol-pointer` in seven).

**The order of the two passes is the design, not an implementation detail.**
The cross-document families are formed **first**, and `(document, type)` then
groups only what no family claimed. Run the other way round, a single shared
anchor chains two entire documents of unrelated defects into one obligation
through the `(document, type)` key — it produced a 35-row monster joining the
dangling-pointer family to `COMPOSES-ATOMIC-COMMITS` before the passes were
separated.

Result: **228 obligations, 2.6 drift verdicts each**. 95 are singletons, the
largest is 14, and the distribution has no monsters.

### 2.3 What the script does not do {#limits}

It does not find semantic families beyond those three signals. Two obligations
that a reader would recognise as one problem, worded differently and on
different anchors, stay separate until a wave merges them by hand. That is
deliberate: a merge the script cannot defend is a judgement, and judgements are
recorded rather than inferred. `merged_by` on every row says which signal fired,
so an over-merge is as visible as an under-merge.

## 3. Decisions taken at the opening {#decisions}

### 3.1 A closure re-judges the anchor; the registry is derived {#closure}

**Decision.** An obligation is not closed by editing a document. It is closed by
editing the document **and re-judging every anchor in its `anchors` list**, so
the verdict cache stops saying `drift`. The registry regenerates from the cache
and shrinks by exactly that many rows.

```bash
python campaigns/packages-2026-09/tasks/merge-verdicts.py <slice.json> --force
```

```bash
cargo run -q -p vibe-cli --bin vibe -- progress seal --campaign campaigns/packages-2026-09 <paths…>
```

**Why:** convergence has to be a measurement, not a feeling. Wave 1's Phase D
moved its tree from 93.0 % confirmed at the Phase C gate to 99.8 % at the D
exit, and that arithmetic is only available if closures write verdicts.
`--force` is required by design — `merge-verdicts.py` refuses to restate a
verdict without it, and that refusal has already caught real mistakes.
**Considered and rejected:** marking obligations `resolved` in the registry and
leaving the cache alone. It makes the registry a second writer for one fact,
which is this campaign's single most-repeated finding.
**Revisit when:** a closure changes a document's anchor set — then
`vibe progress mirror` must run before `merge-verdicts.py`, because its
`addressable()` reads `run/mirror/` and will refuse anchors the mirror has not
seen.

### 3.2 `reality-mismatch` is the residue, and the report says so {#residue}

**Decision.** The classification rules must *positively match* for the four
cheap types. A row that matches none is `reality-mismatch`, under the rule name
`r-default-described-wrongly` — 119 obligations, 359 drifts, and the report
prints that name so the default is never mistaken for a match.

**Why:** `reality-mismatch` is the expensive class — it closes through
sync-from-code with owner approval on every spec diff — so putting it first
would inflate the owner's queue with rows that are really absences or
contradictions. Making it the residue biases the error the safe way: a
misclassified row costs one extra owner read, not a silent unreviewed edit.
**Considered and rejected:** hand-typing all 601. The campaign's own rule is
that a count done by hand is a count that lands wrong, and it has landed wrong
twice already. **Revisit when:** a wave finds the residue mostly re-typable —
then the rules that would have caught it are known and can be written.

### 3.3 A `missing-support` closes by demotion here; the build is Phase E's {#demote}

**Decision.** Where the fact promises a mechanism nothing implements, Phase D's
closure is to make the document **stop claiming it**: the prose says what is
true, the `<status>` marker drops from `@impl/done` to the honest state, and a
DRIFT task is recorded for Phase E if the mechanism should exist. Phase D does
not write the mechanism.

**Why:** the plan splits stitching from coding on purpose, and the entry
condition of Phase E is *unit stability* — «Opus never codes against a moving
spec». A document that claims a built thing while the thing is unbuilt is
exactly what makes the spec unstable. **Considered and rejected:** leaving
`@impl/done` in place and letting Phase E close both at once. That leaves 54
obligations open across the D exit gate and makes E's entry condition
unsatisfiable. **Revisit when:** an obligation's mechanism is a two-line fix —
then building it is cheaper than the round trip, and the decision is recorded
per item rather than by amending this rule.

### 3.4 Ids continue the campaign's one finding space {#ids}

**Decision.** Obligations take `F-NNN` ids continuing the space wave 1 opened
and wave 2 has been minting into: **F-131 … F-350**, with **8 ids adopted**
rather than minted because a Phase C verdict already named that family, and 220
new. The next free id is recorded by the generator, not by a human.

**Ids were unstable for exactly one generation, and the two that moved are
named here rather than quietly repaired.** The first registry assigned ids
positionally, by descending cluster size; carrying them across regenerations
landed one commit later. In that window the two `../flows/…` families moved —
**F-134 → F-136** (11 verdicts, 7 packages) and **F-142 → F-145** (8 verdicts,
8 packages) — and the old numbers had already been written into this plan and
into the campaign's §7 LOG, where they named nothing. Both citations were
re-pointed on 2026-07-29. Since `carry_ids` landed, every regeneration reports
`N carried, 0 newly assigned`, which is the check that this cannot recur
silently.

**Why:** the space is already shared — `run/state/findings.json` carries
F-068…F-077 and the plan's §7 LOG mints F-078…F-129 in prose. A second id
scheme would need a mapping, and the mapping would be the third writer for the
same fact. **Considered and rejected:** a fresh `O-NNN` space for obligations.
It reads cleaner and it breaks every `F-NNN` citation already written into 18
verdict reasons. **Revisit when:** the ledger is consolidated into one file and
the LOG stops minting ids in prose — a Phase F or close-out job.

### 3.6 A package does not yield to a consumer that simply does not comply {#which-side}

**The question this answers, and it governs 191 of the 228 obligations.** When a
shipped package says one thing and the host does another, *which side changes?*
Get it wrong in the easy direction and Phase D quietly rewrites the discipline to
describe a lax consumer — which is, in the owner's own word, the *профанация*
[§0](../../spec/terraforms/PACKAGES-ACTUALIZATION-CAMPAIGN-v0.1.md#mandate)
exists to prevent. The mandate's acceptance criterion is that «the discipline can
be shown to hold itself to its own rule», so the default runs the other way.

**Decision.** Before any edit, the obligation is routed by *which side is wrong*,
and the routes are these three — never a fourth:

- **(a) the package's statement is wrong** — a roster, a path, an internal
  count, a described practice stated as fact, its own example breaking its own
  rule. The package yields: prose edit, re-judge, done. **This is the only route
  that edits a package because of a disagreement with the host.**
- **(b) the rule is sound and the host should keep it** — the package does not
  move. A host obligation is recorded, the registry row goes
  `status: deferred` naming it, and the compliance work belongs to Phase E or a
  host task. Sprawl of work is forbidden; sprawl of records is mandatory.
- **(c) the rule is sound and the host deliberately does otherwise** — the
  exception is **written down on the host side**, as a decision record or a
  marked exception, and the fact is then re-judged confirmed with the exception
  named. This is not a loophole: it is Phase C's own ruling, that **a marked
  exception is not drift** while an unmarked one is, and it converts a silent
  gap into a recorded choice. The owner rules on (c) wherever the exception is a
  policy choice rather than a note.

**What the script settles and what it does not.** `falsifier` is mechanical and
reliable: **37 obligations over 81 drifts are `self`** — every falsifying ref
sits inside the subject package or its own install slot, so the package is wrong
about *itself* and route (a) is unambiguous. The other **191 (`host` 72,
`mixed` 119)** carry the judgement, made per obligation at closure and recorded
in the row. **Considered and rejected:** deciding it with a regex over normative
language (`never` / `every` / `must`). It was written, measured, and thrown away
— it typed `EACH-SEMANTIC-CHANGE-APPENDS-A-DATED-LINE` as descriptive, and a
number that wrong is worse than no number. **Revisit when:** a wave's routing
record shows one of the three dominating, which would be worth knowing before
wave 2 plans its own cut.

### 3.7 A package-scoped search reads every successful adoption as an absence {#compliance-blindness}

**The most expensive thing this phase learned, and it invalidates a class of
Phase C verdict rather than a handful.** Measured on 2026-07-29 over 76
`build-or-demote` verdicts: **eighteen claimed absences were false**, and
**seventeen of those were falsified by HOST artefacts** — nine of them in
`discipline/` or `terraform/`.

That is not a run of bad luck. It is structural:

> **These packages SPECIFY a discipline. The host is the project that ADOPTED
> it. The artefacts that prove adoption — `discipline/registry/`,
> `discipline/golden/`, `terraform/`, `specmap.json`, `conform.toml` — live in
> the CONSUMER, because creating them is what complying means.** A search
> confined to `packages/` therefore cannot see compliance at all, and reads
> every successful adoption back as a missing mechanism.

The stakes are not cosmetic. §3.3 closes a `missing-support` by **moving a
marker**, so each false absence would have written «specified, not built» over a
mechanism the consumer had already built — a silent lie in the shipped surface,
authored by the campaign that exists to remove them.

**The rule.** Before any demotion, the perimeter is the whole tree and it is
named in the record: `packages/**`, `vibedeps/**`, `crates/**`, `xtask/**`,
`tools/**`, `spec/**`, **`discipline/**`**, **`terraform/**`**, `research/**`,
`campaigns/**`, `legacy-spec/**`, and the repository root. Search for the
**thing**, not for the string the verdict used — a mechanism can ship under
another name, in another language, or as a shell script.

**And the four layers, restated because they are why the perimeter keeps
biting:** a mechanism's SPEC lives in `core-ai-native`, its ENGINE in that
package's library crates, its DRIVER in each language stack's CLI, and its
DEPLOYMENT in the consuming project. A fact can be true at any one of those and
invisible at the other three.

**Wave 6's extension, and it runs the opposite way from the rule above.** §3.7
was written against a search confined to `packages/` that could not see the
host. Wave 6 found the mirror image: **three verdicts scoped their search to the
host's `crates/`, and the adopter that falsified them lives inside
`packages/`.** `packages/org.vibevm.fractality/fractality/v0.1.0/` is not a
document collection — it is a **second complete project that adopted this
discipline**, with its own `vibe.toml`, its own `vibedeps/` carrying twenty-odd
installed flows (`flow-managed-blocks` among them), and its own Cargo workspace.
`managed-blocks`' `remove` verb — recorded at §7's Phase C close as one of the
canonical «verbs specified and never built» — is built there, wired to the CLI
at `crates/fractality-cli/src/harness.rs:350-369`, over a `strip()` whose own
doc comment says «We create, update, and remove», under a round-trip test named
`install_into_an_empty_document_then_remove_restores_empty` asserting «a clean
uninstall leaves no residue».

So the invariant is neither «search the host» nor «search the packages». It is:

> **The perimeter must contain every project that adopted the discipline,
> wherever that project sits.** This repository holds at least two — the host,
> and the `fractality` specspace inside `packages/`. A search scoped to either
> one reads the other's compliance as an absence.

That is the same structural error as §3.7 with the direction reversed, which is
the argument for stating the invariant rather than the two instances of it.

**Corollary — consistency propagates an error.** The six `BUILD-ORDER` verdicts
were *restated once to make the family agree*, and the family agreed on a false
premise: the catalog's order is `terraform/adopt-v0.3/LOG.md`'s phase headings,
six for six with pairings intact. When a verdict says it was restated for
consistency, re-verify the whole set, not the row.

### 3.5 Every judged file already differs from its installed copy {#vendored}

**Measured, not decided.** 212 of the 228 obligations touch a file that is
installed under `vibedeps/`, and **all 212 already differ from the installed
copy** — because Phase B marked up the shipped packages in place and that markup
has never been published. The difference therefore carries **no drift signal**
and is not used as one. Two consequences bind the phase: any re-vendor will
carry the markup with it, and «I fixed it in the package» is not the same
sentence as «the consumer reads the fix».

## 4. The waves {#waves}

Wave N = SPEC tasks over every document with an open incoming obligation.
Closures may open new obligations → wave N+1. Wave 1 is therefore the whole
registry; the batching below is *inside* wave 1 and is ordered by review cost,
because §1.2 measured review to be the constraint.

| batch | route | obligations | drifts | why here |
|---|---|---:|---:|---|
| **D1** | `prose-edit` | 105 | 232 | no owner in the loop — runs while the owner's queue is being read |
| **D2** | `build-or-demote` | 54 | 134 | the boss decides build-vs-demote per item; Phase E inherits the builds |
| **D3** | `sync-from-code` | 52 | 176 | a diff per obligation, prepared in advance, presented in batches, **approved one at a time** |
| **D4** | `release` | 17 | 59 | version bump + `cargo xtask sync-engines`; owner before publication |

**D3 and D4 start early and finish last.** Their diffs are *prepared* in the
first hours of the wave so the owner's queue is never empty, and D1/D2 run
against that queue rather than after it. An obligation waiting on the owner is
not a stopped phase; a phase with nothing prepared for the owner is.

### 4.5 The release-event law {#release}

**A finding that spans a package boundary is closed by a published version, not
by an edit.** Seventeen obligations are in that class, and they are not
optional to notice: the two largest are the dangling-pointer family in **eight**
and **seven** packages respectively.

The mechanics, per obligation: fix in the owning package → bump its version →
`cargo xtask sync-engines` to re-vendor into every family member → re-judge the
anchors in **all** of them. A fix landed in one consumer and not the others is
not a closure; it is a new `duplication` obligation, and the registry will mint
it on the next run.

**The open question this raises, stated rather than answered.** The
`../flows/…` family (F-136 at 11 verdicts over 7 packages, F-145 at 8 over 8)
is a compiled-lane defect: the pointer resolves inside the package and inside
the install slot, and not from `spec/boot/` where a session actually reads it.
There are two readings — repair fifteen snippets across fifteen packages, or
repair the boot compiler once so relative links are rewritten on compile. The
second is a host code change and therefore Phase E's, and it would close both
obligations at a stroke. **This goes to the owner with the release batch; the
plan does not choose.**

## 5. Escalation, and where autonomy ends {#stop}

**Escalation (from §5-D, unchanged).** A document pair whose open-obligation
count fails to fall for **two consecutive waves** is a conceptual conflict, not
an editorial one: iteration on that pair **stops**, the obligation goes to
`status: deferred`, and both readings are stated fairly for the owner. Wave 1
spent exactly two escalations over 311 drift rows and both were genuine.

**Where autonomy ends.** Named rather than guessed:

1. **`reality-mismatch` via sync-from-code** — the diff is prepared and shown;
   **the owner approves each spec diff**. 52 obligations.
2. **A release event** — version bump and re-vendor go to the owner **before
   publication**. 17 obligations.
3. **Rule 4's red lines** — history rewrites, force-push, large blobs,
   CI/signing/secrets, anything whose reversal costs work. These bind
   identically whether the boss does the work or delegates it.

Everything else — edits, scripts, `cargo`, `git commit`, push through
`cargo xtask mirror` — proceeds. **A finding is not a reason to stop:** it opens
an obligation and the wave continues.

## 6. Delegation {#delegation}

**Owner ruling, carried forward from Phase C §6 and unchanged: delegated
execution routes to the harness's built-in `opus5` subagent, not to
fractality.** A deliberate local override of the delegation-first flow's
`#route` rule for this campaign.

What is delegated and what is not:

- **The decision to close an obligation is never delegated**, and neither is the
  review of delegated output. A worker prepares an edit and gathers evidence;
  the boss reads the diff and decides.
- **Every brief cites durable files only** — `CLAUDE.md`, `spec/boot/**`,
  `spec/common/**`, `spec/modules/**`, `crates/` — and **never `CONTINUE.md` or
  `spec/WAL.md`**, which every wind-down rewrites wholesale. Phase C ran the
  controlled experiment: the one batch written before that rule carries 116 dead
  refs today; every batch written under it verifies clean.
- **Every brief names the exact output paths and says to flush one file at a
  time**, the moment that file is complete. Phase C lost a worker's whole run to
  a worker that held everything in memory.
- **A worker quiet for several times its siblings' runtime is stuck, not
  thinking.** Re-commission. A late original costs nothing.

### 6.1 Two rules bought at full price on the first wave {#delegation-lessons}

*Both were paid for on 2026-07-29, when 24 obligations were delegated onto
owner routes and had to be reverted wholesale by owner ruling.*

- ##ROUTE-BEFORE-FALSIFIER **A batch is cut by `closure_route` FIRST, and by
  `falsifier` only inside it.** The first wave was cut the other way — by
  `falsifier == "self"`, «the package is wrong about itself» — and 24 of the 28
  obligations it handed out turned out to sit on `release`, `sync-from-code` or
  `build-or-demote`, every one of which §1.2 routes through the owner. The field
  that answers «who approves this» had been written into this plan hours
  earlier and was not read when the work was handed out. Nothing was *closed*
  without approval, because no verdict moved; what landed was the right work in
  the wrong order, and it cost a full revert.
- ##NEVER-CHAIN-MERGE-AND-SEAL **Never chain `merge-verdicts.py` and
  `progress seal` in one shell command.** `merge-verdicts.py` refuses as a whole
  and writes nothing, and a `&&` chain still runs the seal — which then vouches
  the file's *old* verdicts against its *new* text, which is precisely the
  staleness `processed_hash` exists to catch. Run the merge, read its output,
  then seal. This cost nothing in the end only because the merge succeeded on
  the next attempt against unchanged text.
- ##CITED-ANCHORS-ARE-NOT-DEFINITIONS **An `##ANCHOR` inside backticks is a
  citation, not a definition.** A helper that maps changed lines to anchors by
  scanning for `##NAME` will attribute an edit to an anchor the file merely
  *quotes* — three times in one batch, twice for host anchors this package cites
  and once for its own risk id. `merge-verdicts.py` caught all three with «not an
  addressable anchor of this file», which is its third useful refusal in this
  phase.
- ##ABSENCE-NAMES-ITS-PERIMETER **A demotion whose whole basis is an absence
  must name the perimeter it searched, in the record, before the marker moves.**
  Two demotions in the first wave rested on «nothing captures a golden
  transcript», from a grep over one crate's `src/`. The transcripts exist —
  `discipline/golden/capture.sh` and two `.transcript.md` files, in the host.
  This is [§4.5 of the Phase C plan](PHASE-C-BATCH-PLAN.md#perimeter) restated
  where it keeps being needed: **a `not-found` is a fact about the search
  perimeter until the perimeter has been checked.** Phase C paid for it three
  times; Phase D's first wave paid three more — a missing linter read as a
  broken pilot, a package-rooted floor run read as a pilot's chain, and this.

## 7. Convergence and the exit gate {#gate}

**Convergence is loop-until-dry, and it is a command.** A wave ends when every
document with an open incoming obligation has been through a SPEC task. The
registry is then regenerated:

```bash
python campaigns/packages-2026-09/tasks/drift-registry.py --write
```

- **Registry empty** → converged.
- **Registry non-empty but no obligation is new** → the survivors are deferrals
  or escalations; converged with a stated remainder.
- **New obligations present** → wave N+1 over exactly those.

**The exit gate, as four checks:**

1. **Nothing is left owed to a package** — every drift verdict is either
   re-judged or recorded in [`run/state/routing.json`](run/state/routing.json)
   as routed out of the package, and every survivor carries an owner ruling.
   Measured by the generator's CONVERGENCE block, not asserted.

   **The routing record is the half the phase would not converge without, and
   it was missing until wave 2 closed.** §3.6 routes most of this corpus away
   from the package: the rule is sound and the consumer does not keep it. Such
   an anchor is not repaired and therefore never stops reading `drift` — so
   without a record of the determination the registry can never empty, the next
   wave re-derives the same answer, and the gate cannot tell «not worked» from
   «worked, and the work belongs to the host». Wave 2 examined 110 anchors and
   moved nine; the other 102 are in that file, one entry each, with the
   obligation they came from and why. **It is written by the boss at review
   time, never by a worker** — routing an anchor out of a package is the same
   class of judgement as a verdict.
2. **The `<status>` markers of every touched unit are updated in the same edit
   that touched it** (template `RULE-UPDATE-MARKERS`), and
   `vibe progress check` is green over all touched files.
3. **Every closure re-judged its anchors** — `tasks/summary.py`'s drift count
   falls by exactly the number of verdicts the wave's obligations carried, and
   the arithmetic is shown.
4. **`baseline.json` written at the phase close** (amendment A6), as Phase C
   did.

**The prediction wave 1 made, carried here to be tested rather than repeated:**
obligations per wave fall roughly geometrically; **≤3 waves**; **≤2 owner
escalations**. Wave 2 is 1.9× wave 1's drift count (601 against 311) and 4.1×
its finding count (228 against 55), so the honest expectation is that the wave
count holds and the escalation count does not. Scored at the phase close against
what the waves actually cost.
