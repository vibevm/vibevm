# WORKER-REPORT-XML-MEASURE — интеграционная поверхность XML-волны

## Решения и границы замера

Это карта текущей реализации для будущего дизайна: XML должен стать равноправным источником спецификаций, проекты должны допускать Markdown/XML mixed-source, а материализация — Markdown/XML/Mixed, включая MD→XML; в этом пакете запрещены реализация и правки иных файлов. (`PACKET-XML-MEASURE.md:14`, `PACKET-XML-MEASURE.md:17`, `PACKET-XML-MEASURE.md:60`)

Главный вывод замера: единого Markdown frontend/AST сейчас нет. Как минимум четыре независимые семьи читают разные подмножества Markdown: `progress-core`, vendored `core-ai-native-specmap`, boot/tree и точечные `vibe-check`/CLI-сканеры. Поэтому XML нельзя безопасно добавить одной проверкой расширения; нужен общий формат-независимый слой документа либо явные парные frontend'ы, сходящиеся в общий IR. (`crates/progress-core/src/parse/mod.rs:12`, `packages/org.vibevm.ai-native/rust-ai-native-lang/v1.0.0/crates/vendor/core-ai-native-specmap/src/mdspec.rs:232`, `crates/vibe-cli/src/commands/tree/build.rs:381`, `crates/vibe-check/src/lib.rs:375`)

Для трансформирующей materialization источник и производный слот должны иметь разные идентичности: locked `content_hash` продолжает удостоверять опубликованный source-tree, а производный слот требует отдельной записи `(source_hash, output_format, converter_recipe, derived_hash)`. Иначе P011V сравнивает XML/MD-дериват с хэшем исходных байтов и закономерно объявляет слот diverged. (`crates/vibe-install/src/slot_verify.rs:31`, `crates/vibe-install/src/slot_verify.rs:62`, `spec/modules/vibe-registry/PROP-010-local-package-cache.md:63`)

Настройка формата materialization является воспроизводимым свойством проекта/lock, а не UI preference. Канонический дом следует проектировать в `vibe.toml`/`Manifest` с фиксацией эффективного значения и converter recipe в lock/derived manifest; `[install]` user-config годится только как низкоприоритетный operator default. (`crates/vibe-core/src/manifest/document.rs:67`, `crates/vibe-core/src/user_config.rs:4`, `spec/modules/vibe-settings/PROP-040-settings.md:35`)

## 1. Что читает спековый Markdown

### 1.1 `progress-core`

- Оркестратор `parse_document` принимает UTF-8 текст Markdown, строит blocks, heading units, facts, bindings, markers и затем проверяет anchor laws; это не внешний CommonMark parser, а собственный последовательный scanner. (`crates/progress-core/src/parse/mod.rs:39`, `crates/progress-core/src/parse/mod.rs:46`, `crates/progress-core/src/parse/mod.rs:47`)
- Block-слой распознаёт YAML front matter в начале документа, ATX headings, thematic breaks/HTML comments и fenced code blocks. (`crates/progress-core/src/parse/blocks.rs:37`, `crates/progress-core/src/parse/blocks.rs:55`, `crates/progress-core/src/parse/blocks.rs:91`, `crates/progress-core/src/parse/blocks.rs:119`)
- Fence grammar run-matched: opener — минимум три одинаковых backtick или tilde; closer — тот же символ и длина run не меньше opener, а содержимое fence остаётся opaque для marker/anchor scan. (`crates/progress-core/src/parse/delimiters.rs:1`, `crates/progress-core/src/parse/delimiters.rs:18`, `crates/progress-core/src/parse/delimiters.rs:35`)
- Inline-code spans отдельно blank-out'ятся перед структурным scan, поэтому похожие на anchors/markers токены внутри backticks не считаются разметкой. (`crates/progress-core/src/parse/delimiters.rs:58`, `crates/progress-core/src/parse/delimiters.rs:82`)
- Heading unit начинается с ATX heading и продолжается до следующего heading того же или более высокого уровня; явный trailing `{#anchor}` извлекается отдельно. (`crates/progress-core/src/parse/units.rs:8`, `crates/progress-core/src/parse/units.rs:25`, `crates/progress-core/src/parse/units.rs:46`)
- Anchor laws требуют явные section anchors, выявляют duplicate/missing anchors и не дают scanner'у молча выбрать неоднозначный target. (`crates/progress-core/src/parse/anchors.rs:16`, `crates/progress-core/src/parse/anchors.rs:19`, `crates/progress-core/src/parse/anchors.rs:51`)
- Countable facts — paragraph, lead lines, list item и непустая body-cell таблицы; table header и delimiter row считаются структурой, а не facts. (`crates/progress-core/src/parse/facts.rs:1`, `crates/progress-core/src/parse/facts.rs:206`, `crates/progress-core/src/parse/facts.rs:268`, `crates/progress-core/src/parse/facts.rs:315`)
- List grammar поддерживает `-/*/+`, ordered `N.`/`N)` и GFM task boxes `[ ]/[x]/[X]`; box включён в opener, а не в содержимое fact. (`crates/progress-core/src/parse/facts.rs:13`, `crates/progress-core/src/parse/facts.rs:23`, `crates/progress-core/src/parse/facts.rs:41`, `crates/progress-core/src/parse/facts.rs:61`)
- Table cells режутся собственным `|`-scanner'ом; delimiter row определяется по `-`/`:` и исключается из фактов. (`crates/progress-core/src/parse/facts.rs:78`, `crates/progress-core/src/parse/facts.rs:87`, `crates/progress-core/src/parse/facts.rs:245`)
- Typed fact binding знает ровно один тип — `code`; он привязывает последний typed fact блока к следующему fenced block и ошибается на неизвестном type, не-last fact или отсутствии fence. (`crates/progress-core/src/parse/facts.rs:134`, `crates/progress-core/src/parse/facts.rs:138`, `crates/progress-core/src/parse/facts.rs:140`, `crates/progress-core/src/parse/facts.rs:156`)
- Fact identity извлекается из `@fact:<ID>`/`##<ID>`, body получает span и content hash. (`crates/progress-core/src/parse/facts.rs:356`, `crates/progress-core/src/parse/facts.rs:362`, `crates/progress-core/src/parse/facts.rs:368`)
- Marker placement различает document/section standalone marker и marker на первом/последнем token countable unit; нарушенная granularity возвращается issue, а не эвристическая привязка. (`crates/progress-core/src/parse/mod.rs:3`, `crates/progress-core/src/parse/markers.rs:13`, `crates/progress-core/src/parse/markers.rs:65`)
- Поддержаны shorthand `@status:`/`@...` и XML-shaped point marker `<status .../>`; paired `<status ...>fragment</status>` является fragment wrapper и относится к несущему fact. (`crates/progress-core/src/parse/markers.rs:100`, `crates/progress-core/src/parse/markers.rs:118`, `crates/progress-core/src/parse/markers.rs:123`, `crates/progress-core/src/parse/markers.rs:186`)
- Hash документа не byte-identical Markdown hash: перед SHA-256 canonicalizer заменяет `@fact:`→`##` и `@status:`→`@`, чтобы смена spelling не инвалидировала verdict/baseline. (`crates/progress-core/src/parse/mod.rs:58`, `crates/progress-core/src/parse/mod.rs:70`, `crates/progress-core/src/parse/mod.rs:89`)

## 3. Materialization, hashes и трансформация

### 3.1 Текущий pipeline

- `vibedeps` materialization для copy/hardlink очищает существующий slot и рекурсивно переносит source tree; in-place является отдельной стратегией. (`crates/vibe-workspace/src/vibedeps.rs:68`, `crates/vibe-workspace/src/vibedeps.rs:113`, `crates/vibe-workspace/src/vibedeps.rs:129`)
- Recursive copy фильтрует только имя `.git`; directories создаются, обычные files copy/hardlink'ятся, symlinks пропускаются. Это не Markdown-aware и сегодня сохраняет extensions/bytes обычных файлов. (`crates/vibe-workspace/src/vibedeps.rs:309`, `crates/vibe-workspace/src/vibedeps.rs:320`, `crates/vibe-workspace/src/vibedeps.rs:332`, `crates/vibe-workspace/src/vibedeps.rs:350`)
- Incremental install получает `Verified/Diverged/Unverifiable`: verified slot пропускается, diverged предупреждает и re-materialize'ится, unverifiable также re-materialize'ится. (`crates/vibe-workspace/src/install.rs:242`, `crates/vibe-workspace/src/install.rs:250`, `crates/vibe-workspace/src/install.rs:259`, `crates/vibe-workspace/src/install.rs:268`)

### 3.2 Оба `content_hash` recipe

- Recipe 0 `sha256:` — frozen legacy; recipe 1 `sha256-tree/1:` — data-driven live recipe. `vibe-index` default — recipe 1, `vibe-registry` default — recipe 0, но обе реализации поддерживают оба recipe и parity test должен держать их byte-identical для одинакового recipe. (`crates/vibe-index/src/content_hash.rs:3`, `crates/vibe-index/src/content_hash.rs:6`, `crates/vibe-index/src/content_hash.rs:7`, `crates/vibe-registry/src/shippable.rs:63`)
- Оба обходят shippable tree, исключая `.git`, `.vibe`, `target`, `node_modules`, `.vibeignore`, и хэшируют для каждого file `normalized_path || NUL || file_bytes || NUL`. (`crates/vibe-index/src/hash_recipe.rs:48`, `crates/vibe-index/src/content_hash.rs:42`, `crates/vibe-index/src/content_hash.rs:89`, `formats/hash_recipes/1.toml:14`)
- Разница recipe: legacy допускает lossy non-UTF-8 path, сортирует platform path до separator normalization; tree/1 требует UTF-8 и сортирует уже нормализованный `/` path. (`crates/vibe-index/src/content_hash.rs:56`, `crates/vibe-index/src/content_hash.rs:70`, `crates/vibe-index/src/hash_recipe.rs:107`)
- Итог маркируется wire prefix recipe; это делает recipe частью проверяемой derived value. (`crates/vibe-index/src/content_hash.rs:100`, `crates/vibe-index/src/content_hash.rs:106`, `crates/vibe-index/src/hash_recipe.rs:38`)

### 3.3 P011V и boot после materialization

### 3.4 Что сломает transforming materialization

- Любая MD→XML/XML→MD трансформация меняет file path, extension и bytes, следовательно source `content_hash`; в `verify` это станет постоянным `Diverged`, а в `trust-presence` несоответствие останется незамеченным. - Закон PROP-010: “`content_hash` is the integrity gate”; источники одной identity с divergent bytes — collision и никогда не сливаются молча. Значит три materialization-формы нельзя выдавать за одну source identity без derived identity. (`spec/modules/vibe-registry/PROP-010-local-package-cache.md:60`, `spec/modules/vibe-registry/PROP-010-local-package-cache.md:63`)
- Закон PROP-010 также связывает extracted cache form, directory copy и hash shippable tree; transforming slot разрывает предположение, что materialized tree — тот же проверяемый artifact. (`spec/modules/vibe-registry/PROP-010-local-package-cache.md:132`, `spec/modules/vibe-registry/PROP-010-local-package-cache.md:134`)
- Закон PROP-011: slot exact resolved version считается immutable/correct, default skip доверяет presence, optional strategy проверяет `content_hash`. Derived format поэтому обязан войти как минимум в slot key/manifest и freshness decision, иначе смена setting не изменит `(kind,name,version)` и старый формат будет ошибочно skipped.
