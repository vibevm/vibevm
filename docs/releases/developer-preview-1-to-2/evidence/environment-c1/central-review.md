# M-14-C.1 opt-in binding review

The governing PROP-076 operation-binding law was introduced in `0ef17ab55`, strengthened for separate bound state keys and all-or-none replay in `b80b3ce83`, then revised in `8f072d332` to require an explicit target mode. The task split in `eaa448b49` keeps C.1 at the carrier/early-refusal boundary and assigns the first admitted bound effect plus physical alias fencing to C.2. Wire subjects `d4d76a259` and `b82f245ea` register an epoch-one environment operation binding and add optional typed binding to deploy intent/receipt and all six native request arms. Runtime subject `15e4df996` adds a distinct domain-tagged bound deployment key, binding equality at intent/receipt read and write, a separate bound plan hash and a structured inspection value carrying the binding.

The legacy `DeployExecution` entry point retains its old state key, plan hash and record bytes when binding is absent. Strict host-owned intent/receipt use one generated binding vocabulary; the native request has a separate permissive copy checked for equality with the strict host value, never promoted to an effect grant by its shape. Binding includes context, instance, selected generation if present, mode, role, OS/architecture/ABI/libc, principal, storage/root references and admission epoch. Typed validation refuses unsupported epoch, missing required-nullable shape, malformed identities, repeated root roles and mismatched intent/receipt/native carriers. A bound home refuses a copied legacy or other-instance receipt before provider planning or replay. The new bound entry point currently validates its value then **refuses before selection, inverse recovery, provider planning and state creation** because no host-pinned root/effect admission has been issued. Thus neither a request body nor a package descriptor can self-grant a root through this path.

**Accepted C.1 boundary:** opt-in serialized binding continuity, separate logical namespace, binding-aware record inspection and typed refusal before any unadmitted bound effect. Test receipts for two instance IDs are deliberately constructed inside disposable roots; they are not receipts from successful bound deploys. C.2 must pin and use host-issued root handles, share physical destination locks across aliases, check generation/principal/resource grants at admission and commit, and then prove the first supported local builtin bound apply into two disjoint injected homes. Native/plugin/skill bound effects remain unsupported until their providers obey equivalent handle/grant rules. This review grants neither full M-14 acceptance nor public DP2 publication.
