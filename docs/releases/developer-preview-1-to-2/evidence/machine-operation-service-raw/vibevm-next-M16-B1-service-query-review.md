This does not accept B.1 or establish descriptor discovery for extensions/full catalog. No in-progress MCP machine tool, Cargo command, source mutation, Git, provider, or user state was used in this review.

The current `machine_operation.rs` validates schema 1, nonblank namespaced operation/model IDs (at least one), distinct owner/source/capability spellings, epoch-1 `FormatId` references, duplicate identities and the three independent status axes before retaining rows. A source-observed or gap row cannot claim available/admitted, and an unknown validated operation is refused. The sole callable ID is `rust:vibe-workspace:migration_planning`, with exact accepted change/source/capability/evidence and migration request/report/error formats plus separate `PurePlannerAdmission::Admitted`; arbitrary `eval:shell` and unknown IDs do not route. `pure_text_planner` composes only that known pure owner. No `RitualPlan` field, provider, native loader, shell route, JSON parser or Cargo dependency was added to this sibling service.

For that route, `plan_migration` calls `vibe_workspace::migration_planning::plan_migration_request` and validates a produced report with `validate_report_for_request` (exact request replay) or a preflight with `validate_preflight_error`. Its `InvalidDomainResponse { original }` retains the actual rejected response as diagnostic evidence; the public normal return is withheld. Typed `PlanRequest` has already lost JSON presence information for optional fields, so an MCP/JSON adapter still has to use the workspace owner's `decode_migration_request` before invoking this service. The generated descriptor and request structs deny unknown object members, while semantic epoch/status/format checks remain outside JTD. The accepted release-impact record identifies the pure adapter subject used by the service; a text match to that ID is not physical source authentication.

`QueryMcpTool::descriptor` advertises an object with optional string `uri`/`symbol`/`kind`, integer `limit` 1–200, and no extras. `parse_query_args` now rejects null, wrong types, floating numbers, negative/zero/oversized limits and unknown keys before `vibe_trace::search::query`; omitted limit alone uses the owner's default. The generic `Server::handle_tools_call` does not itself enforce each tool's `input_schema`, so this owner-local gate is necessary and presently matches the advertised query shape. Valid query filter meaning remains with `vibe_trace`.
