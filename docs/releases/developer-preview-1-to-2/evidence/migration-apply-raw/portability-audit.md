# Bounded portability audit

Read-only audit; no native gate, crosscompile, install or source edit ran. No proven OS-wide disabling branch was found in the inspected normal path. API availability is supported; macOS/Windows native behavior is NOT verified.

Locking: external.rs opens the barrier read+write, uses blocking std::fs::File::lock and named-identity recheck. Rust documents flock on Unix and LockFileEx on Windows; the selected read/write mode meets its lock precondition. Windows additionally excludes delete sharing for the retained barrier. This implements the declared participating-client barrier, not exclusion of unrelated target writers. [Rust File::lock](https://doc.rust-lang.org/std/fs/struct.File.html#method.lock).

Retention/publication: external_sync.rs opens a regular single-link readable file, adds write access on Windows, confirms actual sync_all then rechecks snapshot/name/identity. Staged publication opens read+write/create_new, closes the stage handle before capability-relative ordinary replacement, validates the visible file, then syncs its parent. No strong no-replace Unsupported path is required for normal migration replacement. Microsoft's FlushFileBuffers requires GENERIC_WRITE; the retained/staged file opens now request it. Genuine file-flush failure refuses before mutation. [Microsoft FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

Unix directory synchronization: operations.rs reopens fixed "." through the retained capability, checks directory/identity before and after sync_all, avoiding the observed Linux O_PATH/EBADF bug. Installed cap-std4.0.3 Dir::open delegates read(true), and cap File::sync_all delegates std. Important distinction: the official current Rust Apple backend uses F_FULLFSYNC, not plain fsync. Apple documents filesystem-dependent full-flush support and errors for unsupported file types; these documents do not establish that the selected readable directory succeeds or universally fails on current APFS. Current classification treats Unsupported/PermissionDenied as reduced support, but InvalidInput/EIO as Failed; runtime correctly refuses genuine failures. An EINVAL directory result would need a bounded, observed classification/API decision, not blanket success. No fix is justified solely by this unmeasured possibility. [Rust Apple fsync implementation](https://doc.rust-lang.org/src/std/sys/fs/unix.rs.html#1413-1425), [Apple fcntl](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fcntl.2.html), [Apple fsync](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html).

Windows directory-tier path: the directory clone's sync result remains actual evidence; supported refusal kinds become JournalRecoverable at existing namespace checkpoints. Runtime observe_durability retains reduced warnings and never upgrades a known-unconfirmed boundary. Retained-image confirmation separately requires successful file-data sync; parent Unsupported remains the explicitly weaker tier, not a file-flush receipt. Recovery passes recorded Unix mode only where available; Windows normal captures carry null and report BytesOnly.

Unrun native gates: on macOS, existing directory_flush_reopens_readable_capability_without_namespace_creation, both retained_image_sync_* exact cases, and runtime apply_reader_mode_restore_and_terminal_replay_preserve_exact_bytes; on Windows, the two portable retained_image_sync_* cases and that runtime case (the directory probe is cfgUnix). Nonzero native execution and actual parent/error tiers remain required. Linux probe/selected tests already observed are retained, not rerun. No recommendation for a new filesystem framework or unconditional fsync guarantee.
